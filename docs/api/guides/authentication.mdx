# Authentication and assurance

Authentication proves who the principal is. On every protected operation,
Proctor still checks that principal against the current resource and the
stored policy before it allows anything. Don't assume permission because
sign-in worked, because the user is a member, or because an earlier request
succeeded. The <Link to="/security/">security review</Link> follows a request
all the way from the credential check to the current, audited decision.

## Credential types

| Credential | How you send it | What it's for |
| --- | --- | --- |
| Web Session | `PROCTOR_ACCESS` secure cookie, or its access credential on operations that allow bearer transport | Interactive browser journeys and trusted Web clients on the same installation |
| Desktop Session | `Authorization: DPoP …` plus a fresh `DPoP` proof | Registered Proctor Desktop clients |
| Personal Access Token | `Authorization: Bearer …` | Automation, on operations that accept a principal credential |
| Web refresh credential | `PROCTOR_REFRESH` cookie, or the bearer transport the refresh operation allows | Refreshing a Web Session, nothing else |
| Desktop refresh credential | `Authorization: DPoP …` plus a `DPoP` proof made for refresh | Refreshing the same registered-key Desktop Session, nothing else |
| Attempt credential | `X-Proctor-Attempt-Credential` plus `X-Proctor-Attempt-Connection-ID` | Extra proof of continuity for protected candidate Attempt operations |

Credential values and Desktop private keys are secrets. Keep them in the
operating system's credential store or a secret manager, remove them from
diagnostics, and never put them in a URL. A DPoP public key, thumbprint,
proof or nonce doesn't replace the access credential. Don't log any of them
as ordinary request metadata either.

## Assurance levels

The endpoint reference shows each operation's `x-proctor-auth` value in its
Authentication panel.

| Contract value | What the request needs |
| --- | --- |
| `public` | No authenticated principal |
| `principal_required` | An allowed Web Session, DPoP-bound Desktop Session or Personal Access Token |
| `session_required` | An allowed Web or Desktop Session. A Personal Access Token isn't enough |
| `recent_session_required` | An allowed Session whose sign-in is recent enough for the operation |
| `strong_recent_session_required` | A recent Session that used the strong factor the operation needs. Some operations also require the Web journey |
| `refresh_credential_required` | A valid Web or Desktop refresh credential, on the refresh operation only |

These are minimum requirements, not a promise of authorization. Proctor can
still reject a valid credential when the principal doesn't have permission
for the resource it asked for.

## CSRF proof in the browser

When a state-changing request is authenticated by the `PROCTOR_ACCESS`
cookie, it must also send the Session's CSRF value in
`X-Proctor-CSRF-Token`. Use the value Proctor issued for the active Session.
Reading a CSRF token from a cookie, or making up a fixed value, won't pass.

```bash
curl --request PATCH \
  --url https://proctor.example.edu/api/v1/users/me \
  --cookie 'PROCTOR_ACCESS=<session-cookie>' \
  --header 'X-Proctor-CSRF-Token: <session-csrf-token>' \
  --header 'Content-Type: application/json' \
  --data '{"display_name":"Amina Diallo"}'
```

Calling the API from a browser on another origin is no substitute for an
application served from the same origin. Deploy the UI and the API under the
address the installation intends, and follow its cookie and `Origin` policy.

## DPoP proof from Proctor Desktop

Proctor Desktop never presents its Session credential as a bearer token.
During Desktop authorization it registers one ES256 P-256 public key, and the
new Desktop Session is bound to that key. From then on, every access request
sends both headers:

```text
Authorization: DPoP <desktop-session-access-credential>
DPoP: <fresh-signed-proof>
```

The proof covers:

- the exact public method and target URI
- a hash of the access credential
- the time the proof was issued
- a unique proof identifier
- the server's current Session nonce

Build a new proof for every request. Proctor rejects a reused proof, a method
or target changed after signing, and a credential sent with the `Bearer`
scheme.

The exchange and any later nonce challenge return the next nonce in the
`DPoP-Nonce` response header. When Proctor answers with
`authentication.dpop.use_nonce`:

1. Store the new nonce.
2. Create a new proof.
3. Retry, but only if the original operation is otherwise safe to retry.

Never resend the rejected proof. `authentication.dpop.replayed` means Proctor
has already seen that proof identifier, and it also needs a newly signed
proof.

Desktop refresh also proves possession of the key, but its proof is made for
refresh and doesn't carry the access credential hash. Keep the code that
builds access proofs separate from the code that builds refresh proofs.

[Implement Desktop authorization](../recipes/desktop-authorization.mdx) walks
through the full sequence: the browser handoff, loopback, PKCE, compatibility
and revocation.

## Recent and strong sign-in

Sensitive account and administration operations can require a recent
sign-in, strong assurance backed by MFA, or both. When an operation returns a
stable error about assurance, send the person through interactive sign-in
again. Retry only once a new Session meets the declared level. Don't quietly
fall back to a Personal Access Token.

For MFA, linked methods, Session review, Desktop Registrations and Personal
Access Token revocation, follow [Manage account security](../recipes/account-security.mdx).

## Candidate Attempt requests

Protected candidate delivery only accepts the exact registered-key Desktop
Session that owns the active Participation. Each request sends that Session's
valid DPoP access credential and proof, together with a continuity credential
for the Attempt and the identity of the Connection:

```text
Authorization: DPoP <desktop-session-access-credential>
DPoP: <fresh-proof-for-this-method-target-and-current-nonce>
X-Proctor-Attempt-Credential: <43-character-raw-url-base64-value>
X-Proctor-Attempt-Connection-ID: <active-connection-id>
```

Request bodies that change state also carry the documented
`participation_id` and `generation`. If the Attempt state is stale or belongs
to another Participation, Proctor rejects the request. Send the credential in
the header only. The [candidate Attempt recipe](../recipes/candidate-attempt.mdx)
covers the full sequence.
