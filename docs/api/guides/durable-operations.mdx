# Durable Jobs and mail

Proctor commits the application's state before it schedules any background
effects. So a command can have succeeded while its Job or its mail is still
queued. Use the administration routes on this page to watch and control that
work. Don't judge application state by looking at a worker process or an
SMTP connection.

## What makes work durable

A Job is a finite, versioned command. Its descriptor fixes the retry policy,
timeout, concurrency, lease, checkpoints, cancellation, visibility and
retention. PostgreSQL holds the queue and decides which worker claims each
Job. A worker's lease and claim token stop an out-of-date worker from acting.
Handlers are still written to be idempotent, because a lost process can mean
the same work runs again.

When an effect must survive a lost process, the same transaction commits the
domain change and the intent to run the Job. Ordinary realtime, cache and
cluster effects don't become Jobs. Clients make up for any they miss by
reading the resource again.

Mail is durable in two layers:

- The occurrence records why the application needs to send a message, and
  fixes the set of people it is for.
- The encrypted Delivery covers sending the rendered message: its stable
  Message-ID, retries, cancellation, expiry and public failure.

When SMTP accepts a message, it only means the chosen relay took it. It
doesn't prove the message reached an inbox.

## Inspect Jobs

<Link to="/api/reference/list-jobs">List Jobs</Link> returns an operational
view of Jobs, in pages with a cursor. Filter by a documented type or state.
Then use <Link to="/api/reference/get-job">Get Job</Link> for the current
record, which is the one to trust, and
<Link to="/api/reference/list-job-attempts">List Job Attempts</Link> for a
limited history of each run.

These views deliberately leave out raw descriptors, credentials, student
data and worker errors of unlimited length. Store the stable Job ID and the
public failure code in your client telemetry. Don't copy internal worker
state into another system and treat it as the truth.

Read attempts in order. A claim can end because the handler:

- completed
- failed
- timed out
- lost its lease
- saw a cancellation
- handed the work to a compatible node

The current Job record decides whether there is more work to do. The last
attempt on its own doesn't.

For work that saves checkpoints, progress means progress in the domain that
has been saved, not just how many times a loop has run. Sitting closure,
onboarding imports, progression, mail expansion and key rotation can resume
from a stable cursor after a lost process. A batch that was reserved but not
checkpointed can stay used up on purpose, so the hard cap on work still
holds.

## Cancel or retry on purpose

<Link to="/api/reference/cancel-job">Cancel Job</Link> asks the Job to stop,
and the handler stops when it notices. A worker may already have committed
an idempotent effect. Read the Job state that comes back, instead of assuming
the cancellation undid any work.

Once the handler sees the cancellation, it doesn't start any new work.
Changes it committed earlier, row by row or idempotently, stay in place, and
undoing them may need a separate correction in the domain. Don't cancel a
finished Job again and again, and don't edit domain records to make its
history look undone.

<Link to="/api/reference/retry-job">Retry Job</Link> only works for Job types
whose descriptor explicitly allows a safe retry. It adds a new, limited run
to the history. It doesn't erase the earlier failure or skip the current
authorization check.

Before you retry, check that the dependency or configuration that failed is
healthy again, and that the domain state still allows the operation. A retry
uses the same versioned payload with the same meaning. You can't use it to
edit hidden Job data.

## Inspect mail delivery

<Link to="/api/reference/list-mail-deliveries">List Mail Deliveries</Link> and
<Link to="/api/reference/get-mail-delivery">Get Mail Delivery</Link> show
delivery metadata that is safe to expose, and where each delivery is in its
lifecycle. They never return the rendered message, recipient secrets,
Invitation claims, provider credentials or encryption keys.

Use <Link to="/api/reference/cancel-mail-delivery">Cancel Mail Delivery</Link>
only while a delivery can still be canceled. Use
<Link to="/api/reference/retry-mail-delivery">Retry Mail Delivery</Link> for a
failed delivery whose current state allows an audited retry. Neither one
changes the application command that queued the message in the first place.

Where the template contract requires it, Proctor checks again that the
message is still relevant to the recipient. A resend or retry can't bring
back a revoked Invitation, a Submission in a final state, or any other
purpose that has been replaced. Delivery views leave out the recipient's
address, the subject and body, claims, ciphertext, provider details and
internal failure text.

## Run mail safely

- <Link to="/api/reference/get-mail-metrics">Get mail metrics</Link> returns
  operational counts within fixed limits, never message contents.
- <Link to="/api/reference/inspect-mail-key-state">Inspect mail key state</Link>
  reports the status of each key version without revealing key bytes.
- <Link to="/api/reference/start-mail-rekey">Start mail rekey</Link> creates
  durable work. Follow it with
  <Link to="/api/reference/get-mail-rekey-status">Get mail rekey status</Link>.
- <Link to="/api/reference/send-controlled-test-mail">Send controlled test mail</Link>
  tests the configured delivery path with a fixed template the server owns.
  It can't send a message of your choosing.

Treat a `503` as a real dependency failure, and use the stable Problem
Details code to decide whether to back off. Proctor already owns durable
delivery and retries, so don't build a second retry loop beside it.

## Clear a backlog

1. Check that the application node is ready and the expected Job workers are
   running. A running process alone doesn't tell you this.
2. Page through the affected type and state. Note the counts, the oldest
   creation time, the public failure codes and the stable IDs, without
   exporting payloads.
3. Look at the attempts for one typical Job, and check the dependency it
   relies on through that dependency's protected diagnostics.
4. Fix the dependency, the configuration, the compatibility problem or the
   missing domain prerequisite.
5. Retry only the failed records that are explicitly retryable. Then watch
   the Job or Delivery record change state.
6. If a permanent failure keeps coming back, escalate it with the request or
   Job correlation and the safe code. Never include credentials, recipients,
   content or raw worker errors.

In an installation with several nodes, workers claim Jobs from the shared
PostgreSQL database. Restarting or adding a node doesn't move control away
from the Job record, and killing a process doesn't cancel a Job. When a lease
expires, abandoned work becomes available to claim again, as the descriptor
allows.

## Watch the administration summary

`GET /api/v1/administration/counts` returns the counts behind the badges in
administration navigation:

- `failed_jobs`: Jobs operators can see that failed in the last seven days
- `failed_mail_deliveries`: deliveries in the final `failed` state
- `pending_invitations`
- `open_onboarding_imports`

Each count stops at 1,000 and comes with an `_is_lower_bound` flag. Each one
runs the same authorization as its own list, so if the caller can't see a
list, its count is missing rather than zero. Use the counts to decide when to
open a list, then page through that list. The first page of
`GET /api/v1/jobs` and `GET /api/v1/mail/deliveries` reports a `total` for the
same filters.
