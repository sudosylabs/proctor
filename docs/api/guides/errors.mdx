# Errors and Problem Details

When a request fails, Proctor answers with RFC 9457 Problem Details. Branch
on the HTTP status and on Proctor's stable `code`. The `title` and `detail`
are text for operators and users to read, not something your program should
parse.

```json
{
  "type": "https://proctor.sudosylabs.com/problems/exam.invalid",
  "title": "Invalid request",
  "status": 400,
  "detail": "The request is invalid.",
  "instance": "/api/v1/exams",
  "code": "exam.invalid",
  "request_id": "req_01J7YN7BR7R2BW0VWP2JEN8M4M",
  "fields": {
    "field": "title"
  }
}
```

The `type` URI points to documentation. The `code` comes from a fixed set
and is what your integration uses in program logic. Each endpoint page lists
the codes it can return under **Stable error codes**.

## How codes are built

Every code has the form `<domain>[.<subdomain>].<condition>`. Segments are
lowercase, separated by dots, and each segment is `snake_case`.

- The domain names the family of resources, such as `exam`, `exam.attempt`
  or `authentication.mfa`.
- The condition is the last segment. When it has a qualifier, the qualifier
  comes first and the condition word last, as in `revision_conflict` or
  `content_invalid`.

The condition decides the HTTP status:

| Condition word | Status |
| --- | --- |
| `invalid` | `400` |
| `denied`, `disabled` | `403` |
| `not_found` | `404` |
| `conflict` | `409` |
| `expired` | `410` |
| `rate_limited` | `429` |
| `internal` | `500` |
| `unavailable`, `busy` | `503` |

A condition that is one of these words, or ends in `_` followed by one of
them, takes that status. Any other condition, such as `archived` or
`deadline_reached`, names a resource state that rejects the request, and
returns `409`.

A few codes are documented exceptions:

- Credential failures in the `authentication` domain return `401` or `403`.
- `exam.attempt.continuity_invalid` returns `404`, so an invalid credential
  reveals nothing.
- The routing codes described below use the statuses HTTP defines for them.

## Handling errors

- Parse a failed response as Problem Details when its content type is
  `application/problem+json`.
- Use `status` for the broad outcome and `code` for the exact Proctor
  condition.
- Escape `detail` and `fields` before you show them, the same way you treat
  any other untrusted response data.
- Record `request_id` in your support trace. Don't attach credentials,
  answers or raw request bodies.
- Treat a code you don't recognize as an unknown failure you can recover
  from. Keep the behavior its HTTP status implies, and never crash or treat
  it as success.

## Validation failures

When `fields` is present, its keys name the request fields that failed and
its values explain the rule each one broke. The object is optional, so your
client must still handle a validation failure that has no field details.

Unknown JSON fields, more than one JSON value and malformed input all fail.
A body larger than the route's limit returns status `413` with code
`request.too_large`, whichever operation received it. Fix the request instead
of retrying it unchanged.

Any operation may also return:

- `404` with code `route.not_found` for an unknown path
- `405` with code `route.method_not_allowed`, with an `Allow` header, for an
  unsupported method
- `500` with code `server.internal` for an unexpected server fault

These routing failures aren't repeated in each endpoint's list of stable
codes.

## Retries

Retry only when both the operation and the failure allow it. Before you
retry a mutation after a timeout or a lost response, follow its documented
idempotency behavior. Authentication, authorization, validation, conflict and
assurance failures usually need a change of state or an action from the user
first.

DPoP has one narrow retry path. On `authentication.dpop.use_nonce`, keep the
new `DPoP-Nonce`, create a completely new proof, and retry only if the
operation is otherwise safe to retry. `authentication.dpop.replayed` also
needs a new proof identifier. Resending the rejected proof never works.

A revoked Desktop Registration or an incompatible Desktop build needs a
person or the installation to act. Refreshing the token in a loop won't fix
it.

Once a WebSocket connection is open, protocol failures arrive as typed
protocol messages instead of HTTP Problem Details. See
[Realtime and replay](./realtime.mdx).
