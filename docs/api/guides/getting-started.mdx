# Getting started

Each Proctor installation serves its own API. Use the installation's address
followed by the versioned `/api/v1` path. There is no shared Proctor cloud
API hostname.

```text
https://proctor.example.edu/api/v1
```

Start with <Link to="/api/reference/get-public-access-discovery">public access discovery</Link>
to find out which sign-in methods the installation offers. You can show its
response before anyone signs in. It doesn't reveal private provider
configuration.

```bash
curl --request GET \
  --url https://proctor.example.edu/api/v1/discovery \
  --header 'Accept: application/json'
```

## Choose a credential

Browser clients usually get a Web Session through
<Link to="/api/reference/login">login</Link>. Integrations that don't run in a
browser use a Personal Access Token, and only on operations whose
**Authentication** panel accepts a principal credential. A token can't stand
in for a recent or strongly authenticated interactive Session.

Proctor Desktop gets a registered-key Desktop Session through its own
browser authorization and DPoP exchange. Don't send a Desktop credential the
way the bearer example below does.

Read [Authentication and assurance](./authentication.mdx) before you make a
protected request.

## Read an endpoint page

Every generated endpoint page gives you four pieces of contract information:

1. **Authentication** says what kind of principal and level of assurance the
   operation needs.
2. **Idempotency** says whether `Idempotency-Key` is forbidden, optional or
   required.
3. **Stable error codes** lists the application codes your client can branch
   on.
4. The request and response schemas define the closed objects sent over the
   wire and the rules Proctor checks them against.

The downloadable <a href="/openapi/openapi.json" download>OpenAPI 3.1 contract</a> is
the same file that is checked against the server's route declarations. The
generated pages are a view of it, not a separate description of the API.

## Send JSON with care

Proctor JSON objects are closed, unless a schema explicitly declares an
extension point. Send one JSON value and use the exact `snake_case` field
names. Leave out any field you don't mean to change. Where a schema allows
both, leaving out an optional field and sending an explicit `null` can mean
different things.

Every timestamp is an RFC 3339 string, in bodies and query parameters alike.

- Lifecycle events have past-tense names such as `created_at`, `updated_at`
  and `archived_at`.
- Responses use UTC, with up to microsecond precision and no trailing
  fractional zeros, for example `2026-08-01T09:30:00.123Z`.
- Requests may use any RFC 3339 offset.
- When a timestamp has no value, such as `archived_at` on an active resource,
  the response leaves it out instead of sending `null` or zero.

Proctor sets fields such as `id` and `created_at` itself, and never accepts
them in create requests.

```bash
curl --request GET \
  --url 'https://proctor.example.edu/api/v1/exams?limit=25' \
  --header 'Accept: application/json' \
  --header 'Authorization: Bearer ${PROCTOR_TOKEN}'
```

Never put access tokens, invitation secrets, attempt credentials, answers or
other sensitive material in a URL, an example fixture or an application log.

## Versions and compatibility

Before the first supported Proctor release, `/api/v1` may change in place.
When it does, the server, the reviewed contract and compatible clients are
switched over together. Pin the exact OpenAPI file your integration uses.

After the first supported release, existing meanings only gain additions,
unless an explicit compatibility decision introduces another version and a
migration. See [Limits and compatibility](./limits-and-compatibility.mdx) for
the rules your client should follow.
