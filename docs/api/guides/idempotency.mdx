# Idempotency and retries

Every operation declares `x-proctor-idempotency` as `none`, `optional` or
`required`, and its generated endpoint page shows the value.

| Value | What your client does |
| --- | --- |
| `none` | Don't send `Idempotency-Key`. Rely on the operation being a read or a replacement |
| `optional` | Send a key when you might retry a mutation whose outcome you're unsure of |
| `required` | Send a key with every request |

An idempotency key is 1–128 case-sensitive ASCII characters, made of
letters, digits, `-`, `.`, `_` and `~`. Generate a new, unpredictable key for
each logical command. Reuse that key only to retry exactly the same request.

```bash
curl --request POST \
  --url https://proctor.example.edu/api/v1/exams \
  --header 'Authorization: Bearer <token>' \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: exam-create-01J7YS5EP6P9M3JAXKQFRHD5TB' \
  --data '{"title":"Calculus I final","owner_academic_unit_id":"01J7YQ4G6V2CKBYZG83K31T6QA"}'
```

## How Proctor handles a replay

When you replay a request correctly, Proctor checks authentication and
authorization again, and records any required audit. It doesn't apply the
change again or repeat its external effects. Proctor keeps idempotency
records for at least 24 hours.

Two cases return a stable error code from the endpoint:

- The same key arrives with different input, compared after Proctor
  normalizes the request. This is a conflict.
- A retry arrives while the original command is still running. Proctor can
  report that the original is in progress.

Handle both explicitly. Don't respond by generating a new key straight away,
because that could run the logical command twice.

## Retry safely

1. Build the exact request payload and one idempotency key, and keep both.
2. Send the command once.
3. On a connection failure, a timeout or a documented transient server
   failure, retry the identical request with the identical key.
4. On a definite client, authorization or conflict failure, stop and fix the
   cause.
5. Store the identifier of the resource Proctor returns. Don't use the key
   as a lasting way to look it up.

Replacement operations may rely on being naturally idempotent instead, with
revision or precondition fields. Follow each endpoint's declared value and
schema, rather than adding a key to every request.
