# Limits and compatibility

Proctor rejects input before it parses more than its limits allow. Treat
every request body, page of a collection, upload, log entry and retry loop as
limited, even when an installation hasn't published a stricter local policy.

## Limits for your client

- Stay within the endpoint's documented `limit` range. Never request or
  assume a collection without limits.
- Stream file content where your client library allows it, and check the
  endpoint's maximum before you upload.
- Put only documented fields in request objects. Proctor rejects unknown JSON
  fields.
- Send exactly one JSON value, with the declared media type.
- Use exponential backoff with jitter for documented transient failures and
  for realtime reconnects.
- When an installation applies rate or concurrency controls, follow its
  response headers and stable error codes. Don't get around them by using
  several credentials in parallel.

The hard limit for a public multipart request is 100 MiB plus 64 KiB of
overhead. A particular route or installation policy can set a lower limit,
and no general maximum overrides the endpoint schema.

## Compatibility within `/api/v1`

Proctor hasn't yet committed to an API for a first supported release. Until
it does, the `/api/v1` contract may change in place. When it changes, the
server, the generated contract and compatible first-party clients are
switched over together. Proctor doesn't create a parallel version just to
keep an older development contract alive. Pin the reviewed OpenAPI file and
the server build that each integration uses, and don't read the version in
the path as a promise of support.

After the first supported release, existing meanings only gain additions,
unless an explicit compatibility decision introduces another version and a
way to migrate. Additions can include operations, optional request fields,
response fields, values in open enums and new stable error codes.

In either period, a well-behaved client:

- ignores response fields it doesn't know
- handles unknown error types and realtime event types safely
- always has a fallback when it switches over an open set of values
- sends only fields that the contract version it targets supports
- never reads meaning into opaque identifiers, cursors, ETags or tokens

After the first supported release, removing a field, making an input
required or changing existing behavior needs an explicit compatibility
decision. For any build, the OpenAPI contract checked into the repository is
the source of truth. Pin or archive the contract you generate a client from,
so that every update is a deliberate choice.

## Telemetry without leaks

Your client telemetry can safely include the HTTP method, the route template,
the status, the duration, the stable `code` and the `request_id`. Never log:

- bearer, DPoP or refresh credentials
- DPoP proofs or nonces
- cookies
- CSRF values
- invitation secrets
- Attempt credentials
- student answers
- raw Exam content
- fields controlled by users that have no length limit
