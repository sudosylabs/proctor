# Uploads and protected content

Upload endpoints accept a deliberately narrow form of multipart request.
Send exactly two parts, in this order:

1. `metadata`: a part that isn't a file, holding strict JSON of no more than
   32 KiB.
2. `content`: the file bytes.

The metadata declares the size in bytes and the SHA-256 digest that the
content part should have. If they don't match, the request fails. Proctor
never quietly accepts or rewrites the content.

```bash
curl --request PUT \
  --url https://proctor.example.edu/api/v1/users/me/profile-picture \
  --header 'Authorization: Bearer <token>' \
  --form 'metadata={"filename":"profile.png","size":18432,"sha256":"<64-lowercase-hex-characters>"};type=application/json' \
  --form 'content=@./profile.png;type=image/png'
```

Don't add extra form fields, swap the order of the parts, or send the
metadata as a file. The hard limit for a public request is 100 MiB plus
64 KiB of multipart overhead. Individual routes and installation policy may
set a lower limit for the content. Check the endpoint schema before you
allocate memory for a file or start streaming it.

## Digest and size

Compute the SHA-256 digest over the exact bytes you send in `content`,
before multipart encoding. Declare the exact length in bytes, not a count of
characters or the length after encoding. If your client changes the file
behind the scenes, compute the metadata after that change.

## Protected downloads

Proctor returns protected content inline, with a strong `ETag` and
`X-Content-Type-Options: nosniff`. It checks authorization again for the
current principal and resource. Knowing a content URL doesn't give you
permission to fetch it.

- Follow the response `Content-Type`. Don't guess the type from a filename.
- Keep protected bytes out of shared HTTP caches and analytics payloads.
- Send `If-None-Match` with the strong ETag when the endpoint's cache policy
  allows revalidation.
- Don't rely on `Content-Disposition` to force a download. The contract
  serves protected content inline.

Downloads of a candidate's workspace and of exam resources also need the
attempt credential headers described in
[Authentication and assurance](./authentication.mdx).
