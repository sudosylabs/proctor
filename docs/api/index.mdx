## The contract is the source of truth

The docs build publishes `openapi.json` straight from the server contract
tracked in the repository. It doesn't work out endpoints from the handlers,
and it doesn't rewrite the contract's descriptions. The generated reference
only displays that contract. It never describes route behavior on its own.

Browse the endpoint groups in the sidebar. Each endpoint page is generated
from the same contract. It shows the operation's authentication, idempotency
and stable error codes before the request and response schemas. The
<Link to="/api/reference/realtime-protocol/">Realtime Protocol</Link>
reference is generated the same way, from the reviewed AsyncAPI contract for
the WebSocket frames.

If this is your first integration, start with [Getting started](./guides/getting-started.mdx).
Then read [Authentication and assurance](./guides/authentication.mdx) and
[Errors and Problem Details](./guides/errors.mdx). The other guides cover
pagination, safe retries, uploads, protected content, realtime recovery and
compatibility.

The [end-to-end recipes](./recipes/bootstrap-installation.mdx) put those
rules together into real workflows:

- bootstrapping an installation
- signing in and recovering an account
- changing the Access Policy
- building the academic structure
- Invitations and onboarding
- publishing an Exam
- running a Sitting
- candidate Attempts
- integrity review
- reading audit history

## Read each operation in full

Every route declares the credential it needs in `x-proctor-auth`. Some
security-sensitive operations also need a strong, recently authenticated
interactive <Term id="session">Session</Term> and CSRF proof. A
<Term id="personal-access-token">Personal Access Token</Term> can't stand in
for that level of assurance.

When a request fails, Proctor answers with RFC 9457 Problem Details and a
stable application code. Each operation lists the codes it can return in
`x-proctor-error-codes`, and agreement tests check that every one maps to a
documented HTTP response.

## Conventions across the contract

- Request and response objects are closed, unless a named extension point is
  deliberately left open.
- Collections are paged with opaque keyset cursors, within fixed limits.
- When you change a resource, Proctor checks the current
  <Term id="principal">principal</Term> against the current stored state, at
  the final step that carries out the change.
- Idempotent commands tell an exact replay apart from a reused key with
  different input.
- Proctor commits a successful change to durable state first. Transient
  cache, cluster and realtime effects come after it.

Read the [HTTP contract conventions](https://github.com/sudosylabs/Proctor/blob/main/server/httpapi/CONTRACT.md)
before you generate a client or design an integration.
