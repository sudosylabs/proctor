# Build the academic structure

Create academic resources parent first, in the order they own each other. The
Class comes last. It is the actual student roster: it belongs to one Programme
Level and names one exact Academic Period that applies to it.

<GovernedFigure asset="academic-structure-ownership-map" />

Proctor checks permissions against the exact resource each call touches.
Programmes, Programme Levels, Academic Periods and Classes resolve to an
Institution, Academic Unit or Class binding scope by following their current
parents in PostgreSQL. Being able to see a parent does not mean the caller can
change its children.

## 1. Create an Academic Unit

Call <Link to="/api/reference/create-root-academic-unit">Create root Academic Unit</Link>,
or <Link to="/api/reference/create-academic-unit-child">create a child</Link>
under an existing Unit. Keep the `id` in the response. The route sets the
parent. An ID repeated in the request body does not.

```json
{
  "name": "computer-science",
  "display_name": "Computer Science",
  "description": "Teaching and research in computing."
}
```

You can nest Units several levels deep. Proctor rejects a cycle, and rejects a
parent from another Institution. Labels such as faculty or department are for
display only. They do not change how scope is inherited.

## 2. Create a Programme and its levels

Call <Link to="/api/reference/create-programme">Create Programme</Link> with the
Academic Unit ID in the path. Then call
<Link to="/api/reference/create-programme-level">Create Programme Level</Link>
with the Programme ID in the path.

```json
{
  "name": "bsc-computer-science",
  "display_name": "BSc Computer Science"
}
```

```json
{
  "name": "level-100",
  "display_name": "Level 100"
}
```

## 3. Create an Academic Period

Call <Link to="/api/reference/create-academic-period">Create Academic Period</Link>
with either the Institution or one Academic Unit as the owner. `start_at` and
`end_at` are RFC 3339 timestamps.

```json
{
  "owner_type": "institution",
  "owner_id": "<institution-id>",
  "name": "2026-2027",
  "display_name": "2026–2027",
  "start_at": "2026-08-01T00:00:00Z",
  "end_at": "2027-07-31T23:59:59Z"
}
```

A Period owned by the Institution applies to every Academic Unit. A Period
owned by a Unit applies to that Unit and the Units below it. Names must be
unique within the owner, but date ranges may overlap. Don't work out a
"current" Period from dates, and don't assume a Unit's Period overrides the
Institution's.

## 4. Create the Class

Call <Link to="/api/reference/create-class">Create Class</Link> under the
Programme Level, and name the exact Academic Period in the body.

```json
{
  "academic_period_id": "<academic-period-id>",
  "name": "cs-level-100-a",
  "display_name": "Computer Science Level 100 — A"
}
```

Proctor checks that the Period applies to the Programme's Academic Unit. Keep
the Class ID from the response. Names are for display and search, and are not
stable keys to store.

## 5. Read the structure back

Check each result with its own read call and its list call:

- <Link to="/api/reference/list-academic-units">List Academic Units</Link> and
  <Link to="/api/reference/list-academic-unit-children">List child Academic Units</Link>
- <Link to="/api/reference/list-programmes">List Programmes</Link> and
  <Link to="/api/reference/list-programme-levels">List Programme Levels</Link>
- <Link to="/api/reference/list-academic-periods">List Academic Periods</Link>
- <Link to="/api/reference/list-classes">List Classes</Link>

Pass each keyset cursor back exactly as you received it. Don't fetch everything
and filter by permission in your client. Lists already show only what the
caller's current scope allows.

## 6. Update or move a resource from its current state

To change display fields, use the resource's update call. Moving an Academic
Unit to a new parent is a bigger change. Proctor checks permissions on both
the old and new parents, and rejects the whole move if it would create a cycle,
cross Institutions or break something that depends on the Unit. Before you move
one, list the Units, Programmes, Period links, memberships and Role Bindings
below it.

If another administrator changed the resource first, read it again and build
the request you actually mean from the new state. A conflict is not a cue to
resend the old input unchanged.

## 7. Archive from the bottom up

Archiving keeps the resource's identity, parents, lifecycle timestamps and
audit history. It never cascades to active children or to anything that
depends on the resource for permissions. Work in this order:

1. End or move active Class and Academic Unit memberships through their own
   lifecycle calls.
2. Resolve any Exams and Sittings that depend on the resource.
3. Archive Classes before their Programme Levels.
4. Archive Programme Levels before their Programmes.
5. Archive child Academic Units before their parent.

You can't archive an Academic Period while specific Classes or relationships
still depend on it. Don't present any of these calls to your users as a
delete.

## Retries and diagnostics

Some create calls accept an optional `Idempotency-Key`. Send a unique one with
each request. Reuse a key only to resend the identical request after you lost
the response. Sending a different body with the same key is a conflict.
Updates and archives don't take idempotency keys, so after a timeout read the
resource first and then decide whether to send the change again.

In your logs, record the route template, status, stable error code, request ID
and safe resource IDs. Don't log profiles, rosters, Invitation data or
free-text descriptions. Don't use a Class to grant permissions. Enrollment
records who is on the roster. Roles and scoped Role Bindings grant
permissions.
