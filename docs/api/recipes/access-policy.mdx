# Change the Access Policy safely

The Access Policy is a versioned record that belongs to one installation. It
decides whether people can register themselves, whether they can sign in and
enroll credentials locally, whether Invitations admit people, how each
provider admits people, and whether Desktop Authorization is available. It does
not hold provider credentials, SMTP settings, Institution profile data or what
the deployment is capable of.

A change takes three calls: read, preflight, replace. The preflight only
advises you about the state it saw. The replace call makes the final decision.

## 1. Read the policy and what the deployment supports

Call <Link to="/api/reference/get-access-policy">Get Access Policy</Link> as an
authorized principal. Keep the opaque policy ID, the current revision, every
policy field, the safe list of configured provider capabilities and the
recent change history.

Build a complete replacement document. Don't patch from a stale form, and
don't drop fields the operator didn't edit. You can select a provider only if
it appears in the capability list the response returned. Issuer URLs, client
secrets, certificates and claim mappings stay in deployment configuration.

Leaving a configured provider out of `provider_admissions` turns off admission
through it. A provider you include takes exactly one of three modes:

- `linked_only` accepts an immutable provider subject that is already linked.
- `invitation_required` admits an unlinked subject only while it accepts a
  valid Invitation issued for that purpose.
- `auto_provision` may create a User with no relationships, but only when the
  provider's checked eligibility also allows it.

None of these modes grants a membership, an Affiliation or a Role Binding.

## 2. Preflight the exact replacement

Call <Link to="/api/reference/preflight-access-policy">Preflight Access Policy</Link>
with:

- a strong, recently authenticated interactive Session;
- current CSRF proof, if you use cookies;
- the revision you read;
- the complete proposed policy;
- your one-time `revoke_existing_sessions` choice.

Read every blocker in the response. Don't reduce it to a single yes or no.
Proctor checks the configured providers, Invitation mail delivery, whether the
policy is valid, and whether every active system administrator can still sign
in. Turning on a mode that depends on Invitations can fail if durable mail
delivery is unavailable. Turning off a provider or local login can fail if
that would remove the last way an administrator can sign in.

A preflight changes nothing. It doesn't reserve the revision or an
administrator's sign-in path. Another administrator or node can change the
state straight afterwards.

## 3. Replace the policy against the revision you read

Call <Link to="/api/reference/replace-access-policy">Replace Access Policy</Link>
with:

- the exact document you preflighted;
- the expected revision;
- a new `Idempotency-Key`;
- strong, recent Session assurance;
- CSRF proof, if you use cookies.

The replace call runs every capability and lockout check again. It is
serialized with any change to credentials, Users or system-administrator
bindings that could remove a sign-in path. It records the attempt, moves the
revision forward and commits. Only after the commit does Proctor clear caches,
notify other nodes and send the realtime revision event, which carries no
policy content.

`revoke_existing_sessions` is not stored in the policy. It applies to this one
change. When it is true, Proctor revokes, in the same transaction, the Sessions
that signed in with a method this change turns off. Sessions that used a method
you kept stay active. When it is false, the method you turned off can't create
new Sessions, but Sessions that already exist carry on as normal.

## 4. Check the result

Read the policy again. The revision and fields must match what you sent. Then
try one safe sign-in for each administrator method you meant to keep. Don't
use public discovery as proof of the change. Discovery is a privacy-safe view
and may be cached for a short time.

If clearing the cache, sending the realtime event or notifying other nodes
fails briefly after the commit, the change still stands. Read the policy again
through the API, which reads it from PostgreSQL. Don't send a corrective
replacement built from stale state.

## Conflicts and recovery

| Result | What to do |
| --- | --- |
| revision conflict | Read the current policy, merge the human decision, preflight again and use a new idempotency key. |
| policy blocked | Keep the current policy. First fix the administrator sign-in path, provider capability or mail delivery the response names. |
| idempotency in progress | Back off, then read the policy before you resend the exact same request and key. |
| idempotency conflict | The key was used for different input. Review the replacement you intend, then choose a new key. |
| assurance required | Sign in again with a supported strong method. A Personal Access Token never counts. |
| every administrator path is lost despite the safeguard | Stop every node and use the documented offline host recovery. There is no network route around it. |
