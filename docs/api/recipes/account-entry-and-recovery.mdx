# Sign in and recover an account

The current Access Policy decides how people can get in. Start with
<Link to="/api/reference/get-public-access-discovery">Public Access Discovery</Link>
rather than guessing whether public registration, local login, an external
provider, Invitation admission or Desktop Authorization is available. The
discovery document shows safe capabilities. It never shows provider secrets or
whether an account exists.

## 1. Choose how the person gets in

Public local registration is one way in. It is not a general API for creating
Users. Call <Link to="/api/reference/register-local-user">Register Local User</Link>
only when discovery says it is allowed. Send exactly the public fields: first
name, last name, username, email and a password that meets the policy.

The person provides their own names, and Proctor uses them only for display.
Registration creates an unverified User and a local credential. It grants no
Affiliation, membership, Role Binding or academic access. If you get
`authentication.registration.invitation_required`, the person needs a valid
Invitation. Don't take it as a reason to try another address or to call an
administrator-only User endpoint.

An Invitation is issued for one purpose. It applies its frozen relationship or
Role package only when someone accepts it successfully. Follow
[Invite and link users](./invite-and-link-users.mdx) for that flow.

## 2. Create a web or native Session

For local credentials, call <Link to="/api/reference/login">Login</Link> with the
right `client_type`. A browser login sets host-only cookies. Eligible
non-browser clients get their credentials in the response body. Proctor
Desktop doesn't call this route or reuse browser cookies. It follows
[Desktop Authorization](./desktop-authorization.mdx) instead.

When MFA is on, include a current TOTP code or one unused recovery code in the
login request. `authentication.mfa.required` means the primary credential alone
wasn't enough. It doesn't let you send a second request that drops or weakens the
challenge. Proctor deliberately limits what invalid-credential failures reveal.
Don't use small differences in the responses to work out which accounts exist.

To sign in with an external provider:

1. Read <Link to="/api/reference/list-authentication-providers">List Authentication Providers</Link>.
2. Send the browser to
   <Link to="/api/reference/begin-external-authentication">Begin External Authentication</Link>
   for the chosen provider. Don't fetch the redirect as a background API
   request, and don't copy provider state from one browser to another.
3. Let the provider return to
   <Link to="/api/reference/complete-external-authentication">Complete External Authentication</Link>.
   The callback uses up the one-time state and its browser binding. A fixed
   hosted completion page then confirms the new Web Session.

Proctor never matches an external identity by email or username. It admits an
unlinked provider subject only under the provider's current mode. Your client
must not add its own rule for linking by email or for creating accounts.

After an administrator resets someone's MFA, a fresh password or provider proof
may give them only a restricted Web Session. The Session's
`mfa_recovery_required` flag sends the hosted flow to `/account/security` to set
up a new authenticator. Don't treat this Session as normal account access, and
don't continue an Invitation, provider link or Desktop handoff until the person
has enrolled again. For an account that signs in only through a provider,
Proctor requires a separate fresh proof for the same existing User from the
original provider. A normal provider callback on its own can't skip that step.

## 3. Verify the email address

A successful public registration returns a plain `202 Accepted` and queues the
first verification email. It returns no Session and no credential. The person
uses the credential from that email on the hosted verification page. The page
waits for the person to press a button before it calls
<Link to="/api/reference/complete-email-verification">Complete Email Verification</Link>,
so mail scanners and link previews can't use up the credential just by
opening the link.

If the person signs in later and still needs a new email, call
<Link to="/api/reference/request-email-verification">Request Email Verification</Link>
with that signed-in Session. Sending a new email may make the previous
credential stop working. Registration doesn't give you a signed-in Session, so
it never calls this resend route.

The raw credential travels in the URL fragment. Remove it from browser history
before the page renders. Whatever the problem with a credential (expired,
already used, replaced, malformed, or beaten by a concurrent request), the fix
is the same: sign in, then request a new email for that account. Never log the
fragment or repeat it in an error message.

## 4. Reset a local password without revealing accounts

Call <Link to="/api/reference/request-password-reset">Request Password Reset</Link>
with the normalized email address the person typed. The accepted response is
the same whether or not an eligible local account exists. Keep it just as
neutral in your UI, telemetry, timing analysis and support scripts.

The hosted reset page reads the credential from the fragment, removes it from
history, asks for a new password that meets the policy and calls
<Link to="/api/reference/complete-password-reset">Complete Password Reset</Link>.
A successful reset uses up the credential, changes the password and revokes the
affected Sessions in one transaction. It doesn't quietly create an Affiliation,
link a provider, skip MFA or grant administrator rights.

If you can't tell whether the reset went through, don't keep resending the
same secret. Send the person back to login with the new password. If that
fails, request a new reset email.

A password reset doesn't remove local MFA or a recovery restriction an
administrator started. If the authenticator and every unused recovery code are
also lost, the institution verifies the person's identity and then a
separately authorized administrator resets MFA, as described in
[Manage account security](./account-security.mdx#5-recover-after-an-assisted-mfa-reset).
The person still has to give fresh proof and enroll a new authenticator
afterwards.

## 5. Refresh or end the current Session

Call <Link to="/api/reference/refresh-session">Refresh Session</Link> only with
the current refresh credential. Refreshing replaces the access and refresh
credentials and, with cookies, the CSRF credential too. If a refresh credential
that was already used comes back, Proctor treats it as a replay and invalidates
that whole family of Sessions.

A Desktop refresh uses `Authorization: DPoP` with a fresh proof and the
current nonce. You can't swap it for a browser cookie or a plain bearer
refresh.

Call <Link to="/api/reference/logout">Logout</Link> to revoke the current
Session and clear its browser cookies. The person's other Sessions stay
active. For a lost or compromised device, continue with
[Manage account security](./account-security.mdx) and revoke the narrowest
thing affected: one Session, a Desktop Registration or a token.

## Failures and recovery

| Failure | What to do |
| --- | --- |
| capability disabled | Read discovery again. Don't call a hidden method directly. |
| invalid credentials | Show one neutral failure message and back off. Don't reveal whether the User exists. |
| verification link unusable | Request a new email from a signed-in Session. |
| reset request accepted but no mail arrives | Keep the neutral response. Check mail operations without confirming that the account exists. |
| refresh replay or invalid Session | Throw away the local credentials and start a new supported login. |
| provider is unlinked | Use Invitation admission, or a signed-in provider connection flow if the policy allows it. Never match by email. |
| MFA recovery is required | Go to the hosted account security page with the restricted Web Session and enroll a new authenticator. |
| MFA service is unavailable during recovery | Ask the operator to restore the enrollment service. The recovery restriction stays in place. |
| sensitive task needs fresh proof | Use the hosted password or original-provider reauthentication flow, return to the current state, then choose the action again. |
