# Write and publish an Exam

An Exam has a stable identity, a record of who created it, a current owner,
Managers, an archive state and one Draft you can edit. Publishing freezes the
whole Draft as the next numbered Revision, which never changes. A Sitting
picks one Revision and never follows later changes to the Draft.

<GovernedFigure asset="exam-publication-delivery-lifecycle" />

## 1. Create the Exam in its Academic Unit

Call <Link to="/api/reference/create-exam">Create Exam</Link>. The creator is
recorded permanently as the creator, and becomes the owner and first Manager.

```json
{
  "academic_unit_id": "<academic-unit-id>",
  "title": "Algorithms — final examination",
  "instructions_markdown": "Read every question before you begin."
}
```

Keep the Exam ID, the Exam revision and the Draft revision from the response.
They guard different changes. Manager and ownership changes check the Exam
revision. Changes to the written content check the Draft revision.

## 2. Edit the text against the Draft revision

<Link to="/api/reference/edit-exam-draft-text">Edit Draft text</Link> needs the
exact `expected_revision`.

```json
{
  "expected_revision": 3,
  "title": "Algorithms — final examination",
  "instructions_markdown": "Answer all questions. Save source files in answers/."
}
```

A field you leave out of the PATCH stays as it is. An empty instructions value
clears the instructions. After every successful change, replace your local copy
of the Draft with the response. If you get `exam.draft.revision_conflict`,
fetch the Draft again and compare every part of it. Never guess the next
revision by adding one to a stale value.

## 3. Set the Browser Policy and Focus Loss rule

Replace the Browser Policy with
<Link to="/api/reference/configure-exam-draft-browser-policy">Configure Draft Browser Policy</Link>.
An enabled policy has schema version 1, one start rule, and between 1 and 64
HTTPS rules. Each rule sets a closed host match, a path prefix, whether
redirects are allowed, and what happens to a blocked navigation, which is
recorded.

```json
{
  "expected_revision": 4,
  "browser_policy": {
    "schema_version": 1,
    "enabled": true,
    "start_rule_id": "reference",
    "rules": [{
      "rule_id": "reference",
      "origin": "https://reference.example.edu",
      "path_prefix": "/algorithms/",
      "host_match": "exact",
      "allow_redirects": false,
      "blocked_navigation_outcome": "record"
    }]
  }
}
```

Replace the Focus Loss rule with
<Link to="/api/reference/configure-exam-draft-focus-loss">Configure Draft Focus Loss</Link>.
The duration, number of incidents, time window and outcome work together as
one rule.

```json
{
  "expected_revision": 5,
  "enabled": true,
  "minimum_duration_milliseconds": 1500,
  "incident_count": 3,
  "window_milliseconds": 300000,
  "outcome": "flag_and_warn"
}
```

Connection Loss always uses the `flag_and_suspend` outcome, and you can't
change it. Don't invent a general policy object, and don't put grades, rubrics
or pass/fail values in these fields.

## 4. Attach protected Resources

Call <Link to="/api/reference/create-exam-draft-resource">Create Draft Resource</Link>
for the metadata. Then upload the content with
<Link to="/api/reference/replace-exam-draft-resource-content">Replace Draft Resource content</Link>,
following its strict multipart format. Each upload creates a new File Revision
that never changes. Revisions you already published keep the old file.

Call <Link to="/api/reference/reorder-exam-draft-resources">Reorder Draft Resources</Link>
with the complete order of active Resources you expect. Removing a Resource
closes the gap in the Draft's order without deleting published history. Read
content only through the protected inline call. The API never gives you a
storage key or a public URL.

## 5. Build the Starter Workspace

Start with <Link to="/api/reference/list-exam-draft-starter-workspace">List Draft Starter Workspace</Link>.
Create directories and files with their own calls. Then move or replace
specific Entries, passing their current content versions and the Draft
revision.

Paths are case-sensitive, relative POSIX paths in one standard form. Reject
traversal, backslashes, repeated separators and `.proctor`.
Deleting a directory that isn't empty doesn't delete its contents. Check the
Institution's current limits on entries, size per file and total bytes before
you upload, but still handle a rejection from Proctor when you make the change.

## 6. Manage Managers and ownership

Call <Link to="/api/reference/list-exam-managers">List Exam Managers</Link> to
see each Manager and how they were added. A new Manager must be active and
belong to the Exam's exact Academic Unit right now.

- <Link to="/api/reference/add-exam-manager">Add Exam Manager</Link> gives
  someone equal responsibility without changing the owner.
- <Link to="/api/reference/transfer-exam-ownership">Transfer Exam ownership</Link>
  changes the protected owner. The previous owner stays on as a Manager.
- <Link to="/api/reference/remove-exam-manager">Remove Exam Manager</Link>
  can't remove the current owner.

All three check `expected_revision`, require an idempotency key and keep the
history of who was added by whom. Each one sends a matching safe notice in the
same transaction, and resending the identical request doesn't send it twice.

## 7. Publish the complete Draft

Fetch the complete current authoring view and check the title, rendered
instructions, policies, Resource order and content, Starter Workspace,
capacity totals and Draft revision. Then call
<Link to="/api/reference/publish-exam-revision">Publish Exam Revision</Link>
with an idempotency key, which is required.

```bash
curl --request POST \
  --url https://proctor.example.edu/api/v1/exams/<exam-id>/revisions \
  --header 'Authorization: Bearer <interactive-session-access-token>' \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: publish-algorithms-final-12' \
  --data '{"expected_revision":12}'
```

In one transaction, Proctor checks and freezes the whole Draft, the current
capacity values, the publisher, the time and the content digests. If the Draft
hasn't changed since the last Revision, you get a no-changes result instead of
a new Revision. Keep the Revision ID. You need it to schedule a Sitting.

What to do when publishing doesn't succeed:

- After a timeout, resend exactly the same body with the same key.
- If the Draft is stale, fetch it again and review it.
- If content or image checks fail, fix the part of the Draft that the error
  names. Once its revision has moved on, publish with a new key.

Don't create a second Exam to get around a failed step.
