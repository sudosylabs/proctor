# Start, continue and submit an Attempt

A candidate takes an Exam through a Desktop Session tied to a registered key,
a WebSocket and HTTP calls, all working together. A general backend
integration or a browser Session can't make up an Attempt or a continuity
credential. The privileged candidate coordinator gets both when it is admitted
through an authenticated `exam_attempt.connect` on the versioned WebSocket
protocol.

## 1. Find out what the candidate can do now

Start with <Link to="/api/reference/list-candidate-exam-activity">Candidate Exam Activity</Link>.
This list drives navigation. It shows upcoming, available, active, submitted,
released and past activity. Follow only an action the list returns for the
current item. Don't work out availability from a cached schedule.

The first eligible entry creates, on demand, the candidate's one Ready Attempt
and a copy-on-write Workspace. It does **not** create a Participation or a
Connection. Keeping these apart means navigation and preparing durable work
don't depend on secure Desktop admission, and Proctor doesn't create Attempts
for candidates who never show up.

## 2. Open the Desktop Session and the socket

Finish Desktop browser authorization, so that the installation has registered
the client's P-256 key and issued a DPoP-bound Desktop Session. Then
<Link to="/api/reference/connect-web-socket">connect the WebSocket</Link> with
that Session's DPoP access credential and a fresh proof bound to the nonce.

Before admission, call <Link to="/api/reference/ping-system">System ping</Link>
with the exact Desktop release, build, target and realtime protocol. Stop if
the server reports maintenance, a required update, an incompatible server, an
unsupported target or a revoked build. A client must not change what it
reports about itself to look compatible.

When Proctor accepts `exam_attempt.connect`, it checks again:

- the candidate's current Class membership;
- the Sitting's state;
- the registered key and the Session;
- build compatibility;
- the runtime posture;
- the lock that allows one unresolved Attempt per User Session;
- the Ready Attempt.

It then creates one Participation generation and one current Connection, tied
to that exact Desktop Session. Keep these returned values only in protected
runtime memory:

- `exam_attempt_id`
- `participation_id` and `generation`
- `connection_id`
- the 32-byte continuity credential
- renewal interval and lease expiry

Admission can also carry the Attempt Configuration. Proctor builds it from the
candidate's settings and the verified Desktop capability registry, and it
never changes. Treat it as the fixed runtime input for that Attempt, not as a
local preference anyone can edit. Reconnecting, or a manager re-allowing the
Attempt, never rebuilds it.

The exact messages for connect, renewal, focus loss, acknowledgements and
errors belong to the versioned WebSocket protocol. They are not HTTP request
bodies. Never put the continuity credential in a URL, form field or log.

## 3. Read the presentation

For protected HTTP requests, send a fresh Desktop DPoP proof along with the
two Attempt headers:

```bash
curl --request GET \
  --url https://proctor.example.edu/api/v1/exam-attempts/<attempt-id>/presentation \
  --header 'Authorization: DPoP <desktop-session-access-credential>' \
  --header 'DPoP: <fresh-proof-for-this-get-target-and-current-nonce>' \
  --header 'X-Proctor-Attempt-Credential: <continuity-credential>' \
  --header 'X-Proctor-Attempt-Connection-ID: <connection-id>'
```

<Link to="/api/reference/get-candidate-exam-presentation">Get candidate presentation</Link>
returns the Revision the candidate was admitted on and the Sitting's current
Revision, which never changes once created. It also says whether the candidate
must acknowledge a live correction. Fetch protected Resources through their
content routes for this Attempt.

## 4. Save Workspace changes

Every Workspace change includes `participation_id` and `generation`. For
uploads, put those values in the `metadata` part. Keep the Workspace cursor and
content version from each acknowledged change. Send an idempotency key where
the endpoint requires one.

```json
{
  "participation_id": "<participation-id>",
  "generation": 2,
  "path": "answers"
}
```

After the client recovers from an interruption, call
<Link to="/api/reference/list-candidate-exam-workspace-changes">Workspace changes</Link>
to catch up on the changes Proctor acknowledged. This ordered log keeps only
a limited history. If Proctor can't bridge from the cursor you send, rebuild
your local copy from a complete manifest. Don't push a local tree that Proctor
never acknowledged over the server's copy.

## 5. Send integrity signals

While the current Participation allows collection, send focus loss and Browser
Activity on their versioned WebSocket streams. Browser Activity records
top-level navigation with as little detail as possible. It is not page content
or a general browsing history. Keep the highest sequence number Proctor has
acknowledged for each stream, because submission closes both streams.

Each Browser Activity batch holds 1 to 64 events, is at most 256 KiB once
encoded, and covers no more than 16 source sessions. Proctor keeps only a
reduced location. It leaves out the query, fragment, credentials in the URL,
page content, title, referrer, headers, cookies, DOM, downloaded bodies and
local paths. Gaps stay recorded as unknown rather than filled with invented
observations.

<GovernedFigure asset="browser-activity-privacy-boundary" />

If Browser Activity doesn't apply to the Attempt Configuration, the submission
reports `not_applicable`. Otherwise it reports either the complete final
acknowledged sequence or an explicit gap. Don't send `not_applicable` to get
around a collection policy that is turned on.

## 6. Acknowledge live corrections

When the presentation says a correction needs acknowledging, stop governed
navigation, Workspace changes and voluntary submission. Keep renewing the lease
and sending the integrity signals that are still allowed. Show the correction,
then acknowledge the oldest pending Revision with the current Participation
details, `expected_current_revision_id` and a stable idempotency key. Fetch the
presentation again after acknowledging, before the candidate carries on.

## 7. Renew or reconnect

The privileged coordinator renews the Participation explicitly, at the
interval the server gives it, with sequence numbers that only go up. A
WebSocket ping doesn't renew it. A short reconnect may keep the same
generation. A generation that expired or was interrupted is closed for good,
and the candidate needs a fresh admission. If the Attempt is suspended, a
manager must re-allow it before a new generation can start.

The server currently starts with a 5-second renewal interval, a 20-second
lease and a 2-second expiry scan. The server returns or enforces these values.
A client shouldn't hard-code them. Proctor uses PostgreSQL's clock for lease
expiry, and a lease is already invalid at the exact expiry time.

After a reconnect, fetch the presentation again and catch up on Workspace
changes. Don't assume a socket sequence number you kept locally proves the
server's state is current.

## 8. Submit against acknowledged state

Submit only once the client has acknowledgements for its last Workspace change
and its last focus-loss signal.

```json
{
  "participation_id": "<participation-id>",
  "generation": 2,
  "expected_current_revision_id": "<current-revision-id>",
  "expected_workspace_cursor": 18,
  "final_focus_loss_sequence": 3,
  "browser_activity": {
    "state": "complete",
    "final_sequence": 12
  }
}
```

<Link to="/api/reference/submit-exam-attempt">Submit Exam Attempt</Link> seals
the Workspace in one transaction and returns a receipt that is safe to show the
candidate. If you're not sure whether it worked, retry only with the exact same
body and idempotency key, and a fresh DPoP proof for the retry. Submission
detaches the Attempt from the runtime but leaves the normal authenticated socket
open.

A submission conflict tells you the client is out of step. If the Workspace
cursor, focus-loss sequence, current Revision, a pending correction or Browser
Activity conflicts, catch up with the server's state before you offer
submission again. Never lower a guard value, and never leave out the final
integrity state.
