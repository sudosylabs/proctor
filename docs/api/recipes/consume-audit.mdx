# Read audit history

<Link to="/api/reference/list-audit-events">List audit events</Link> returns
only the history the current principal may see for the Institution or
Academic Unit scope you ask for. Being authenticated never skips that check.

Institution `audit.view` and scoped `academic_audit.view` are different
permissions. The academic one covers only the caller's authorized Unit or
Class subtree and a fixed list of academic actions. It doesn't show unrelated
identity, provider, credential or security history.

## Page through the results

Choose a fixed set of filters you're authorized for, ask for one page of
limited size, and pass `next_cursor` back unchanged until it no longer
appears. The response calls its array `events`. It is always present, even
when empty.

```bash
curl --get \
  --url https://proctor.example.edu/api/v1/audits \
  --header 'Authorization: Bearer <token>' \
  --data-urlencode 'resource_type=exam' \
  --data-urlencode 'resource_id=<exam-id>' \
  --data-urlencode 'limit=100' \
  --data-urlencode 'cursor=<next-cursor-if-present>'
```

The endpoint reference lists the current filters and how you can combine
them. If you change the scope or a filter, the old cursor no longer applies.
Start again without it.

## Read an event

Rely on `action`, `resource` and `status` as the lasting facts of the event.
`request_id` can link the event to an operational trace you're allowed to see.
The actor, session, client, network, node and error fields are optional. They
may be missing depending on the event and on what the caller is allowed to
see.

Audit history doesn't contain secret request payloads. Don't expect to find,
or try to rebuild, credentials, exam answers, protected content or unsafe
free-text fields from it. Make your ingestion idempotent by audit event ID.
Keep the server's event timestamps and status values, rather than replacing
them with the time you collected the event.

An `attempt` records the start of a security-sensitive change. `success` and
`fail` are the final outcomes of a change. `allow` and `deny` are
authorization decisions. If operational logs suggest a change succeeded but the
required final audit record couldn't be completed, don't create the missing event in a
downstream system. Escalate it to an operator to reconcile.
