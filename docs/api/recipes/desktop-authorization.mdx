# Implement Desktop Authorization

Desktop Authorization hands off from the browser to a public client. The
Desktop client owns the state value, PKCE, the P-256 private key, the loopback
listener and where the Session credentials are stored. The hosted server signs
the person in and asks them to approve the request explicitly. Never write a
password, provider credential, browser proof, code or Session credential to
application logs.

## 1. Pin the server and check the build

Read <Link to="/api/reference/get-public-access-discovery">public discovery</Link>
from the address the user typed. Its canonical origin and installation
identity must stay the same for the whole flow. Production uses HTTPS. Only
explicit loopback development may use HTTP.

Call <Link to="/api/reference/ping-system">Ping system</Link> with the exact
Desktop release, build ID, platform, architecture and realtime protocol.
`availability` and `compatibility` are separate values. A well-formed request
returns `200` even when the result is maintenance, update required,
incompatible or unsupported. Don't start authorization unless the response
says the server is available and the build is compatible.

## 2. Create one authorization request

Generate each of these separately:

- a state value of at least 43 raw URL-safe base64 characters;
- a high-entropy PKCE verifier and its S256 challenge;
- an ES256 P-256 key pair;
- an HTTP loopback callback on the literal address `127.0.0.1` or `[::1]`, with
  an ephemeral port and an unpredictable path.

Don't use `localhost`, a wildcard listener, a remote callback, or a callback
whose host, port or path can change after you start. Keep the private key and
the verifier inside the Desktop process.

POST the public JWK, challenge, callback, state and exact build details to
<Link to="/api/reference/start-desktop-authorization">Start Desktop Authorization</Link>.
Keep the `DPoP-Nonce` response header. Open only the returned
`authorization_url`, in the system browser. Don't take it apart to build your
own sign-in screen.

## 3. Let the browser handle sign-in

The server page reads the request handle, the proof in the URL fragment and the
state once, then removes the sensitive parts of the URL from history. It may
use an existing Web Session, a local password or a configured provider. Each of
these is tied to this purpose, and each ends on a screen where the person
approves the request.

The client doesn't call the bind, context, authenticate, approve, reset or
cancel endpoints for the browser. Those belong to the hosted flow in that same
browser tab and its HttpOnly route cookie.

## 4. Check the loopback callback

Accept exactly one callback on the expected literal address, port and random
path. Compare the returned state in constant time before you read the code.
Reject a callback that is missing, mismatched, repeated or late, and close the
listener.

The redirect carries no access credential. A cancellation, an expired request
or an active Attempt Session lock ends the flow. Start again with a new state,
verifier, key and callback, and only when the user chooses to retry.

## 5. Exchange the code with the same key and verifier

POST the code, the exact state, the original verifier, the same public JWK and
the same build details to
<Link to="/api/reference/exchange-desktop-authorization-code">Exchange Desktop Authorization code</Link>.
Sign a fresh exchange proof with the private key and the current nonce. In one
transaction, Proctor uses up the code, creates or refreshes the Desktop
Registration and creates a Desktop Session. It returns access and refresh
credentials bound to the proof, plus the next nonce.

If the network result is unclear, that doesn't mean you can reuse the code.
First find out whether the exchange completed, from the response details you
have or from the account security view. If it didn't, start the whole
authorization again. The code and the proof can each be used only once.

## 6. Sign every Desktop request

<GovernedFigure asset="desktop-dpop-boundary" />

For each request, build a new DPoP proof that covers the exact canonical public
method and URI, a hash of the access credential, the time it was issued, a
unique proof ID and the current Session nonce. Send:

```text
Authorization: DPoP <access-credential>
DPoP: <new-proof>
```

If you get `authentication.dpop.use_nonce`, take the new value from
`DPoP-Nonce`, sign a new proof, and retry only if the call's idempotency rules
allow it. If you get `authentication.dpop.replayed`, never send that proof
again. Refreshing uses the same key, but with a proof made for refresh that
leaves out the access-credential hash.

## 7. Handle revocation and storage failure

When a Desktop Registration is revoked, its Sessions and credentials stop
working, and you can't restore them. Clear the affected credentials in the
client, and ask the person to approve again in the browser with a new key.

The server doesn't define how a Desktop client presents secure storage. A
client that can't protect the private key and refresh credential must not write
them to ordinary files, console output, crash reports or analytics. Make that
product decision openly in the Desktop repository. Don't invent a fallback in an
API integration.
