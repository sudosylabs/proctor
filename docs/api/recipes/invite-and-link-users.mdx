# Invite and link users

Pick the invitation type from the relationship you want to create. Each
Invitation carries a package that never changes. The package sets the exact
target scope and the Role or membership. Owning the email address doesn't
widen it.

<GovernedFigure asset="invitation-lifecycle" />

No Invitation creates a disabled placeholder User. The person issuing it must
be allowed to grant everything in the package. When someone accepts, Proctor
checks the current state of the inviter, the policy, the target, the Role, the
account and the academic structure again before committing.

## Invite a student to a Class

Call <Link to="/api/reference/issue-student-class-invitation">Issue student Class invitation</Link>
with the Class ID in the path.

```json
{
  "email": "student.one@example.edu",
  "suggested_username": "student-one",
  "suggested_display_name": "Student One",
  "suggested_locale": "en",
  "suggested_timezone": "Europe/Paris"
}
```

Proctor sends the one-time invitation claim through the configured mail
delivery. Never show that claim in an administrator UI log or an analytics
event.

Every create body, and the replacement body, takes an optional
`expires_in_days` from 1 to 30:

- When you issue an Invitation, it defaults to 7.
- A replacement keeps the lifetime of the Invitation it replaces, in whole
  days.
- A value outside the range is rejected with `invitation.invalid`.
- Resending never extends the expiry.
- Batch Invitations always last 7 days.

## Invite staff to a scope

- Use <Link to="/api/reference/issue-teacher-academic-unit-invitation">Teacher Academic Unit invitation</Link>
  for the teacher relationship and its delegated Role package.
- Use <Link to="/api/reference/issue-academic-unit-role-invitation">Academic Unit Role invitation</Link>
  for any other Role package scoped to one Unit.
- Use <Link to="/api/reference/issue-institution-role-invitation">Institution Role invitation</Link>
  for a package that applies across the Institution.

Membership and Affiliation describe relationships. They don't grant
unrestricted access. When a User who is already linked needs an explicit
permission, use <Link to="/api/reference/create-role-binding">Role Bindings</Link>.

## Accept or manage an Invitation

Links that create an account go through the browser invitation flow:

1. Call <Link to="/api/reference/start-browser-invitation">Start browser invitation</Link>
   to exchange the claim for a browser transaction tied to this purpose.
2. Call <Link to="/api/reference/accept-browser-invitation">accept with account creation</Link>
   or <Link to="/api/reference/accept-browser-invitation-with-session">accept with the current Session</Link>,
   whichever fits.

For an existing signed-in account, call the acceptance that matches the
Invitation type:

- <Link to="/api/reference/accept-institution-role-invitation">Accept Institution Role Invitation</Link>
- <Link to="/api/reference/accept-academic-unit-role-invitation">Accept Academic Unit Role Invitation</Link>
- <Link to="/api/reference/accept-teacher-academic-unit-invitation">Accept Teacher Academic Unit Invitation</Link>
- <Link to="/api/reference/accept-student-class-invitation">Accept Student Class Invitation</Link>

<Link to="/api/reference/resend-invitation">Resending</Link> issues a new claim
without changing the package. To change the scope or Roles,
<Link to="/api/reference/replace-invitation">replace the invitation</Link>.
Don't change what a claim you already sent means. Call
<Link to="/api/reference/revoke-invitation">Revoke Invitation</Link> when the
package must stop working for good.

## What each action does to the Invitation and its mail

| Action | Effect on the Invitation | Effect on mail |
| --- | --- | --- |
| issue | Creates one pending package that never changes, and one durable mail request. | Queues the first email. |
| resend | Keeps the package. Issues a new claim and deadline. | Queues a new email. Every old link stops working. |
| replace | Creates a new package and replaces the previous Invitation. | The new Invitation handles its own delivery. |
| revoke | Ends one Invitation for good. | Cancels queued delivery when it can. Mail already sent is harmless. |
| accept | Applies the package and uses up the Invitation in one transaction. | Stops queued emails that carry the now-useless claim. |
| expire | Prevents acceptance after the deadline, by PostgreSQL's clock. | Pending delivery is no longer useful. |

`pending` doesn't mean delivered, and SMTP `accepted` doesn't prove the email
reached an inbox. A production API never returns the raw invitation link.

## Keep the effective dates honest

An Invitation can start in the future. Acceptance takes effect at the intended
start or at the time of acceptance, whichever is later, so it never grants
permissions backdated. An Invitation whose intended end has already passed
can't be accepted.

Teacher packages remember where they came from. Ending the Unit membership a
package created also ends, in the same transaction, the Role Bindings that
package created. Bindings created separately stay in place. Ending any
relationship doesn't end the User's wider Affiliation.

## Batch small changes

<Link to="/api/reference/run-invitation-batch">Run Invitation Batch</Link>
takes at most 200 typed items. Give the batch the idempotency key it requires,
and give each item a short key that is unique within the request. Repeated item
keys are invalid. Proctor keeps a small, secret-free outcome for each item that
succeeds, so a retry with the items in a different order can't create another
Invitation or send another email.

For larger files, previews that don't change, cancellation, reports and
student progression, continue with
[Run onboarding imports and progression](./onboarding-imports-and-progression.mdx).

## Recover from conflicts

- An expired, replaced, revoked or used claim never comes back to life. Issue
  a new Invitation or resend through the normal lifecycle.
- A target or Role conflict needs a new replacement package, after the
  administrator reviews the current scope.
- An email address that already belongs to an unlinked User is not a reason to
  merge accounts. The person signs in with a method they already have, then
  uses the supported connection flow or accepts with their existing Session.
- A provider or mail outage doesn't weaken the claim check. Restore the service
  and resend while the Invitation is still eligible.
