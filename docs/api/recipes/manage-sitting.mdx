# Schedule and run a Sitting

A Sitting delivers one published Revision to one exact Class within a time
window. The window includes its start and excludes its end. Each command checks
the revision you send, is audited, and is idempotent where the reference says
so. Realtime messages only tell a client to fetch the current state again.

<GovernedFigure asset="sitting-lifecycle-controls" />

## 1. Schedule a Revision for a Class

Call <Link to="/api/reference/schedule-exam-sitting">Schedule Exam Sitting</Link>
with RFC 3339 timestamps and an idempotency key, which is required.

```json
{
  "exam_revision_id": "<published-revision-id>",
  "class_id": "<class-id>",
  "scheduled_start_at": "2026-12-14T09:00:00Z",
  "scheduled_end_at": "2026-12-14T11:00:00Z"
}
```

Proctor accepts the request only if:

- the Class sits under the Exam's Academic Unit;
- the Revision belongs to the Exam;
- the window fits inside the Class's exact Academic Period;
- the start, or a new start when you reschedule, is later than the current
  PostgreSQL time.

Permissions over the academic structure never let you skip these rules.

Before the Sitting opens,
<Link to="/api/reference/update-exam-sitting-schedule">Update Exam Sitting schedule</Link>
can change the Revision, the Class or the window. Send the current Sitting
revision. Only a Scheduled Sitting can be rescheduled or
<Link to="/api/reference/cancel-exam-sitting">canceled</Link>.

## 2. Read the Sitting and who is present

Call <Link to="/api/reference/get-exam-sitting">Get Exam Sitting</Link> for the
current state. Call
<Link to="/api/reference/list-exam-sitting-candidate-statuses">List Sitting candidate statuses</Link>
for a board that isn't cached and reflects a single server time given in the
response. Keep its keyset cursor and filters the same across pages.

Each candidate's status is one of `not_started`, `ready`, `connected`,
`reconnecting`, `lease_expired`, `suspended` or `submitted`. The status says
whether the candidate is present and working. It is not a judgement on
integrity. It doesn't show any Session, Registration, credential, Connection,
private reason or evidence.

<Link to="/api/reference/list-exam-sitting-no-shows">List Sitting no-shows</Link>
uses the memberships that were active when the Sitting opened, as the server
recorded it, and leaves out every User who has an Attempt. Proctor never
creates an Attempt to represent a no-show.

## 3. Send the lifecycle command you need

- <Link to="/api/reference/pause-exam-sitting">Pause</Link> keeps the
  presentation readable and integrity monitoring running, but blocks admission,
  changes and submission.
- <Link to="/api/reference/resume-exam-sitting">Resume</Link> brings delivery
  back for eligible candidates. Paused time doesn't extend the deadline.
- <Link to="/api/reference/extend-exam-sitting">Extend</Link> moves only the end
  later.
- <Link to="/api/reference/close-exam-sitting">Close</Link> moves the Sitting
  into Closing and starts sealing unfinished Attempts, with limits on the work.

Send the current Sitting revision, a new idempotency key for each new decision,
and a short private reason where the call needs one. At or after the deadline,
by PostgreSQL's clock, the scheduled end wins over a manager's command.

Closing isn't Closed. Refuse new changes straight away, then keep watching
until every Attempt that was created has one Submission and the Sitting reports
Closed. The sealing Job can't be canceled, and it recovers if a process stops.

## 4. Stage and apply a live correction

<GovernedFigure asset="correction-acknowledgement-sequence" />

For every new or replacement Resource file, call
<Link to="/api/reference/stage-exam-sitting-correction-resource-content">Stage correction Resource content</Link>
for the exact Sitting, base Revision and Resource. Keep each `stage_id` that
comes back ready. Staging on its own changes nothing that anyone can see.

Then call <Link to="/api/reference/apply-exam-sitting-correction">Apply Sitting correction</Link>
with:

- the expected Sitting revision and current Revision;
- new instructions and a new Browser Policy, if you're changing them;
- one complete, ordered list of Resources;
- a summary of 1 to 500 characters that is safe to show candidates;
- the standard names of the areas that changed;
- an explicit `acknowledgement_required`;
- a separate private reason for managers;
- a new idempotency key.

In the Resource list, an item without a stage keeps the base file, an item
with a ready stage uses the new file, and leaving an item out removes that
Resource. The correction creates a new live-correction Revision that never
changes, and points only this Sitting at it. The correction fails if it would
change the Exam Policy, the Starter Workspace, eligibility, the schedule or
protected digests.

## 5. Track acknowledgements

The candidate presentation lists the notices in order, and shows each
Attempt's acknowledgement state. Candidates acknowledge required notices oldest
first, through the route for that exact Revision. Each acknowledgement must
carry the candidate's current DPoP proof, Participation, continuity credential,
Session and Connection.

While an acknowledgement is pending, the candidate can't change their work,
use the governed browser or submit voluntarily. They can still read protected
content, renew the lease, report Browser Activity and Focus Loss, and
acknowledge. An authorized close can still seal the Attempt, and records the
missing acknowledgement as a discrepancy.

## 6. Suspend, re-allow or end one Attempt

First read the exact Attempt, and the Suspension details in the candidate
status.

<Link to="/api/reference/suspend-exam-attempt">Suspend Exam Attempt</Link> is
the immediate manual Kick of an Active Attempt. Send the expected Attempt
revision, a private reason and an idempotency key. The call:

- ends the live Participation generation and Connection as `kicked`;
- opens a `manual` Suspension with the `manager_suspended` reason shown to
  the candidate;
- creates no Integrity Flag.

<Link to="/api/reference/reallow-exam-attempt">Re-allow Exam Attempt</Link>
needs the exact active Suspension, the expected Attempt revision, a private
reason and an idempotency key. It puts the Attempt back to Ready. When the
candidate is admitted again on Desktop, Proctor creates a new Participation
generation. Flags, evidence, configuration and history stay as they were.

<Link to="/api/reference/end-exam-attempt-by-manager">End Exam Attempt by Manager</Link>
seals the last acknowledged Workspace of a Ready, Active or Suspended Attempt,
and creates one final Submission marked `manager_ended_attempt`. It isn't a
Kick, and you can't undo it. At or after the Sitting deadline, the close seals
the Attempt instead.

## Failures and retries

| Condition | What to do |
| --- | --- |
| Sitting revision conflict | Fetch the whole Sitting again and reconsider the command. |
| deadline race | Accept the scheduled-end result and watch Closing. |
| correction stage invalid or expired | Create a new stage for this target. Don't reuse a file staged for another target. |
| correction no changes | Don't create another Revision. |
| acknowledgement pending | Show the oldest notice, and call only the acknowledgement endpoint. |
| re-allow conflict | Fetch the exact Suspension and Attempt revision again. |
| unclear result from an idempotent change | Resend exactly the same body with the same key. |
| realtime event missed | Fetch the current state over HTTP again. |
