# Review and turn on Institution retention

One Institution Retention Policy covers, across every server node:

- examination work;
- integrity evidence and Submission Reviews;
- audit history;
- temporary examination exports.

Cleanup starts turned off, and saving retention periods never turns it on. A
system administrator has to approve a fresh preview for the exact policy
revision, with a strong, recent interactive sign-in.

This recipe covers the server APIs. The wider administration and examination
screens will live in the future desktop client. Deleting accounts and
exporting general personal data are separate features that don't exist yet.

## 1. Complete the examination records

Once a Sitting is Closed, resolve its Reviews and call
<Link to="/api/reference/complete-exam-sitting-records">Complete Sitting Records</Link>.
The separate `exam.records.complete` permission follows the usual Exam Manager
and scoped override rules. Every relevant Submission needs a finalized Review,
or an explicit waiver with a reason. A manager can't waive their own Submission
or skip a Flag that hasn't been decided.

Completing the records starts the examination retention clock. If new
integrity evidence is accepted, the Sitting's completion becomes stale, any
pending grace is canceled, and someone has to complete it again. The new
completion restarts the clock. An exact duplicate doesn't. Categories that
have been retired reject further evidence, and completing again later can't
bring back records that were removed.

## 2. Set the policy

Call <Link to="/api/reference/get-retention-policy">Get Retention Policy</Link>
with a Session that has `retention_policy.view`, and keep the revision. Then
call <Link to="/api/reference/replace-retention-policy">Replace Retention Policy</Link>
with a strong, recently authenticated system-administrator Session and a new
`Idempotency-Key`. With cookies, also send CSRF proof.

Send all seven periods. `candidate_notices` is optional and defaults to false:

```json
{
  "expected_revision": 1,
  "submission_retention_days": 0,
  "integrity_retention_days": 0,
  "browser_activity_retention_days": 0,
  "security_operational_retention_days": 0,
  "audit_retention_days": 0,
  "export_retention_days": 1,
  "deletion_grace_days": 7,
  "candidate_notices": false
}
```

This example keeps examination and audit records with no end date, makes
exports last 24 hours and sets seven days of grace. Those two operational
values are suggestions, not examination retention periods anyone has chosen.
The institution must choose its own periods for work, integrity, Browser
Activity, security operational records and audit before it approves cleanup.

How the values work:

- Zero means no expiry or grace is configured. It never means delete
  immediately.
- Positive periods count 24-hour days.
- Work, integrity, Browser Activity, security operational, audit and grace
  settings accept up to 36,500 days.
- Export retention accepts zero when not configured, or a fixed period of
  **1 through 7 days**. Set a positive export period before you create an
  export.
- No call shortens a configured period without telling you.

The policy, its audit record and the retry outcome commit together. A request
that changes nothing keeps the revision, timestamps and approval as they are.
Any real change to the settings pauses cleanup and cancels existing grace. If
you lose the response, retry with the same key and document. If you get
`retention_policy.revision_conflict`, read and review the current policy again
before you send a new revision with a new key.

## 3. Review the preview and approve cleanup

Call <Link to="/api/reference/create-retention-preview">Create Retention Preview</Link>
with the current policy revision and an idempotency key. A preview lasts one
hour. It holds counts for work, integrity, Browser Activity, security
operational records, audit and retirement receipts. It holds no answers,
evidence text or private reasons.

<Link to="/api/reference/list-retention-records">List Retention Records</Link>
pages through which examination records are eligible. Each Submission adds four
category records: work, integrity, Browser Activity and security operational.
The page limit counts Submissions, so a page can hold up to four times that
many category records. Pass its opaque cursor back unchanged.

Before you approve, review what can block cleanup:

- An incomplete or stale Sitting completion stops examination records from
  retiring.
- Preservation holds protect their exact Exam, Sitting or Submission.
- A period that isn't configured keeps that category.
- Integrity records that are still kept protect the work they support, until
  both periods allow it to go. A zero integrity period can therefore keep that
  work with no end date.
- An export that is being built protects its exact source categories for a
  while.
- Shared published Exam materials keep their own separate references.
- Unfinished or referenced audit, an incomplete purge and active export
  references can stop audit records or receipts from expiring.

Then call <Link to="/api/reference/change-retention-control">Change Retention Control</Link>
with `state: "enabled"`, the current control revision, the current policy
revision and the fresh preview ID. This needs `retention_cleanup.manage`, a
protected system-administrator Session, a strong recent sign-in and an
idempotency key. At least one examination or audit period, and a positive grace
period, must be set. Every worker checks the live policy and dependencies
again. A preview is not a frozen instruction to delete.

## 4. Grace, holds and notices

Eligible records get a positive grace period before they retire. Seven days is
a good starting point. To stop new retirements, call the control endpoint with
`state: "paused"`. A policy change, a hold, a new export protecting its sources
or a stale completion cancels the affected grace. When records become eligible
again, they get a fresh grace period instead of the old deadline.

<Link to="/api/reference/create-retention-hold">Create a Preservation Hold</Link>
on an Exam, Sitting or Submission with `exam.records.hold`, through the manager
or scoped override route. A hold also covers records added to that scope later,
and it doesn't expire on its own. A strong, recently authenticated system
administrator must <Link to="/api/reference/release-retention-hold">release the hold</Link>
with `retention_hold.release` and a recorded reason. If a hold races a
retirement, it either protects the record first or reports that the material
was already retired. A hold can't bring data back. Wider holds still protect
whatever remains below them.

When grace is scheduled, Proctor creates lasting notices, in the same
transaction, for the responsible Exam Managers and active institution
operators. Notices to candidates are opt-in.
<Link to="/api/reference/list-retention-notices">List My Retention Notices</Link>
returns only the current Session User's notices, including whether they were
canceled and their mail delivery state. It grants no access to examinations,
and it doesn't mark a message as read.

Failures while preparing, queuing or sending notice mail over SMTP stay visible,
but they don't hold up cleanup forever. A cancellation makes the notice's date
invalid, and Proctor drops a queued notice that has gone stale before sending
it. An SMTP send that has already started can finish. Retention and file
cleanup are scheduled hourly, and notice expansion every ten minutes, with
durable retries after a failure.

## 5. Retirement and physical cleanup

Retirement is the step you can't undo. The retirement transaction:

- removes the private category records;
- expires their retry copies;
- stops normal reads and late additions;
- leaves permanent retirement markers.

The four examination categories retire separately. Retiring Browser or native
operational records keeps the separate Review evidence copies. Retiring
integrity records removes those copies and stops new integrity records from
arriving. A read of the work after integrity has retired reports
`integrity_state: "retired"` and `integrity_retired_at`, and leaves out the old
counters. Shared published Exam materials are kept.

Small receipts hold identifiers, dates and state. They follow the configured
audit period from their own event, with positive grace, as audit history does.
Zero keeps them with no end date. Unfinished work and lasting references still
block them, explicitly. Detailed cleanup audit that is eligible can expire. Its
own receipt alone doesn't keep it forever. Permanent retirement markers outlast
the receipts, so expired records can never become readable again.

Removing the stored files is a separate step that Proctor retries. A delete
response from the storage backend isn't enough. Proctor then checks that the
exact current object key is gone. If Proctor doesn't know whether a writer
finished, it keeps checking that key and still reports it as pending, even after
seeing it absent once, because a delayed write could appear later.

Confirming the current key is gone does **not** prove the storage media was
securely erased. It doesn't stop a download that has already started, and it
doesn't remove copies in backups, snapshots, older object versions or replicas
that operators manage. Operators must manage those copies and their own backup
lifecycle separately. These status labels promise nothing more about erasure.

## Exports and other cleanup

Use the <Link to="/api/recipes/exam-exports">examination export workflow</Link>
for archives of a Submission or a Sitting. Only the requester can download an
export. Each one can be checked, and expires on its own schedule. You don't
need an export before records are deleted. Downloads, retries and later holds
don't extend its lifetime.

Cleanup of operational tokens, upload leases, abandoned stages, ordinary retry
outcomes, mail history and Job history follows its own rules. Institution
retention settings don't replace those security and maintenance lifetimes.
