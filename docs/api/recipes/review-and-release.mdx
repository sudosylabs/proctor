# Review integrity and release a result

The Submission, the integrity Review and the candidate's result are separate
resources, each with its own permissions:

- The Submission keeps the acknowledged work and a record of how the Attempt
  ended.
- The Review keeps the managers' private interpretation.
- Releasing creates a smaller view for the candidate.

None of them calculates a grade or decides guilt automatically.

<GovernedFigure asset="submission-provenance-boundary" />

## 1. Check access and inspect the Submission

Start with <Link to="/api/reference/get-exam-submission">Get Submission</Link>.
Proctor first checks permission on the Submission itself, then checks the
caller's current Exam Manager relationship and scope. If the Exam, Sitting or
Attempt in the path doesn't match, Proctor answers as if it wasn't found.

The header records how the Attempt ended, the Revision it ran on, the
acknowledged Workspace Cursor, the integrity state, the number of
discrepancies and the time. Page through the
<Link to="/api/reference/list-exam-submission-manifest">manifest, which never changes</Link>,
by stable Entry identity. Fetch file bytes only through the protected
<Link to="/api/reference/get-exam-submission-file-content">Submission content route</Link>.
Don't build storage URLs, and don't treat VFS keys as a folder structure.

Managers can look at files only after the Workspace is sealed. No manager
endpoint reads a candidate's live Workspace. A no-show has no Attempt or
Submission, and Proctor doesn't create one.

## 2. Load everything the Review needs

Call <Link to="/api/reference/get-exam-integrity-review">Get integrity review</Link>,
then page through <Link to="/api/reference/list-exam-integrity-flags">Flags</Link>,
<Link to="/api/reference/list-exam-integrity-evidence">evidence</Link> for the
purpose you need, and
<Link to="/api/reference/list-exam-integrity-discrepancies">discrepancies</Link>
as needed. Keep these private records out of general analytics, ordinary logs
and any cache a candidate can see.

<GovernedFigure asset="integrity-review-release-boundary" />

Read the chain in this order: observation, signal, finding, evidence, Flag,
then the Review's outcome. A Flag groups evidence that matched a policy. It
doesn't say the candidate meant to do anything. A discrepancy records
something uncertain, such as a gap in a sequence, an incomplete Browser
Activity source, a missing correction acknowledgement or a late Focus Loss.

## 3. Create or update the Review text

<Link to="/api/reference/update-exam-integrity-review">Update integrity review</Link>
replaces both editable text fields if the revision matches. Send zero when
this call creates the Review. Otherwise send the Review's ID and its exact
current revision.

```json
{
  "submission_review_id": "<review-id>",
  "expected_revision": 3,
  "manager_notes": "Private evidence assessment is complete.",
  "student_remarks_markdown": "Your submission was received and reviewed."
}
```

`manager_notes` stays private. `student_remarks_markdown` is optional, approved
text for the candidate, and Proctor sanitizes it again when it shows it.
Neither field should hold credentials, secrets, student data you don't need, or
an academic grade, which Proctor doesn't model.

## 4. Record a decision for every Flag

Send the Review's current revision and the decision's current revision. Zero
means create. A positive value must match the current revision.

```json
{
  "submission_review_id": "<review-id>",
  "expected_revision": 0,
  "expected_review_revision": 4,
  "outcome": "inconclusive",
  "private_rationale": "The retained evidence does not establish a reliable conclusion."
}
```

<Link to="/api/reference/save-exam-integrity-decision">Save integrity decision</Link>
accepts only `confirmed`, `dismissed` or `inconclusive`. The outcome is a
non-academic disposition. It is never a grade or a finding of guilt. The
rationale is required, is trimmed, and only managers can see it.

Every change to the text or a decision moves the single Review revision
forward. On a conflict, read the snapshot again and reconcile with the other
person's work. Never guess the next number. Use a stable idempotency key for
exact retries.

## 5. Finalize the inventory

Fetch a fresh snapshot. Check that integrity collection has finished as
`settled` or `gapped`, and that every current Flag has a current decision.
Then call <Link to="/api/reference/finalize-exam-integrity-review">Finalize review</Link>:

```json
{
  "submission_review_id": "<review-id>",
  "expected_revision": 7
}
```

Finalizing locks the Submission. It freezes the stable identities and decision
revisions into a canonical digest, including Browser groups and overflow, and
the ordered inventory of native conditions. A limit error doesn't let you
leave records out. Every past finalization snapshot stays unchanged.

If new qualifying Browser or native condition records arrive, Proctor
withdraws the current approval and holds back the released result. The Review
goes back to draft, and the affected Browser Flag decisions become stale. Fetch
the Review again, look at the updated inventory, refresh those decisions, then
finalize and release again. Replaying the same receipt can't withdraw approval
again and again.

## 6. Release the result

<Link to="/api/reference/release-student-exam-result">Release student result</Link>
is a separate, idempotent step that checks the revision. It releases the
approved snapshot and takes the same request shape as finalizing:

```json
{
  "submission_review_id": "<review-id>",
  "expected_revision": 8
}
```

Until the release succeeds,
<Link to="/api/reference/get-student-exam-result">the candidate result route</Link>
answers as if the result doesn't exist. After release, it returns only the
Review, Submission and Attempt IDs, the sanitized approved remarks and the
release time. It never returns Flags, evidence, discrepancies, decisions,
private rationale or notes, Workspace content, a grade, a score, a rubric,
pass/fail or any other academic outcome.

If you lose the response to a finalize or release call, retry with the exact
same body and idempotency key, after creating whatever transport proof the new
HTTP request needs. Don't make up a new key for the same logical operation.
