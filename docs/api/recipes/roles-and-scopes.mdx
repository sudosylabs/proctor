# Define Roles and scoped bindings

A Role is a reusable set of actions that applies across the Institution. A Role
Binding grants one Role to one User at one supported scope. Relationship
records don't grant permissions, and the display name of a binding plays no
part in permission checks.

## 1. Look at the actions and the existing Roles

Call <Link to="/api/reference/list-roles">List Roles</Link> and
<Link to="/api/reference/get-role">Get Role</Link> with the caller's current
`role.view` permission. `system_admin` is protected. Don't copy it as a quick
way to make a custom administrator.

Create a custom Role with <Link to="/api/reference/create-role">Create Role</Link>.
Pick the fewest actions one responsibility needs. Actions are stable domain
names such as `class.members.view`, not route names or HTTP verbs. Adding an
action later changes every active binding of that Role, so think through what
that means for each scope before you
<Link to="/api/reference/update-role">update it</Link>.

## 2. Work out the target scope

Bindings apply at Institution, Academic Unit or Class scope. Calls on
Programmes, Programme Levels, Academic Periods, Exams, Sittings, Attempts and
Submissions resolve to one of those scopes by following their parents. Don't
invent a binding type for them.

## 3. Create the binding

Call <Link to="/api/reference/create-role-binding">Create Role Binding</Link>
with the target User, the Role, a supported scope type, the exact resource ID,
the effective time and, if you want one, an end time within the limits the
current schema sets. Proctor checks that the caller can manage bindings at that
scope and can delegate every action in the Role.

Resending the identical request with the same idempotency key may return the
stored result. Reusing the key for another User, Role, scope or effective
period is a conflict.

## 4. Check the permissions work

Call <Link to="/api/reference/list-role-bindings">List Role Bindings</Link>
filtered to a scope you're allowed to see. Then try a safe read on the resource
you meant to grant access to. Don't treat the list as a lasting record of
permissions. For every decision, Proctor reads the active Roles, bindings,
parents and relationships again.

## 5. End a binding instead of deleting it

Call <Link to="/api/reference/end-role-binding">End Role Binding</Link> with the
current lifecycle details. The history stays.
<Link to="/api/reference/delete-role">Delete Role</Link> is blocked while any
active binding uses the Role, and it never removes the protected built-in Role.

When a person's Unit or Class relationship ends, review separately any bindings
that no longer have a reason to exist. Ending a relationship doesn't end the
permissions with it. That is deliberate.

After an authorized Role or Binding change, call
<Link to="/api/reference/list-audit-events">List Audit Events</Link> to confirm
the security decision was recorded. Audit history shows the decision that was
made. It doesn't show current permissions. Permission checks still use the live
Roles, Bindings, scopes and relationships.

## Failures and recovery

| Failure | What to do |
| --- | --- |
| authorization denied | Narrow the actions or the scope. Don't retry under a parent resource you guessed. |
| target concealed as not found | Check the exact typed ID and what the caller can see, without probing sibling scopes. |
| conflict | Fetch the Role or Binding again and reconsider the current effective state. |
| idempotency in progress | Back off, and look up the resulting resource before you resend the exact request. |
| audit unavailable | Stop. This security-sensitive decision must fail closed. |
