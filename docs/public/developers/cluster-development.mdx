# Run the three-node development cluster

The tracked cluster answers one engineering question. Can three active Proctor
nodes share the same durable state, find compatible peers, report their own
readiness and metrics, and stay reachable when one node stops?

It is a topology for certifying development work. It is not a production
high-availability deployment on a single host.

## What runs in the cluster

| Component | Development responsibility |
| --- | --- |
| HAProxy gateway | Listens on `http://127.0.0.1:18065`, health-checks node readiness, and round-robins healthy requests |
| `node-a`, `node-b`, `node-c` | Run the same immutable Proctor image with stable node identities and shared infrastructure |
| Memberlist | Discovers peers over TCP and UDP port 7946 and rejects incompatible members continuously |
| PostgreSQL | Remains the only durable application authority shared by all nodes |
| Redis | Supplies disposable Installation-shared cache and realtime coordination |
| MinIO and Mailpit | Supply shared local object storage and captured mail |
| Prometheus | Scrapes all three protected metrics listeners through generated cluster targets |
| Grafana, Loki, Collector | Present metrics and aggregate per-node structured logs |

HAProxy adds an `X-Proctor-Node` header to each response, so you can see which
node served a local request. It checks `/health/ready` and takes a node that
isn't ready out of rotation. That doesn't change what readiness means to the
application.

The cluster's public URL, credentials and ports, and the single Docker host it
runs on, are local test fixtures. Real high availability needs separate
failure domains and redundant external infrastructure.

## 1. Prepare the repository

Finish the [single-node setup](./local-setup.mdx) first. At a minimum,
`make dev-tools` must succeed.

If you want the synthetic users and Exam in the cluster, seed the single-node
Installation before you switch. Both topologies use the same default Compose
project and the same persistent volumes.

Stop the single-node server running in the foreground with
<kbd>Control</kbd>+<kbd>C</kbd>. Then stop its containers without deleting any
state:

```sh
make dev-down
```

Don't run `make dev-reset` unless you mean to delete that Installation.

## 2. Start three active nodes

In terminal 1, run:

```sh
make run-cluster
```

The first run builds the server binary, the hosted webapp and a minimal
runtime image that doesn't run as root. Compose then starts the shared
dependencies, the three Proctor nodes, observability and HAProxy. Once every
health check passes, the command follows the gateway and node logs.

In terminal 2, check the gateway:

```sh
curl --fail --silent --show-error http://127.0.0.1:18065/health/ready
```

You should see:

```json
{"status":"ok"}
```

If you didn't seed the shared Installation earlier, you can run the guarded
seed through the gateway by pointing its loopback API port at it for this one
run:

```sh
make PROCTOR_SERVER_PORT=18065 dev-seed
```

The seed still reads captured invitations from the default Mailpit port. It
doesn't need to know which healthy node HAProxy picks.

## 3. Watch the load balancing

Look at the backend header across several requests:

```sh
for request in 1 2 3 4 5 6; do
  curl --fail --silent --show-error \
    --dump-header - --output /dev/null \
    http://127.0.0.1:18065/health/ready |
    awk 'tolower($1) == "x-proctor-node:" {print $2}'
done
```

Once you trim the terminal's carriage returns, the output should include
`node-a`, `node-b` and `node-c`. The exact order is not part of any API
contract. The smoke test only requires that every healthy node gets traffic.

Prometheus should report three ready targets, and two peers for each node:

```sh
curl --fail --silent --get \
  --data-urlencode 'query=proctor_ready{job="proctor",topology="cluster"}' \
  http://127.0.0.1:19090/api/v1/query | jq '.data.result'

curl --fail --silent --get \
  --data-urlencode 'query=proctor_cluster_peers{job="proctor",topology="cluster"}' \
  http://127.0.0.1:19090/api/v1/query | jq '.data.result'
```

Metrics take time to show up. After startup or recovery, wait for several
five-second scrape intervals before you treat an empty result as a bug.

## 4. Run the repository certification

In terminal 2, run:

```sh
make cluster-smoke
```

The certification runs these checks in order:

1. All three metrics targets report that they are up and ready.
2. Every node reports exactly two compatible peers.
3. HAProxy routes requests to all three backends.
4. The gateway reports the expected build version and commit.
5. `node-b` is stopped.
6. HAProxy stays ready and stops routing to `node-b`.
7. `node-b` is restarted, and the metrics and peer view for all three nodes
   agree again.

The command stops one development node on purpose and then brings it back. It
doesn't delete shared data or volumes.

## 5. Inspect Memberlist and node identity

The node definitions and seed addresses are in `build/compose/cluster.yaml`.
Each node has:

- a stable `PROCTOR_CLUSTER_NODE_ID`;
- a Memberlist advertise address that uses its Compose service name;
- one or more seed peers;
- TCP and UDP port 7946, open only inside the development network;
- its own generated configuration and log path.

Memberlist is a transient way to carry messages and find peers. Durable
coordination still comes from PostgreSQL: its serving leases and the records
it holds as the source of truth. A single-node installation is the simplest case of the same
architecture, not a separate edition of the product.

To follow only the application and gateway logs, run:

```sh
make cluster-logs
```

Each node also writes structured logs to a file:

```text
.build/dev/logs/node-a/server.log
.build/dev/logs/node-b/server.log
.build/dev/logs/node-c/server.log
```

Use these files and Loki to diagnose problems. For durable evidence, use the
PostgreSQL audit records and application state, not logs.

## 6. Stop and recover a node by hand

The automated smoke test is the normal way to prove recovery. If you need more
time to debug, stop one node yourself:

```sh
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  -f build/compose/cluster.yaml \
  stop node-b
```

Check that the gateway is still ready, and look at `X-Proctor-Node`. Requests
must keep going through `node-a` and `node-c`. Then bring the node back:

```sh
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  -f build/compose/cluster.yaml \
  up --detach --no-deps --wait node-b
```

Run `make cluster-smoke` again to prove the cluster has fully recovered. A
restarted node must recover from the shared durable state. Copying a cache by
hand or replaying cluster messages doesn't count.

## 7. Capture diagnostics

When startup or certification fails, run:

```sh
make cluster-diagnostics
```

The command prints the Compose state and the last 300 log lines for HAProxy,
all three nodes, Prometheus and the Collector. The limit is deliberate. It
keeps the evidence small enough to review, and makes it less likely that you
copy unrelated local data.

Work through failures in this order:

| Symptom | First evidence to inspect |
| --- | --- |
| Gateway never becomes ready | node health in Compose, then the first node startup error |
| One backend never appears | that node's readiness and HAProxy health-check logs |
| Peer count remains below two | Memberlist admission, address, key-ring, and compatibility records for the affected node |
| All nodes are ready but metrics query is empty | Prometheus targets, generated cluster target file, TLS CA, and bearer credential |
| Requests fail after one node stops | HAProxy backend state and whether the failure was actually shared PostgreSQL, Redis, or MinIO |
| Restored node does not converge | stable node identity, serving lease, Memberlist admission, then PostgreSQL connectivity |

Don't try to fix convergence by deleting PostgreSQL state or turning off the
compatibility checks. Capture the diagnostics and find the boundary that
failed.

## 8. Stop the cluster and keep its state

Stop the cluster and its shared services:

```sh
make cluster-down
```

The named volumes and the ignored generated state stay in place. Start again
later with `make run-cluster`, or go back to the single-node topology with
`make run-server`.

Use `make dev-reset` only when you really want to delete the shared local
Installation, object data, captured mail, dashboards, the logs stored in named
volumes, and the guarded seed credentials.

For ports, image pins, project names and persistent local overrides, continue
with [development configuration](./development-configuration.mdx).
