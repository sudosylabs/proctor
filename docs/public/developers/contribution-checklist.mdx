# Prepare a contribution

This checklist takes you from a change you understand to a diff that is ready
for review. It covers the technical steps the repository expects. Governance,
issue intake, the DCO, licensing, conduct and review expectations are in the
repository's
[contribution guide](https://github.com/sudosylabs/Proctor/blob/main/CONTRIBUTING.md).

## 1. Set the scope

- Write down what changes for the user, operator, developer or system.
- Identify the domain terms involved and the rules that must hold.
- Find the current implementation, its tests, the nearest component contract,
  and the public maturity statement that applies.
- Run `git status` and tell existing work apart from your change.
- Before you edit anything, list the public contracts, generated artifacts and
  documentation sources your change touches.
- Stop and ask for a decision when missing information would change behavior,
  security, compatibility, licensing or deployment support in a meaningful way.

## 2. Choose the smallest complete slice

A complete slice crosses every boundary that one behavior needs, and no more.
It can include a model transition, an application use case, a Store operation,
an HTTP mapping, the OpenAPI source, tests and public guidance, all together.

Leave out:

- placeholder packages or interfaces;
- broad refactors whose only reason is symmetry or file size;
- a second source of truth for a contract that already exists;
- unrelated formatting changes or generated noise;
- speculative support for a platform, provider or workflow nobody has chosen.

## 3. Make the change where it belongs

Follow the workflow that applies:

- [server behavior](./server-workflow.mdx)
- [hosted webapp](./webapp-workflow.mdx)
- [reusable module](./reusable-modules.mdx)
- [HTTP and OpenAPI](./http-and-openapi.mdx)
- [persistence](./persistence.mdx)
- [documentation](./documentation.mdx)

Change source and tests together. When a behavior, or the place that defines
it, changes, update its component contract, its public guide and maturity, the
API source, or the tracked reference that owns it, in the same slice.

If users, operators or module consumers will notice the change, add a line
under `Unreleased` in the repository
[changelog](https://github.com/sudosylabs/Proctor/blob/main/CHANGELOG.md). Mark
an incompatible change as breaking, both in the changelog and in the commit,
following the breaking-change rules in the
[versioning policy](https://github.com/sudosylabs/Proctor/blob/main/build/README.md#versioning-policy).

## 4. Handle upstream work correctly

You may use Mattermost as a reference for behavior and source, but it is not a
template to follow by default. Before you copy or substantially adapt upstream
code or text:

1. Record the exact repository, revision, path and governing license.
2. Confirm that the license is compatible with where the code is going.
3. Rework the behavior to fit Proctor's domain, architecture, security and
   accessibility boundaries.
4. Keep any notices the license requires, and record where the work came from
   straight away.
5. Check for copied branding, fixtures, secrets and assumptions.

The reusable Apache-2.0 modules can't contain code copied from AGPL,
source-available or commercial Mattermost code. When it is required, record
Mattermost-derived server work in `server/NOTICE`.

## 5. Check in widening steps

Run the focused test while you work. Then run the gate for the module that owns
the change, the relevant integration target, and the highest product gate that
honestly applies. Use the [testing guide](./testing.mdx) rather than running
every expensive suite after every edit.

Before you hand off, run at least:

```sh
git diff --check
git status --short
make quality
```

Run `make vulncheck` when Go source or module dependencies changed. This scan
against a live database is separate from the hermetic product gate.

When you change server boundaries, or the documentation that describes them,
also run:

```sh
make -C server architecture
```

## 6. Review the diff as a reviewer would

- Read the whole diff, including generated artifacts.
- Confirm that generated files match the human-written inputs they come from.
- Search for credentials, tokens, private keys, real email addresses, student
  data, Exam answers, local paths, hostnames and oversized fixtures.
- Check that errors, logs, metrics, audit values and examples stay within
  their limits.
- Confirm that you neither staged nor reformatted anyone else's work.
- Reread changed prose for promises that released behavior doesn't back up.
- When you moved where something is defined, check that you removed the old
  copy, rather than leaving it behind for compatibility.

## 7. Hand off clearly

Report:

1. the outcome, not only the files you changed;
2. the boundary or contract that now owns it;
3. the focused and broad checks that passed;
4. any integration or environment-dependent check you didn't run;
5. every decision or source TODO that is still open.

Don't describe a preview behavior as generally available, a best-effort effect
as durable, an integrity flag as a finding of guilt, or a platform you only
assumed as supported.
