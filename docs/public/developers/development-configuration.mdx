# Configure the development runtime

Configure local development through the root Makefile. Use its variables to
avoid port clashes or to try an image upgrade under control. Don't edit the
Compose files, generated JSON or generated secrets to suit your own machine.

## Which value wins

For the root Make lifecycle, the first source in this list that sets a value
wins:

1. a value on the Make command line;
2. an assignment in the root `config.override.mk`, which Git ignores;
3. an environment variable;
4. the tracked default in `build/make/config.mk`.

This order applies to operational settings such as ports, addresses and
images. The repository fixes some values for everyone: the Go version,
`GOTOOLCHAIN`, `GOWORK`, `GOFLAGS`, the module and install directories for
pinned tools, and the path to each pinned tool. These ignore the environment
and `config.override.mk`, so your shell can't quietly change the checks that
everyone shares. Only an explicit value on the Make command line overrides
them, for a deliberate experiment.

For a one-off experiment, use the command line:

```sh
make PROCTOR_SERVER_PORT=18080 run-server
```

When a parent tool sets the value, use the environment:

```sh
PROCTOR_SERVER_PORT=18080 make run-server
```

For a setting you always want on your machine, use `config.override.mk`:

```makefile title="config.override.mk"
PROCTOR_SERVER_PORT := 18080
PROCTOR_POSTGRES_PORT := 25432
PROCTOR_REDIS_PORT := 26379
```

Git ignores `config.override.mk`. Keep it on your machine. Never put
production credentials or the connection details of a shared environment in
it.

## The listener port and the public address are separate

`PROCTOR_SERVER_PORT` chooses the port the server listens on, on loopback.
`PROCTOR_SERVER_PUBLIC_URL` defaults to `http://localhost:` followed by that
port. The public URL is the browser address Proctor uses for redirects,
browser transactions and the action links in local mail.

For the compiled hosted webapp, changing only the port is enough:

```sh
make PROCTOR_SERVER_PORT=18080 run-server
```

For a Vite flow that depends on the address, set the public URL to match Vite
instead:

```sh
make PROCTOR_SERVER_PUBLIC_URL=http://127.0.0.1:5173 run-server
```

`localhost` and `127.0.0.1` both point at loopback, but browsers treat them as
different origins. Use the exact scheme, host and port you configured for the
whole flow.

Proctor accepts plain HTTP action links only when the public URL is explicitly a
loopback address. A plain HTTP public URL that isn't loopback is still invalid.
Production addresses use HTTPS.

| `PROCTOR_POSTGRES_PORT` | `15432` | PostgreSQL host binding |
| `PROCTOR_REDIS_PORT` | `16379` | Redis host binding |
| `PROCTOR_MINIO_PORT` | `19000` | MinIO S3 API |
| `PROCTOR_MINIO_CONSOLE_PORT` | `19001` | MinIO console |
| `PROCTOR_MAILPIT_SMTP_PORT` | `11025` | Mailpit SMTP listener |

When you change a service port through Make, the generated server
configuration, the Compose binding and the matching test address all get the
same value. If your own tool bypasses Make, it has to keep those in step
itself.

To run two checkouts of the repository at the same time, give each a
different `PROCTOR_COMPOSE_PROJECT_NAME`. Give them different host ports as
well. A project name keeps containers and volumes apart, but not the ports
they listen on.

## Override an image under control

The tracked defaults pin each service to an exact version and an immutable
multi-platform digest. These variables select the images:

```text
PROCTOR_POSTGRES_IMAGE
PROCTOR_REDIS_IMAGE
PROCTOR_MINIO_IMAGE
PROCTOR_MAILPIT_IMAGE
PROCTOR_PROMETHEUS_IMAGE
PROCTOR_GRAFANA_IMAGE
PROCTOR_LOKI_IMAGE
PROCTOR_OTEL_IMAGE
PROCTOR_JAEGER_IMAGE
PROCTOR_HAPROXY_IMAGE
PROCTOR_GO_IMAGE
PROCTOR_RUNTIME_IMAGE
PROCTOR_BUILDENV_IMAGE
```

Override an image only when you mean to test compatibility or an upgrade.
Record the exact tag and digest in your review evidence. A tag alone can move,
so it doesn't prove which image passed.

`PROCTOR_GO_IMAGE` is the base of the maintainer build environment. Keep its
Go tag in step with the version in `go.work`, and always pair the tag with its
immutable digest.

## Generated state in `.build/dev`

`make dev-state` rebuilds the derived configuration and keeps any secrets it
already generated. By default, this ignored directory contains:

| Path | Meaning | Safe to commit? |
| --- | --- | --- |
| `.build/dev/config/` | Generated single-node and per-cluster-node configuration, including the bundled local server environment | No |
| `.build/dev/secrets/environment` | Bootstrap, sealing, and other development secret values | No |
| `.build/dev/secrets/metrics-token` | Prometheus bearer credential | No |
| `.build/dev/secrets/metrics-*.pem` | Local metrics certificate and private key | No |
| `.build/dev/observability/` | Generated Prometheus target discovery | No |
| `.build/dev/logs/` | Single-node and per-node structured logs | No |
| `.build/dev/prometheus/` | Local time-series history | No |
| `.build/dev/otel/` | Collector file-read checkpoints | No |
| `.build/dev/seed/credentials.json` | Random synthetic account credentials, mode `0600` | Never |
| `.build/dev/seed/fixture.json` | Synthetic fixture identifiers, mode `0600` | No |
| `.build/dev/diagnostics/` | Focused local test profiles and execution traces | No |
| `.build/bin/` | Repository-pinned Go developer binaries | No |

These files are output. They are not documentation, and they are not where
configuration is defined. To change them, change what generates them: the
tracked server example, the build scripts, the Make variables or the topology
files. A direct edit can vanish on the next lifecycle run, and nobody can
review it properly.

## Keep or replace secrets on purpose

Generating secrets is idempotent. Ordinary runs of `make run-server`,
`make run-cluster` and `make dev-state` reuse the values that already exist.
That keeps encrypted local data and protected metrics readable across
restarts.

`make dev-down` stops the containers and keeps the generated state.
`make dev-reset` deletes the Compose named volumes and the guarded seed files.
It is not meant as a general command for deleting all ignored build output.

Treat rotating or removing a secret as a separate maintenance decision on your
machine. Once a key is gone, the old data it encrypted can no longer be read.

## When an override seems to have no effect

Check these before you change any code:

1. Check whether the same variable was set on the Make command line.
2. Look in `config.override.mk` for a local assignment that takes priority.
3. Check the exported environment.
4. Compare the spelling with `make help` and `build/make/config.mk`.
5. Restart the process or containers that only read their configuration at
   startup.
6. Check the resulting listener or generated file, without printing secrets.

Don't paste all of `.build/dev/secrets/environment` into a terminal or an
issue. Look only at the non-secret field you need, and redact values before you
share any output.
