# Contribute documentation

Documentation is part of what Proctor promises. A good change gives one reader
what they need to finish a task. It doesn't turn prose into a second list of
everything the code does.

## Choose where it goes

| Information | Author it in |
| --- | --- |
| Public task guidance for operators, administrators, security reviewers, or developers | `docs/public` |
| Authored API concepts and worked recipes | `docs/api` |
| Exact public paths, schemas, errors, authentication, and examples | `server/openapi` |
| Docusaurus rendering, components, search, and generated adapters | `docs/site` |
| Exact behavior of one component | Comments on the code that enforces it, or a README beside it |
| Canonical domain terms | `docs/glossary.md` |
| Repository-wide rules for contributors and agents | `AGENTS.md`, with subtree differences in the nearest `AGENTS.md` |
| Public availability or maturity | The affected public page and the implementation and tests that support it |
| Discoverable implementation detail | Code, tests, configuration, or command help |

Don't copy architecture rules or code comments into public prose. Explain
the reader's task and what follows from it. When a contributor needs more
engineering detail, link to the exact source.

## Write a public page

Every hand-written page starts with the required metadata:

```mdx
---
title: Clear Task-Oriented Title
description: One sentence describing the outcome and scope.
audience: developer
maturity: preview
slug: /developers/example/
---
```

The allowed maturity values are `available`, `preview` and `planned`. Planned
pages stay out of the normal navigation until they describe behavior people
can use. Maturity reports how far the implementation and release have got. It
is not a marketing label.

A page that lasts should answer these questions:

1. Who is it for?
2. What can they do now?
3. What do they need to know before they start?
4. Which command or decision moves the task forward?
5. How do they check it worked, and recover if it didn't?
6. Where do they go next?

## Use the glossary terms

Use the terms defined in the public [glossary](../reference/glossary.mdx), and
keep the distinctions that matter. An Installation is not a tenant. A Class is
not a generic group. An Exam Revision is not an Exam Sitting. An
authentication Session is not an Exam Attempt.

Use the inline `Term` glossary component only on a first occurrence you choose
on purpose, where the definition really helps the reader. Keep tooltips out of
headings, code, API paths, tables full of repeated terms, and illustrations.

When the source glossary changes, regenerate and check its public views from
`docs/site`:

```sh
npm run generate:glossary
npm run check:glossary
npm run test:glossary
```

## Add a figure only when it explains something

A diagram or screenshot is evidence, not decoration. Add one when it makes
ownership, a sequence, a lifecycle, a spatial relationship or a stable UI
procedure much easier to follow than prose.

Every figure needs all of the following:

- one registry record in `docs/public/assets.json`;
- the exact file under `docs/public/static/assets`;
- synthetic content that has passed a privacy review;
- useful alternative text and a caption;
- its dimensions;
- review triggers;
- a visual acceptance hash.

Public MDX refers to the figure through `GovernedFigure`, using only its stable
registry ID.

Don't add Markdown images, raw `img` elements, image imports, direct asset
paths, unregistered files, screenshots of real operations, or copied vendor
artwork.

Review diagrams at full size and inside the page. Every word must stay inside
its box, and every connector must join its source and its target. The whole
structure must still be recognizable at 390 × 844. The meaning must survive
printing, a dark interface around it, and the loss of color.

Run the figure checks from `docs/site`:

```sh
npm run validate:assets
npm run test:assets
```

## Keep search and the API pages current

When you change public or API content, regenerate the local search index:

```sh
cd docs/site
npm run generate:search
npm run check:search
npm run test:search
```

The index is built the same way every time and stays local. It never sends a
reader's search to an outside service.

The API endpoint and product-area pages are generated from the reviewed
`server/openapi.json` artifact. Edit the human-written YAML modules and follow
the [HTTP and OpenAPI workflow](./http-and-openapi.mdx). Never edit the output
in `docs/api/reference`.

## Keep the technical references current

The environment variable reference is generated from the server's typed
override declarations. The command-line reference is written by hand on
purpose, but a check compares its required commands and flags against the
Cobra source. After you change configuration overrides or the CLI, run from
`docs/site`:

```sh
npm run generate:technical-reference
npm run check:technical-reference
```

Don't edit `docs/public/reference/environment-variables.mdx` by hand. Change
`server/config/environment_overlay.go`, then regenerate the page.

Update `docs/public/reference/command-line.mdx` when a command's purpose,
arguments, side effects, output, failure behavior or recovery guidance
changes. The technical reference check catches environment output that is out
of date, and required CLI contracts that no longer match their source
declarations.

## Preview and check

Start the documentation site from the repository root:

```sh
make docs-start
```

Before you hand off, run:

```sh
make docs-check
make -C server architecture
```

The docs gate checks metadata, terminology adapters, design tokens, icons,
search, governed figures, OpenAPI content and rendering, TypeScript, broken
links and the production build.

For a change people can see, look at the desktop and mobile layouts, both
themes, keyboard order and focus, reduced motion, zoom, text wrapping, how
legible the figures are, and any horizontal overflow you didn't intend.

## Review your page

- Does the page help with a task, rather than repeat a list of files?
- Does every statement belong on this page?
- Are open questions written as explicit TODO comments, rather than invented
  promises?
- Are the examples synthetic, with no credentials, student data, Exam answers,
  hostnames, object keys or local paths?
- Do external links use HTTPS, and have internal routes been checked?
- Did every affected generated page rebuild from the tracked input it names?
