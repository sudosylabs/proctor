# Change HTTP and OpenAPI

Proctor's public API is written by hand in one place and read by several
checked consumers. YAML modules under `server/openapi`, organized by resource,
define the wire contract and the reference text. The compiler turns them into
`server/openapi.json`. The runtime agreement tests, the webapp type generator
and the documentation site all read that reviewed file.

Never edit `server/openapi.json` or the generated endpoint pages by hand.

## Find the file that owns the operation

Search by path or by stable operation ID:

```sh
rg -n '/api/v1/exams|operationId: createExam' server/openapi/fragments
```

Pick the existing product-area directory and the narrowest resource module.
Only create another YAML file, with a descriptive name, when no existing
resource is a natural home. Files are found recursively, so there is no
manifest to update.

Definitions that one resource uses stay in that resource's file. Move a schema,
parameter, request body or response into the product area's `shared.yaml` only
when several resources in that area use it. The root `shared.yaml` is for
definitions that truly span product areas.

## Build one complete operation

Changing an operation usually means changing all of these together:

1. **Application capability.** A typed command or query, and its result.
2. **HTTP resource.** A strict request DTO, an explicit mapping into the
   domain, a typed result, and an allowlist of public errors.
3. **Route catalog.** One explicit credential and assurance requirement.
4. **OpenAPI source.** The exact path, method, schema, prose, examples and
   Proctor extensions.
5. **DTO registry.** Register each new request or response DTO in the
   DTO→schema registry. Agreement on routes, authentication, idempotency,
   public errors and DTO schemas is worked out from it.
6. **Consumer adapters.** Regenerate the webapp API types, or update the
   hand-written API recipes, when the public contract requires it.

The HTTP Routing Kernel, package `server/httpapi/route`, is sealed before the
server starts serving. Resources in `server/httpapi` use its exported names and
never reach past them. Add your resource to the explicit production catalog in
`server/httpapi/resources.go`. Don't register routes during initialization,
expose the router's internals, or add a general-purpose way to write raw
responses.

## Follow the sealed route catalog

The production route path is easy to search for on purpose:

```text
httpapi.New
  → productionResources
  → one cohesive <domain>Resource
  → one route.Endpoint{…} literal per route
  → route.New: catalog validation and immutable dispatch
  → one application capability
```

The resource constructor declares each route as one `route.Endpoint` struct
literal with named fields: `Method`, `Path`, `Auth`, `Errors`, and the
operation in `Handle`. You always write `Auth`, even for `route.AuthPublic`.

The handler receives a `route.Request` and returns either a `route.Result` or
the application's error. A route sets `Idempotency`, `MaxBodyBytes` or a named
`Protocol` operation only when it needs one.

A route keeps only the narrow application capability it uses. It never keeps
the full HTTP options, the application facade, the router, the root Store, the
platform or a concrete adapter.

Before the server can accept traffic, the catalog rejects:

- two routes with the same normalized method and path;
- unknown parameter kinds;
- invalid authentication requirements;
- incomplete public-error mappings.

Every entry point appears in this catalog, including the WebSocket upgrade.

## Keep handlers mechanical

A normal handler should be easy to review in one read:

1. Decode a request, within its size limit, into a DTO that the transport
   owns.
2. Parse the canonical IDs and other wire values.
3. Map them explicitly into one typed application command or query.
4. Call one application capability with the immutable invocation.
5. Map the safe result into a response DTO.

Apply the body limit before you decode. A JSON request must contain exactly
one value. Proctor rejects unknown fields and trailing content. Use
`Optional[T]` when the contract needs to tell apart a missing field, a zero
value and an explicit null. Only a named extension object with its own limits
may accept unknown keys.

A domain model is never used as a request or response DTO. Adding a harmless
field to a domain record must never quietly add a public field.

Ordinary operations return a typed status and body result, and an `error`.
Redirects, uploads, downloads and upgrade transfer use reviewed, named result
types. The WebSocket handshake is the only operation allowed to write a raw
response, because a successful upgrade hands the connection over to the
WebSocket transport.

## Declare credentials and assurance separately

Every route declares what identifies its principal. The options are public,
authenticated, interactive Session, refresh credential, strong authentication,
recent reauthentication, or a combination of these. Administrative permission
is not one of these classes. The application use case checks it against the
current resource.

An unsafe request authenticated by cookie also needs the route's CSRF proof.
A request can't mix bearer and cookie credentials and have Proctor pick one by
priority. Keep the runtime declaration, the OpenAPI `security` and the
`x-proctor-auth` value in exact agreement.

## Map every expected failure

An expected application failure uses a stable dotted code and only fields
that are explicitly safe. It contains no HTTP status, localized text, request
ID, SQL detail or stack trace. The transport maps only allowlisted codes to
the declared RFC 9457 Problem Details responses.

Any unknown or undeclared error becomes a generic internal failure with a
correlation ID. It is logged once, at the outer operational boundary. Never
make up a status from an error string. The derived route agreement checks each
route's public errors against OpenAPI.

Read [authorization, errors, and audit](./server/authorization-errors-audit.mdx)
before you decide whether to answer a denied request for a specific resource
with forbidden, or to hide it as not found.

## Design collections and cursors

A new collection returns an object with an `items` array that is never null,
and an optional `next_cursor`. A collection without a size limit uses keyset
pagination, not growing offsets.

Cursors are opaque, versioned, limited in size, and untrusted. Clients send
them back unchanged. The shared envelope checks that a cursor is canonically
encoded and has the right shape. The resource owns the keyset fields, a stable
order, checking what the values mean, and any compatibility window. Never put
a private Workspace path, a credential or an unbounded filter in a cursor.

## Fill in the whole contract

Every operation has exactly one public product-area tag, and all of the
following:

- a short `summary` in the imperative;
- a `description` that explains the behavior in substance;
- an explicit OpenAPI `security`;
- `x-proctor-auth`, matching the runtime route;
- `x-proctor-error-codes`, matching the declared responses;
- `x-proctor-idempotency`, set to `none`, `optional` or `required`;
- a description of the purpose of every parameter and request body;
- for mutations, a synthetic request example that is valid against the
  schema, or for bodyless and multipart mutations, an executable
  `x-codeSamples` example.

Public failures use RFC 9457 Problem Details and stable application codes.
Unknown application errors fail closed. Don't turn an undeclared internal
error into a public response you made up.

Examples must never contain real Institutions, Users, Exams, answers,
credentials, email addresses, object keys, hostnames or local paths. Use
values that are obviously synthetic, and clear placeholders for credentials.

## Build and check agreement

Regenerate the reviewed artifact:

```sh
make -C server openapi-build
```

Review the diff in `server/openapi.json`. Then check that the source and the
artifact haven't drifted apart:

```sh
make -C server openapi-check
```

Check agreement with the registered HTTP routes:

```sh
make -C server openapi-agreement
```

If you changed reference content or how it is presented, also run:

```sh
cd docs/site
npm run audit:openapi
npm run test:openapi-audit
npm run test:openapi-reference
```

Finish with `make docs-check` when you changed endpoint pages, product-area
navigation, API recipes or how the reference is presented.

## Regenerate the browser types

When the hosted webapp uses a schema you changed:

```sh
cd webapp
npm run api:generate
npm run api:check
```

The generated TypeScript schema is built from the reviewed OpenAPI artifact.
Don't patch it to make up for a source contract that is incomplete.

## Compatibility

The public API lives under `/api/v1`, but Proctor hasn't yet made its first
API commitment for a supported release. Until then, you can change a contract
in place, but only when the server, the reviewed OpenAPI artifact, the
agreement tests and the clients that depend on it all change together. Don't
create a parallel version only to keep an old development contract alive.

After the first supported release, an established meaning can only grow by
adding to it. The exception is an explicit compatibility decision that
introduces another version and a migration path. Renaming a field, narrowing
the values accepted, changing what is hidden, or removing a public error can be
a breaking change even when the Go code still compiles.
