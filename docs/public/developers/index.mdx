# Developer guide

This guide is for people who change Proctor itself. It walks you from a fresh
checkout to a change that is ready for review.

Proctor lives in one repository. It holds four Go modules that are each
versioned on their own, a React application that the server hosts, and a
documentation site that is built separately. Most of the work in a change is
knowing which of these parts owns it. The guide follows that order: start the
product, decide which part owns your change, work against the contract closest
to it, and run checks from the cheapest to the most expensive.

## Your path through the guide

1. [Prepare your local environment](./local-setup.mdx) and install the pinned
   [tools and debugger setup](./tooling-and-debugging.mdx). Create the guarded
   synthetic fixture, then confirm that your first browser session works.
2. [Learn the repository boundaries](./repository-boundaries.mdx) before you
   decide where a change belongs.
3. Follow the workflow for the part you are changing. Then work through the
   [testing ladder](./testing.mdx) before you propose the change.

If your environment or a workflow breaks, run
[`make dev-doctor`](./troubleshooting/index.mdx) first. It changes nothing. It
finds the first boundary that fails and points you to a focused diagnosis,
without wiping your local state.

## Pick the workflow for your change

| Goal | Start with | Finish with |
| --- | --- | --- |
| Change domain or server behavior | [Server workflow](./server-workflow.mdx) | Focused tests, server check, affected integration suite |
| Change a hosted browser flow | [Webapp workflow](./webapp-workflow.mdx) | Generated adapters, browser matrix, webapp check |
| Change cache, mail, or VFS behavior | [Reusable modules](./reusable-modules.mdx) | Module conformance, race, vet, workspace-independent build |
| Add or change an HTTP operation | [HTTP and OpenAPI](./http-and-openapi.mdx) | OpenAPI build, agreement, reference audit |
| Change durable data or SQL | [Persistence workflow](./persistence.mdx) | Store conformance, migration and PostgreSQL integration tests |
| Change public or maintainer documentation | [Documentation workflow](./documentation.mdx) | Affected generators, docs check, architecture gate |
| Diagnose a failing development workflow | [Troubleshooting](./troubleshooting/index.mdx) | Narrow reproduction, boundary check, original workflow |
| Prepare work for review | [Contribution checklist](./contribution-checklist.mdx) | Clean diff and the highest relevant repository gate |

Two of these workflows are full manuals.

The [server development manual](./server-workflow.mdx) follows a change all the
way through the server. It starts with where the package goes and the domain
rules, then covers Store transactions, HTTP and OpenAPI, authorization and
audit, Jobs, mail, files, realtime, clustering, runtime integration and final
review. If you are new to the server, read its
[User Settings slice](./server/user-settings-slice.mdx) first. It shows one
complete feature end to end.

The [webapp development manual](./webapp-workflow.mdx) follows a browser
feature from the route the server hosts, through bootstrap that keeps
credentials safe, generated API and localization adapters, interaction state,
accessibility and responsive layout, to evidence from three browser engines.
If you are new to the webapp, read its
[password reset slice](./webapp/password-reset-slice.mdx) first.

## Write each fact down once

Each kind of information has one home:

- Public guides, like this one, explain tasks and what follows from them.
- The OpenAPI YAML modules define the public HTTP contract.
- Component contracts and module READMEs describe behavior at their boundary
  that you could not guess from the code.
- Code, tests, configuration and command help are the reference for any detail
  you can find by reading them.

When your change affects more than one of these, update them together. Don't
fix drift by copying the same list into several documents.

## Four rules that save rework

1. **Decide who owns it before you abstract it.** Add a package or interface
   only for a responsibility that is stable and has a real consumer.
2. **Keep policy on the inside.** The HTTP, WebSocket, SQL, Redis, SMTP, VFS
   and Memberlist adapters don't own business rules.
3. **Commit before side effects.** Durable state commits before any cache
   invalidation, cluster fan-out, realtime publication or delivery.
4. **Test the smallest honest scope first.** A focused test gives you fast
   feedback. The module and product gates then prove the whole boundary.
