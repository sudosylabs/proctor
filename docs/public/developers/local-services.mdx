# Local development services

`make run-server` starts the whole local stack together. Each service has one
job:

- PostgreSQL stores everything that has to last.
- Redis speeds things up and coordinates work between nodes.
- MinIO stores the bytes of managed files.
- Mailpit catches outgoing mail.
- Prometheus, Grafana, Loki, OpenTelemetry and Jaeger let you watch the node.

The default lifecycle waits for every container on this page. In a production
design some of these services may be optional, but the tracked development
command configures Proctor to use them all, so none of them is optional here.

| Redis | `127.0.0.1:16379` | Required, thrown away on purpose | `build/compose/dependencies.yaml` |

| Mailpit SMTP | `127.0.0.1:11025` | Required when local mail is turned on | `build/compose/dependencies.yaml` |

| Prometheus | `http://127.0.0.1:19090` | Required by the tracked lifecycle | `build/observability/prometheus/` |
| Grafana | `http://127.0.0.1:13000` | Required by the tracked lifecycle | `build/observability/grafana/` |
| Loki | `http://127.0.0.1:13100` | Required by the tracked lifecycle | `build/observability/loki/` |

Every published port listens on loopback only. The credentials, endpoints,
anonymous dashboards and insecure protocols here are choices for development.
Don't copy them into a production deployment.

## Check the whole stack

List each service and its health:

```sh
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  ps
```

Follow the logs of every container:

```sh
make dev-logs
```

To see recent logs from one service, name its container and limit the output:

```sh
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  logs --tail=100 postgres
```

Replace `postgres` with `redis`, `minio`, `mailpit`, `prometheus`, `grafana`,
`loki`, `otel-collector` or `jaeger`. Proctor's own output appears in
terminal 1 and in `.build/dev/logs/local/server.log`.

## PostgreSQL: lasting application data

**What it's for.** PostgreSQL holds all application state that must survive:
the Installation and identity records, academic structure, Exams, Sittings,
audit, Jobs, queued mail and managed-file metadata. Proctor never rebuilds
this state from Redis or from cluster messages.

**Checking it.** The Compose health check runs `pg_isready`. You can run the
same quick check yourself without opening a SQL shell:

```sh
docker compose -f build/compose/dependencies.yaml \
  exec postgres pg_isready -U proctor -d proctor
```

The output should end with `accepting connections`. Proctor also logs
`database migrations complete` during startup, before it becomes ready.

**Logs and reset.** Look in the `postgres` container logs for recovery,
storage or connection errors. `make dev-down` keeps the `postgres-data`
volume. `make dev-reset` deletes it, and with it the local Installation. Never
point the development reset commands at a shared or production database.

**What failure looks like.** Proctor doesn't finish starting, readiness stays
unavailable, migration errors appear before `server started`, or HTTP requests
that change data return an error saying persistence is unavailable.

**Tests that cover it.** Run `make -C server integration-postgres` for the
Store and application integration tests, or `make integration` at the root
for every server suite that needs real dependencies.

## Redis: shared coordination you can throw away

**What it's for.** The default server uses Redis for the application cache
that the whole Installation shares, for authentication counters, and for
short-lived coordination between nodes. The in-process Store cache on each
node is separate: a size-limited LRU.

**Checking it.** Compose uses `redis-cli ping`:

```sh
docker compose -f build/compose/dependencies.yaml \
  exec redis redis-cli ping
```

You should see `PONG`. When the server starts, its `application cache ready`
record should name `redis` and `installation_shared`.

**Logs and reset.** Redis runs read-only, with `/data` on tmpfs and both
snapshots and append-only persistence turned off. `make dev-down` removes the
container and everything cached in it. No Redis volume is kept. That's
intended, because Proctor can rebuild everything it needs from PostgreSQL.

**What failure looks like.** Authentication rate limits or cache operations
degrade, multi-node realtime tests don't converge, or the server reports at
startup that the cache backend is unavailable. Deleting Redis data must never
delete a User, an Exam, an audit event or anything else that has to last.

**Tests that cover it.** Run `make -C server integration-redis` for the shared
cache conformance suite, and `make -C server integration-realtime` for
multi-node realtime behavior backed by Redis.

## MinIO: local S3-compatible file storage

**What it's for.** MinIO provides the S3 API that the VFS layer talks to.
PostgreSQL holds the metadata for each managed file, and MinIO holds the
bytes. The `minio-init` container runs once and creates the `proctor-dev`
bucket. Running it again is safe.

**Checking it.** Call the S3 health endpoint:

```sh
curl --fail --silent --show-error \
  http://127.0.0.1:19000/minio/health/live
```

An empty, successful response means MinIO is healthy. Use the MinIO console
at `http://127.0.0.1:19001` only to look at synthetic local objects. The local
credentials are `proctorminio` and `proctorminio-secret`.

**Logs and reset.** Look in the `minio` and `minio-init` logs when the bucket
isn't created or objects can't be read or written. `make dev-down` keeps
`minio-data`, and `make dev-reset` deletes it. When you want a clean
Installation, reset PostgreSQL and MinIO together so the metadata and the bytes
can't get out of step.

**What failure looks like.** Startup reports the filesystem backend
unavailable. Uploads, renditions, Workspace projection or purges fail. Or
`minio-init` can't create the bucket.

**Tests that cover it.** Run `make -C server integration-s3`. It runs the
shared S3 conformance suite plus the server's file-purge and Attempt Workspace
integration tests.

## Mailpit: captured development mail

**What it's for.** Mailpit accepts SMTP from Proctor's real, durable mail
worker and keeps every message local. It's the only supported way for the development seed to pick up
Invitation claims. The API, audit, logs and fixture files never reveal those
credentials.

**Checking it.** Open Mailpit at `http://127.0.0.1:18025`. The Compose health
check uses Mailpit's built-in readiness command. After `make dev-seed`, filter
for `ada.lovelace@northbridge.example` or
`samira.okafor@northbridge.example`.

The SMTP listener is `127.0.0.1:11025`, and the Proctor server connects to it
directly. Don't set up a real recipient or an external relay for the synthetic
fixture.

**Logs and reset.** Look in the `mailpit` container logs for listener or
database errors, and in Proctor's logs for mail failure codes. `make dev-down`
keeps the captured messages in `mailpit-data`, and `make dev-reset` deletes
them.

**What failure looks like.** Creating an Invitation reports that mail is
unavailable, `make dev-seed` times out waiting for a claim, the mail health
record shows degraded, or queued Mail Delivery Jobs can't reach SMTP.

**Tests that cover it.** `make integration` at the root covers paths that go
from the application through SMTP. The mail-specific checks live in
`make -C server phase-transactional-mail`, which includes delivery through
Mailpit.

## Prometheus: metrics and rules

**What it's for.** Prometheus scrapes Proctor's metrics listener, which is
protected by TLS and a bearer token. A generated file tells it whether to
scrape the single node or the three-node cluster. Tracked rules evaluate
operational signals.

**Checking it.** First check Prometheus itself:

```sh
curl --fail --silent --show-error http://127.0.0.1:19090/-/ready
```

Then check that it can scrape Proctor:

```sh
curl --fail --silent --get \
  --data-urlencode 'query=up{job="proctor"}' \
  http://127.0.0.1:19090/api/v1/query | jq '.data.result'
```

The tracked configuration is `build/observability/prometheus/prometheus.yaml`,
with the rules next to it. The target list, the local CA and the bearer token
are generated under `.build/dev`.

**Logs and reset.** Look in the `prometheus` logs for TLS, bearer token,
target discovery or rule-loading errors. Compose keeps time-series data in the
ignored `.build/dev/prometheus` directory, which holds no application data.
It's safe to delete metrics history, but a deleted history doesn't mean the
application state was reset.

**What failure looks like.** The Proctor target is down, dashboards show no
series, `cluster-smoke` can't see readiness or the peer count, or the logs
report a certificate or bearer token mismatch.

**Tests that cover it.** `make cluster-smoke` checks the number of targets,
node readiness, peer metrics and build identity. `make build-scripts-check`
checks the generated inputs for development observability.

## Grafana: read-only local dashboards

**What it's for.** Grafana loads the tracked Proctor overview dashboard and
sets up Prometheus and Loki as data sources. Anonymous local visitors get
Viewer rights. The login form and online update checks are turned off.

**Checking it.** Call the API, then open the dashboard:

```sh
curl --fail --silent --show-error http://127.0.0.1:13000/api/health | jq .
```

The Proctor overview is at
`http://127.0.0.1:13000/d/proctor-overview/proctor-overview`. Dashboards
loaded this way are read-only. To change one for good, edit it in
`build/observability/grafana/`, not in the local UI.

**Logs and reset.** Look in the `grafana` logs for provisioning or data source
errors. `make dev-down` keeps `grafana-data`, and `make dev-reset` removes the
volume. Either way, the tracked dashboard is what Grafana loads next time.

**What failure looks like.** If Grafana is healthy but panels are empty,
Prometheus can't scrape or Loki has no logs. A provisioning failure shows up
in Grafana's startup logs instead.

**Tests that cover it.** The health wait in the development stack and
`cluster-smoke` both exercise the data path behind the dashboards. Dashboard
JSON is reviewed along with the repository and documentation changes.

## Loki: local log store

**What it's for.** Loki stores the structured server records collected from
ignored local log files. It's only for observability. It's never a record of
audit or application data.

**Checking it.** Check readiness:

```sh
curl --fail --silent --show-error http://127.0.0.1:13100/ready
```

You should see `ready`. Query logs in Grafana's Explore view with the Loki
data source that's already set up. Limit queries by time and labels. Ordinary
logs must not contain credentials, exam answers or unlimited user content.

**Logs and reset.** Look in the `loki` logs for ingestion and storage errors.
`make dev-down` keeps `loki-data`, and `make dev-reset` removes it. Losing Loki
history doesn't remove the security audit records that PostgreSQL keeps.

**What failure looks like.** Grafana log panels are empty, the collector
reports export failures, or the Loki readiness endpoint doesn't return 200.

**Tests that cover it.** The tracked lifecycle health-checks Loki and the
collector. When the cluster path fails, `make cluster-diagnostics` includes
recent output from both containers.

## OpenTelemetry Collector: log and trace pipeline

**What it's for.** The Collector tails `.build/dev/logs/*/server.log`, parses
the JSON records, adds the Proctor service and node identity, and exports them
to Loki over OTLP HTTP. It also receives spans over OTLP/HTTP from the local
server and the cluster nodes, prints one line per span in its log, and passes
them on to Jaeger.

**Checking it.** Call its health extension:

```sh
curl --fail --silent --show-error http://127.0.0.1:13133/
```

It must return HTTP 200. The Collector's configuration is in
`build/observability/otel/collector.yaml`. It records how far it has read each
file in the ignored `.build/dev/otel` directory.

**Logs and reset.** Look in the `otel-collector` logs for file discovery,
parsing, read-position or Loki export errors. If you reset its read positions,
it may send local log files to Loki again. Duplicate log records are fine,
because logs aren't the source of truth for any state.

**What failure looks like.** Proctor writes structured log files but Grafana
shows no recent logs, exporter retries mention Loki, or the health port isn't
reachable.

**Tests that cover it.** `make build-scripts-check` covers the scripts that
generate targets and configuration. When the cluster fails, the captured
output includes the Collector logs.

## Jaeger: local trace store and UI

**What it's for.** Jaeger stores the spans the Collector sends it, so you can
follow one request, Store operation or Job run from start to finish. It runs
the all-in-one image with its default in-memory store, and only the UI is
published. It's a view for development, not a production trace backend or a
retention policy.

**Checking it.** Open `http://127.0.0.1:16686`, choose the `proctor` service,
and select **Find Traces**. To find one request's trace, copy its `trace_id`
from `.build/dev/logs/local/server.log` into the UI's trace ID search. The
container health check calls Jaeger's own health extension from inside the
Compose network.

**Logs and reset.** Look in the `jaeger` logs for storage or receiver errors.
Traces live only in memory. `make dev-up`, `make dev-down` and any container
restart throw them away.

**What failure looks like.** The `proctor` service is missing from the UI
because tracing is turned off, the server can't reach the Collector on port
`14318`, or the Collector log reports failures exporting to `jaeger:4318`.

**Tests that cover it.** `make dev-doctor` checks the container's health. No
test checks trace content in Jaeger. The server's exporter tests cover what
spans contain.

## Stop and reset without losing the wrong data

For an ordinary stop, use `make dev-down`. It keeps the named volumes and the
ignored `.build/dev` configuration, secrets, logs, metrics history, Collector
read positions and seed files. Redis contents are lost, because Redis is
meant to be thrown away.

Use `make dev-reset` only when you mean to delete the PostgreSQL, MinIO,
Mailpit, Grafana and Loki named volumes and the protected seed files. It
leaves the generated secrets, configuration, logs, Prometheus history and
Collector read positions in place. These are ignored local build output that
you can regenerate or delete separately, and Proctor never restores
application data from any of them.
