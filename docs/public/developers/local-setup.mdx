# Set up Proctor for local development

This is the shortest supported way to go from a clean machine to a local
Proctor Installation that you can sign in to and change. Follow it once as
written, without swapping in other services or editing the generated
configuration by hand. You end up with a real single-node server, not a
cut-down mock.

When you finish, you'll have:

- a running Proctor server and hosted webapp
- a synthetic Institution, academic structure, Exam Manager, Candidate, Exam,
  published Revision and future Sitting
- invitation mail captured in Mailpit
- live metrics, dashboards and structured logs

## 1. Check that your system is supported

| Environment | Support | Notes |
| --- | --- | --- |
| macOS | Supported | Use Docker Desktop and a POSIX shell. Apple silicon and Intel Macs both use the repository's pinned multi-platform images. |
| Linux | Supported | CI runs on Ubuntu 24.04. Other current distributions may work if Docker Engine and the host tools below are available. |
| Windows with WSL 2 | Supported | Work inside the Linux distribution, keep the checkout on its Linux filesystem, and turn on Docker Desktop's WSL integration. |
| Native Windows shell | Not supported | The tracked Make and build scripts need a POSIX shell. Use WSL 2 rather than PowerShell or Command Prompt to run repository commands. |

Install these tools on your machine before you clone:

| Tool | Version or behavior you need | Where to get it |
| --- | --- | --- |
| Git | A current Git 2.x release | [Install Git](https://git-scm.com/book/en/v2/Getting-Started-Installing-Git) |
| Go | The patched version declared in the root `go.work` | [Install Go](https://go.dev/doc/install) |
| Node.js and npm | The Node version pinned in `webapp/.nvmrc`, with the npm that comes with it | [Download Node.js](https://nodejs.org/en/download) |
| Docker | A running Docker Engine with the Compose plugin | [Docker Desktop for macOS](https://docs.docker.com/desktop/setup/install/mac-install/) or [Docker Engine for Linux](https://docs.docker.com/engine/install/) |
| Shell utilities | POSIX `sh`, `make`, `jq`, `curl` and `openssl` | Your operating system's package manager |

On Windows, set up [Docker Desktop with WSL 2](https://docs.docker.com/desktop/features/wsl/)
and clone into a Linux path such as `~/src`, not `/mnt/c`. Installing
dependencies and watching files is needlessly slow on mounted Windows drives.

You **don't** need to install PostgreSQL, Redis, MinIO, Mailpit, Prometheus,
Grafana, Loki or the OpenTelemetry Collector yourself. Docker Compose starts
and stops them for you.

## 2. Fork and clone the repository

If you plan to contribute changes, fork the repository on GitHub first. Then
clone your fork and add the main repository as `upstream`:

```sh
git clone https://github.com/YOUR-USERNAME/Proctor.git
cd Proctor
git remote add upstream https://github.com/sudosylabs/Proctor.git
git remote -v
```

If you only want to read or build Proctor, clone the main repository
directly:

```sh
git clone https://github.com/sudosylabs/Proctor.git
cd Proctor
```

Run every command in this guide from the repository root. That's the
directory that contains `Makefile`, `go.work`, `server/`, `packages/`,
`webapp/` and `docs/`. Create a branch for your change before you edit
anything:

```sh
git switch -c feat/short-description
```

## 3. Check your tools

Run the repository's own check:

```sh
make dev-tools
```

If everything is in place, the command prints nothing and exits with status
zero. It checks that your Go and Node versions are compatible, and that npm,
`jq`, `curl`, `openssl` and Docker Compose are present and the Docker daemon is
running. If something is wrong, it names the first missing or unsupported
item.

The usual first-run problems are easy to fix:

- `docker daemon is not available`: start Docker Desktop or Docker Engine.
- An unsupported Node version: switch to the version in `webapp/.nvmrc`.
- A missing `jq`, `curl` or `openssl`: install it with your package manager,
  then run the command again.

Don't go on until `make dev-tools` succeeds.

Next, install the pinned Go tools and the locked JavaScript dependencies:

```sh
make bootstrap
make tools-check
```

The Go binaries go into the ignored `.build/bin` directory, so you don't need
to install any Go tools globally. You can run `bootstrap` again safely. Go's
build cache and npm's download cache cut down on repeated work, and the
lockfiles make every npm install the same. See
[tooling and debugging](./tooling-and-debugging.mdx) for the formatter,
linter, vulnerability scanner, language server, debugger and editor setups.

## 4. Start Proctor on one node

In terminal 1, run:

```sh
make run-server
```

The first run downloads pinned container images and installs locked webapp
dependencies, so it takes longer than later runs. The command then:

1. compiles the React webapp that the server hosts
2. generates ignored development secrets and configuration, keeping any
   secrets from an earlier run
3. starts PostgreSQL, Redis, MinIO, Mailpit, Prometheus, Grafana, Loki and the
   OpenTelemetry Collector, and waits until each one is healthy
4. runs the Go server in the foreground at `http://localhost:8065`

The server is ready when its output includes a `server started` record with
`listen_address` set to `127.0.0.1:8065`. Leave this terminal open. You'll see
shutdown logs and request failures here, and the same structured records are
also written to `.build/dev/logs/local/server.log`.

## 5. Check liveness and readiness

In terminal 2, check the process before you create any data:

```sh
curl --fail --silent --show-error http://127.0.0.1:8065/health/live
curl --fail --silent --show-error http://127.0.0.1:8065/health/ready
```

You should get:

```json
{"status":"ok"}
{"status":"ok"}
```

Liveness means the process can serve HTTP. Readiness also means the node has
finished starting up and can take application traffic. When you're tracking
down a dependency or migration problem, look at readiness, not liveness.

You can also check that the Installation is still untouched:

```sh
curl --fail --silent --show-error http://127.0.0.1:8065/api/v1/bootstrap
```

Before the first bootstrap, the response is:

```json
{"initialized":false}
```

## 6. Create the development fixture

Leave terminal 1 running, and in terminal 2 run:

```sh
make dev-seed
```

The seed works through the public HTTP API and uses the invitation claims
delivered to the local Mailpit inbox. It never imports SQL and never skips
authorization. It creates the synthetic **Northbridge University**
Installation, then adds:

- a system administrator
- the School of Computing, BSc Computer Science, Level 100, a rolling Academic
  Period and one Class
- Ada Lovelace as an Academic Unit member and Exam Manager
- Samira Okafor as a Candidate in the Class
- an Introduction to Programming Exam with a published Revision and a Sitting
  scheduled seven days ahead

When it succeeds, it names two private local files:

```text
Development fixture is ready.
Fixture summary: .../.build/dev/seed/fixture.json
Local credentials: .../.build/dev/seed/credentials.json (mode 600; do not share or commit)
```

Both files are ignored by Git and have mode `0600`. The credentials are
randomly generated for this Installation. To print only the administrator
login, in a private local terminal:

```sh
jq -r '.users.administrator | "username=\(.username)\npassword=\(.password)"' \
  .build/dev/seed/credentials.json
```

That command prints a password. Don't run it in a terminal that's being
recorded, don't paste the output into an issue, and don't commit either seed
file.

The seed protects itself on purpose:

- It only accepts loopback Proctor and Mailpit URLs.
- It refuses an Installation that's already set up, unless this seed set it up.
- It refuses to carry on from a partial, interrupted run rather than guess
  what's missing.
- If you run it again after it has finished, it reports the existing fixture
  and changes nothing.

If the seed stops after bootstrap or after any other change, run
`make dev-reset` and start again. The marker file it leaves behind explains
why.

## 7. Sign in through the browser

Open `http://localhost:8065/login` and sign in with the administrator username
and password from the local credentials file. After you sign in, you'll see
the screen that confirms your session. You've now exercised the compiled
webapp, password sign-in, the browser Session cookie, identity stored in
PostgreSQL, and the server's fallback route for webapp pages.

For work that needs a particular role, the same credentials file holds the
synthetic Exam Manager and Candidate accounts:

```sh
jq -r '.users | to_entries[] | "\(.key): \(.value.username)"' \
  .build/dev/seed/credentials.json
```

Open Mailpit at `http://127.0.0.1:18025` and check that the Exam Manager and
Candidate invitations arrived. Acceptance notices may follow as the delivery
Jobs finish. The messages contain only synthetic local data.

## 8. Check metrics, logs and traces

Print the observability addresses:

```sh
make metrics-urls
```

In Grafana, open the Proctor overview dashboard at
`http://127.0.0.1:13000/d/proctor-overview/proctor-overview`. Anonymous local
access is read-only. Within a few scrape intervals, the dashboard should show
one ready Proctor target. You can also ask Prometheus directly:

```sh
curl --fail --silent --get \
  --data-urlencode 'query=up{job="proctor",topology="single-node"}' \
  http://127.0.0.1:19090/api/v1/query | jq '.data.result'
```

The local server sends traces to the development collector, which passes them
on to Jaeger. Open `http://127.0.0.1:16686`, choose the `proctor` service, and
select **Find Traces** to see recent requests, Store operations and Jobs.

For checks and failure symptoms for each service, see
[local services](./local-services.mdx).

## 9. Use Vite for browser changes

The hosted build on port 8065 is the right place to get things working first.
When you change browser code, leave the server running and start Vite in
terminal 3:

```sh
make run-webapp
```

Open `http://127.0.0.1:5173`. Vite reloads modules as you edit them and passes
`/api` and WebSocket traffic to `http://127.0.0.1:8065`.

Some sign-in, callback and redirect flows are tied to the configured public
address. For those, restart terminal 1 with the Vite address:

```sh
make PROCTOR_SERVER_PUBLIC_URL=http://127.0.0.1:5173 run-server
```

Then use only that Vite URL in the browser. `localhost` and `127.0.0.1` count
as different origins, as do a different scheme or port. A mismatch can break a
browser flow that is otherwise correct.

## 10. Stop or reset

Stop the foreground server with <kbd>Control</kbd>+<kbd>C</kbd>. Its dependency
containers keep running, so the server starts quickly next time.

| Command | What it does | What happens to your data |
| --- | --- | --- |
| `make dev-down` | Stops the dependency and observability containers | Keeps the PostgreSQL, MinIO, Mailpit, Grafana and Loki volumes, the generated secrets and the seed files |
| `make run-server` | Starts the single-node stack again | Reuses the kept local state and generated secrets |
| `make dev-reset` | Removes the development containers, persistent volumes and protected seed files | Permanently deletes the local Installation and the synthetic credentials |

`make dev-reset` deletes data on purpose. Use it to test a first run, to
recover from an interrupted seed, or to reset the schema before a release.
Don't use it as your usual way to stop work.

## Check your setup

Before you move on, make sure that:

- `make dev-tools` succeeds
- both health endpoints return the JSON shown above
- `make dev-seed` reports a ready fixture
- the administrator can sign in through the browser
- Mailpit holds the synthetic invitation mail
- Prometheus reports the local Proctor target and Grafana opens the overview
- you know whether `dev-down` or `dev-reset` keeps the data you want to keep
