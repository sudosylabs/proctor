# Change persistence and migrations

PostgreSQL is the source of truth for Proctor's durable application state.
Persistence does more than run queries. It owns locking, decisions based on
database time, constraints, optimistic concurrency, and the named atomic
guarantees that application use cases rely on.

Redis, in-process caches, cluster messages and runtime projections can all be
thrown away and rebuilt. Never let one of them hold the only copy of state that
must survive a restart or a failover.

## Start from what the application needs

Before you write SQL, name the whole operation the application needs. A change
that spans several models should become a typed, named Store operation, such
as a bootstrap, a transfer, a command outcome or a lifecycle transition. It
should not be a generic transaction callback handed to application code.

The application owns the policy and what the transaction is meant to do. The
SQL adapter owns:

- row and advisory locks;
- evaluating time in PostgreSQL;
- uniqueness and referential constraints;
- revision and idempotency fences;
- the order of statements;
- commit or rollback;
- translating results into portable Store outcomes.

Raw SQL transactions, SQL handles and `WithTransaction(func(Store))` never
reach `server/app`.

## Make a Store change

1. Add or refine the smallest cohesive Store contract under `server/store`.
2. Add conformance cases that describe the results callers can observe and
   which writer wins a race.
3. Implement the contract in `server/store/sqlstore`, with explicit, bounded
   queries and constraints.
4. Update the memory or test adapters that consumers use. Don't weaken the
   contract to make a fake easier to write.
5. When transaction behavior affects a use case, add application integration
   tests that run through the real composition graph.
6. Record metrics through the existing bounded recorder or wrapper. Don't add
   query text, resource IDs or error text as labels.

Read paths must stay bounded. Where visibility is part of the query, they must
also take authorization into account. Don't load a whole collection and then
filter it in application memory.

## Say exactly what "not found" means

Store methods handle a missing record in three different ways:

| Operation | Meaning when no record exists |
| --- | --- |
| `Get` | Return `store.ErrNotFound` |
| `Find` | Return the explicit `found` value as false |
| `List` | Return an empty collection |

`(nil, nil)` never means "not found". Before a record leaves the adapter, it is
turned back into a domain type and checked. A stored record that fails the
check is an integrity failure, not a missing record.

Store contracts return domain values, or projections and aggregate results
that the Store defines explicitly. SQL rows, nullable driver types, query
builders, column names and transaction handles stay private to `sqlstore`.

## Name the atomic guarantee

A named Store operation is worth having when its name and parameters show the
whole race it has to settle. For example, a conditional replacement might
need to:

1. lock the current aggregate;
2. look up an existing idempotent outcome;
3. compare the expected revision;
4. write the new state;
5. write the required audit;
6. keep a bounded result for replay;
7. commit all of these together.

The application prepares the inputs that carry policy. The Store contract says
who wins when writers compete. The SQL implementation chooses the row locks,
advisory locks, constraints and statement order.

Don't split a guarantee into several public Store calls just to make each call
smaller. Another node can act between those calls.

## Use constraints and locks together

Choose the narrowest PostgreSQL mechanism that protects the rule:

- A unique, foreign-key, check or exclusion constraint, for facts that must
  hold no matter who the caller is.
- `SELECT … FOR UPDATE`, when one current row puts a transition in order.
- A transaction-scoped advisory lock, for a bounded namespace that doesn't
  have a natural row yet.
- `SKIP LOCKED`, for claiming work or for bounded maintenance where several
  nodes can safely share out the eligible rows.

Checks in the application can give better error messages, but they never
replace the constraint or lock that closes the race. Translate expected
constraint outcomes into typed Store errors. Keep unexpected driver detail only
in the wrapped internal cause.

When a transaction touches several aggregates, lock them in one agreed order.
Before you add another order, review the existing named operations that touch
the same rows.

## Keep revisions, time and idempotency apart

Each of these answers a different question:

| Mechanism | Question |
| --- | --- |
| Explicit revision | Is this still the exact state the caller inspected? |
| PostgreSQL time | Is a deadline, lease, or effective period current at commit? |
| Idempotency key | Has this authenticated semantic command already completed? |
| Unique constraint | Can two durable records with this identity coexist? |

Don't use timestamps as optimistic revisions. Don't treat an idempotency key as
permission to skip the current authorization check. An exact replay returns
its saved result only after the current use case has repeated the checks its
contract requires.

Retry only operations on an explicit list of safe ones. A temporary database
failure can happen after a commit whose outcome you can't know. So an
operation isn't safe to retry just because its SQL looks simple.

The layers stack in a fixed order. Retry sits closest to SQL. Timing wraps the
whole path taken on a cache miss. The cache sits outside both, so a cache hit
doesn't look as if database work happened.

## Keep Store conformance up to date

Each Store contract has a reusable conformance suite. It is the runnable
description of the contract's portable behavior. Add cases for:

- invalid input, and exactly how a missing record is reported;
- successful outcomes and outcomes that change nothing;
- stale revisions and competing writers;
- idempotent replay, conflict, and in-progress states;
- failure to write required audit;
- expiry or lease fences based on database time;
- unknown outcomes and translation of adapter errors.

The PostgreSQL adapter must pass the same suite as any test or memory adapter.
When a guarantee depends on real locking or constraints, which a sequential
fake can't show, add a race test that runs against PostgreSQL.

## How migrations work before the first release

For now, the repository has one schema baseline that you rewrite in place:

```text
server/migrations/postgres/000001_baseline.up.sql
server/migrations/postgres/000001_baseline.down.sql
```

Until the first stable release, Proctor doesn't upgrade development schemas
that are incompatible. Schema work changes that baseline and its round-trip
tests. Developers with affected databases must throw them away and create them
again. Don't add a chain of historical development migrations that looks like
a supported upgrade path.

Reset the local environment the repository manages with:

```sh
make dev-reset
```

This deletes your local developer containers and volumes. Save anything you
need before you run it.

## Run focused PostgreSQL tests

Start with the affected package or conformance test. Then run the repository
target, which starts PostgreSQL for the tests and removes it afterwards:

```sh
make -C server integration-postgres
```

The target covers Store conformance, migrations, application transactions,
identity and authorization races, Jobs, files, mail, examinations and other
behavior that relies on PostgreSQL. When you run an integration suite and
PostgreSQL isn't available, the suite fails. It doesn't skip.

You still need the hermetic server gate:

```sh
make -C server check
```

## Caches are adapters

The Store read-through cache is a bounded local optimization. The application
cache can use memory or Redis. Neither one changes PostgreSQL's role as the
source of truth.

Commit durable state first, then invalidate or publish. If an invalidation is
missed, the system must recover through a bounded TTL, current reads,
revalidation or client resynchronization. Don't treat a cache entry as proof of
authorization. Don't treat cluster delivery as proof that another node has
seen a commit.

## Review persistence safety

- Are lists, scans, retries and saved fields bounded?
- Does each named operation show the whole atomic guarantee?
- Where races matter, are current authority and database-time conditions
  checked inside the transaction?
- Do constraints protect the rules even when two nodes act at the same time?
- Are retries safe when the commit outcome is unknown?
- Do logs, metrics, errors and audit data leave out SQL text, secrets,
  answers, content and values nobody controls?
- Does the change pass the migration round trip and the affected conformance
  suite?
