# Repository boundaries

Proctor is a monorepo, but it is not one Go module. The root workspace makes
local development easier. Each Go module still keeps its own dependencies,
compatibility promises, tests and license.

## The four Go modules

| Module | Owns | Must not own |
| --- | --- | --- |
| `packages/cache` | Portable cache behavior, codecs, TTLs, conditional writes, counters, memory and Redis adapters | Proctor cache eligibility, authorization, durable state, server types |
| `packages/mail` | Transport-neutral messages, validation, MIME, SMTP, delivery outcome classification | Proctor templates, recipients, retry, queueing, institution policy |
| `packages/vfs` | Portable streaming file operations and local, memory, and S3-compatible backends | Proctor metadata, authorization, retention, Exam or User meaning |
| `server` | Domain, application policy, persistence contracts and adapters, transports, runtime composition | Browser presentation or portable behavior without a Proctor-independent contract |

The root `go.work` file joins these modules together for work inside the
repository. Production builds don't depend on it, and it can't hide a module
that fails when built on its own.

## Other parts of the product

| Directory | What it holds |
| --- | --- |
| `webapp` | The React application the server hosts, and its browser contracts |
| `docs/public` and `docs/api` | Task-based public guides and hand-written API guides |
| `docs/site` | Docusaurus rendering, generated adapters, search and presentation |
| `build` and the root Makefile | Product lifecycle, local infrastructure, checks, packaging and release inputs |
| `deploy` | Tracked deployment support files and examples |

These parts can ship with the server, but they never become extra Go modules
or another place where the server is assembled.

## Decide where a change belongs

Ask these questions in order:

1. **Does the behavior make sense without Proctor?** A portable guarantee about
   caching, mail or files may belong in a reusable module. Rules about
   Institutions, access, examinations, audit and delivery stay in the server.
2. **Who uses the behavior?** Put a narrow interface next to the code that uses
   it. Don't design an abstraction around a provider and make every caller
   depend on it.
3. **Is the responsibility stable?** File size, symmetry or a backend you might
   add one day are not reasons for a new package.
4. **Where is the real infrastructure chosen?** Only the `server.New`
   composition path at the module root picks production adapters.
5. **Which contract changes?** Update the code comment, public contract, test
   or guide in the same slice.

## Which way server dependencies point

Inside `server`, each layer has one job:

- Domain models own the rules that a single model can check on its own.
- Application services own use-case policy, current authorization, what a
  transaction should do, audit, and when side effects happen.
- Persistence implements the bounded Store contracts.
- HTTP and WebSocket are outer adapters. They translate requests into
  application calls and results back into responses.

Infrastructure depends inward:

```text
HTTP / WebSocket / Jobs
          ↓
   application use cases
          ↓
domain models + Store contracts
          ↑
SQL / Redis / VFS / SMTP / cluster adapters
```

The arrows show which code depends on which, and where policy lives. They
don't show the order in which a request runs. Application services never get a
platform service locator or a root Store accessor. Transport code never calls
SQL directly.

## Where things live in the server

| Location | Use it for |
| --- | --- |
| `server/model` | Cohesive domain state, local validation, and transitions |
| `server/app` | Use cases, authorization timing, audit intent, coordination, and post-commit effects |
| `server/store` | Bounded persistence and named aggregate contracts |
| `server/store/sqlstore` | PostgreSQL implementation, locking, constraints, and migration integration |
| `server/httpapi` | Route catalog, DTOs, credential requirements, Problem Details, and HTTP mapping |
| `server/websocket` | Authenticated connection transport and protocol behavior |
| `server/platform` | Infrastructure lifecycle and health, never application service location |
| module-root `server` | Concrete composition, readiness, serving, and reverse shutdown |

Name each package after one responsibility. Don't use `util`, `common`,
`shared`, `base`, `core`, `services` or `repositories` as a place to put
everything else.

## Check the boundaries

Run the import policy check whenever you change a server package, or the
documentation that describes its boundaries:

```sh
make -C server architecture
```

Before you change a reusable module's contract, or how the server uses it, run
every Go module without the workspace:

```sh
make independent-modules
```

The first command rejects production imports that aren't allowed. The second
runs test, race, vet and build checks with `GOWORK=off` across all four
modules.
