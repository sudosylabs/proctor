# Develop the Proctor server

The Proctor server is organized by who owns what, not by framework layers. A
change starts from a behavior that a user or operator can see. It crosses only
the boundaries that behavior needs, and it ends with tests at every boundary it
changed. The goal is not to add a model, a service, a Store and a route because
the pattern suggests it. The goal is to make one behavior work correctly from
end to end.

This manual is for contributors who already write Go but don't yet know where
Proctor keeps its rules, its durable guarantees, its transport rules, or its
runtime ownership. For your first server change, read it in order. During
review, come back to the chapter you need.

## Where each decision goes

Ask which code must stay correct if the transport, the database, the cache or
the node running the application changes.

| Decision | Owner |
| --- | --- |
| Whether one value or state transition is locally valid | `server/model` |
| Whether the current actor may perform the use case, and in what order | `server/app` or one justified application child |
| What must commit atomically and which races have one winner | A named contract under `server/store` |
| How PostgreSQL locks, constrains, retries, and commits it | `server/store/sqlstore` |
| How an HTTP request becomes a typed command and a safe response | `server/httpapi` |
| What the public wire contract promises | Human-owned YAML under `server/openapi` |
| How a WebSocket connection sequences, replays, and sheds load | `server/websocket` |
| How portable cache, mail, or VFS mechanics work | The corresponding independent module under `packages` |
| Which concrete adapters run and who closes them | Module-root `server.New` and `platform.Service` |

If two rows seem to own the same decision, the design isn't finished yet. For
example, the transport owns strict JSON decoding, and the domain decides
whether the decoded value is valid. PostgreSQL may enforce the same rule again
to handle concurrency, but that doesn't make it the author of the business
rule.

## Work on one vertical slice at a time

Before you edit anything, write a short boundary map in your notes:

```text
Behavior:        what changes for a User or operator?
Domain term:     which canonical concept and transition are involved?
Principal:       who or what invokes the behavior?
Action/resource: what current authority is required?
Durable fact:    what must survive process loss?
Public shape:    which route, DTO, errors, and examples change?
Effects:         what happens only after commit?
Evidence:        which focused, conformance, integration, and broad tests prove it?
```

Then read the current code and tests. Don't create an interface until you know
who will use it and everything they need from it. Don't create a child package
until the responsibility is stable enough to outlive its current callers. Don't
add a route until the application behavior works without HTTP.

## Keep this order

For a change that depends on who is acting, the usual order is:

1. Build a bounded, immutable invocation from what the transport proved about
   the caller.
2. Resolve the canonical resource and the caller's current authority.
3. Authorize just before any expensive work or change.
4. Prepare safe audit details and, when required, the command's idempotency.
5. Commit the durable state, required audit, retained outcome, Job or mail
   intent through one named Store operation.
6. Only after the commit, publish cache, cluster, WebSocket or other effects
   that can be rebuilt.
7. Turn the result into a public response that contains only allowed fields.

Not every read or change uses every step. When you skip one, it must be because
the owning contract says so, not because it is easier in a handler.

## Where the details live

This manual explains how to work. It deliberately doesn't repeat lists that
change often. While you work, use:

- the [server module guide](https://github.com/sudosylabs/Proctor/blob/main/server/README.md),
  for the package map, one traced request, and the commands a change needs;
- the [routing kernel](https://github.com/sudosylabs/Proctor/blob/main/server/httpapi/route/doc.go),
  for how routes are declared and how errors map to responses;
- the [OpenAPI authoring guide](https://github.com/sudosylabs/Proctor/blob/main/server/openapi/README.md),
  for the workflow that writes the public contract by hand first;
- the [cluster guarantees](https://github.com/sudosylabs/Proctor/blob/main/server/cluster/GUARANTEES.md),
  for exact delivery and recovery behavior;
- code, tests, configuration examples and command help, for implementation
  details you can find by reading them.

## Your first change

For a first contribution, read the [User Settings vertical slice](./server/user-settings-slice.mdx)
before you change another feature. It shows what each file adds, without
handing you a package template to copy. Your feature may need fewer
boundaries, or different ones.

Finish with the [server review checklists](./server/review-checklists.mdx) and
the repository [testing ladder](./testing.mdx).
