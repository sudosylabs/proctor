# Server architecture and composition

Production code builds the server in exactly one place: the `server.New`
function at the module root. It picks the concrete infrastructure, hands
ownership of that infrastructure to the platform service, builds the
application and the transports, and returns a server that does nothing yet.
`Server.Run` is what starts it. Because building and starting are separate,
tests can build the real graph without opening listeners or starting
background work.

## Read dependencies from the outside in

Policy normally flows in this direction:

```text
HTTP · WebSocket · Jobs
          ↓
 application use cases
          ↓
 domain + Store contracts
          ↑
 SQL · VFS · cache · SMTP · cluster adapters
```

The arrows show which package imports which, and where policy lives. They do
not show the order in which a request travels. Each layer has one job:

- An outer adapter translates.
- An application use case decides.
- A domain model keeps itself locally valid.
- A Store contract names a durable guarantee.
- A concrete adapter implements that guarantee.

The root package may import whatever it needs to build things, because it
assembles the graph. That exception does not make it a place for business
rules.

## The main landmarks

Use this table to find your way around. It is not a full list of packages.

| Location | What it owns | Common mistake |
| --- | --- | --- |
| `server/model` | Cohesive domain values, records, constructors and local transitions | Adding transport or SQL fields to a domain type |
| `server/app` | Use-case policy, current authorization, audit intent, coordination and when effects run | Holding on to the root Store or configuration as a service locator |
| `server/app/job` | The generic mechanics of running durable Jobs, and the operator Job service | Importing the parent application or a concrete handler catalog |
| `server/app/realtime` | Transport-neutral events and how they propagate to peers | Owning WebSocket connection state or retrying a failed transient publish |
| `server/store` | Bounded Store contracts and named aggregate operations | Exposing raw transaction callbacks or SQL rows |
| `server/store/sqlstore` | The PostgreSQL implementation, locks, constraints and migrations | Deciding application policy again inside SQL code |
| `server/httpapi` | HTTP resources: the routes, DTOs, credential requirements and error tables of each API area | Reaching straight into the Store or SQL |
| `server/httpapi/route` | The routing kernel: endpoint declarations, the sealed route catalog, credential checks and Problem Details | Knowing about an API area or importing a resource |
| `server/websocket` | The connection protocol, sequencing, replay, liveness and backpressure | Treating a socket as durable authority |
| `server/platform` | Infrastructure lifecycle and health | Passing it into the application as a locator |
| module-root `server` | Choosing adapters, wiring, readiness, serving and shutdown | Adding a second constructor path in a command or test |
| `server/operator` | Offline host commands that read or migrate an installation without starting it | Importing the application or the module root to reach a use case |

A child package exists only when a responsibility has enough structure of its
own and can still point inward without importing its parent. Don't copy the
existing child layout just to make the tree look even.

## Follow one request

The quickest way to learn the server is to follow one request from the route
down to SQL. Files are named after their entity in every layer, so the same
word leads you through each step.

### Create a Class

`POST /api/v1/programme-levels/{programme_level_id}/classes`

1. **Route.** `httpapi/class.go` declares the route in `classResource` as a
   `route.Endpoint` literal. Its `Auth: route.AuthPrincipalRequired` field
   says the route needs a signed-in principal, and its `Errors` field lists
   the errors it may return. `classHandlers.create` decodes the body into
   `createClassRequest` and builds an `academic.CreateClassCommand`.
2. **Use case.** `academic.Service.CreateClass` in `app/academic/class.go`
   works through these steps:
   1. It checks the Programme Level ID.
   2. It authorizes `model.ActionClassManage` against that Programme Level.
   3. It builds a `model.Class` and calls `Validate`.
   4. It records the change through `access.RunAudited`
      (`app/access/mutation_attempt.go`).
3. **Store contract.** `store.ClassStore.Create`, declared in
   `store/academic.go`, takes a `store.ClassCreation` that carries both the
   Class and its audit event, so the two commit together.
4. **SQL.** `SQLClassStore.Create` in `store/sqlstore/class_store.go` inserts
   the row and completes the audit event in one transaction. On the way the
   call passes through the generated timing and retry layers
   (`store/timerlayer`, `store/retrylayer`), which add no behavior.
5. **Errors.** The service's `apperror.StoreTable` turns a typed Store error
   into an application error. `httpapi/route` then turns that into a Problem
   Details response, using the status that `httpapi/route/error_catalog.yaml`
   gives its code.

### Submit an Attempt

`POST /api/v1/exam-attempts/{exam_attempt_id}/submissions`

1. **Route.** `httpapi/exam_attempt.go` declares the route as a
   `route.Endpoint` literal with `Auth: route.AuthSessionRequired` and
   `Idempotency: route.IdempotencyRequired`, so it needs a Session and an
   idempotency key. The handler is `examAttemptHandlers.submit` in
   `httpapi/exam_attempt_submission.go`.
2. **Use case.** `SubmitExamAttempt` in `app/exam/attempt/submission.go`
   works through these steps:
   1. It resolves the candidate's current Workspace.
   2. It prepares idempotency.
   3. It checks the seal target.
   4. It begins the audit record.
   5. It prepares the submission receipt mail.
3. **Store contract.** `store.ExamSubmissionStore.Seal` freezes the
   Submission. In the same transaction it writes the prepared mail and the Job
   that delivers it (`store/sqlstore/exam_submission_store.go`).
4. **After commit.** The service calls `publishAttemptSubmitted`
   (`app/exam/attempt/effects.go`). That builds the realtime events, publishes
   them through the service's `realtime.Publisher`, and then unbinds the
   Attempt connection. These effects run only once the Submission is durable,
   and if they fail they never undo it.
5. **Background.** When a Sitting closes, the `exam_sitting.sealing` Job in
   `app/jobs/exam_sitting_sealing.go` seals the remaining Attempts through
   `attempt.Service.SealForSittingClose`.

## Follow `server.New`

Read [`server/server.go`](https://github.com/sudosylabs/Proctor/blob/main/server/server.go)
and the construction files beside it as one path. These are the steps where
ownership changes hands:

1. Load and check the configuration the operator must provide.
2. Build PostgreSQL and the chosen cache, mail, VFS, cluster, logging, metrics
   and provider adapters.
3. Give the shared infrastructure to `platform.Service`. From then on it owns
   that infrastructure's health, reconfiguration and disposal.
4. Build stateless or application-facing views, such as File Content, over
   borrowed capabilities. Callers get those views, not the platform.
5. Turn configuration into small immutable policies or narrow dynamic
   providers.
6. Call `app.New`, the only application constructor.
7. Build the WebSocket hub from the services it needs. Then call
   `httpapi.New(application, settings)`, which builds each HTTP resource from
   the application service that owns its use cases.
8. Attach local sinks and cluster fan-out once, then throw away the temporary
   wiring views.

If a later step fails, construction must unwind every owner it has already
acquired. A server that has just been built has no listener, worker or
maintenance goroutine running.

The module-root package is about building and running one node. Start with
`server.go`, `infrastructure.go`, `composition.go`,
`application_dependencies.go` and `shutdown.go`. Most other files there hold
one adapter each and are named for the two sides they join, such as
`authentication_cache.go` or `mail_sender.go`. A wrapper that only measures a
port, such as `metrics.WrapCache`, lives in `server/metrics` instead.

## Follow `app.New`

[`app.New`](https://github.com/sudosylabs/Proctor/blob/main/server/app/new.go)
reads from top to bottom. It checks its dependencies, builds the shared
mechanics and Access Control, and builds each area in dependency order. Then
it builds the optional Job runtime and the services that span areas, and
returns the `app.App` value. Helpers beside it build the larger areas, such as
`newExamServices` in `new_exam.go` and `newJobRuntime` in `new_jobs.go`. `App`
is a collection of use cases. It is not a way to reach persistence.

Each domain area is one package (`app/academic`, `app/user`, `app/identity`,
`app/exam`, ...). `App` gives every service its own named field and embeds
nothing, so a call reads `app.Academic.CreateClass(...)` or
`app.Search.Search(...)`.

When you add a dependency:

- Hold the concrete type, or the `store` contract you call. Add an interface
  only when something real stands in behind it.
- In tests, fake a Store contract by embedding it and overriding the methods
  the test uses.
- Check required dependencies in the constructor.
- Keep constructors inert.
- Update the architecture policy when you mean to add a new production import.

If you find yourself reaching through `App`, `platform.Service`,
`config.Config` or a root Store, the consumer's boundary is usually still too
broad.

## Startup and readiness

`Server.Run` moves through its runtime stages in dependency order. Broadly, it:

1. starts the shared platform dependencies
2. commits the PostgreSQL serving-node lease
3. reconciles protected roles and any pending offline recovery
4. starts durable Jobs and the periodic work that must run
5. starts WebSocket, metrics, listener ownership and HTTP serving
6. reports ready only once the node can safely take traffic

Liveness, readiness and detailed diagnostics answer different questions:

- Liveness means the process can respond.
- Readiness means it is safe to send traffic to the node.
- Detailed dependency state is for operators only. Never slip it into a
  public health response.

A host-process readiness observer, such as the systemd notification adapter,
runs only after the server is ready internally. Its shutdown observer runs
once, when a running node starts to stop. These observers report outward. They
do not own the server's lifecycle, and they cannot make a ready server fail or
hold up shutdown. The host process, not the server, feeds a supervisor
watchdog from `Server.Ready`.

## Reverse shutdown

A node can stop because of cancellation, `Close`, a startup failure, a serving
failure or a lost dependency. Every one of these goes through the same ordered
shutdown sequence. It first makes the node unready, then drains each consumer
before the things it depends on:

```text
public readiness off
        ↓
listener → HTTP drain → Jobs → WebSocket → HTTP transport → serving lease → metrics → tracing → Platform
```

The whole sequence shares one budget, `Server.ShutdownTimeout`, counted from
the moment shutdown starts. Several steps wait: the HTTP drain and serving
exit, the Job and WebSocket drains, the metrics listener, the tracing flush,
and Platform leaving the cluster. Each takes its deadline from what is left of
that budget, never from a new timer. Metrics and tracing may only shorten it
with their own cap. So a slow step leaves less time for the steps after it
instead of making shutdown longer. The run reports why it stopped and whether
HTTP must drain or close at once. The sequence decides nothing else.

Only stages that started successfully need to drain actively, but every owner
that was built must be disposed exactly once. Close before start, a partial
startup failure, concurrent close and repeated close are normal test cases,
not edge cases to leave undefined. `Run` and every `Close` return the same
shutdown result.

A failure to renew the serving lease takes a stricter path. The node becomes
unready and force-stops HTTP before the lease can expire. Don't withdraw a
failed lease as though this were a graceful shutdown. Letting the lease expire
in PostgreSQL is what stops offline recovery from starting too early.

## Add or move a package

Before you pull out a package, answer all of these:

1. What stable responsibility does it own?
2. Which production package uses it?
3. Which dependencies must it import, and which must it never import?
4. Can it arrive with working behavior rather than empty scaffolding?
5. Would deleting it make its responsibility less clear?

Add a package comment that says what it owns, what it excludes and which
dependencies it may use. Then run:

```sh
make -C server architecture
```

The architecture gate is an import policy that runs as code. There is no
waiver or debt list. Even a new edge you add on purpose must keep the graph
pointing inward.

## Composition checklist

- Is `server.New` still the only way production builds the server?
- Are constructors inert, and do they fail fast?
- Did each acquired owner change hands exactly once, and unwind on failure?
- Does `platform.Service` stay out of application policy?
- Did configuration become a small policy or provider before it reached `app`?
- Does shutdown undo the stages that started, in reverse, within its deadlines?
- Can `testlib` exercise the real graph without rebuilding composition?
