# Attempt continuity

Attempt continuity is durable domain state. It is not the same thing as a
WebSocket staying alive. A ping only shows that bytes crossed a transport.
Only an authenticated, monotonic renewal can extend a Participation lease, and
only PostgreSQL's clock can decide that a lease has expired.

## Start in the owning package

`server/app/exam/attempt` owns all of this:

- admission
- Participation and Connection fencing
- renewal and expiry enforcement
- Focus Loss
- correction acknowledgement
- protected Workspace access
- Submission sealing
- manager inspection

`app.App` names the Attempt service in its `Attempts` field, and the service
publishes its own effects after commit.
`server/app/jobs/exam_attempt_expiry.go` only schedules bounded scans. It does
not decide what expiry means.

Three roles stay separate:

- The domain model owns valid states and transitions.
- The bounded Store contract owns lock order, the database-time comparison,
  idempotent outcomes and invariants across rows, all in one atomic
  operation.
- The transport owns socket envelopes and teardown.

## Model the current generation exactly

An unresolved Attempt has at most one current Participation generation and
one current Connection. The Participation binds the exact Desktop Session, the
hashed continuity credential, the generation, the renewal sequence and the
lease. Protected HTTP access must also name the current Connection and pass
DPoP authentication.

Never authorize from an Attempt ID and a valid Session alone. Never let a new
generation bring an old continuity credential or sequence back to life.
Connection IDs, Participation IDs, generation numbers and credential hashes
are all selectors, and each means something different. Don't merge them into
one token field.

## Renew monotonically

The renewal Store operation locks the row and compares the current generation,
bound Session, credential hash, Connection, lease and sequence. An exact
duplicate gets back the result that was kept the first time. A stale or
changed sequence cannot extend the lease. The new expiry comes from database
time, not from the client's clock or the application node's clock.

The first runtime renews every 5 seconds, grants a 20-second lease and runs a
bounded expiry scan every 2 seconds. These values belong to the server. Don't
treat them as permanent client constants. The client takes its schedule from
the admission result.

## Expire once and fence forever

Once `expires_at <= database_now`, the generation is dead. One named atomic
operation then:

1. closes the Connection
2. ends Participation
3. records neutral Connection Loss evidence
4. opens one Suspension episode and one Flag
5. moves the Attempt state on

A retry gets back the kept terminal outcome. It does not open a second
episode.

Effects follow the commit. The server closes the local transport, publishes a
Suspension that is safe for the candidate to see, notifies manager
subscriptions and fans out to peers. If any of those effects fail, the durable
state does not roll back. A client that misses an event fetches the
authoritative state again.

One failed HTTP request, one socket close or one missed ping is not Connection
Loss. Don't add an eager application timer that races PostgreSQL and turns
brief network noise into an accusation.

## Recover without overwriting authority

Before expiry, a reconnect may replace the Connection and keep the same
generation, if current policy allows it. The client then fetches its
presentation again and replays the bounded Workspace journal from its last
acknowledged cursor. If the journal cannot cover the gap, the client replaces
its local copy from a complete manifest.

After expiry, a Kick or a Suspension, only a manager re-allow can close that
exact episode, and the re-allow is fenced by revision. A fresh admission then
creates the next generation. The Attempt, Workspace, frozen configuration,
Flags, evidence and the record of earlier Suspensions all carry over.

## Keep corrections scoped to the Attempt

When a live correction needs acknowledging, that requirement belongs to the
Attempt, not to a Participation. So it survives reconnect and re-allow.

While an acknowledgement is pending, the candidate cannot use governed
navigation, change the Workspace or submit voluntarily. Protected reads,
renewal, integrity delivery and the acknowledgement itself still work.

Acknowledgements go oldest first. Each is fenced by revision, idempotent, and
bound to the current Participation, generation, Session, credential and
Connection. Never clear the requirement from a handler that only knows about
one socket.

## Focused tests

From `server/`, run:

```sh
go test ./app/exam/attempt -run 'Test.*Participation|Test.*Expiry|Test.*Reconnect|Test.*Correction'
go test ./app -run 'TestParticipationExpiry|TestExamAttemptExpiry'
go test ./store/sqlstore -run 'Test.*Participation|Test.*Attempt.*Race'
go test -race ./app/exam/attempt ./app
make architecture
```

Cover these cases:

- duplicate and stale renewal
- expiry at the exact boundary
- two scanners racing
- an effect failing after commit
- reconnect before and after expiry
- access from an old generation
- two managers re-allowing
- a correction surviving across generations
- recovery from a journal gap
