# Authorization, concealment and audit

Three questions come up on every protected operation, and Proctor keeps them
apart:

- **Authentication** asks which principal presented acceptable proof.
- **Authorization** asks whether that principal may perform this action on
  this exact resource right now.
- **Audit** records the decision or change that matters for security.

Keeping them separate means a valid credential, an old membership or a stale
snapshot of someone's roles can never quietly grant authority.

## Start with principal, action and resource

The transport builds an immutable principal. It carries bounded context about
the identity, credential, provider, assurance, client and authentication
time. It carries no permissions and no snapshot of roles.

Application authorization combines four things:

- that principal
- one stable domain action, such as `class.members.view`
- the canonical resource being acted on
- the current roles, bindings, relationships, state and credential ceilings,
  read from authoritative storage

Action names describe what the domain lets you do. They are not HTTP verbs or
route names. Role Bindings add up, and anything not granted is denied. A
binding's Institution, Academic Unit or Class scope is resolved against the
actual resource. It is never guessed from a path parameter the caller sent.

## Put each check where it belongs

| Question | Who answers it |
| --- | --- |
| Is a credential present and valid for this route? | The HTTP or WebSocket transport |
| Does the route need an interactive, strong or recent Session? | The transport declaration and authentication |
| Does this action make sense for this kind of resource? | The Access Control application boundary |
| What is the resource's current authorization scope? | The application scope resolver, using authoritative Store facts |
| May this principal perform the action now? | The use case that owns the action |
| Should a denial be forbidden or concealed? | The owning use case, and the transport's mapping contract |
| Must the decision or change be durably audited? | The application and a named Store operation |

Transport middleware must not check permissions up front and hand the
application a reusable "authorized" receipt. State can change between the
middleware and the mutation. And authorization for lists and searches often
belongs inside a bounded query anyway.

For operations that depend on exactly who the actor is, resolve current
authority immediately before any expensive work or mutation. For collections,
first work out a bounded visibility scope, then let persistence apply it in
the query. Don't fetch everything and filter in memory.

## Credential assurance is a separate axis

A route may require one of these:

- any authenticated principal
- an interactive Session rather than a Personal Access Token
- strong authentication
- recent reauthentication
- both strong and recent authentication
- a refresh credential or protected Attempt credential issued for that
  purpose

These are ceilings on the credential, not permissions. A strong, recent
Session can still lack the action on the resource. And no role grant can make
a Personal Access Token pass a route reserved for interactive Sessions.

When you add a sensitive operation, test both axes:

| Credential and assurance | Current authority | Expected outcome |
| --- | --- | --- |
| Not enough | Any | Authentication or assurance failure |
| Enough | Denied | Forbidden or concealed response |
| Enough | Allowed | The use case may continue |
| Enough at sign-in, revoked since | Denied | The current decision wins |

## Choose concealment on purpose

A forbidden response confirms that the target exists. For some private
resources, that fact is itself sensitive: another User's protected data, or an
Exam Sitting, Submission, Attempt or file the caller may not see. So the use
case that owns the resource decides whether a target that is denied, missing,
mismatched, inactive or out of scope must all get the same not-found
response.

Concealment only works if it is consistent:

- Resolve only the state you need to make the safe decision.
- Map every concealed case to the same public code and shape.
- Leave out private IDs, state, scope and mismatch detail.
- Keep internal causes only for bounded diagnostics outside the response.
- Test horizontal access with two synthetic resources in different scopes.

Don't return forbidden on one failure path and not found on another if the
difference reveals the fact you are protecting.

## Build stable application errors

Expected failures use `*app.Error`, which holds:

- one stable dotted code
- a small allowlist of safe fields
- optionally, a wrapped internal cause

An application error has no status code, localization, request ID, SQL
message, provider payload or stack trace. HTTP and WebSocket each own their
own complete mapping to their protocol.

```text
driver or adapter failure
          ↓
typed Store or port failure
          ↓
application interpretation
          ↓
stable app.Error when public and expected
          ↓
Problem Details or WebSocket error envelope
```

Any unknown failure becomes a generic internal error with a correlation ID.
The transport resolves the localized `title` and `detail` at the very edge.
The type, status, code, safe fields and request correlation stay the same in
every locale.

### Public error checklist

- Does the code help a client without exposing private state?
- Is every field bounded, typed and explicitly safe?
- Is it allowlisted by the resource and declared in OpenAPI?
- Does every declared code map to a response?
- Do unknown errors fail closed?
- Are localized messages only presentation, never durable machine state?

## Make audit a durable contract

Operational logs and audit events do different jobs. Logs explain what the
runtime did, and they may be dropped or rotated. Audit records in PostgreSQL
are the authoritative security evidence.

A safe audit event may contain:

- the actor or system principal
- the stable action
- the canonical resource
- the resolved academic scope
- the outcome
- request and node correlation
- the time
- approved, bounded views of the state before and after

It never contains credentials, secrets, Exam answers, mail or file content, a
manager's private rationale, provider assertions or unbounded user input.

If an authorization decision needs audit and the durable event cannot be
written, the decision fails closed. A critical mutation may use an
attempt-to-terminal protocol:

1. Save the audit attempt.
2. Perform the named mutation.
3. On success, commit the terminal audit together with the durable outcome.
4. If no state committed, complete the failure audit separately.

If completing the terminal audit fails after state has committed, return an
internal failure and keep the incomplete attempt so an operator can
reconcile it. Don't claim the mutation rolled back when it did not.

Sometimes the success audit belongs in the same transaction as the mutation.
In that case the application prepares a safe audit intent, and the named Store
operation commits the state, the audit and the kept idempotent outcome
together.

## Keep observability safe

Application services that handle requests usually return errors rather than
log them. The outer operational boundary logs an unexpected failure once, with
bounded scalar fields such as the component, request ID, node ID and approved
entity IDs.

Never put arbitrary maps or whole structs in logs or metrics. Metrics use a
closed set of low-cardinality labels: route templates, operation names, result
classes and configured backend types. They never use User IDs, paths,
addresses, cache keys, recipient data or error strings.

## Authorization and audit test matrix

For a change that depends on who the actor is, cover:

- the allowed action at the exact scope and at inherited scopes
- action and resource pairs that don't fit together
- resources that are denied, missing, archived or out of scope
- stale membership, Role Binding, account and credential state
- the action and scope ceilings of a Personal Access Token
- required strong or recent assurance
- matching concealed responses, and redacted response fields
- audit on success, on denial, and when the audit write fails
- idempotent replay that still authorizes again
- invalidation failing after commit
- correct behavior across nodes without an authorization cache

Then run the owning package's tests, the HTTP and OpenAPI agreement checks
where they apply, and:

```sh
make -C server architecture
make -C server check
```
