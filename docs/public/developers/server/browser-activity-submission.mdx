# Browser Activity and Submission

Browser Activity is a narrow stream of integrity evidence. It is not a way to
watch a candidate's browsing. Submission is a final snapshot of the Workspace
state the server has acknowledged. It is not a copy of whatever happens to be
in a local editor buffer.

## Collect only what the frozen policy allows

An author writes the Browser Policy as a typed field on the Draft, and it is
frozen into an immutable Exam Revision. It governs one Desktop Browser surface
through reviewed rules for HTTPS origin, host, path, redirects and start
pages. Candidate admission exposes the exact frozen policy. A Desktop client
must not widen it locally.

Ownership is split three ways:

- `server/model/browser_activity.go` owns the closed shapes for events,
  reasons and minimized locations.
- `server/app/exam/attempt/browser_activity.go` owns access to the current
  Attempt and how collection behaves.
- SQL persistence owns source sequencing, reorder limits, exact replay and
  the gaps it keeps.

Don't add a generic telemetry envelope. A new event, or a new meaning for a
field, needs a privacy review, strict model validation, wire versioning, a
retention decision and updated terminal accounting.

## Minimize before anything is stored

Proctor keeps only three kinds of event:

- a top-level browser opening or closing
- an allowed navigation or redirect
- a blocked navigation

It leaves out the query, fragment, credentials in the URL, page content,
title, referrer, headers, cookies, DOM, downloaded bodies, local paths and
scheme payloads. Other integrity evidence also leaves out screenshots, webcam,
clipboard, source code and arbitrary payloads.

Minimizing happens before anything is stored durably, and before anything
reaches logs, metrics, audit or realtime publication. What a manager receives
is a bounded view that leaves out Session, Registration, Connection,
credentials and private Review state.

## Keep sources and sequences exact

Each Participation allows:

| Source kind | Limit |
| --- | --- |
| Initial source | 1 |
| Policy-correction starts | Up to 32 |
| Runtime resets | Up to 16 |
| Source identities in total | At most 49 |

A reset names the source it replaces and one reason from a closed list.
Earlier source boundaries never change.

A batch holds 1 to 64 events and at most 256 KiB. Persistence accepts an exact
replay. It rejects a duplicate whose content changed, and it rejects a reorder
distance above 4,096. It returns the highest contiguous sequence, the highest
sequence seen, and at most 32 missing ranges.

A gap is evidence that something is uncertain. Never invent a navigation event
to fill it. Delivery may carry on while the Sitting is paused or a correction
is waiting for acknowledgement, because catching up on evidence does not give
the candidate any way to interact.

## Keep Review evidence independent

A Browser Flag can come only from a validated blocked navigation that is
attributed to a frozen rule which selects integrity evidence. Each group of
evidence is scoped to one Participation, policy Revision and rule.

| Limit | Value |
| --- | --- |
| Detail copies per group | 100 |
| Groups per Attempt | 256 |
| Copies per Attempt | 10,000 |
| Copied evidence per Attempt | 8 MiB |

Once a limit is reached, further validated events only update bounded
overflow counts. Replaying a receipt never creates another copy.

Seeing ordinary history needs both the exact Exam Manager relationship and
`exam.attempt.browser_activity.view`. A scoped override cannot grant it.
Review works from its own minimized copies, kept separately and read under
Review authorization. Deleting ordinary Browser history does not delete those
copies.

## Seal only acknowledged Workspace state

Voluntary submission runs in this order:

1. Refuse new edits.
2. Settle Workspace changes.
3. Reconcile the terminal accounting for Focus Loss and Browser Activity.
4. Call one named atomic Store operation.

The request fences on the current Revision, Workspace Cursor, final Focus Loss
sequence, Participation, generation, credential, bound Session and open
Connection.

The server works out Browser settlement itself, across every source the
Attempt owns. Clients never send a claim about Browser settlement. If no
source was recorded, the result is `not_applicable`. Otherwise the response
shows source counts and the gaps as they really are. A gap does not stop
sealing.

Closing a source fixes its known allocation boundary and its deadline for
historical uploads. Receipts acknowledge records that actually arrived. A loss
declaration settles uncertainty without inventing receipts.

<GovernedFigure asset="submission-provenance-boundary" />

The atomic operation does all of this together:

- creates one immutable manifest
- marks the Attempt Submitted
- ends Participation
- keeps the idempotent receipt that is safe for the candidate to see
- commits the audit

A Submission made by the candidate, ended by a manager, or closed with the
Sitting all use the same immutable Submission contract. They differ in their
prerequisites and in the provenance they record. In every case the
acknowledged state is what counts.

## Keep terminal state terminal

There is no reopen, no resubmit, and no change to the Workspace after the
seal.

- A late Focus Loss that carries an exact, kept causal selector goes into a
  bounded discrepancy stream. It does not change the sealed work.
- New qualifying Browser or native condition evidence, accepted within its
  historical window, invalidates the current Review approval and Sitting
  Records Completion. Earlier finalization snapshots stay as they were.
  Managers must acknowledge the changed inventory before they release again.
- A no-show has no Attempt and no Submission.

If the response to a voluntary submission is uncertain, an exact replay sends
the same body, with the same meaning, and the same idempotency key, with fresh
transport proof. A retry with different content is a conflict. If a realtime
publish or runtime unbind fails after commit, that must never cause a second
seal.

## Focused tests

```sh
cd server
go test ./model -run 'TestBrowserActivity|TestExamSubmission'
go test ./app/exam/attempt -run 'Test.*Browser|Test.*Submission'
go test ./store/sqlstore -run 'Test.*Browser|Test.*Submission'
go test ./httpapi -run 'Test.*Submission|Test.*Workspace'
go test -race ./app/exam/attempt
make architecture
```

Cover these cases:

- rejecting private fields
- malformed and oversized batches
- source reset
- a duplicate with changed content
- reorder gaps
- collection during a correction and during a pause
- every submission fence
- exact retry
- automatic close
- manager end
- late evidence ordered against finalization
