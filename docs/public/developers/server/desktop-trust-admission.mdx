# Desktop trust and candidate admission

Candidate admission is not "sign in, then open a socket". It is a chain of
proofs, and each one can be revoked on its own:

1. Desktop Registration
2. a Session bound to the registered key
3. the current Participation generation
4. the current Connection

Keep each proof with its owner, so that revoking one layer can't be got
around through another.

## Who owns what

| Concern | Main owner |
| --- | --- |
| Desktop Authorization lifecycle and compatibility evaluation | `server/app/identity/desktop_authorization*.go`, `desktop_compatibility.go` |
| DPoP proof checks, nonce, replay and the registered-key principal | `server/app/dpop*.go` |
| HTTP DTOs, loopback rules and route declarations | `server/httpapi/desktop_*.go` |
| Durable one-use transactions, Registration, Session and policy state | `server/store` and `server/store/sqlstore` |
| Candidate admission, Participation and Connection | `server/app/exam/attempt` |
| Versioned socket envelopes | The realtime transport and its explicit protocol catalog |
| Public wire contract | `server/openapi/fragments/authentication` and `access-policy` |

Don't move compatibility or Participation decisions into DPoP middleware.
DPoP proves possession of a key for one request. It does not prove current
Exam access, Sitting state or that the candidate is eligible.

## Keep the browser handoff intact

Desktop Authorization is a public-client flow:

1. Desktop creates an S256 PKCE pair, a state value, a P-256 key and an exact
   loopback callback.
2. The hosted browser page binds the one-use request, authenticates the
   person and gets their explicit approval.
3. The page returns only a short-lived code and the state.
4. Desktop exchanges the code using the same verifier and public key.

<GovernedFigure asset="desktop-authorization-handoff" />

When you change this flow:

- Keep the private key and the PKCE verifier inside Desktop.
- Accept only an exact IP-literal loopback callback, with its pinned port and
  path.
- Bind approval and exchange to the issuer, public key, build identity,
  request, state, code hash and expiry.
- Use every code exactly once, and keep a terminal failure safely.
- Create the Registration and the ordinary rotating Session in one atomic
  step.
- Publish effects only after the durable commit.

Loopback HTTP is a narrow local exception. A development option may allow an
HTTP issuer, but only for explicit loopback development. It must never widen
to a LAN address or a production address.

## The hosted browser states

The hosted page is a state machine built for this one purpose. It is not a
general sign-in form. Before rendering, `webapp/src/app/HostedRoutes.tsx`
removes the fragment proof and the one-use `request` handle from browser
history, and leaves only the bounded opaque state in the URL.
`DesktopAuthorizationPage.tsx` then moves through these states, each backed
by the server:

| State | What the browser does | What moves it on |
| --- | --- | --- |
| Initial binding | Sends the in-memory handle, proof and state exactly once | A route-scoped HttpOnly transaction cookie |
| Account selection | Offers the current Web Session, local authentication or a configured provider | No Desktop credential and no new Web Session |
| Authenticated confirmation | Shows only the Institution presentation, canonical username and a bounded device label | An explicit approve, use-another-account or cancel action |
| Approved | Follows only the exact loopback redirect the server returned | The short-lived code and original state go back to Desktop |
| Terminal rejection | Replaces the task with guidance for canceled, expired, consumed, invalid or active Attempt Session | No retry with the old proof |

Signing in with a local password proves the account for this transaction only.
Provider authentication leaves and comes back in the same tab. "Use another
account" clears the chosen account without rebuilding the original proof.
When a person's action leads to a terminal state, the page moves focus to the
replacement task and announces it. Background checks don't steal focus.

Before you change a state, read the comments in
`webapp/src/features/desktop-authorization/DesktopAuthorizationApi.ts`. These
tests cover the page:

- `webapp/src/app/HostedRoutes.test.tsx` covers credential purpose, URL
  cleanup, state limits and rendering of every route.
- `webapp/src/features/desktop-authorization/DesktopAuthorizationContext.test.ts`
  covers public discovery and how the transaction context is classified.
- `webapp/tests/browser/hosted-access.spec.ts` covers exact binding, same-tab
  authentication, account reset, explicit approval, cancellation, lockout,
  focus, privacy, narrow viewports and the dark theme.

Run the component tests and the Chromium browser tests from `webapp/`:

```sh
npm test -- src/app/HostedRoutes.test.tsx \
  src/features/desktop-authorization/DesktopAuthorizationContext.test.ts
npx playwright test tests/browser/hosted-access.spec.ts \
  --project=chromium --grep 'Desktop'
```

Add a browser case whenever a change adds a visible state, a new way into or
out of a state, or new sensitive input. Assert that history is clean, and that
no proof, password, provider token, account identifier or resulting Desktop
credential appears in rendered text or URLs.

## Check every DPoP request from scratch

<GovernedFigure asset="desktop-dpop-boundary" />

A proof binds the exact method, canonical target URI, access-credential hash,
public key, issue time, unique identifier and current nonce. The replay store
and nonce state are security dependencies, not best-effort caches. If either
is unavailable, authentication fails closed.

On `authentication.dpop.use_nonce`, return the new nonce and require a freshly
signed proof. Never accept a replay of the proof you rejected. Access and
refresh credential rotation stay in the Session model. Don't invent an
authorization snapshot just for Desktop.

## Keep compatibility apart from authorization

`system/ping` and Desktop Authorization check the exact release, build ID,
platform, architecture and realtime protocol against the current
compatibility policy and the compiled build catalog. The result is one of:

- compatible
- update required
- server incompatible
- unsupported target
- revoked build
- maintenance

Compatibility is a precondition for admission, not a Role permission.
Changing the policy is an administrative mutation that needs strong, recent
authentication and is audited. A build string the client reports is untrusted
input. On its own it never selects server behavior.

## Test a Desktop client you are developing

1. From the server repository, run `make run-server`.
2. In another terminal, run `make dev-seed`.
3. From the Desktop checkout, run `npm run dev -- --allow-http-loopback` and
   connect to `http://localhost:8065`.

The browser uses the seeded credentials and goes through the real approval
handoff.

`make run-server` compiles with the explicit `dev` Go build tag. That makes it
default to the `dev` service environment, which skips the Desktop login
compatibility checks. You don't need a manifest or a configuration entry.

- To turn on production checks locally, run
  `PROCTOR_SERVICE_ENVIRONMENT=production make run-server`.
- The variable is read from the process only. It also accepts `test`, which
  enforces compatibility.
- Every build without the tag defaults to production behavior. That includes
  release packages, runtime images and a plain `go build`.

Production compatibility uses the verified build catalog, which is compiled
from exact signed release tuples. Until a release embeds verified Desktop
artifacts, that catalog is empty, and every Desktop login is rejected as an
unsupported build.

Development still enforces request validity, readiness, maintenance, account
access, PKCE, DPoP and Session checks. Protected Attempt admission needs a
verified native build in every service environment.

## Admit an Attempt only after activity entry

Two steps happen in two places:

- Candidate Exam Activity owns navigation, and creates one Ready Attempt and
  its copy-on-write Workspace lazily.
- Secure socket admission creates the Participation and the Connection.

Don't create the Attempt again during `exam_attempt.connect`, and don't create
a Participation when the candidate is only listing activity.

Admission checks these again against authoritative state:

- Class membership
- Sitting state
- the current Revision
- Ready Attempt state
- the registered key and Session
- compatibility
- runtime posture
- the lock that allows one unresolved Attempt per User and Session

It then freezes one Attempt Configuration from the portable settings document
and the supported Desktop manifest. Reconnect and re-allow keep that
configuration.

## Tests that define the boundary

Run the focused tests from `server/`:

```sh
go test ./app -run 'TestDesktopAuthorization|TestDPoP|TestDesktopCompatibility'
go test ./httpapi -run 'TestDesktopAuthorization|TestDesktopCompatibility|TestDPoP'
go test ./app/exam/attempt -run 'Test.*Admi|Test.*Participation'
go test ./store/sqlstore -run 'Test.*Desktop|Test.*Attempt'
make architecture
```

Include these cases:

- replay with a changed code
- a wrong nonce
- a wrong method or target
- a mismatched key
- an expired code
- a callback mismatch
- a policy change
- Registration revocation
- stale membership
- an incompatible build
- continuing on another node

Finish with the OpenAPI agreement check and whichever broader server gate
fits the change.
