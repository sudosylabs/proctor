# Domain and application design

Domain models and application use cases solve different problems. A domain
model can tell you whether a value, or a change to it, is valid on its own
terms. An application use case answers the bigger questions:

- May this principal make that change now?
- Which records must change together?
- Which effects follow once the commit succeeds?

Keeping the two apart means HTTP, WebSocket, a durable Job or a command can all
use the same behavior, without copying policy into each entry point.

## Start with the exact meaning

Before you add a type, name the concept in Proctor's vocabulary and find the
model that already holds it. Everyday words that sound alike are not
interchangeable here. A Session is not an Exam Attempt. An Exam Revision is
not an Exam Sitting. A Workspace Content Version is not a retained File
Revision.

A domain model usually owns:

- canonical identifiers and closed sets of state values
- validation in its constructor, and normalized local values
- transitions that depend only on the aggregate's current state and the
  inputs it is given
- the order of local events in time
- safe cloning or projection where it holds mutable slices or maps

It does not own HTTP status codes, SQL column names, authorization lookups,
SMTP delivery, WebSocket messages, deployment configuration or finding other
services.

## Write constructors that produce valid state

Prefer a constructor that returns either a valid value or an error:

```go
document, err := model.NewUserSettingsDocument(userID, revision, createdAt)
if err != nil {
	return err
}
```

Keep `Validate` useful for rebuilding values from the Store and for checks at
the boundary. Invalid data read back from persistence is an internal integrity
failure. It is not an ordinary not-found, and a transport handler must never
quietly repair it.

Give each transition method a name that says what changes. `Archive`,
`Publish`, `Renew` and `Submit` tell the reader far more than a generic
`Update` or `Process`. Treat timestamps as facts, not as tokens for optimistic
concurrency. When callers need to fence a write, use an explicit revision.

### Domain checklist

- Can the type exist without HTTP, SQL, Redis, VFS, SMTP or the cluster?
- Does the constructor reject every state that is invalid locally?
- Are zero, absent, expired, archived, disabled and terminal states all
  distinct?
- Are mutable inputs copied where callers could keep a reference to them?
- Do tests cover transition boundaries and rejected states, not just the
  constructor's happy path?

## Shape one application use case

Public application methods take typed commands or queries and return typed
results:

```go
result, err := application.ReplaceOwnUserSettings(
	ctx,
	invocation,
	app.ReplaceOwnUserSettingsCommand{
		Source: source,
		FormatVersion: 1,
		ExpectedRevision: revision,
		IdempotencyKey: key,
	},
)
```

Each argument has one job:

- `context.Context` carries cancellation, deadlines and propagation. It never
  hides a User, a permission, a Store, the origin of a mutation or any other
  security state.
- `invocation.Invocation` carries the immutable principal and the bounded call
  metadata that authorization and audit need.
- The command carries the input to the use case.

The service behind a use case usually stays unexported, behind methods on
`app.App`. Its constructor receives narrow ports that the consumer defines.
Keep the facade easy for transports to call, without letting it become a
general way to look up services or Stores.

## Authorize against current state

Authentication proves a credential and sets up a principal. It does not grant
permission. A use case that depends on who the actor is resolves the
canonical resource, then checks the stable action against the current
authoritative relationships, immediately before any expensive work or
mutation.

Never authorize from:

- a role snapshot stored in a Session
- an Affiliation or membership on its own
- a receipt from a transport preflight
- the presence of something in a cache
- a route name or HTTP method
- an earlier read whose authority may since have gone stale

Some resources a user owns have built-in application policy instead of a role
action anyone can be granted. That exception still lives in the use case, and
it still respects the credential's ceiling. User Settings, for example, need
the principal of the current interactive Session, and accept no User ID from
the caller.

## Prepare durable intent before calling the Store

The application decides what the transaction means:

- which canonical resource is changing
- which current authorization must hold
- whether idempotency is required, and which input, by meaning, it
  fingerprints
- which safe audit event is mandatory
- which domain records or durable work must commit together
- which result is safe to keep for replay

It then calls a named Store operation. The application never coordinates this
with a generic SQL transaction callback.

Idempotency is about meaning. The owner of the command defines a stable
operation name and normalizes the bounded inputs that make two requests "the
same". Don't hash an HTTP body blindly, and don't let the transport decide what
counts as a business replay.

## Publish only after commit

An application event is a small fact in the past tense, such as
`UserSettingsChanged`. It carries approved IDs, the revision and the time. It
never carries a mutable entity, a credential, an answer, an arbitrary map or
JSON shaped for a transport.

After the Store returns success, the use case may ask for cache invalidation,
local realtime publication, fan-out to peers, or another effect that can be
rebuilt. If one of those effects fails, the failure is diagnosed, but the
durable outcome is neither rolled back nor repeated.

Use a durable Job or a mail occurrence when the follow-up or the delivery
itself must survive the process dying. Ordinary realtime fan-out does not
become an outbox by default.

## Add application child packages only for a reason

The parent `server/app` package only assembles the application: the `App`
type, how it is built, and the dependencies composition supplies. Behavior
lives in child packages. A child package earns its place when it owns
substantial, stable mechanics, has several collaborators, can offer a narrow
facade and can point inward without importing its parent.

The current child packages each exist for a different reason:

- `app/job` owns a generic engine that knows nothing of domain handlers, and
  the operator Job service built on it.
- `app/realtime` owns transport-neutral event and propagation contracts.
- `app/mail` owns product mail preparation and rendering contracts, and the
  operator mail service.
- `app/search` owns the single search across Exams, Classes and Users.
- Focused children of `app/exam` own separate parts of how examinations work.

They are not a folder template. A new capability doesn't get a child package
just because another capability has one.

## Test application policy

Use small handwritten fakes for exactly the ports the consumer defines. Test
the order of what happens and the outcomes you can observe:

- An invalid principal or input fails before anything is persisted.
- Current authorization is checked at the right point.
- An audit failure stops a mutation that must fail closed.
- The named Store command carries every fact it is meant to.
- A replay does not repeat the effects that follow commit.
- A changed outcome publishes the expected safe event.
- A brief effect failure does not rewrite a committed result.

Then use Store conformance or integration tests for the atomic guarantee, and
the real composition graph when the wiring matters.
