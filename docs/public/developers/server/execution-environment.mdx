# Design the Execution Environment

The execution environment gives a candidate real terminals beside the editor in
a programming exam. Each Attempt that uses it gets an isolated machine on
[execenv](https://github.com/sudosylabs/execenv), with the Attempt Workspace
synced into `/workspace`.

Execution is an optional feature of the **core**, not a plugin. It touches
admission, the Attempt Workspace, Submission and evidence, and it will not be
the last actor to do so: an AI assistant that edits files and runs commands, or
tests a grader runs, would use the same paths. Each of those must be a new
*author*, never a new write path.

This page records the design the owner settled and is being built in the
order below. The earlier `execution` plugin and the plugin seams only it used
are deleted. Where this design changes a contract, the old form is removed.

## Goals

1. **Integrity first.** A Submission is exactly the candidate's acknowledged
   work. Nothing an environment does can change what was sealed, and the seal
   never waits on an execution host.
2. **One authority, many actors.** The Attempt Workspace is the only authority
   for the candidate's files. The editor, the environment and any later actor
   write through the same use case, and every change names its author.
3. **Feels local.** A file saved in the editor is in the terminal within a
   second. A file a program writes is in the editor within about a second. A
   reconnect resumes the terminal exactly.
4. **Survives failure.** A Proctor node, an execenv daemon or a whole host can
   fail. The candidate loses at most the last second of guest changes and the
   running processes, and the loss is recorded.
5. **Scales by placement, not by polling.** An idle Attempt costs almost
   nothing, and a Sitting of hundreds starts in seconds.

## What execenv gives us

One execenv `Host` is one Linux machine. A grant is one isolated machine with
its own CPU, memory and disk, restored from a per-image template in about
150 ms. execenv provides:

- **Files.** A projection into `/workspace` with stable entry IDs and opaque
  versions, content addressed by SHA-256. Changed paths are reported as the
  guest makes them, and bodies are read live; `ErrStale` means the file
  changed again.
- **Seeds.** A tree put to a host once and cloned into each grant.
- **Processes.** Started by tag, with or without a PTY. Output and input are
  addressed by offset, a terminal process has a `Screen`, and any number of
  clients may attach. A process log reports what each process started.
- **Lifecycle.** Fenced freeze, thaw and revoke, idle suspend to disk, grant
  and host watches, and grants that survive a daemon restart.

What execenv leaves to the caller is placement across hosts, recovery from a
lost host, and every decision about what a change means.

## The Attempt Workspace changes

Execution turns the Attempt Workspace into a store with several writers that
others observe. Each change below is useful without execution.

### Authors instead of origins

Every write names an *author*: a kind and a reference.

| Kind | Reference |
| --- | --- |
| `candidate` | The Attempt Connection the editor wrote through |
| `environment` | The environment incarnation and, when known, the process tag that wrote the path |

Later kinds, such as `assistant` or `grader`, are added the same way.

- The author is stored on every journal entry, in the audit value of every
  batch and on every evidence record. It replaces the journal's `editor` and
  `environment` origins.
- The Submission manifest records, for each entry, the author of its last
  change, so a reviewer sees who wrote what.
- Every author acts on behalf of the candidate under the same permission. The
  kind decides the extra check: a `candidate` author must hold a live
  Connection, and an `environment` author a live environment fence.

### One write path

*Apply Workspace Batch* is the only write path, for every author: 1 to 128
mutations, each with its per-entry fence, applied all or nothing. A batch is
one access check, one idempotency outcome, one audit pair holding counts,
bytes, the cursor range and the author (never paths), one multi-row journal
insert and one change notification.

### Conflicts follow the journal

The journal order is the truth: whatever commits first wins, and a mutation
whose expected version is stale is refused. Each author reacts in its own way:

- **The editor** shows the candidate a conflict on that file, with the current
  content, as an editor does when a file changed on disk.
- **The environment** does not retry. The core projects the current Workspace
  version back into the guest and keeps the lost guest version as an
  *overwritten* evidence record. Until execenv can discard an unconfirmed
  guest change, a projection onto it is refused; when the refusal outlasts
  three rounds without new guest activity, the owner replaces the machine
  from the Workspace and records a gap.
- **A later actor** is told its change was superseded.

A guest's changes are separate system calls, not a transaction. The harvest
therefore groups only changes that depend on each other, such as a directory
and the files created in it, or a move and later writes under its new path.
Each group is its own batch, so one stale file never drops unrelated changes.
Replacing the whole machine is kept for a machine that is lost.

### Change notifications in the core

A commit already sends clients a workspace-changed hint. The core gets a
subscription on the same post-commit outbox, so the environment's owner wakes
on a change instead of reading the journal on a timer. Cluster delivery stays a
best-effort accelerator, and a slow backstop catches a missed hint.

### Retention by cursor

The journal is kept back to the lowest cursor a live reader still needs, such
as the projection or an open editor, up to a hard ceiling. A fixed count would
let a busy build push the editor past the retained window. A reader past the
ceiling refreshes from the manifest.

### Budgets per author kind

Write-rate budgets are kept per Attempt **and** per author kind. An editor's
budget suits a person; the environment's is sized by its profile, because a
build can write hundreds of files in a second. Quotas on entries, file size and
total size stay per Workspace and bind every author.

### Sync status

A guest file can fail to reach the Workspace: it is over quota, on a path the
Workspace refuses, or it lost a conflict. Each path the environment reports has
a *sync status*, `synced`, `ignored` or `refused` with a reason, that the
editor and the terminal show. It is derived from the last harvest and is not an
authority.

### What is kept: `.proctorignore`

Every Attempt Workspace has a `/workspace/.proctorignore` in gitignore syntax.
It names paths that stay on the machine and are never forwarded to the
Workspace.

- **A default copy.** A new Attempt Workspace that uses execution gets a
  `.proctorignore` holding Proctor's default patterns, unless its Starter
  Workspace has one. They play the part of a standard `.gitignore`:
  `node_modules/`, `.venv/`, `__pycache__/`, `target/`, `build/`, `dist/`,
  `*.o`, `*.class` and similar build output. While the file is missing or does
  not parse, the defaults apply.
- **The git rule.** A pattern only stops *new* paths. Anything already in the
  Workspace keeps syncing, so a careless `*.py` can never empty a Submission.
  To stop syncing a file, the candidate deletes it in the editor.
- **The file always syncs itself** and is submitted, so a reviewer sees what
  the candidate kept off the record.
- **Staying on the machine** means the path is never in the editor or the
  Submission, and is lost with the machine.

execenv does not know the name. The core passes the Workspace's copy as
execenv's ignore rules, with the defaults as the fallback. Before storing a
harvest, the core still tests each change against the Workspace's own copy and
drops anything it ignores.

## The Attempt Environment

### Model

An *Attempt Environment* is one row per Attempt that uses execution:

| Field | Meaning |
| --- | --- |
| Attempt | The Attempt it belongs to |
| Profile and image | Frozen from the Revision's execution policy |
| State | `creating`, `running`, `frozen`, `suspended`, `waiting_capacity`, `lost` or `ended` |
| Incarnation | Raised on every replacement machine |
| Grant | The execenv grant, its epoch and host |
| Fence | The last execenv fence revision applied |
| Cursors | The Workspace cursor projected, and the observation and process-log positions acknowledged |

The processes the core starts are not rows. The machine is the authority for
what runs on it, and any node asks it: a process's tag (`terminal:1`,
`terminal:2`, later others) names its kind and, through the kind, its author,
and the machine reports when it started and how it exited. A new incarnation
starts with no processes.

The environment belongs to the **Attempt**, not to a Participation. A
disconnect freezes it and a reconnect thaws it, so the machine, its processes
and its terminals survive. A long absence suspends it to disk with the disk
still reserved. A machine that is lost for good is replaced by a new
incarnation from the Workspace, and the gap is recorded.

### Lifecycle

The owner drives the environment from Attempt facts:

| Attempt fact | Environment |
| --- | --- |
| First admission with execution on | `creating`: restore from the profile's template and the Revision's seed, then project the Workspace |
| Participation active | `running` |
| Participation ended without a Submission, or the Sitting paused | `frozen` |
| Frozen longer than the profile's idle window | `suspended` |
| Submission requested, or the Sitting closing | Settle, then `ended` |
| Attempt sealed | `ended`, with the grant revoked after the settle |

Admission never waits for the environment. The candidate is admitted, the
environment comes up behind, and the client shows *starting* or *waiting for
capacity*. The editor and Submission work throughout, and time is never
extended for a wait.

### Profiles, hosts and placement

- **Environment profiles** are installation-level and managed by
  administrators in the database. A profile names an execenv image, CPU,
  memory and disk, the network (none, or an allowlist), the idle window and the
  maximum number of terminals. A profile in use is never edited; a change makes
  a new profile.
- **Hosts** stay in configuration, with their addresses, certificate
  authorities and tokens. Their capacity comes from execenv's host watch.
- **Placement** picks the host with the most free resources for the profile,
  and tries the next on `ErrCapacity`.
- **Templates.** Every host builds a template per image and profile shape.
- **Seeds.** When a Sitting opens, the Revision's Starter Workspace is put to
  each host as a seed, once. An environment starts from the seed, and the
  projection applies only what differs.
- **Pre-warm** at Sitting open is the seed upload and a capacity forecast,
  Class size times the profile, shown to the manager. Admission reserves no
  capacity.

### The owner

A core *attempt runtime* keeps one owner for each environment that has not
ended.

- The owner holds a lease in PostgreSQL with a fence, renewed by its node.
  Every core write it makes carries that fence, so the store refuses a stale
  owner after a takeover.
- It wakes on a Workspace commit for its Attempt, an Attempt lifecycle change,
  its grant's state from execenv's grant watch, and new guest changes. A slow
  backstop catches anything missed.
- Each node bounds how many owners it holds; a full node leaves leases to
  others.
- Everything a new owner needs is in the Attempt Environment row, so it
  continues from the stored cursors.

### Sync in both directions

**Workspace to guest.** The owner reads the journal after the projected cursor
and applies it with execenv's projection, uploading only bodies the guest
lacks.

**Guest to Workspace.**

1. The owner waits on a long-polled observation, so it blocks instead of
   polling each grant.
2. A path is harvested once it has been quiet for about 200 ms, and after 1 s
   at the latest. A burst of writes to one file becomes one change, and a
   change whose SHA-256 matches the current content is dropped.
3. The owner plans against the core's own Workspace state, groups dependent
   changes, and commits each group with author `environment` and the writing
   process's tag when execenv reports it.
4. Bodies are read live. An `ErrStale` read is skipped, because a later
   observation carries the newer content.
5. Only after the commit does the owner confirm the echo and acknowledge the
   observation.

### The settle and the seal

The seal never waits long on an environment, but a cooperative environment
should not lose its last second. A *settle* runs before every seal:

1. Drain: one complete observation and a harvest of everything in it.
2. Confirm and acknowledge.
3. Freeze the guest, when the environment is to be frozen. execenv serves no
   observation once a machine is frozen, so the drain comes first.

A settle is asked through the environment's row, so the owner answers it on
whichever node holds the lease: the seal counts one more requested settle,
wakes the owner, and waits until the owner records it complete. A voluntary
submit and a manager end settle, then seal; a replay settles nothing. A
closing Sitting asks every environment of the Sitting to settle, and its
sealing Job waits the settle budget before it runs. Each settle has 5 seconds.
Past that, or with the host unreachable, the seal records a *settle gap*
(`{"gap": "settle_incomplete"}`, by the current incarnation's `settle`
stream) and goes ahead. A voluntary seal's expected cursor fences only the
candidate's own changes, so what the settle harvested is sealed.

Only Attempt Workspace content counts. Terminal output, shell history, the
scratch home and ignored paths never do.

### Processes and terminals

- The core starts processes by tag. Terminals are PTY processes running the
  image's login shell, tagged `terminal:1`, `terminal:2` and so on in the order
  the machine opened them. A machine never reuses a tag, so a terminal's input
  offsets, and the input evidence numbered by them, belong to one process; at
  most the policy's number of terminals run at once, and a machine opens at
  most 64. A terminal's tag makes the candidate its author.
- **Input** is written at an offset, so a resend after a lost connection never
  types twice. Resize and interrupt are passed through; a candidate may send no
  other signal.
- **Any Proctor node** serves a terminal. The Attempt service checks the
  candidate's Attempt access; the node then reads the environment row, which
  must be running, ensures the machine from the row exactly as the owner does,
  refuses a machine of another epoch, and writes under the row's current
  control fence, reading the row once more when the owner has moved it. It
  holds no lease. Terminal bytes never travel over cluster peer delivery, which
  is best effort and drops the oldest messages.
- **Reconnect.** The client sends the output offset it has, and the server
  replays from there, reporting what the history no longer holds, so even
  full-screen programs come back intact. A client with no screen of its own
  asks for the `Screen`, draws it, and attaches from its offset.
- **Several attachers** may read one terminal, such as the candidate on two
  windows. Input is accepted only from the process's author, and the
  attachers share one input offset.
- **The socket** is a binary WebSocket whose frames carry output at an
  offset, truncation, the exit, input at an offset with the offset it reached,
  the window and the screen; the operation's description in the API reference
  is its contract. An open socket checks the candidate's access and the
  environment row every 15 seconds and closes with 4003 once the Attempt is
  sealed, the Participation ends, or the machine ends or is replaced.
- **The process log** names, for every command, the tag of the terminal or
  tool that ran it: the owner follows each started process's parent to the
  process a Start created and records that tag as the event's `origin`, beside
  the host's own `tag`. The attribution lives in the owner's memory for one
  machine epoch, so an owner that takes over attributes only what it saw
  start; its records leave `origin` empty rather than guess.

### When something fails

| What fails | What the candidate sees | What survives |
| --- | --- | --- |
| A Proctor node | A brief reconnect | The machine, its processes and their output |
| The network | A reconnect, resumed from the last offset | The machine, its processes and their output |
| The execenv daemon | A brief reconnect | The machine, which the daemon adopts again |
| The host, for good | "Environment restarted" | Every synced file |

## Evidence

Evidence from execution goes into Attempt-owned, append-only *Attempt
evidence*. Each record names its author, and the kind, author and sequence
identify it, so every author keeps its own streams. Because the records
belong to the Attempt, a settle gap is recordable after the Participation has
ended.

| Kind | What it holds |
| --- | --- |
| `execution.process` | The command log: bounded command line, working directory, start, exit status and duration, with the process tag and the `origin` terminal or tool |
| `execution.input` | Terminal input with its timing and window size changes, only when the Exam opts in |
| `execution.gap` | A lost machine, a wait for capacity, a settle gap or a break in the process log |
| `execution.overwritten` | A guest change lost to a newer Workspace version |
| `execution.refused` | A guest change the Workspace refused, with the reason |

- **Storage.** Bounded records in PostgreSQL, with an inventory that carries a
  digest chain and refuses updates once sealed. Each Attempt keeps at most
  4,096 records and 8 MiB; an append past them is counted, not stored. Appends
  after the Submission are refused, except the settle's.
- **The command log** comes from execenv's guest agent, which runs outside the
  candidate's workload. The workload cannot read or change it, and a gap in its
  sequence is itself recorded. Candidates are told that commands are logged.
  Work that starts no process, such as `exec()` inside Python, is invisible.
- **Terminal input** is captured at the Proctor node that serves the socket,
  so it never passes through the guest. Output is never recorded. It is
  stored as `execution.input` records, not VFS chunks: what a session wrote
  within about a second, up to 16 KiB, is one record by the incarnation and
  the terminal's tag, numbered by its first byte's input offset, so a resend
  repeats a record rather than adding one. The serving node holds no lease,
  so its append is checked against the environment's current incarnation and
  the Attempt's lack of a Submission instead. A window change is kept with the
  input after it.
- **Review.** A command line can hold an answer, so the streams are sealed with
  the Submission and only reviewers see them. Gaps and overwritten changes are
  review context, never Flags.
- **Later rules.** Because execution is core, the rule engine can raise Flags
  from these streams under the same Policy Set rules as other evidence. The
  first version raises none.

## Policy and API

### Execution policy

The Exam Policy Set gains a typed execution policy, frozen into the Exam
Revision and its digest:

| Field | Meaning | Default |
| --- | --- | --- |
| `Enabled` | Whether Attempts get an environment | `false` |
| `Profile` | The environment profile's name | — |
| `RecordInput` | Whether terminal input is recorded | `false` |
| `Terminals` | How many terminals a candidate may open, from 1 to the profile's maximum | 1 |

The core validates it on save and at publication: the profile exists and
execution is on for the installation. Publication never dials a host.

### Candidate routes

| Route | Purpose |
| --- | --- |
| `GET /exam-attempts/{id}/environment` | State, incarnation, terminal limit, and `projection_cursor`: a Workspace entry whose last change is past it is not in the machine yet |
| `POST /exam-attempts/{id}/environment/terminals` | Open a terminal; answers with its number and tag |
| `GET /exam-attempts/{id}/environment/terminals` | The terminals on the current machine and the policy's limit |
| `GET /exam-attempts/{id}/environment/terminals/{n}/socket` | Binary socket: output and input by offset, resize, screen |
| `POST /exam-attempts/{id}/environment/terminals/{n}/signal` | Interrupt |

A terminal is addressed by its number `n`, so terminal `1` is `terminal:1`.

The Workspace routes are unchanged, apart from the per-path sync status.

### Managers and reviewers

- **Managers** see, for each Sitting, environment states and how many
  candidates wait for capacity, and can replace a candidate's environment.
  The Sitting's candidate-status board carries each candidate's environment
  (state, desired state, incarnation, and since when it waits for capacity)
  and a Sitting-wide count of environments waiting for capacity.
  `POST /exams/{exam_id}/sittings/{exam_sitting_id}/attempts/{exam_attempt_id}/environment/replace`
  names the incarnation the manager saw; the owner replaces that machine
  from the Workspace and records the restart as a gap. Asking again for the
  same incarnation changes nothing, and a newer incarnation conflicts.
- **Reviewers** see the command log, terminal input when recorded, gaps,
  overwritten and refused changes, and authorship for every entry in the
  Submission. The evidence comes from the Submission's Attempt evidence
  route, and each entry of the Submission manifest names the author of its
  last change.

### Clients

- **Desktop** shows the terminal pane with several tabs, live editor updates
  from the journal, and conflict and "not saved" markers.
- **The webapp** shows the manager and reviewer views.

## What execenv adds

Two small additions, neither of which changes an existing contract:

1. **Long-polled observation.** An observation request waits until there is
   something to report or a timeout passes.
2. **The writing process.** The guest agent maps the process that wrote a path
   to the tagged process it descends from, and the observation carries that
   tag. A path written by several processes names the last.
3. **Discarding a guest change.** A projection may replace an unconfirmed
   guest change on the paths it writes, so a change that lost to the journal
   is overwritten in place instead of replacing the machine.
4. **Suspending a frozen machine.** Idle suspend applies to a machine the
   owner froze, not only to a running one, so a long absence frees its
   memory.

## Data model

New core tables, in the baseline migration:

- `exam_attempt_environments`, one row per Attempt that uses execution;
- `attempt_runtime_leases`, the owners' fenced leases;
- `exam_attempt_evidence` and `exam_attempt_evidence_inventories`, which
  replace capability evidence;
- `environment_profiles`;
- `author_kind` and `author_ref` on the Workspace journal, replacing `origin`.

Removed with the plugin: its records and leases, Exam plugin sections, plugin
routes, workers, event subscriptions, and the plugin capabilities for
Workspace access and evidence, and the environment bindings: the owner's
fenced lease is the environment's Workspace access.

## Build order

Each step is a vertical slice with its own tests. Steps 1 to 5 are built. The execenv additions of step 6 are built in execenv and wait for its next release before Proctor adopts them.

1. **Workspace foundation:** authors on the journal, audit and idempotency
   outcomes, the last author of every entry sealed in the Submission, and
   budgets per author kind. The Workspace already refuses a stale version
   per mutation.
2. **Evidence foundation:** Attempt evidence of the core's closed kinds,
   owned by the Attempt and named by its author, in place of capability
   evidence, with the seal, review, export and retention moved over.
3. **Attempt Environment:** the execution policy, environment profiles and
   the execution configuration first, since nothing can create an
   environment without them; then the model, lifecycle, placement, sync and
   the settle, under the owner's fenced runtime lease with wakeups. Seeds and
   retention by cursor are deferred: an environment starts empty and is
   initialized with the full Workspace, and a pruned journal restarts it. The three Workspace changes whose only reader is the owner land
   here with it: change notifications in the core, retention by cursor, and
   grouped harvest batches. `server/plugin/execution` and its seams are
   deleted in this step, and evidence is appended under the owner's fence
   instead of a binding.
4. **Processes and terminals:** tags, the terminal routes and socket with
   offsets and screens, the command log as evidence with each command's origin, and
   terminal input as `execution.input` records rather than the VFS chunks this
   step first named. Processes are read from the machine; no process rows
   are kept.
5. **API:** the candidate, manager and reviewer routes, and sync status.
6. **The execenv additions,** alongside steps 3 and 4.
7. **Clients:** the Desktop terminal pane and editor updates, and the webapp
   views.

## Rejected alternatives

- **The guest as the authority while it runs.** It removes sync conflicts, but
  every save would depend on a host being reachable.
- **An environment per Participation.** A reconnect would lose the machine, and
  nothing could be recorded once the Participation had ended.
- **Execution as a plugin.** It needed core seams for Workspace access,
  evidence and leases that only one plugin used, kept a second copy of the
  Workspace rules, and assumed one writer and one terminal.
- **Reserving capacity for every Class member** when a Sitting is scheduled.
  It needs a capacity calendar across hosts and wastes machines on absent
  students.
- **Dropping a path once a pattern ignores it,** which silently empties a
  Submission, or freezing its server copy, which makes the Submission differ
  from what the candidate ran.
- **A subset of devcontainer.json.** Its container fields do not map to
  execenv's images, and most would let an author reach the host.

## Open risks

- **Load from builds.** Builds across a whole Class load the VFS and
  PostgreSQL. Per-author budgets bound it, but a load test must come before the
  first large Sitting.
- **Host upgrades.** Grants survive a daemon restart, but not a host reboot, so
  a reboot should not run while a Sitting is open.
- **Lost changes.** Up to a second of guest changes can be lost when a host
  dies, and up to the settle budget's worth when a settle fails.
- **Local VFS.** Local VFS publishes under one lock per node. Installations
  that turn execution on should use S3.
