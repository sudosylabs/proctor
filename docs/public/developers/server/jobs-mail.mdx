# Durable Jobs and transactional mail

A goroutine is not durable work. If the process can disappear after a user has
been told the request succeeded, then any follow-up that must happen has to
exist already as a PostgreSQL fact that another node can claim. Proctor uses
Jobs for finite background work, and a separate mail domain for the durable
intent to send a notification.

## Decide whether work is a Job

Use a Job when the work is finite, can be retried, and is worth tracing after
the request or the process has ended. Examples include content processing,
generating a default picture, bounded cleanup, mail delivery and closing a
Sitting.

Don't create a Job for a loop that runs as long as the runtime does, such as:

- WebSocket ping and liveness
- keeping cluster discovery up to date
- reaping the cache
- another owner's ongoing lifecycle

A small, bounded maintenance pass that runs periodically may run under the Job
engine's lifecycle without creating a durable Job occurrence. That is allowed
when its named PostgreSQL operation already brings every node to the same
state. Write that distinction down explicitly.

## Who owns what

| Boundary | Owns |
| --- | --- |
| Domain model | The stable intent of a Job, its current lifecycle and its append-only Job Attempt history |
| `store.JobStore` | The guarantees for enqueue, claim, lease fencing, checkpoints, terminal transitions and retention |
| `app/job` | The generic engine mechanics and safe views, plus `job.Operations`, the operator service that authorizes and audits listing, cancellation and retry |
| The application capability that owns the work | Why the work exists, actor authorization, domain policy and durable effects |
| `app/jobs` | The typed handler catalog, strict payloads, descriptors, recurrence definitions and the concrete handlers |
| Module-root server | Starting the engine, taking part in readiness, and close order |

A worker gets only the capabilities its handler declares. It does not get
`App`, a root Store, the platform or a service catalog.

## Define the descriptor before the handler

Each closed Job Type declares:

- whether it records resumable checkpoints
- its timeout and how many can run at once on each node
- the maximum number of failed attempts, and a bounded backoff
- whether it can be canceled
- what is safe to show, and its public failure codes
- retention
- its natural or deduplication identity
- the exact handler

Each kind of Job document has a fixed role:

- Commands are immutable typed documents.
- Checkpoints are typed, bounded progress that can change.
- Results are safe typed summaries.

Arbitrary JSON maps are not a Job API, even though PostgreSQL stores the
documents as JSONB.

At startup, the server builds one immutable catalog for the instance. It
rejects duplicate types, missing handlers and invalid descriptors. Don't use
package initialization or a registry global to the process.

## Design for at-least-once execution

PostgreSQL claims a bounded, ordered selection of Jobs. For each one it
creates a Job Attempt with a claim token that can't be guessed and a lease
expiry. Heartbeats, checkpoints and terminal updates all need that current
token. Once a lease expires, another worker can reclaim the Job, and the old
worker can never change its state again.

That has consequences for handlers:

- Handlers must be idempotent.
- If an external call succeeded but the database acknowledgement was lost,
  the outcome is unknown. It is not proof that the call failed.
- Domain state must commit before the Job checkpoint claims the progress.
- The retry path must notice durable effects that already completed.

At-least-once execution doesn't mean every external system gives you
exactly-once effects.

## Use checkpoints and work budgets

Write a checkpoint only once the durable unit of work that its cursor stands
for has finished. Store a stable cursor and safe counts. Don't store a whole
result set or an unbounded error history.

For a bounded occurrence, when a retry must not reuse capacity whose fate is
unknown, reserve the work durably before processing it. If a reservation turns
up ahead of the checkpoint, it is written off as unknown work. This is
stricter than working out progress again from process memory, and it stops a
lost lease from pushing the occurrence over its budget.

Progress uses optional `Current` and `Total` fields and one safe stage from a
closed set. Show a percentage only when the total is known.

## Classify completion and cancellation

A handler returns one of a small set of results: succeeded, retryable
failure, relinquished because the node is incompatible, permanent failure, or
canceled.

- Retry brief dependency failures within the descriptor's bounded policy.
- Fail permanently on invalid payloads and broken invariants.
- Relinquish immutable work when another node may have a deployment
  capability the work needs. This doesn't use up the failed-attempt budget.
- Contain a panic, record only a safe failure code, and apply the retry
  policy.

Cancellation is cooperative. Queued work can cancel at once. Running work
records the request, and its context is canceled once the request is seen. An
atomic commit that can't be canceled finishes. The fenced terminal operation
then settles the race, without pretending that committed domain state was
rolled back.

## Keep Job operations safe

The generic Job operations offer bounded listing, detail, Attempt history,
cancellation, and retry where a type explicitly supports it. They never show
the raw command, checkpoint, result, deduplication key, claim token, internal
error, mail body, file content or student work.

`job.view` protects safe inspection, and `job.manage` protects cancellation
and retry. Neither action lets anyone create arbitrary Job Types, and neither
grants access to a payload that belongs to a domain, such as an onboarding
roster.

## Treat mail as its own durable domain

Transactional mail tells one specific recipient about one bounded application
or security fact. Two packages share the work:

- The independent `packages/mail` module owns portable MIME, validation, SMTP
  and the classification of transport outcomes.
- Server-owned `app/mail` owns what each message means: definitions,
  localization, templates, recipient rules, encrypted frozen payloads,
  suppression, delivery policy and building a stable Message-ID.

`app/mail` also holds `mail.Operations`, the operator service for inspecting,
canceling and retrying deliveries, metrics, test mail and rotating the payload
key. Alongside it are the mail telemetry contracts and the health that the
delivery Jobs report through.

Two records matter:

- A `MailOccurrence` is one logical notification, caused by a domain
  transition.
- A `MailDelivery` is one frozen delivery to one recipient.

A generic Job carries out the expansion or delivery, but it doesn't replace
either mail record.

The named Store mutation that starts it all commits:

1. the business change
2. the required audit
3. the Mail Occurrence
4. one or more Mail Deliveries
5. the delivery or expansion Job

SMTP is never called inside that transaction. If mail is enabled and required
for the transition, and its durable intent can't be prepared or saved, the
business mutation rolls back.

## Freeze the meaning before delivery

Don't look up the recipient address, locale or template data again when a
worker runs.

- Direct delivery freezes the exact recipient and the rendered alternatives.
- Fan-out freezes a bounded render bundle indexed by locale, then expands each
  recipient under the contract of the roster that owns them.

The recoverable payload is encrypted at rest. It is destroyed after
acceptance, terminal suppression, cancellation or expiry. Plain durable
metadata is only a safe view used for routing.

A stable Message-ID survives both automatic and operator retries. SMTP
acceptance means the remote SMTP server accepted DATA. It does not mean the
message reached an inbox.

Before each attempt, run the relevance check for that template family. An
expired recovery credential, or a Sitting fact that has since been replaced,
is suppressed rather than delivered late. Historical security notices and
receipts may still be relevant.

## Write templates and localization

Human copy belongs in the localization catalogs. Typed template data, authored
MJML, generated HTML, authored plain text and reusable partials stay under
`server/templates`. Each template receives one closed, typed presentation
model. Templates don't query application state, build routes, read
environment values or choose headers.

When you change templates or message copy, follow the
[transactional-mail template workflow](https://github.com/sudosylabs/Proctor/blob/main/server/templates/README.md).
Regenerate the tracked HTML, render the synthetic preview set and check both
alternatives. Never use real recipient data from production in previews.

## Test failure and recovery

For Jobs, test claim fencing, lease expiry, checkpoint replay, incompatible
nodes, cancellation, retention, unknown outcomes and several nodes competing
for work.

For mail, also test:

- the business change and the mail committing atomically
- complete definitions and typed rendering
- locale fallback and escaping
- encryption, key availability and rotation
- suppression when mail is disabled
- relevance checks, and retry with a stable Message-ID
- bounded fan-out and removing duplicate recipients
- behavior from the application through to SMTP, using the isolated capture
  service

Use the focused phase targets in the current server Makefile, then run:

```sh
make -C server check
make -C server architecture
```

When delivery fails locally, use the [Jobs and realtime troubleshooting guide](../troubleshooting/jobs-realtime.mdx)
or the [mail troubleshooting guide](../troubleshooting/mail.mdx).
