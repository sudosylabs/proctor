# Build Plugins

A plugin is an edge adapter: a sign-in protocol, an export encoding, or later
a sync with a learning management system. It connects Proctor to something
outside it, and an installation can turn it on or off. Plugins are
first-party: they are compiled into the server and stay dormant until they
are enabled. Proctor never loads code from outside its own binaries.

A plugin never acts on an Attempt. Anything that touches admission, the
Attempt Workspace, Submission, integrity evidence or review is part of the
core, even when most institutions leave it off. Code execution is one such
feature; [Design the Execution Environment](execution-environment.mdx)
describes it.

## Where a plugin lives

Each plugin has one folder, `server/plugin/<name>/`. The contracts it
implements are in `server/plugin`. A plugin may import the contracts,
`model`, `config`, its own dependencies, and the support packages named for
it, such as `platform/externalauth` for sign-in protocols. Only the
module-root `server` package imports a plugin, and `builtinPlugins()` lists
them all. The architecture gate enforces both rules.

A sign-in protocol owns everything about its providers except their identity.
Proctor keeps each configured provider's ID, type, name, whether it is on and
whether it may create accounts; the protocol's `Settings` and `Secrets` are
documents only its plugin decodes and validates, handed over in
`plugin.IdentityProviderDefinition`. Proctor bounds both and always redacts
`Secrets`. Adding a protocol therefore changes no configuration type.

## Seams

| Seam | What it lets a plugin do |
| --- | --- |
| Lifecycle | Activate and deactivate, with deadlines, containment and metrics |
| Sign-in protocols | Offer an identity provider type that builds configured providers |
| Export formats | Offer an encoding for Exam exports, whose files the core chooses, bounds and verifies |
| Installation settings | Have settings an administrator changes at runtime, applied on every node |

A plugin registers what it offers on the `plugin.Host` it is given during
`Activate`. The Host grows one typed method per capability, added only when
a plugin needs it. There is no broad API, store contract or database access.

## Guarantees the core keeps

- **The core keeps the decisions it owns.** It resolves accounts and opens
  Sessions for an identity provider's assertion, and it chooses, bounds and
  verifies every file an export format writes.
- **A broken plugin never takes the server down.** Panics are contained,
  calls are bounded, and a failed plugin is reported in readiness and metrics
  while the node keeps serving.

## Settings

An administrator turns a plugin on or off and edits its settings through the
plugin administration API. Each plugin publishes a settings schema that a UI
draws its form from, and validates a document before it is saved. A change
is audited and applied live: every node converges within a few seconds. A
required plugin, such as the zip export, cannot be turned off. A save records
the on or off choice and the settings together, so a saved plugin always has
both; a plugin nobody has saved keeps its manifest default.

A plugin publishes its schema in `Manifest.SettingsSchema`, checks a
document by implementing `plugin.SettingsValidator`, and can take new
settings in place by implementing `plugin.Reconfigurer`; otherwise the host
restarts it with them. Secrets never go through the API. They stay in the
configuration file under `Plugins.<id>.Secrets`, which is always redacted.
See [Plugins configuration](../../reference/configuration/plugins.mdx).
