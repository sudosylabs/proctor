# Review a server change

Work through only the sections your change touches, then finish with the
checks that cross boundaries. A checklist helps your judgment. It doesn't
replace reading the current code, the tests and the contract that owns the
behavior.

## Domain model

- Does the name keep its exact Proctor meaning?
- Does the constructor produce a value that is completely valid?
- Are state transitions named, and complete on their own terms?
- Are timestamps facts rather than revision tokens?
- Are absent, inactive, expired, archived, disabled and terminal states each
  represented separately?
- Does invalid state read back from storage fail as an integrity error?
- Are slices, maps and byte values cloned where ownership could be unclear?
- Do table-driven tests cover invalid boundaries and the transition races you
  can see at the model level?

## Application use case

- Is there one typed command or query, and one typed result?
- Does `context.Context` carry only cancellation, deadlines and propagation?
- Does `Invocation` carry the immutable principal and safe call metadata?
- Is current authorization checked immediately before the work or mutation?
- Is built-in self-service policy written out explicitly, rather than being a
  check someone forgot?
- Does the use case prepare the audit and idempotency by meaning?
- Does it call one named Store guarantee rather than coordinating CRUD calls?
- Do effects run only after the Store returns?
- Can a replay, a no-op or a brief effect failure avoid repeating effects?
- Are interfaces owned by the consumer, narrow, and kept beside the consumer?

## Store contract and PostgreSQL

- Does the contract state exactly what happens on absence, and its atomicity,
  concurrency and race outcomes?
- Does it return domain values or explicit Store views rather than SQL rows?
- Is every list bounded, and limited by authorization where needed?
- Do constraints enforce invariants even without the application's
  pre-checks?
- Is the lock order consistent with related aggregate operations?
- Does PostgreSQL time decide deadlines and leases that race with commits?
- Are revisions, idempotency keys, time and unique identity each used for
  their own purpose?
- Is retry limited to an operation that is explicitly safe to retry?
- Do conformance tests and a PostgreSQL race test prove the guarantee?
- Does migration work follow the current pre-release baseline policy?

## HTTP resource

- Is the route in one cohesive resource, and in the sealed production
  catalog?
- Does it keep only a narrow application capability?
- Is the credential and assurance classification explicit?
- Are the CSRF and Origin rules for cookie mutations correct?
- Is the request body size limited before decoding?
- Does strict JSON reject unknown fields, duplicates where required, and
  trailing values?
- Are request and response DTOs separate from domain and Store types?
- Are public errors allowlisted, and do unknown errors fail closed?
- Does concealment avoid revealing that a protected resource exists?
- Are upload, download, redirect or upgrade effects expressed as a named
  result rather than free writing to the response?

## OpenAPI and compatibility

- Is the human-owned YAML module the only public contract source you edited?
- Do security, `x-proctor-auth`, idempotency and error codes match the
  runtime?
- Does every parameter and request body explain what it is for?
- Are mutation examples valid against the schema, synthetic, and free of
  secrets and local data?
- Are collection and cursor shapes bounded, and can they only grow?
- Could any rename, tighter validation, removed error, changed concealment or
  new required input break an existing v1 client?
- Is every new request and response DTO registered in the DTO→schema
  registry?
- Did you regenerate the JSON artifact, browser types and API reference rather
  than patch them?

## Authorization and audit

- Does authentication establish proof without pretending to grant permission?
- Does the stable action make sense for the canonical resource?
- Is scope resolved from current authoritative relationships?
- Are Personal Access Token actions and subtree ceilings intersected with
  current roles?
- Are strong and recent assurance tested separately from permission?
- Are the allow, deny, stale-authority and cross-scope paths covered?
- Does a failed required audit stop the operation?
- Are audit values bounded, and free of credentials, content, answers and
  private rationale?
- Does a critical attempt reach one terminal outcome, or stay visible for
  reconciliation?

## Jobs and mail

- Is the work finite, and would losing the process really lose it?
- Does the descriptor pin down checkpointing, retry, timeout, concurrency,
  cancellation, visibility and retention?
- Is claim ownership fenced by token and lease?
- Does the handler stay idempotent under at-least-once execution?
- Does checkpointing follow durable domain progress?
- Can an incompatible node relinquish work without using up failed attempts?
- Does a business transaction that produces mail commit the occurrence, the
  encrypted delivery and the Job intent atomically?
- Is what the recipient receives frozen, is relevance checked again, and is
  the Message-ID stable?
- Are raw Job documents, recipients, copy and internal failures kept out of
  generic views?

## Files and Workspaces

- Does PostgreSQL hold the meaning, while VFS stores opaque bytes?
- Is this a File Revision, a Workspace Content Version or another existing
  model, rather than something forced into a generic file?
- Does byte staging that can fail happen before the atomic step that makes it
  visible?
- Can cleanup tell apart an invisible orphan, an unknown outcome, a kept
  reference and something eligible for purge?
- Do reads built for one purpose authorize the metadata before opening the
  bytes?
- Are there no public or signed storage URLs?
- Does an acknowledged Workspace change survive the loss of every transient
  view?
- Are paths, content and credentials kept out of logs and events?

## Realtime and cluster

- Is the event a minimal fact in the past tense, published after commit?
- Can the client rebuild the truth after a missed or duplicated event?
- Are connection queues, replay, payloads and fan-out bounded?
- Is the behavior for a slow consumer explicit?
- Does subscription authorization use current action and resource policy?
- Does replay on one node fall back to HTTP resynchronization after a gap or a
  change of node?
- Are events received from a peer stopped from being broadcast again?
- Is cluster delivery treated as a speed-up rather than the authority?
- Are compatibility, malformed input, handler panics and key rotation
  covered?

## Runtime and integration

- Is each value correctly classed as deployment configuration or application
  data?
- Is every secret redacted from display, errors, logs, metrics, audit and
  examples?
- Is reload atomic, or is a restart stated and tested?
- Does the root choose the concrete adapter exactly once?
- Is the lifecycle owner explicit, and is reverse shutdown bounded?
- Does external identity use the exact provider ID and an opaque subject?
- Does the CLI stay a thin caller of the root facade?
- Are stable machine fields the same in every locale?
- Are metric labels a closed, low-cardinality set?

## Before you finish

1. Read the final diff as a reviewer, not as its author.
2. Confirm that every behavior has one authority, with no stale duplicate.
3. Search for leaked secrets, credentials, student data, Exam answers, mail or
   file content, raw provider data and local paths.
4. Run focused tests first, and fix what they show before the broad gates.
5. Run every generator affected by a human-owned input.
6. Run the dependency-backed integration suite that applies.
7. Run:

~~~sh
make -C server architecture
make -C server check
git diff --check
~~~

8. Add `make docs-check` for public or API documentation, and the matching
   independent-module gate when you change a reusable package.
9. Report exactly what ran, what didn't, and any narrow TODO that remains.

The general [verification ladder](../testing.mdx) maps the remaining product
and CI gates.
