# Runtime and external integrations

Runtime code takes the configuration an operator owns, turns it into concrete
capabilities, and owns their lifecycle. Application code only sees small
policies and narrow ports. That boundary is what lets a one-node installation
and an active-active one behave the same way as a product while using
different adapters.

## Keep configuration apart from application data

Deployment configuration covers listeners, the public URL, PostgreSQL, the
cache, the cluster, VFS, SMTP, external providers, logging, metrics, secrets
and process limits. It is JSON the operator owns, plus explicit `PROCTOR_`
environment overrides.

Institution presentation, academic policy, Exam defaults, invitation behavior,
roles and the revisioned Access Policy are application data. They live in
PostgreSQL and change through authorized use cases.

Don't put deployment secrets in application tables, and don't turn
application settings into environment variables. Don't hand `config.Config`
or `config.Store` to a use case. The composition root turns configuration into
one of:

- a small immutable policy
- a narrow provider, for behavior that is explicitly dynamic
- a concrete adapter behind an interface the consumer owns

The active configuration file is required. Proctor never generates it or
quietly overwrites it. Unknown fields fail validation. Secret fields stay
redacted in display, logs, diagnostics and errors.

## Reload or restart

Make something reloadable only when its owner can check a complete
replacement and swap it in atomically, while callers already in flight keep a
consistent snapshot.

Only two things reload: logging (`Log`) and the external-provider registry
(`Authentication.External`). A reload applies their changes as one
transaction. If either consumer can't apply its change, the other is put back,
the running configuration stays in force, and the reload reports failure.

Every other changed setting keeps its running value until restart. That
includes listener addresses, TLS mode, trusted proxies, HSTS, rate limits,
body limits, the cluster backend and node identity. The reload warns and names
those settings. Don't claim a field is reloadable just because its Go struct
can be changed.

When you add configuration:

1. Add the typed field and its built-in default.
2. Add the field to the canonical example. If it is secret, show it with a
   visible empty value.
3. Add a stable environment override only when overriding a scalar makes
   sense.
4. Check the shape separately from external connectivity.
5. Redact it on purpose if it is sensitive.
6. State whether it reloads or needs a restart.
7. Add drift tests for the schema, default and example.

Structured host and provider entries stay in the file, so that identity,
endpoint, trust and credentials are reviewed together.

## Build external authentication as an adapter

The CAS and OIDC implementations live under `server/platform/externalauth`,
behind an application contract that doesn't depend on the protocol. The
composition root builds a registry for the instance from configuration, and
can replace the whole set of providers atomically.

The adapter owns the protocol mechanics:

- authorization or service URLs
- callback exchange and checks
- bounded network requests and responses
- checking the signature, issuer, audience, nonce, ticket or subject
- turning the response into a bounded, opaque provider result

The application owns:

- one-use login state and browser proof, backed by PostgreSQL
- the purpose of the flow: a Web Session, Desktop authorization, an
  Invitation or identity linking
- Access Policy admission
- identity by exact provider ID plus opaque subject
- provisioning or linking the User
- issuing the Session
- audit and safe public failures

Never link an existing User just because the provider's email or username
happens to match. Never store or log provider tokens, codes, tickets, raw
claims, subjects or response bodies. Changes to a provider profile don't
quietly rewrite Proctor fields that are already set.

CAS and OIDC are the provider families that exist today. SAML/RENATER, LDAP
and synchronizing with a provider directory are still product decisions.
Don't document or scaffold them as supported behavior.

## Keep CLI commands thin

The `proctor` command builds its Cobra tree under
`server/cmd/proctor/commands`. Commands reach the server in one of two ways:

- A command that needs the application, such as `serve` or administrator
  recovery, calls the module-root server facade.
- A command that only reads or migrates an installation (`config`, `migrate`,
  `jobs`, `cluster status`) calls `server/operator`. That opens the
  configuration and the database without building a node.

The command tree may parse flags, pick an explicit configuration path, show
safe output and decide how the process exits. It must not build PostgreSQL,
application services or platform adapters on its own.

For each command:

- Create fresh command state on every run.
- Keep secrets out of arguments, where they would show up in process
  listings.
- Read a secret the command needs from private standard input.
- Choose structured or human output on purpose.
- Keep command help as the exact, discoverable list of options.
- Reach application policy through the root facade, never by calling the
  Store.

An offline recovery command still uses named Store guarantees and audit. It
doesn't give you license to add a hidden network endpoint or a second normal
runtime.

## Add localization at the presentation edge

Stable machine values stay the same in every locale: error codes, HTTP
status, state, actions, resources and protocol fields. Human titles, details,
built-in role copy, mail copy, command copy and bounded WebSocket messages
come from the embedded localization catalogs.

Each transport picks a locale differently:

- HTTP negotiates from `Accept-Language`, then falls back to the Installation
  locale and then English.
- A WebSocket fixes its locale during the handshake.
- Mail freezes copy localized for the recipient before durable delivery.

Add the canonical English messages first. Keep IDs stable and meaningful.
Tests must prove placeholder signatures, fallback behavior and that catalogs
are complete. Never store translated text in durable machine-state fields
when the code or the meaning is the real contract.

The packages split the work:

- `server/i18n` and `server/templates` hold only data and build tooling.
- Translation behavior lives in `server/localization`.
- Mail rendering lives beside mail composition in `server/app/mail`.

Each server package registers every message it owns, including dynamic
families that a scan of source literals can't find. The browser owns the
delegated `webapp.*` namespace, and checks its own coverage while it generates
its typed catalog.

```sh
make -C server i18n-check              # server coverage and placeholder contracts
npm --prefix webapp run i18n:check     # browser ownership, from the repository root
```

From `server`, `go run ./cmd/ptool i18n` also offers `list`, `missing` and
`format`. Formatting writes files only when you ask it to. The normal check
never rewrites a catalog.

## Instrument at boundaries

Application services that handle requests return failures rather than log
them. An unexpected failure is logged once, at the outer boundary. Long-lived
workers get a narrow logger, only for events nobody could see otherwise.

Logging fields are bounded scalars. Don't log whole structs, configuration,
credentials, Sessions, provider payloads, mail or file content, Workspace
paths, Exam answers or raw claims.

Metrics use one private Prometheus registry, with a closed set of
low-cardinality labels. Instrument HTTP route templates, classes of Store
operation, adapter outcomes, queue state and other stable boundaries. Never
use a User, resource, node, host, path, recipient, cache key, payload or raw
error text as a label.

The optional metrics listener belongs to one node, and by default it binds to
loopback only. Exposing it beyond loopback needs static TLS and bearer
protection. It serves `GET /metrics` only, never profiling routes, and it
shares the server's owned lifecycle.

## Add an infrastructure adapter

Before you wire in a new adapter:

1. Find the existing contract the consumer owns.
2. Keep the choice of adapter in module-root `server.New`.
3. Check configuration and connectivity before readiness.
4. Hand lifecycle ownership to exactly one owner.
5. Sort failures into the narrow portable contract.
6. Provide a conformance suite when several adapters implement the behavior.
7. Report bounded health, without private configuration.
8. Close it in reverse order, under a deadline.

Don't create a platform getter so application code can find the adapter. If a
consumer needs only one operation, give it only that operation.

## Runtime checklist

- Is the input deployment configuration or durable application data?
- Is every secret redacted and kept out of diagnostics?
- Is reconfiguration atomic, or is a restart explicitly required?
- Does the application see only a policy or a narrow port?
- Does external authentication resolve identity only by provider ID and
  opaque subject?
- Is the CLI a thin caller of the root facade?
- Are localization and protocol values kept apart?
- Are logging and metrics bounded and low-cardinality?
- Does readiness fail when a required capability can't be used?
- Is shutdown ownership exact, and can it be undone after a partial startup?

Run the affected configuration, provider, localization, logging, metrics and
lifecycle tests. Then run the matching integration target and
`make -C server architecture`. When a local node won't start, use
[runtime and readiness troubleshooting](../troubleshooting/runtime-readiness.mdx).
