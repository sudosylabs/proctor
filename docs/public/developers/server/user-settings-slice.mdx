# Trace the User Settings slice

This tutorial reads one behavior that already exists from end to end:
replacing the signed-in User's exact User Settings Document. It makes a good
teaching example because it has real concurrency, privacy, idempotency, audit
and realtime requirements, without the extra lifecycle of an Exam or a file
upload.

The point isn't to copy its files for every feature. The point is to see how
one decision is carried across the boundaries that need it, and nowhere else.

## Say what the behavior is before reading code

The operation is:

~~~text
PUT /api/v1/users/me/settings
~~~

Here is what it must do:

- An interactive Session may replace only its own settings source, and only
  as a whole.
- The request sends the exact current revision and a required idempotency
  key.
- A stale revision can't overwrite a save made by another client.
- The committed change, a safe audit event and the replay outcome that is kept
  all happen atomically.
- Realtime sends one hint to refetch after commit, and never carries the
  source document.

That description already tells you which boundaries are involved:

| Concern | Boundary |
| --- | --- |
| Valid source, format, revision and timestamps | Domain model |
| Ownership by the Session only, JSONC policy, audit intent, what idempotency means, when effects run | Application |
| Atomic revision fence, audit and replay outcome | Store contract |
| Locking and the SQL transaction | PostgreSQL adapter |
| Strict JSON, body limit, Session and CSRF, DTOs, response cache policy | HTTP |
| Public fields, examples, errors and operation metadata | OpenAPI |
| The browser's compile-time contract | Generated TypeScript |
| Fast tests and tests backed by real dependencies | Tests |

## 1. Begin at the domain model

Read [server/model/user_settings.go](https://github.com/sudosylabs/Proctor/blob/main/server/model/user_settings.go).

`UserSettingsDocument` defines:

- one owning User ID
- the exact source, held so that generic JSON can't expose it by accident
- a positive format version
- an opaque revision token
- creation and update times
- hard limits on source size and structure

`NewUserSettingsDocument` produces the canonical initial source. `Validate`
checks that a stored document is valid on its own terms, including UTF-8,
source size, revision shape and the order of its timestamps. It doesn't parse
HTTP, identify the caller, authorize access or query PostgreSQL.

Run the model tests:

~~~sh
cd server
go test ./model -run '^Test(UserSettings|NewUserSettings)' -count=1
~~~

When you design another model, stop at this point until invalid state and
transitions are covered without any transport or persistence involved.

## 2. Read the application command

Read [server/app/user/settings.go](https://github.com/sudosylabs/Proctor/blob/main/server/app/user/settings.go).

The public command spells out its input:

~~~go
type ReplaceOwnUserSettingsCommand struct {
	Source           string
	FormatVersion    int
	ExpectedRevision model.UserSettingsRevision
	IdempotencyKey   string
}
~~~

There is no User ID from the caller. The application works out the owner from
the immutable Session principal. That is a deliberate self-service policy, not
a shortcut taken by HTTP.

Follow `ReplaceOwn` in order:

1. Require a valid interactive Session principal.
2. Require the idempotency key and a supported format.
3. Check the exact JSONC source against structural limits the application
   owns.
4. Read the caller's current document, and reject it if the stored state is
   invalid.
5. Derive a new opaque revision and an update time that only moves forward.
6. Prepare idempotency, by meaning, for `user_settings.replace`.
7. Prepare a safe audit event, but only when the expected revision matches and
   the content really changes.
8. Call the named Store replacement.
9. Map typed Store conflicts to stable application errors.
10. Publish one refetch event, and only for a new committed change.

The effect failure reporter records a bounded, transient diagnostic. It can't
change the committed result that is returned.

Run the focused application tests:

~~~sh
cd server
go test ./app -run '^TestUserSettings' -count=1
~~~

Read the test names as a checklist of the policy. They cover reading the exact
source, read-only formats that aren't supported, the Session requirement, safe
failures, the input to the atomic mutation, invalid source, mapping conflicts,
unknown outcomes, one hint after commit, suppressing effects on replay,
concurrent writers and effect failure.

## 3. Look at the narrow Store contract

Read the `UserSettingsStore` contract in
[server/store/user_settings.go](https://github.com/sudosylabs/Proctor/blob/main/server/store/user_settings.go).

The consumer needs two operations:

~~~go
type UserSettingsStore interface {
	Get(context.Context, model.UserID) (*model.UserSettingsDocument, error)
	Replace(
		context.Context,
		*UserSettingsReplacement,
		*CommandIdempotency,
	) (*UserSettingsReplacementResult, error)
}
~~~

`Replace` is not a generic CRUD update:

- Its command carries the expected and next revisions, the exact source, the
  format, the time and an optional prepared audit event.
- Its second input carries the bounded, authenticated command, by meaning.
- Its result says explicitly whether the outcome was a change or a replay.

With this contract the application can express its policy without knowing
about row locks, SQL statements or a transaction handle.

## 4. Follow the PostgreSQL transaction

Read [server/store/sqlstore/user_settings_store.go](https://github.com/sudosylabs/Proctor/blob/main/server/store/sqlstore/user_settings_store.go).

The adapter:

1. checks the complete replacement and idempotency command
2. enters the shared idempotent-mutation transaction
3. locks the User Settings row with `FOR UPDATE`
4. checks the current document it read back
5. compares the expected revision
6. returns a no-op outcome when the source and format already match
7. requires a valid prepared audit event for a real change
8. conditionally updates the exact row and revision
9. inserts the successful audit event
10. encodes the bounded, versioned replay outcome
11. commits or rolls back the whole result

The kept outcome leaves out the settings source. An identical retry can
return the committed revision without running the mutation or the effect
again. Reusing the same key for a different command, by meaning, is a
conflict.

The reusable Store conformance suite is in
[server/store/storetest/user_settings_store.go](https://github.com/sudosylabs/Proctor/blob/main/server/store/storetest/user_settings_store.go).
The SQL adapter runs it inside the PostgreSQL integration suite. That is where
real locking, concurrent writers and outcomes at persistence time are proved.

## 5. Read the HTTP resource

Read [server/httpapi/user_settings.go](https://github.com/sudosylabs/Proctor/blob/main/server/httpapi/user_settings.go).

The resource has separate request and response DTOs. The replacement route:

- is a `PUT` on the single literal self path
- requires a Session
- adds cookie CSRF through the Session mutation class
- requires `Idempotency-Key`
- applies a hard body limit before decoding
- declares its full allowlist of public errors
- returns `Cache-Control: private, no-store`

The handler strictly decodes one JSON value, parses the opaque revision, maps
it to the application command, and maps the safe result back. It doesn't parse
JSONC itself, read the Store, authorize another User, write audit or publish
realtime.

Run the transport and agreement tests:

~~~sh
cd server
go test ./httpapi -run '^TestUserSettings' -count=1
~~~

The tests prove strict handling of the body and fields, handling of the
maximum source size, the Session and path restrictions, private caching, that
the source isn't echoed back after replacement, and that the runtime and
OpenAPI agree.

## 6. Read the human-owned OpenAPI

Read [server/openapi/fragments/users/users-settings.yaml](https://github.com/sudosylabs/Proctor/blob/main/server/openapi/fragments/users/users-settings.yaml).

The YAML owns the public path, summaries, behavior, security, Proctor's
authentication, idempotency and error metadata, the purpose of the request
body, the schemas, the response cache header and a synthetic example. It does
not dictate the domain model or the SQL table.

If the public shape changes, edit this YAML and run:

~~~sh
make -C server openapi-build
make -C server openapi-check
make -C server openapi-agreement
~~~

Review the diff of the generated `server/openapi.json`. Don't edit it.

## 7. Regenerate the browser consumer

The hosted webapp uses the reviewed OpenAPI artifact through generated types
in `webapp/src/api/generated/schema.ts`. It gets typed
`UserSettingsReplaceRequest`, `UserSettingsResponse` and
`UserSettingsReplacementResponse` shapes without importing any Go DTOs.

After you change an OpenAPI schema:

~~~sh
cd webapp
npm run api:generate
npm run api:check
~~~

Don't patch the generated TypeScript to make up for missing OpenAPI fields.
Fix the source contract instead.

## 8. Prove the whole slice

While you implement, run the focused model, application and HTTP commands
above. Then run:

~~~sh
make -C server openapi-agreement
make -C server architecture
make -C server check
~~~

When PostgreSQL is available, add the tests for the real transaction and
composition:

~~~sh
make -C server integration-postgres
~~~

For a change to public documentation or the API reference, finish with:

~~~sh
make docs-check
~~~

## Use the pattern without copying it

For another feature, ask which of these boundaries it really needs:

- A pure domain transition may need no route, SQL or realtime event.
- A read may need current authorization, but no audit or idempotency.
- A mutation across models may need a larger named aggregate operation.
- Follow-up work that must survive the process dying may add a Job.
- Communication that must happen may add mail intent in the same commit.
- File content may add a staged VFS operation and a cleanup safety window.

The rule is not "every feature has these files". The rule is that every owner
the feature needs takes part, no owner is duplicated, and the widest test that
applies proves the assembled behavior.
