# Test and check your changes

Run checks from cheapest to most expensive. The narrowest test should explain
a failure close to where it happens. The widest check that applies should show
that your finished change still works with the rest of the product.

To compare the root product checks with the module targets, or to see what a
command changes, use the [Make command reference](./make-commands.mdx).

## The verification ladder

### 0. Repository standards

Before you try to make sense of a module failure, check formatting and static
analysis:

```sh
make quality
```

Run `make vulncheck` when Go source or dependencies change. It queries the
current vulnerability database, so it's kept apart from the product check,
which doesn't depend on anything outside the checkout. See
[tooling and debugging](./tooling-and-debugging.mdx) for which tool checks
what, and for commands to debug a single test.

### 1. The behavior you're changing

While you work, run the exact package and test:

```sh
cd server
go test ./app -run '^TestExactBehavior$' -count=1
```

Add `-race` when concurrency or shared state is involved. Keep isolated pure
tests off the network, and run them in parallel where it's safe.

### 2. The package or module you changed

| Area | Full local check |
| --- | --- |
| Server | `make -C server check` |
| Webapp | `npm --prefix webapp run check` |
| Cache | `make -C packages/cache check` |
| Mail | `make -C packages/mail check` |
| VFS | `GOWORK=off go test -race ./...` and `GOWORK=off go vet ./...` from `packages/vfs` |
| Documentation | `make docs-check` |

### 3. Behavior that needs real dependencies

| What it tests | Command |
| --- | --- |
| Every tagged server integration test | `make -C server integration-all` |
| PostgreSQL Store, migrations and application behavior | `make -C server integration-postgres` |
| Redis cache conformance | `make -C server integration-redis` |
| S3-compatible VFS and server file content | `make -C server integration-s3` |
| CAS and OIDC application integration | `make -C server integration-providers` |
| WebSocket and two-node Memberlist behavior | `make -C server integration-realtime` |

These targets start pinned dependencies, wait until they're healthy, and
remove them after the tests. If a service the test needs isn't available, the
test fails. It never quietly reports success.

Server integration tests carry the `integration` build tag. That keeps the
default `test`, `test-race` and `check` targets self-contained: they don't
need PostgreSQL, Redis, SMTP or S3. Tests that only use a local `httptest`
server stay in the default suite.

`integration-postgres` finds every `integration`-tagged test in the
module-root, `app`, `cmd/proctor/commands` and `store/sqlstore` packages, so a
new PostgreSQL test doesn't need a Makefile change. It only skips the
WebSocket and Mailpit tests, which belong to `integration-realtime` and
`phase-transactional-mail`. The S3 variants skip themselves unless `VFS_S3_*`
is set. The SQL package also runs the Store conformance suites through the
local cache layer, which is why these targets allow a long timeout per
package. Each operation and fixture still has its own deadline, which limits
each test. `conformance-postgres` and `conformance-realtime` still work as
aliases of `integration-postgres` and `integration-realtime`.

The checked-in PostgreSQL service keeps its database on a temporary
filesystem. Recreate it to get an empty database at the current baseline:

```sh
make -C server postgres-down
make -C server postgres-up
```

To inspect SMTP without the root development stack, start the same pinned
Mailpit with `make -C server mailpit-up`, and use `mailpit-logs` and
`mailpit-down` to follow and stop it. It listens for SMTP on `127.0.0.1:11025`
and for HTTP on `http://127.0.0.1:18025`.

Three server phase checks combine suites for one area. Maintainers and CI use
them to sign off a phase:

| Check | What it combines |
| --- | --- |
| `make -C server phase-file-jobs` | The self-contained server check, PostgreSQL integration including clustered recovery, shared-object VFS integration, and `GOWORK=off` builds and tests of all four modules. |
| `make -C server phase-access-onboarding` | The self-contained check plus the real composition graph, administration backed by PostgreSQL, multi-node protocol and recovery scenarios, decorated Store conformance, lock-order regression tests and the migration round trip. It covers the server protocol and domain, not hosted pages or the Desktop UI. |
| `make -C server phase-transactional-mail` | The self-contained check, PostgreSQL integration, independent module builds and tests, template freshness and rendering, SMTP sender conformance, and a flow from the application through Mailpit. |

The server module pins published revisions of the shared modules. That way a
`GOWORK=off` check can't quietly pick up newer APIs through `go.work`. Those
versions must be published before the server module is distributed outside
this repository. While the repository is private, Git must be signed in to
`github.com`. The server Makefile exports the matching `GOPRIVATE` pattern, so
Go skips the public module proxy and checksum database for these
dependencies.

### 4. Browser journeys against a real server

```sh
make e2e
```

The end-to-end suite drives Chromium against one real `proctor serve` node.
It covers first-run setup, local sign-in and sign-out, MFA enrollment and its
sign-in challenge, a password reset by mail, and an Invitation by mail. The
target:

1. builds the webapp and server
2. starts throwaway PostgreSQL and Mailpit from `server/compose.yaml`
3. generates a loopback configuration and secrets under `.build/e2e/run`
4. waits for readiness
5. runs `webapp/tests/e2e`
6. tears everything down, even when a test fails

No API route is mocked. To pass arguments to Playwright, use `E2E_ARGS`, for
example `make e2e E2E_ARGS='--grep MFA'`. Install the pinned browser once with
`npx --prefix webapp playwright install chromium`.

When a test fails, the trace, screenshot and HTML report stay in
`.build/e2e/run/report`. Open a trace with
`npx --prefix webapp playwright show-trace <trace.zip>`. CI runs this check
after the self-contained job, and on failure it uploads the same files plus
the server log.

### 5. Checks across modules and the whole product

```sh
make independent-modules
make check
```

`independent-modules` runs test, race, vet and build with `GOWORK=off` for all
four Go modules. The root `check` covers the build scripts, the webapp, the
documentation, transactional-mail template freshness and the self-contained
server check. The template check needs Node, so it lives in the root check
rather than in `make -C server check`, which doesn't need Node.

When your change calls for packaging and every suite that needs real
dependencies, run the full CI check:

```sh
make ci
```

`make ci` also builds and checks a release-style package. The release output
directory must not exist yet. The packaging targets refuse to reuse a
directory, because it might hold operator configuration.

## Match tests to risk

| Change | The least extra evidence you need |
| --- | --- |
| Domain constructor or transition | Table-driven tests of invariants and transitions |
| Application authorization or audit | Allow, deny, concealment, stale authority, and behavior when audit fails |
| Named Store operation | Shared conformance plus a PostgreSQL race or integration test |
| Cache, mail, VFS or cluster adapter | Shared conformance and correct classification of failures |
| HTTP resource | DTO, credential, assurance, Problem Details, result ordering and OpenAPI agreement |
| WebSocket behavior | Authentication, subscription authorization, replay and resync, limits, and backpressure |
| Job behavior | Claim, lease, checkpoint, retry, cancellation, process loss and retention |
| Webapp interaction | Unit tests of state plus browser behavior in Chromium, Firefox and WebKit |
| Hosted access journey or the server contract behind it | A `make e2e` journey that checks both the page and the server state |
| How documentation looks | Generator checks, the production build, and a browser review on desktop and mobile, in light and dark |

## Diagnose a cluster failure

The three-node development check is separate from the ordinary unit and
integration tests:

```sh
make cluster-smoke
```

If it fails, print the container state and recent logs:

```sh
make cluster-diagnostics
```

The smoke target checks readiness, metrics, peer discovery, build identity and
traffic through the gateway. It also stops one node, checks that the cluster
recovers, and then brings the node back.

## Keep tests trustworthy

- Test behavior you can observe, not how many times something was called.
- Use small handwritten fakes for application ports that the consumer owns.
- Test exported contracts from an external test package. Save same-package
  tests for unexported details that matter.
- Make concurrency deterministic with synchronization, not sleeps.
- Keep fixtures synthetic and small.
- Never put credentials, student data, Exam answers, mail bodies, Workspace
  content or operational identifiers in failure output.
- Don't weaken a conformance suite to suit one adapter. Fix the adapter, or
  make the capability explicitly optional.

## Before you hand off

1. Run `git diff --check`.
2. Run `make quality` if you changed Go code.
3. Look over generated output and make sure it came from the tracked source.
4. Check the diff for secrets, local paths, snapshots and unrelated changes.
5. Run the highest check above that applies to your change.
6. Report exactly what passed, and any check needing real dependencies that
   you didn't run.

The record of what passed lives in CI and release artifacts for the exact
commit being built. Generated OpenAPI is tracked in the repository, but raw
test logs, screenshots and hand-copied status tables are not kept there as a
second record.
