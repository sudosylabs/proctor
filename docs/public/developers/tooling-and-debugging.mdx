# Tooling and debugging

The repository, not your editor, decides how Proctor is built, checked and
debugged. Every editor uses the same pinned binaries, Make targets, generated
local state, ports and quality settings. So you can switch editors without
changing what counts as formatted, lint-clean, vulnerable or debuggable.

## Install the development environment

After you install the host tools listed in [local setup](./local-setup.mdx),
run:

```sh
make bootstrap
make tools-check
```

`bootstrap` checks Go, Node, Docker and the shell utilities you need. It then
installs the exact Go developer binaries into the ignored `.build/bin`
directory, and installs the locked webapp and documentation dependencies. You
can run it again safely. Go's build cache and npm's download cache cut down on
repeated work, and the npm lockfiles make every clean install the same. The
repository's install targets always include development dependencies, even if
your shell sets npm to install production dependencies only.

The tool manifests `build/tools/go.mod` and `build/tools/gopls/go.mod` set the
versions of the external Go tools. `gopls` has its own manifest because its
newest release that works with Go 1.26 needs a different revision of
`golang.org/x/tools` from the pinned linter. The profile and trace viewers are
built from the standard Go command sources, using the exact Go toolchain that
`go.work` selects. All of these binaries go into the same `.build/bin`
directory.

If only the Go binaries are missing, run `make tools`. Don't install your own
unversioned `golangci-lint`, `gopls`, `govulncheck`, `goimports` or `dlv` and
assume it matches CI.

## Shared standards

The repository splits up settings that editors often lump together:

| What | Set by |
| --- | --- |
| Encoding, line endings, indentation, final newline | `.editorconfig` and `.gitattributes` |
| Go syntax and import grouping | `gofmt`, pinned `goimports`, and `.golangci.yml` |
| Go static analysis, including `gosec` | pinned `golangci-lint` and `.golangci.yml` |
| Known Go vulnerabilities your code can reach | pinned `govulncheck` against the current public database |
| Which Go workspace to use | root `go.work`, passed to repository and editor tools through their environment |
| Go language features in the editor | pinned `gopls` |
| Go debugging | pinned Delve |
| Go profile and trace viewing | viewers built from the pinned Go toolchain |

Run the check that matches your work:

```sh
make fmt          # change versioned and unignored Go files in place
make fmt-check    # read-only formatting gate
make lint-config  # validate the linter configuration
make lint         # new findings across all four product modules
make lint-full    # complete legacy and new finding backlog
make vulncheck    # live vulnerability database
make quality      # fmt-check plus lint
make security     # lint plus vulnerability scan
make precommit    # build-script tests plus quality
```

The first scan of the whole repository found a large backlog of existing
analyzer findings. So `lint` and the CI targets run golangci-lint in new-issue
mode: changed Go lines can't add findings, and `lint-full` keeps the old
backlog visible for when you set out to clean it up. No existing finding is
hidden with a source annotation. The module checks still run tests, race
detection and `go vet`. Linting adds to those checks. It doesn't replace them.
When you change the linter configuration, a tool pin or a Go dependency
manifest, the configured analyzers also run against every product module,
without failing on the existing backlog.

Locally, `lint` compares your whole feature branch with its merge base on the
checkout's tracked default branch, so findings from your earlier commits on
the branch still count. CI passes the exact pull request or push base in
`LINT_BASE_REV`. Set that variable yourself only when your checkout has no
`origin` default branch it can find and no local `main` branch.

`govulncheck` runs in its own CI workflow, on a schedule and when dependencies
change. Its database changes independently of the source, so the result isn't
reproducible from the checkout alone. Each product module is scanned with
`GOWORK=off`, so the workspace's version choices can't hide a vulnerability in
a module's own dependency graph. The same workflow audits the webapp's
production npm dependencies from its lockfile and fails on a moderate or
higher advisory, because those packages ship to every browser.

## Debug the server without an IDE

For an interactive Delve terminal:

```sh
make debug-server
```

This target installs the pinned debugger, builds the webapp, generates local
configuration and secrets, and starts the dependencies, waiting until they're
healthy. It then sets the same environment as `make run-server` and launches
the real `server/cmd/proctor` entry point. Your breakpoints run against the
supported single-node setup, not a cut-down mock. The debug build stamps the
webapp with the server's default debugger identity, `dev/unknown`. That way
the server's build-integrity check stays on and passes without the optimized
release linker flags.

Delve pauses the process at breakpoints, so requests may time out while the
server is stopped. That's expected. Stop the debugger with
<kbd>Control</kbd>+<kbd>C</kbd>. The dependency containers keep running until
you run `make dev-down`. The repository's launchers put temporary Delve
executables in the ignored `.build/dev/diagnostics` directory, even when a
session is interrupted.

## VS Code

Look over the checkout, open the repository root, give VS Code the usual
workspace trust, and accept the recommended extensions. Then run
`make bootstrap` once, and use **Go: Locate Configured Go Tools** to check that
`gopls` and `dlv` come from `.build/bin`.

Choose a configuration in **Run and Debug**:

- **Proctor server (repository DAP)** starts the repository's DAP task on
  `127.0.0.1:2345`, prepares the whole local stack and launches the server.
- **Selected Go test** and **Go tests in current package** use the pinned
  Delve binary set in the workspace settings.
- **Hosted webapp (Chrome)** attaches the JavaScript debugger to a running
  server on port 8065, built the way production builds it.
- **Vite webapp (Chrome)** starts Vite and opens the hot-reload address on
  port 5173.

The Vite browser configuration expects the API server to be running already.
For a flow that depends on the public address, start that server with
`PROCTOR_SERVER_PUBLIC_URL=http://127.0.0.1:5173`, as described in
[local setup](./local-setup.mdx).

The workspace settings turn off automatic Go tool updates, point the Go
extension at `.build/bin/gopls` and `.build/bin/dlv`, and give Go processes
started by the editor the exact toolchain and workspace declared in `go.work`.
Format on save is just a convenience. `make fmt-check` is what reviewers go
by.

The tracked tasks run repository code, and the debugger can run the program
you choose. If you stop trusting the checkout later, revoke VS Code's
workspace trust.

## GoLand

GoLand has its own code intelligence, so it doesn't need `gopls` for
navigation. Set the project SDK to the Go version declared in the root
`go.work`, then open the repository root so GoLand's Go workspace support
finds the workspace and all four product modules. For formatting, linting,
tests and vulnerability checks, run the root Make targets as external tools or
run configurations. Don't copy them into IDE inspection settings.

To debug the server:

1. Run `make debug-server-headless` in a terminal.
2. In **Run | Edit Configurations**, add a **Go Remote** configuration.
3. Set the host to `127.0.0.1` and the port to `2346`. The Make target chooses
   Delve's API v2, because GoLand's Go Remote configuration has no field
   for it.
4. Start the Go Remote configuration and set breakpoints in the checkout.

The Make target launches the real server and sets its environment. The GoLand
configuration only attaches to it. Don't change the listener to `0.0.0.0` or
expose it through a tunnel.

## Neovim

The tracked example `contrib/editors/neovim/proctor.lua` is for Neovim 0.11+
and `nvim-dap`. Copy the parts you need into your own configuration after
reading them, then run:

```sh
make tools
make debug-server-dap
```

The example starts the pinned `gopls` for the workspace and attaches
`nvim-dap` to `127.0.0.1:2345`. It doesn't turn on automatic loading of Lua
from the repository, on purpose: a freshly cloned repository must not run
editor configuration before you've read it.

## Debug and measure a single test

The diagnostic targets need exactly one package, given relative to the module.
They reject recursive `...` patterns so that each output file always comes
from one test binary. For example:

```sh
make debug-test \
  DEBUG_MODULE=server \
  DEBUG_PACKAGE=./app \
  DEBUG_TEST='^TestExactBehavior$$'

make profile-test \
  DEBUG_MODULE=server \
  DEBUG_PACKAGE=./app \
  DEBUG_TEST='^TestExactBehavior$$' \
  DEBUG_PROFILE=cpu

make profile-open DEBUG_PROFILE=cpu

make trace-test \
  DEBUG_MODULE=server \
  DEBUG_PACKAGE=./app \
  DEBUG_TEST='^TestExactBehavior$$'

make trace-open
```

Profiles can be `cpu`, `memory`, `mutex` or `block`. Generated profiles, kept
test binaries and traces all stay in the ignored `.build/dev/diagnostics`
directory. They can contain code paths, labels and test data, so review and
redact them before you share them.

Proctor doesn't expose Go `pprof` on the production metrics listener.
Profiling a running server would need its own design, with authentication and
limits. For now, the repository supports profiles and traces of single tests
on your machine instead.

## Keep debug listeners local

Both debugger servers listen on loopback only, by design. Delve gives
control over a process and can run code with that process's permissions. It
isn't an authenticated remote administration service. Never publish ports
2345 or 2346, put them behind a shared ingress, or attach them to a
production process.

If you need to run two checkouts at the same time, change the local ports with
`PROCTOR_DAP_PORT` and `PROCTOR_DLV_PORT`. Point your own editor attachment at
the same value. Don't edit the tracked launch files for a preference that only
applies to your machine.
