# Browser application

Proctor has two ways to run the webapp in a browser, on purpose.
`make run-server` serves the compiled webapp, set up as it is in production.
`make run-webapp` runs Vite with hot module replacement and passes API and
WebSocket traffic through to Proctor. Work out which one is failing before you
compare how they behave.

## Work out which mode you're in

| What to look at | Hosted build | Vite |
| --- | --- | --- |
| Browser URL | The server's public URL, usually port `8065` | The Vite URL, usually port `5173` |
| Where files come from | `webapp/dist` | The Vite development server |
| Build identity | `webapp/dist/webapp-build.json` must match | A development bundle |
| API and WebSocket | Served from the same Proctor origin | Passed through to `PROCTOR_SERVER_DEV_URL` |

If the hosted sign-in route fails, start with:

```sh
make webapp-build
make dev-doctor
```

Don't delete `webapp/dist` first. If the server refuses files that are out of
date or don't match, the build identity in that folder tells you why.

## Read the browser's network record

For one interaction that fails, write down:

- The page's origin and the request URL.
- The method, status, Problem Details `code` and request ID.
- Whether the request used a cookie or a bearer token.
- Whether a cookie request that changes data sent the CSRF header.
- Whether the response was HTML, JSON, a redirect or a static file.

Never copy credential values, cookies, authorization headers, CSRF tokens,
private response bodies, exam answers or student data. Use made-up test data
where you can, and a screenshot cropped and redacted to show only the part
that matters.

If an API call or WebSocket works when you call it directly but fails through
Vite, compare the origin the browser shows, the configured public URL, and
`PROCTOR_SERVER_DEV_URL`. Fix those values together, as one decision about
the origin. Don't turn off Origin or CSRF checks.

## Find out-of-date generated code

Generated adapters can still compile after their source has changed. Run the
checks for the area you're working on:

```sh
make -C server openapi-check
cd webapp
npm run api:check
npm run i18n:check
npm run routes:check
npm run check:design-system
```

When a check reports a difference, change the source file and run the
repository's generator for it. Don't edit a generated adapter by hand to make
the check pass. The [webapp workflow](../webapp-workflow.mdx) shows which
generator belongs to each source.

## Narrow down browser test failures

If Playwright says the browser engines are missing, install the ones the
repository uses:

```sh
cd webapp
npx playwright install chromium firefox webkit
```

Reproduce the failure in one browser before you run them all:

```sh
npm run test:browser -- --project=chromium
npm run test:browser -- --project=firefox
npm run test:browser -- --project=webkit
```

If only one browser fails, the cause is a difference in compatibility, timing,
focus or platform behavior. Don't add an arbitrary delay. First find the
condition the test should wait for. Select elements by accessible role and
check results the user would see, not implementation details.

Playwright keeps a trace when a test fails, in test output that Git ignores. A
trace can contain full URLs, page text, request details and screenshots.
Review it on your machine and redact it before you share it. Never commit
traces or screenshots taken from an environment with real data.

## Debugging tools in the repository

Use the browser's developer tools and Playwright traces to look at browser
state. If you use VS Code, the repository includes Chrome launch
configurations for the hosted webapp and for Vite. When you need to follow a
request into Go code, use the repository's Delve targets. The full recipes for
VS Code, GoLand, Neovim, the CLI, profiling and traces are in
[tooling and debugging](../tooling-and-debugging.mdx).

## Confirm the fix

Repeat the small interaction in the mode that failed. Then run:

```sh
cd webapp
npm run check
```

For a problem with the hosted build, rebuild it and check the route on the
server running in the foreground. For a problem with browser behavior, run
the full set of Chromium, Firefox and WebKit tests.
