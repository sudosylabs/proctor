# Cluster failures

One Proctor installation can run several identical application nodes, but
they still share one PostgreSQL database as the source of truth. Work out
whether the problem is in gateway routing, a node serving, peers finding each
other, or the messages nodes send after a commit. Don't mistake a missed
cluster message for a lost database commit.

## Capture the state of the cluster

```sh
make cluster-diagnostics
```

This prints the Compose state and the end of the logs for the gateway, the
three Proctor nodes, Prometheus, and the OpenTelemetry Collector. Keep the
first error from a specific node. Don't swap it for one long combined log.

Then check each layer in turn:

1. Gateway readiness and the public cluster port.
2. Liveness and readiness for each node.
3. That each node has a stable identity and a compatible cluster protocol.
4. Member discovery, the advertised address, and that all nodes share the same
   encryption key.
5. Prometheus target health for every node you expect.

[Cluster development](../cluster-development.mdx) lists the exact local ports,
node names and expected layout.

## Common symptoms

| Symptom | Likely cause | What to look at |
| --- | --- | --- |
| The gateway is down but the nodes are ready | The gateway container or its routing configuration | Gateway status and the end of its log |
| One node is live but not ready | Something that node needs before it can serve | The node's readiness and its first startup error |
| Nodes serve HTTP but report too few peers | Member discovery, the advertised address, the protocol or the key | Membership state and cluster metrics |
| Requests work on only one node | Gateway routing, or state or configuration specific to one node | Which node answers each time, and each node's response |
| Data read from the database is right but a live view is out of date | Cluster or WebSocket messages sent after the commit | The HTTP result, the message delivery metric, and the client's resync |
| Prometheus is missing one node | Generated scrape targets, TLS, or the metrics listener | Target status and the node's metrics health |
| Work pauses after a node goes down | Job lease recovery, or a node not being allowed to serve | Job attempts, lease expiry, and readiness of the remaining nodes |

## Keep PostgreSQL as the source of truth

Nodes share PostgreSQL and the managed content configuration. Redis,
membership messages, cache invalidations and WebSocket fan-out can all be
rebuilt, or are sent on a best-effort basis. After a failure where you can't
tell what happened, read the real state over HTTP before you retry a change.

Don't fix membership by changing PostgreSQL rows, turning off the check that
lets a node serve, giving two nodes the same identity, or loosening protocol
or key checks. Those protections stop a node with incompatible or incomplete
state from taking traffic.

## Test losing one node

The repository's smoke test checks three-node readiness, metrics and load
balancing, and that the installation recovers while one node is stopped:

```sh
make cluster-smoke
```

The target stops and restarts a node itself, in a controlled way. Don't kill a
random node by hand while another test or development session uses the same
Compose project.

If the smoke test fails, keep its first error and run
`make cluster-diagnostics` straight away, before you take the cluster down.
Investigate the stage that failed instead of running the whole smoke test
again until it passes.

## Confirm the fix

First repeat the smallest check on the node, gateway or membership. Then run
`make cluster-smoke` from a known starting point. Confirm that:

- Every node you expect becomes ready.
- The gateway spreads requests across the healthy nodes.
- Metrics identify each serving node.
- The installation stays available when one node is lost.
- The restored node rejoins without changing what PostgreSQL holds.
