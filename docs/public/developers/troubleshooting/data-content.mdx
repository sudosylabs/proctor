# Data and managed content

From the outside, three different things can all look like "data" in Proctor:

- PostgreSQL is the source of truth for lasting application state and for the
  details about managed files.
- Redis holds cache state that is disposable and can be rebuilt.
- The VFS stores the bytes of managed files. Locally, the S3-compatible adapter
  uses MinIO.

Work out which of the three is wrong before you clear or repair anything.

## Start by asking which one owns it

| Symptom | Check | Don't assume |
| --- | --- | --- |
| A User, Exam, Job, Session or authorization record is missing | PostgreSQL | That Redis can bring it back |
| A value stays out of date after a saved change | The PostgreSQL result, then Redis invalidation | That the cache is the source of truth |
| A file's metadata exists but its content can't be read | PostgreSQL metadata and the VFS bytes | That deleting the metadata fixes the object |
| An object exists in MinIO but no File shows for it | The PostgreSQL workflow and cleanup state | That every stored object is content Proctor can publish |
| Startup fails while applying schema changes | PostgreSQL migration state | That resetting the browser or cache can help |

## PostgreSQL: confirm what is saved

Check the container and the end of its logs first:

```sh
docker compose -f build/compose/dependencies.yaml ps postgres
docker compose -f build/compose/dependencies.yaml \
  logs --no-color --tail=100 postgres
```

Then run the focused store test, or the PostgreSQL integration suite, for the
model that owns the behavior:

```sh
make -C server integration-postgres
```

Use application and Store contract tests rather than one-off SQL updates.
Changing rows by hand skips revision fences, named aggregate transactions,
stored audit records, idempotent outcomes, and the order of effects after a
commit. It often turns a bug you can reproduce into a new one.

If a migration fails, keep the first error from the server and from
PostgreSQL. An old pre-release development database may need to be recreated,
on purpose, against a new baseline. Read
[Runtime and readiness](./runtime-readiness.mdx) before you delete it.

## Redis: the cache can be rebuilt

Check that the service is reachable:

```sh
docker compose -f build/compose/dependencies.yaml ps redis
docker compose -f build/compose/dependencies.yaml \
  logs --no-color --tail=100 redis
docker compose -f build/compose/dependencies.yaml \
  exec redis redis-cli ping
```

If PostgreSQL has the right saved state but a read is still out of date, test
cache invalidation or revision behavior at the Store boundary. The portable
cache conformance tests and the server's Redis integration tests are the right
way to prove it:

```sh
make -C server integration-redis
```

Clearing a local Redis database removes disposable state. Do it only once the
evidence shows the bug is in the cache. Never present it as a fix for state
missing from PostgreSQL.

## VFS and MinIO: match metadata to bytes

Check the local object service without listing or exposing what the objects
contain:

```sh
curl --fail --silent --show-error http://127.0.0.1:19000/minio/health/live
docker compose -f build/compose/dependencies.yaml \
  logs --no-color --tail=100 minio
make -C server integration-s3
```

The VFS adapter handles reading and writing bytes. PostgreSQL holds the File
record, its scope, status, retention policy, authorization context, and links
to other records. Uploading an object successfully doesn't make the bytes a
valid managed File on its own.

When the metadata and the bytes disagree:

1. Note the test File's ID and the operation that created it.
2. Work out whether the failure happened before or after the PostgreSQL
   commit.
3. Look at the outcome of the command, the cleanup, or the rendition workflow
   involved.
4. Reproduce it through the application service that owns it, and with a
   focused Store or VFS test.

Don't fix it by copying an object by hand, making up a row, or making a
private object public. Doing so skips authorization, retention, integrity and
audit protections.

## Protect privacy while you look at files

Use made-up content. Share IDs, status names, byte counts, media types and
checksums only when they aren't sensitive and you need them. Don't attach
student uploads, exam resources, answers, rendition bytes, object keys, signed
URLs, local storage paths or raw database exports.

## Confirm the fix

Run the focused conformance or integration suite for the adapter that failed.
Then repeat the operation the user saw, through the application. Confirm that
PostgreSQL commits before any cache invalidation, cleanup or other temporary
effect, and that retrying the exact same request gives the documented
idempotent outcome.
