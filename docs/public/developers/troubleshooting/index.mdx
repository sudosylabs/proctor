# Troubleshooting development problems

A good diagnosis names the first part of the system that goes wrong. It doesn't
start with a reset. Keep the evidence, narrow the failure down to one area,
and only then change anything.

## The first five minutes

From the repository root, run the local check. It only reads:

```sh
make dev-doctor
```

The command checks the tools you need, Docker, the containers it expects,
generated development state, the services Proctor depends on, server health,
and the hosted sign-in route. It prints a fixed set of pass or error labels.
It doesn't start or stop services, read secrets, look at application records,
or print response bodies.

Then work through these steps in order:

1. Keep the first error. Later failures are often caused by it.
2. Reproduce it with the smallest command or request that still fails.
3. Pick the guide for the part of the system that owns that error.
4. Make one recovery change that you can undo.
5. Run the small reproduction again, then the checks or tests for that area.

## Where to start for each symptom

| What you see | Check first | Then read |
| --- | --- | --- |
| A command you need is missing or has the wrong version | `make dev-tools` | [Runtime and readiness](./runtime-readiness.mdx) |
| Docker isn't running, a container is missing, or a service is unhealthy | `make dev-doctor` | [Runtime and readiness](./runtime-readiness.mdx) |
| The server starts but never becomes ready | `/health/live`, then `/health/ready` | [Runtime and readiness](./runtime-readiness.mdx) |
| A port can't bind, or the browser reaches a different process | Which process owns that exact port | [Runtime and readiness](./runtime-readiness.mdx) |
| An API request returns a Problem Details response | `status`, `code` and `request_id` | [HTTP access and authorization](./http-access.mdx) |
| Sign-in works but a browser request that changes data fails | The cookie, the CSRF header and the exact Origin | [HTTP access and authorization](./http-access.mdx) |
| A row, cache entry or stored file looks wrong | Whether PostgreSQL, Redis or the VFS owns it | [Data and managed content](./data-content.mdx) |
| An action was saved but no message went out | Mail Delivery state, Job state, then SMTP | [Transactional mail](./mail.mdx) |
| Work is queued, retried, stuck or done twice | Job and Job Attempt history | [Jobs and realtime](./jobs-realtime.mdx) |
| Live updates stop, or arrive with a gap in the sequence | The WebSocket close, the replay result, then HTTP state | [Jobs and realtime](./jobs-realtime.mdx) |
| Vite and the hosted build behave differently | Build identity, proxy target and the browser's network trace | [Browser application](./browser.mdx) |
| One cluster node disappears, or results differ between nodes | Cluster diagnostics and each node's readiness | [Cluster failures](./cluster.mdx) |

## Write a minimal reproduction

Write the reproduction so that another developer can run it without guessing:

```text
Starting state:
Command or request:
Expected result:
Actual result:
First failing boundary:
Relevant commit:
Environment versions:
Verification after recovery:
```

A focused test, one HTTP request or one UI action is better than a long manual
walkthrough. If the failure crosses layers, test each step on its own: client
to HTTP, HTTP to the use case that owns the work, the use case to PostgreSQL,
and only then whatever happens after the commit.

## Collect evidence safely

Good evidence is small and easy to match up with other records:

- The exact command that failed, and its first error.
- The HTTP status, the stable Problem Details `code`, and the `request_id`.
- The shortest useful end of the structured logs.
- Job, Mail Delivery or Attempt IDs, and the names of their states.
- The Git commit, and the Go, Node.js, npm, Docker and Compose versions.
- What you expected, written separately from what you saw.

Don't attach credentials, cookies, authorization or CSRF headers, invitation
claims, generated secrets, configuration files, environment dumps, message
bodies, email addresses, student data, exam content or answers, workspace
content, private reasons for authorization decisions, or whole logs. A request
ID is usually enough to match an HTTP response to the server's record.

## Recover with care

Choose the least destructive fix for the part you've shown is broken.
Restarting a disposable service that died may be the right call. Clearing
Redis can be fine, because Proctor can rebuild it. Deleting PostgreSQL or VFS
data is a different decision, because they hold the real records and the
stored files.

`make dev-reset` deletes the local Compose volumes. Use it only once you've
decided that the whole local setup, and the evidence in it, can go. It isn't a
diagnostic command.

## When you're done

A failure is fixed only when all three of these are true:

1. The small reproduction now passes.
2. The check or test for that part of the system passes.
3. The original workflow the user saw works, without a wider workaround.

If your explanation still relies on "it worked after a reset", keep looking.
The reset may have removed the evidence rather than the cause.
