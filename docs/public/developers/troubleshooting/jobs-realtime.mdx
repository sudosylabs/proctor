# Jobs and realtime

Jobs and WebSocket events do different jobs. A Job records a finite piece of
work that must survive the process going away. A WebSocket event is a
best-effort notice that tells a connected client to refresh. Neither replaces
the state in PostgreSQL, which is the source of truth.

## Use a Job's saved history

Use the authenticated operations in the <a href="/api/">API reference</a> to
list Jobs, fetch one Job, and list its attempts. Write down only test IDs,
state names, error codes, attempt numbers and times.

| Job state | What it means | What to check next |
| --- | --- | --- |
| `Queued` | A compatible worker can pick up the work | Queue latency, descriptor compatibility and capacity |
| `Running` | One current claim token and lease own the run | The attempt's heartbeat, how old the lease is, and the activity checkpoint |
| `CancelRequested` | The cancellation is saved, but the worker hasn't finished it | The worker's checkpoint and how it handles cancellation |
| `Succeeded` | The final outcome is committed | Check the result where it is owned, rather than running the work again |
| `Failed` | The retry policy, or an operator, ended the run | Attempt history and the failure code |
| `Canceled` | Cancellation finished, and the Job is done | Who canceled it, and the documented cancellation path |

Proctor runs each Job at least once, and possibly more. A worker can stop after
it has changed something outside Proctor but before it saves its outcome. Job
code must use idempotent activities, checkpoints and a stable operation ID,
rather than assuming it runs only once.

## Leases and retries

By default, a claim lease lasts 60 seconds and the worker sends a heartbeat
every 15 seconds. When a lease expires, another worker can claim the work. The
newer claim token then blocks the old worker from saving its outcome. This can
look like the work ran twice, while still protecting the single saved outcome.

Look at the whole sequence, not only the last error:

1. When the Job was created, and its descriptor version.
2. Which node claimed it, the attempt number, and when.
3. The heartbeats and the current lease deadline.
4. The activity checkpoint, or the result of a finished activity.
5. Retry scheduling, cancellation or the final commit.

A restore that doesn't match the worker doesn't use up an attempt. Fix the
compatibility between the worker and the descriptor, rather than retrying the
same mismatch again and again. Retention never deletes queued or running
Jobs.

These metric families are useful:

- `proctor_jobs_executions_total`
- `proctor_jobs_execution_duration_seconds`
- `proctor_jobs_active`
- `proctor_jobs_activities_total`
- `proctor_jobs_activity_duration_seconds`
- `proctor_jobs_queue_latency_seconds`

Use the metrics to find which kind of Job is failing. Then use the saved
history of one test Job to explain why. Metrics don't replace the Job record.

## When a WebSocket won't connect

If the connection never opens, look at the browser's handshake:

- The URL and the configured public origin.
- That the request uses exactly one allowed kind of credential: cookie, bearer
  or DPoP.
- The exact Origin, for connections that use a cookie.
- The HTTP status and the stable Problem Details code, if the upgrade is
  rejected.
- Server readiness on the node that received the handshake.

Don't paste cookies, bearer or DPoP credentials, DPoP proofs or nonces, or a
full export of the handshake into an issue.

## Missing events or gaps in the sequence

Each connection numbers its events, within limits. When a client reconnects,
it can ask the node for a replay. But each node keeps only a limited replay
history of its own. If the reconnect reaches a different node, or asks for a
sequence older than the node still holds, the replay may not be possible.

When there is a gap or a replay fails, the client should:

1. Drop anything it assumed from the missing notice.
2. Fetch the affected resource again over HTTP.
3. Replace its local copy with that response.
4. Resume realtime updates from that new point.

Cluster messages and WebSocket events go out after the commit. Losing them can
delay what a view shows, but it must never undo the saved outcome.

The relevant metric families are `proctor_websocket_connections`,
`proctor_websocket_messages_total`, `proctor_websocket_replays_total`,
`proctor_websocket_backpressure_disconnects_total` and
`proctor_websocket_subscriptions`. A backpressure disconnect means the client
couldn't keep up with the limited outgoing queue. The client must reconnect
and resync, rather than expect the server to buffer without limit.

## Confirm the fix

For a Job problem, add a focused test for claim fencing, retry, checkpoints,
cancellation or the final outcome, whichever applies. For a WebSocket problem,
test both the realtime path and resyncing over HTTP. Then run the PostgreSQL
or cluster integration suite that applies, and repeat one end-to-end workflow
with test data.
