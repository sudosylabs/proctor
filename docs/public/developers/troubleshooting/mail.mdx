# Transactional mail

"No email arrived" doesn't tell you which step failed. Proctor first saves the
change and the request to send mail. Then a background Job renders the
message and hands it to SMTP. The SMTP server can accept the message without
any guarantee that the recipient's mail provider will put it in their inbox.

## Find the furthest step that was saved

Go through the steps in order:

1. Was the change itself saved?
2. Was the exact mail occurrence and its Mail Delivery saved with it?
3. Does the related Job exist, and is it in a state where it can run?
4. Did the template render, and did the message pass its checks?
5. What SMTP outcome did Proctor record?
6. In local development, does Mailpit show the test message?

Don't repeat the original change until you know its idempotency outcome. A
retry may return the result that was already saved, rather than create a
second mail occurrence.

## What each delivery state means

| State | What it means | Where to look |
| --- | --- | --- |
| `Queued` | The delivery work is saved and waiting to run | Job claiming and queue latency |
| `Sending` | A worker owns the current send attempt | The current attempt and its lease |
| `Accepted` | SMTP accepted the finished DATA transaction | Mailpit locally, or delivery further along outside Proctor |
| `Failed` | The delivery failed for good | The outcome and the attempt history |
| `Suppressed` | A policy stops the message from being sent, on purpose | The reason it was suppressed. Don't force it through |
| `Canceled` | The delivery work was canceled | The decision that canceled it, and who owns that decision |

`Accepted` doesn't prove the message reached an inbox. On the other hand, if
Mailpit is empty and no Delivery was saved, the failure happened before SMTP.
It isn't a Mailpit problem.

## Check local SMTP

```sh
make dev-doctor
docker compose -f build/compose/dependencies.yaml ps mailpit
docker compose -f build/compose/dependencies.yaml \
  logs --no-color --tail=100 mailpit
```

Open the local Mailpit interface at the URL in
[Local services](../local-services.mdx). Use only the protected test fixture.
The Mailpit UI shows full message bodies and recipient addresses, so don't
take screenshots of it or export from it when it holds real or personal data.

For bugs in how messages are put together, or in the SMTP adapter, run the
mail module tests with Go workspace mode turned off:

```sh
GOWORK=off go test ./...
GOWORK=off go test -race ./...
```

Run those commands from `packages/mail`. Templates, translations, choosing
recipients, the retry policy and delivery state all belong to the server, and
need their own focused server tests.

## Use metrics without exposing messages

These metric families report outcomes, not message content:

- `proctor_mail_health`
- `proctor_mail_queue`
- `proctor_mail_deliveries_total`
- `proctor_smtp_messages_total`

To query one family through local Prometheus:

```sh
curl --silent --get \
  --data-urlencode 'query=proctor_mail_health' \
  http://127.0.0.1:19090/api/v1/query \
  | jq '.data.result'
```

Use IDs and state or outcome labels to match up a test failure. Never add
recipient addresses, subjects, template data, SMTP credentials, reset links,
invitation claims or message bodies to metrics or ordinary logs.

## Choose the right fix

| What you found | What to do |
| --- | --- |
| The change was saved but no delivery request exists | Fix the aggregate transaction that owns it, and add a regression test |
| The delivery is queued but no attempt starts | Look at the Job runner. If its Job already failed, use the operator retry, with permission |
| Rendering fails | Fix the server's template, the locale data, or the contract for the frozen payload |
| SMTP is down for a while | Keep the delivery work, and let the retry policy handle it within its limits |
| The delivery failed for good | Fix the cause first, then use the operator retry, with permission |
| The delivery is suppressed | Fix the policy or configuration behind it. Don't bypass it for single messages |

Turning mail off suppresses all outstanding mail work for good. It changes
the operator's policy, and isn't a way to pause mail while SMTP is briefly
down.

## Confirm the fix

Create one new test occurrence through the real application use case. Check
that the change, the Delivery and the Job are saved together as one outcome.
Watch the state change to `Accepted`, and find the message in local Mailpit.
Then run the focused server test and the mail module's conformance checks for
the part you changed.
