# Runtime and readiness

Your local environment has three separate layers: the tools on your machine,
the Docker services that keep running in the background, and the Proctor
process in the foreground. Check them in that order, so you don't mistake a
problem with a dependency for a problem with the application.

## Find the layer that fails

```sh
make dev-doctor
```

Read the output from top to bottom. The first error points to the earliest
layer that isn't working yet. If the PostgreSQL container is unhealthy, a
missing server endpoint after it doesn't yet show a bug in the server.

| First error | What it means | Run next |
| --- | --- | --- |
| `toolchain` | A pinned or required command isn't available on your machine | `make dev-tools` |
| `Docker Compose plugin` | The Docker client can't run Compose v2 | `docker compose version` |
| `Docker daemon` | The client can't reach the Docker engine | `docker info` |
| `container … is missing` | The expected Compose project has no such service | `make dev-up` |
| `container … is unhealthy` | The service started but failed its health check | Look at the end of that service's logs |
| Generated configuration or webapp identity is missing | The local state built from your inputs is incomplete | `make dev-state` or `make webapp-build` |
| A dependency endpoint fails | The container may be running but not serving correctly | Check its health endpoint and logs |
| Server liveness fails | No healthy server process is serving that address | Look at the output of the server in the foreground |
| Server readiness fails | The process is running but can't yet take product traffic safely | Follow the readiness steps below |

## Check the tools on your machine

```sh
make dev-tools
```

This command decides which versions of Go, Node.js, npm, Docker, Compose, `jq`
and `curl` are correct. Fix the first mismatch it reports before you reinstall
application dependencies. If you upgraded a tool, open a new shell so the
command path and cached versions are up to date.

## Check the containers before the server

```sh
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  ps
docker compose \
  -f build/compose/dependencies.yaml \
  -f build/compose/observability.yaml \
  logs --no-color --tail=100 postgres redis minio
```

Look only at the end of the logs, and only for the service whose health check
failed. The usual local start-up is:

```sh
make dev-up
make run-server
```

`make run-server` keeps Proctor in the foreground on purpose. The first
startup error stays on screen, and `Ctrl-C` starts a normal shutdown. Don't
move the process to the background while you're looking into a startup
problem.

## Fix a port conflict without killing unknown processes

On macOS, find what is listening on the exact port:

```sh
lsof -nP -iTCP:8065 -sTCP:LISTEN
```

On Linux:

```sh
ss -ltnp 'sport = :8065'
```

Make sure the process belongs to this development environment before you stop
it. If another project really does need the port, choose a full set of Proctor
ports that don't overlap, using the supported `PROCTOR_*_PORT` Make overrides
described in [Development configuration](../development-configuration.mdx).
If you change only the HTTP port, the public origin, Vite proxy, metrics or
dependency addresses can stop matching.

## Liveness and readiness are different

```sh
curl --fail --silent --show-error http://127.0.0.1:8065/health/live
curl --fail --silent --show-error http://127.0.0.1:8065/health/ready
```

Liveness means the process is running. Readiness means the server has finished
starting and everything it needs to serve is available. A process that is
live but not ready should get no traffic from the load balancer.

When readiness fails:

1. Keep the startup output from the foreground server.
2. Check PostgreSQL first, because it holds the application's lasting state.
3. Check the other services you configured, such as the VFS, mail and the
   cluster's check on whether a node may serve. Don't assume every optional
   integration affects readiness in the same way.
4. Fix the first one that is unavailable, then check readiness again.

Don't weaken the readiness check to make the endpoint go green. The failing
check is what protects you.

## Generated local state

The local setup generates configuration under `.build/dev`, which Git ignores.
It serves the compiled webapp only when `webapp/dist/webapp-build.json`
matches the server's build identity.

```sh
make dev-state
make webapp-build
make dev-doctor
```

Treat generated state as output. To change it for good, edit the configuration
templates or Make inputs in the repository and generate again. Don't edit the
ignored JSON directly. Never attach the generated configuration or secrets to
an issue.

## Migration failures

Migration errors come from PostgreSQL, not from Redis or the browser. Keep the
first migration message and the database logs before you do anything.

Proctor is pre-release. Old development databases that you can throw away may
not work with the current baseline, and you may need to recreate them on
purpose. That doesn't make deleting the database the default answer:

1. Decide whether the database holds anything you need to keep.
2. Save any development-only evidence you're allowed to keep somewhere the
   reset won't touch.
3. Stop the foreground server.
4. Only if the setup is meant to be thrown away, run `make dev-reset` and
   recreate it with the documented local setup.

Never use this development recovery on an operator's installation, and never
mark a failed migration as complete by hand.

## Confirm the fix

Run `make dev-doctor` again, then the command that failed in the first place.
For a server change, finish with the focused Go test and the server checks
that apply. If you changed how the runtime is put together, also run:

```sh
make -C server architecture
make -C server check
```
