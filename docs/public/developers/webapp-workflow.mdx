# Develop the hosted webapp

The private `webapp` package builds the React and Vite application that
Proctor serves. Today it covers a fixed set of access and onboarding pages:

- setup
- sign-in
- registration
- Invitation acceptance
- password recovery
- email verification
- Desktop authorization
- provider connection
- terminal Session confirmation

The browser owns presentation and interaction. It doesn't get to redefine
routes, HTTP shapes, localization messages, authentication policy or durable
application state. So a complete feature uses the generated adapters, sorts
what the server returns into a small set of feature states, and renders each
state with components whose contracts already fit the behavior.

## Make each decision in one place

| Decision | Owner |
| --- | --- |
| Which browser paths the server hosts | `server/webui/hosted_routes.json` |
| How each hosted route sanitizes bootstrap input and selects a page | `webapp/src/app/HostedRoutes.tsx` |
| Public request and response shapes | Human-owned YAML under `server/openapi` |
| Browser compile-time HTTP types | Generated `webapp/src/api/generated/schema.ts` |
| Same-origin credentials and CSRF transport mechanics | `webapp/src/api/client.ts` and `webapp/src/auth` |
| Which remote outcomes matter to one feature | The feature-owned API action |
| Feature state, validation, recovery, and visible copy selection | The owning feature and presentation module |
| Repeated domain-neutral interaction behavior | A shared component with a narrow adjacent contract |
| Visible English source messages | The `webapp.*` namespace under `server/i18n` |
| Product tokens and durable visual rules | `webapp/design-system/tokens.mjs` and `webapp/DESIGN_SYSTEM.md` |
| Reset and document defaults | `webapp/src/styles` |
| Feature and component styling | Colocated CSS Modules |

If two rows seem to own the same choice, stop and remove the duplicate. For
example, OpenAPI lists the error codes an operation can return. The feature's
API action decides which of those codes lead to the same safe outcome on
screen. The presentation component receives that outcome. It never checks HTTP
statuses or Problem Details itself.

## Start from states, not screens

Before you change any code, write a feature map:

~~~text
Purpose:          what task can the person complete?
Hosted route:     which server-owned path presents it?
Bootstrap input:  what sanitized, purpose-specific input reaches React?
API operations:   which generated operations are consumed?
States:           initial, loading, ready, empty, invalid, denied, unavailable,
                  pending, complete, and terminal states that can really occur
Recovery:         which state preserves values, retries, redirects, or stops?
Focus:            where does focus begin and move after each user action?
Copy:             which webapp.* messages are required?
Components:       which existing contracts apply, and what remains local?
Evidence:         which unit and browser tests prove behavior and presentation?
~~~

Don't start from a page mockup and then squeeze every state into it. A loading
view might have no form at all. A terminal result might remove the button that
triggered it and move focus to a heading that replaces it. An ordinary failed
submission should usually keep the field values, the position of the action
and the focus where they were.

## Keep the browser's trust boundary

The hosted webapp always talks to the Installation that served it. There is no
setting to point it at a different API. Cookie credentials stay same-origin.
Unsafe methods add the CSRF header when the server's cookie is present.
Sensitive credentials in the URL fragment are removed from browser history
before React renders.

The browser can give better guidance, but the server still checks input,
authenticates the principal, authorizes actions and commits durable state.
Never render arbitrary error text from the server. Never assume a permission
because a control is hidden. Never treat browser storage as a source of truth.

## Where the details live

This manual explains contributor tasks. It doesn't repeat every route or
component. While you work, read:

- the [webapp package guide](https://github.com/sudosylabs/Proctor/blob/main/webapp/README.md);
- the [product design-system contract](https://github.com/sudosylabs/Proctor/blob/main/webapp/DESIGN_SYSTEM.md);
- the `CONTRACT.md` files next to the features and components you change;
- the reviewed OpenAPI YAML, for public HTTP behavior;
- the server localization catalog, for visible messages;
- the current unit and Playwright tests, for behavior you can run.
