# Webapp architecture and routing

The hosted webapp isn't a general single-page router that takes over every
unknown path. It works in three parts:

- The server owns a fixed catalog of routes.
- The browser generates a typed adapter from that catalog, listing which
  routes exist.
- One hand-written descriptor map supplies the behavior for every generated
  route.

Because of this, when the routes and the browser drift apart, generation,
type-checking or tests fail. You find out then, not from a page nobody can
reach in production.

## Read the code from the outside in

| Location | What it does |
| --- | --- |
| `server/webui/hosted_routes.json` | The sealed list of paths served with the browser application |
| `webapp/src/app/routes.ts` | The generated read-only route tuple and `HostedRoute` union |
| `webapp/src/app/HostedRoutes.tsx` | The exhaustive descriptor, bootstrap projection, document-title key and page renderer for each route |
| `webapp/src/app/App.tsx` | Keeps the root document in sync, sets the localized title and renders the selected page |
| `webapp/src/features/<feature>` | A thin route page and the feature's own transport action |
| `webapp/src/components/<Component>` | Presentation that one or more real consumers already use |
| `webapp/src/theme` | Works out the one product theme in effect |
| `webapp/src/styles` | The reset, generated tokens and document defaults |

Use the table to find your way around. Don't copy it into the code as a new
registry of the architecture. The current tree and its contracts are the
source of truth.

## Generated routes, hand-written behavior

The route generator reads the server catalog and writes `src/app/routes.ts`.
That file exports the literal `hostedRoutes` tuple and the union derived from
it. Nobody edits it by hand.

`HostedRoutes.tsx` is its hand-written counterpart. Its descriptor map is
typed over the generated union, so every route must supply:

- one localized document-title key
- one explicit fragment policy
- one bootstrap projection made for that route's purpose
- one page renderer

If you add a server route without its browser behavior, compilation fails.
If you remove a server route, the hand-written map is left with an extra key,
and the completeness tests reject it. An unknown path gets no bootstrap and
no catch-all browser page.

After you change the server catalog, run:

~~~sh
cd webapp
npm run routes:generate
npm run routes:check
~~~

Review both the server catalog and the generated adapter. Adding a route is
a decision about what the server publicly serves, even when the page itself
needs no sign-in.

## Clean the URL before React renders

Some hosted pages start with a short-lived value in the URL fragment. The
browser doesn't send fragments in the HTTP request. But if the fragment
stays around, it can still leak through history, screenshots, copied
addresses, extensions or browser code that runs later.

So the root bootstrap:

1. recognizes only the fragment policy declared for that exact route
2. removes the whole fragment from browser history before reading it
3. accepts one exact parameter, and rejects extra or empty values
4. turns it into a credential type made for that one purpose
5. passes only that value to the selected feature

The bootstrap union tells apart an Invitation claim, a password reset token,
an email verification token and a Desktop browser proof. It deliberately has
no general `token` object that a feature could hand to the wrong exchange by
mistake.

Pages that take no credential clear unexpected fragments too. Login
recognizes only its one exact notice of an external sign-in failure, which
has a length limit. The Desktop query evidence has its own length limit,
separate from its fragment proof.

## Keep the root small

The root owns only what must be right before a feature can render safely:

- mounting in Strict Mode
- the cleaned-up bootstrap input
- exhaustive dispatch to the hosted route
- the document's language, direction, title, theme and theme-color metadata
- a fatal render boundary with limited scope

It doesn't own feature API calls, form values, password policy, Invitation
state, navigation decisions or visible recovery. If a feature can recognize
a remote failure and recover from it, the feature renders that recovery
itself. The fatal boundary is only for bootstrap or rendering failures that
stop the feature from doing so.

## Use the shared initial-resource lifecycle with care

A route that loads one initial result, of limited size, may use the
`AsyncResource` lifecycle the application owns. It:

- reuses the current promise when React Strict Mode remounts
- gives each retry a newer identity
- ignores completions that arrive late
- stops sending notifications after you unsubscribe

The loader you give it must already return a feature result. The lifecycle
doesn't interpret HTTP, Problem Details, copy, focus or recovery. Don't turn
it into a global data-fetching service or a place to keep domain state.

The password reset route makes no initial request, because the bootstrap has
already decided whether a usable credential is present. Other routes, such
as provider connection, use the lifecycle because what they show depends on
a limited discovery request to the server.

## Build the page from parts with clear owners

`AccessPageShell` gives the hosted access pages the Proctor identity, a skip
link, one main landmark, a frame of limited size and a responsive structural
variant. It doesn't own headings, forms, evidence, API state or navigation.

The shared `ProductTheme` resolves the system preference or an explicit
choice, once. The document and the shell both use that same result. Features
don't pick theme assets or query `prefers-color-scheme` on their own.

Inside the shell:

- the feature page connects the real transport action to the presentation
- feature content owns state, values, choice of copy and recovery
- shared components own only the interaction and visual behavior in their
  contract
- CSS Modules own the presentation of features and components
- the generated token layer supplies semantic values in every registered
  theme

The current shell is for access and onboarding pages. Don't take it as a
sign of what a future signed-in application shell, sidebar, dashboard or
navigation model will look like.

## Add a hosted route

Build a new route in this order:

1. Define the server-hosted path and how the server serves it.
2. Regenerate the typed route adapter.
3. Add the exhaustive hand-written descriptor and a bootstrap type made for
   the route's purpose.
4. Write a feature contract that describes the real states, credentials,
   transport, recovery and exclusions.
5. Add the feature action and presentation, without giving the root more to
   own.
6. Add localized messages to the server-owned `webapp.*` catalog.
7. Add unit and browser evidence for the whole route.
8. Run the route, API, i18n, type, lint, test, browser and production build
   gates.

If the route needs a new kind of bootstrap credential, review URL cleaning
and privacy before you build the page. If an existing shared component needs
new behavior for it, update that component's contract and the tests of every
consumer in the same change.

## Review the boundary

- Does the server catalog decide which routes exist, while the browser owns
  presentation?
- Is the descriptor exhaustive, and is the bootstrap type made for this
  route's purpose?
- Is sensitive fragment material removed before rendering?
- Does the root stay free of feature transport and state?
- Does the page have one main landmark, one `h1` and a skip link you can
  reach with the keyboard?
- Is the theme resolved in one shared place, rather than guessed by each
  page?
- Does an unknown route stay unknown, rather than falling through to a
  general app?
