# Features, API calls and localization

A webapp feature owns one task for the user, and the browser decisions it
needs to present that task safely. It doesn't copy the server's domain
policy. It doesn't hand raw transport results to visual components. And it
doesn't create abstractions before a second consumer shows it needs the same
behavior.

## Start with the feature contract

Read the feature's own `CONTRACT.md` before the code. A useful contract
names:

- the hosted route and its purpose
- the cleaned-up bootstrap input and how long it lives
- the API operations and the success responses the feature accepts
- the fixed set of feature states
- what happens on validation, while pending, on failure, on retry and at the
  end
- which fields or credentials must never be rendered, stored or logged
- how focus and announcements behave
- the shared component contracts that apply
- behavior the feature deliberately leaves to others

The contract records behavior that is stable and not obvious. It doesn't
list every function, CSS class, message key or test name, which a
contributor can find in the tree.

## Keep the route page thin

The page at the route level connects real dependencies to presentation. For
example, the password reset page picks the single-column access shell, gives
it the localized skip-link label, and passes the real completion action to
the reset content.

With that split, you can test the presentation with an in-memory action and
test the transport action on its own. Don't put form state in the route
catalog, and don't make a shared shell import a feature's API.

A typical split looks like this:

| Part | Owns |
| --- | --- |
| Feature page | Wiring up real dependencies and choosing the page shell |
| Feature API action | The generated HTTP call, the accepted success, mapping an allowlist of Problem Details codes, and a safe fallback |
| Feature content | Values, validation, pending state, semantic results, focus, announcements and recovery |
| Shared components | Behavior and interaction that know nothing about the domain and that real consumers already use |
| CSS Module | Local layout, using semantic tokens |

The exact files may differ. Keep the split of responsibilities rather than
copying file names mechanically.

## Use the same-origin API client

`src/api/client.ts` builds the typed `openapi-fetch` client with an empty
base URL and `same-origin` credentials. A hosted page always calls the
Installation that served it. It can't pick another issuer or API host.

The shared request middleware:

- keeps same-origin credentials
- reads the CSRF cookie the server issued, and only inside the browser
- adds `X-Proctor-CSRF-Token` to unsafe methods when the cookie is there
- leaves safe methods, and any header you supply yourself, unchanged

Feature actions call an operation from the generated `paths` contract. They
don't build a second API client, paste request interfaces from Go, or widen
the base URL to save effort.

## Turn transport into meaningful results

An API action accepts only the response the feature contract declares. A
200 can't stand in for a declared 204 just because both are successful HTTP
statuses.

Map an allowlist of Problem Details codes into a small, fixed union:

~~~ts
type Result =
  | { kind: "complete" }
  | { kind: "invalid" }
  | { kind: "password_rejected" }
  | { kind: "rate_limited" }
  | { kind: "unavailable" };
~~~

The union is safe to present. It holds no server title, detail, stack,
credential, request ID or arbitrary code. An unknown status, a malformed
body, an unknown problem code or a rejected request all end up as
`unavailable`, unless the feature defines a stricter final outcome.

Presentation branches on `kind`, never on the HTTP status or on Problem
Details. That keeps copy, recovery, focus and privacy in the feature's hands.

## OpenAPI is where the browser contract comes from

Hand-written YAML under `server/openapi` defines each public operation. The
reviewed `server/openapi.json` is generated from it, and the webapp's
`src/api/generated/schema.ts` is generated from that file in turn.

When the public shape changes, run:

~~~sh
make -C server openapi-build
make -C server openapi-agreement
cd webapp
npm run api:generate
npm run api:check
~~~

Review the YAML and the generated diffs. Don't patch `schema.ts`, add a
hand-written response interface beside it, or accept an undeclared response
to make a browser test pass.

The feature still sorts responses at run time. TypeScript proves the shape
the contract declares at compile time. It can't prove that a response from
the server actually has that shape.

## Keep visible text in the server catalog

Text the browser shows comes from the server-owned `webapp.*` message
namespace. The webapp generator checks that the messages come from there,
and produces the typed `src/generated/i18n/catalogs.ts` adapter. `message()`
accepts only a generated message ID.

After you add or change visible text, run:

~~~sh
cd webapp
npm run i18n:generate
npm run i18n:check
~~~

Don't tuck English source strings into components, join translated pieces
together, or render an API error's `title` or `detail`. Keep placeholders
few and specific to their purpose. Format dates, times, numbers, durations
and lists with `Intl`, not by hand in English.

Layouts must cope with longer translations, and with right-to-left text in
the future. Use logical CSS properties, let text wrap, and don't let an
English button label set a fixed control width.

## Reuse components by their contract

Use a shared component only when its purpose and its states match the
feature. The access pages have a deliberately narrow set:

- `AccessPageShell` for identity, the skip link, the main landmark and the
  frame
- `AccessTaskIntro` to introduce one focused task
- `TaskState` to replace the task with a loading, unavailable or final state
- `InputField` and `PasswordField` for single-line controls that follow the
  design system
- `Button` and `ButtonLink` for the hierarchy of actions and navigation
- `Notice` for stable inline evidence
- `FormFeedback` for a submission failure that stays next to the action

These names don't promise a general component library. For example,
`TaskState` doesn't replace field errors, and `Notice` isn't a toast or a
live region by default.

Start a new visual pattern inside the first feature that needs it. Promote it
only once a second real consumer needs the same behavior. Then, in one
change, add:

- a narrow component contract
- focused tests
- evidence in both themes
- evidence that it copes with longer content
- the move of every existing consumer to the new component

## Keep CSS local

The browser imports global styles in this order:

~~~text
reset.css
tokens.css
base.css
~~~

The reset makes browsers behave the same way. The generated tokens own the
system scales and complete semantic themes. Base CSS sets document defaults.
Component and feature CSS lives next to its code, in CSS Modules.

Hand-written CSS uses semantic variables. It never adds:

- literal colors or font families
- shadows nobody has reviewed
- `transition: all`
- removed focus outlines
- arbitrary stacking values

A one-off layout value may stay local until it repeats often enough to
deserve a token. Copying a palette is never an acceptable local exception.

## Review the feature boundary

- Does the contract describe real behavior, without turning into a list of
  files?
- Does the route page wire up dependencies without taking on feature state?
- Does the API action use the generated same-origin client?
- Are the accepted successes exact, and do unknown failures land in a known
  result?
- Does presentation get meaningful results rather than transport values?
- Is every visible message generated from the server catalog?
- Does reuse of a component follow its existing contract?
- Are new styles local, semantic, complete in every theme and safe for
  focus?
