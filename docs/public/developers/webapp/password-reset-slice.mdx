# Walk through the password reset feature

This tutorial reads the existing `/account/reset-password` browser feature
from end to end. It makes a good example because one small page touches
almost every part of the webapp:

- route generation
- a sensitive credential in the URL fragment
- types generated from OpenAPI
- same-origin transport
- field and form validation
- replacing the form with a final state
- localization
- shared components
- unit tests
- browser tests in three engines

The goal is to understand why each part takes part. If your feature has no
credential, form, final replacement or API call, don't copy every file.

## Describe the behavior before reading code

The browser route receives one password reset token in the URL fragment.
Before React renders, Proctor removes the whole fragment from history and
turns the value into a credential made only for password reset.

The ready form takes a new password and a confirmation that stays in the
browser.

- On success, the page clears the credential and the fields, replaces the
  form with a completion task, announces the new state and focuses its
  heading.
- An unusable credential leads to a different final task.
- If the password breaks the password policy, focus goes back to the
  password field.
- Rate limiting and transport failures stay as form feedback the user can
  recover from.

The browser never renders or stores the token, never sends the confirmation
field, and never shows server error text it hasn't chosen.

| Concern | Owner |
| --- | --- |
| Hosted path | Server route catalog |
| Type listing which routes exist | Generated browser route adapter |
| Cleaning the fragment and typing it for its purpose | Root hosted-route bootstrap |
| Public request, success and errors | OpenAPI YAML |
| Request shape at compile time | Generated browser API schema |
| Accepted response and mapping to meaningful results | Feature API action |
| Values, validation, focus, announcements and recovery | Reset password content |
| Labels and messages | Server-owned `webapp.*` catalog and its generated adapter |
| Field, action, evidence, feedback and task behavior used in many places | Shared component contracts |
| Behavior and presentation of the assembled page | Vitest and Playwright |

## 1. Start at the server's route

Read [server/webui/hosted_routes.json](https://github.com/sudosylabs/Proctor/blob/main/server/webui/hosted_routes.json).
`/account/reset-password` is one of the fixed set of paths the hosted
application serves.

Run the route generator:

~~~sh
cd webapp
npm run routes:generate
npm run routes:check
~~~

The generated
[webapp/src/app/routes.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/app/routes.ts)
adds the literal path to `hostedRoutes`. The `HostedRoute` union derived from
it then forces you to write browser behavior for that route. Never edit the
generated file.

## 2. Follow the bootstrap that keeps the credential safe

Read
[webapp/src/app/HostedRoutes.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/app/HostedRoutes.tsx)
and
[webapp/src/auth/fragments.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/auth/fragments.ts).

The hand-written descriptor declares:

- the document title key `webapp.reset_password.document_title`
- the fragment policy `password_reset_token`, with the parameter `token`
- a bootstrap projection whose credential has exactly that kind
- the `ResetPasswordPage` renderer

`captureFragmentCredential` removes the whole fragment with
`history.replaceState` before it parses the parameter. It accepts exactly one
value that isn't empty. A malformed fragment, an extra parameter or a missing
value gives no credential.

The order matters. If the code cleaned the URL only after parsing succeeded,
a malformed secret would stay in browser history. If it passed a general
token object, it would be easier to use the credential for the wrong
purpose.

The root test suite checks, for every route that carries a credential, that
the credential has exactly the right type, that the wrong credential is
rejected and that the fragment is removed.

## 3. Read the feature contract and the thin page

Read the
[reset password contract](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/CONTRACT.md)
before the implementation.

The contract settles how long the credential lives, the exact API operation,
the confirmation that stays in the browser, how failures map to results, the
feedback that persists, the final replacement, focus behavior, and which
sensitive data stays out.

[ResetPasswordPage.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/ResetPasswordPage.tsx)
then only wires up real dependencies. It:

- picks the `single` access-shell variant
- looks up the localized skip-link label
- passes the cleaned-up token
- passes the real `completePasswordReset` action

It doesn't own the form state, and it doesn't make the transport call while
rendering.

## 4. Look at the public HTTP contract

Read
[server/openapi/fragments/authentication/auth-password-reset.yaml](https://github.com/sudosylabs/Proctor/blob/main/server/openapi/fragments/authentication/auth-password-reset.yaml).

`POST /api/v1/auth/password-reset/complete` declares:

- public authentication, with empty OpenAPI security
- no idempotency key
- a strict body with only `token` and `password`
- HTTP 204 as the success response
- bad-request, rate-limit and unavailable responses, each with limited
  content
- explicit error codes for the password, the token, recovery, the request
  and rate limiting

The password confirmation isn't there, because it only helps the person in
the browser and isn't server input. Credentials that are expired, replayed,
superseded, malformed, or lost a race with a concurrent request all look the
same: the server treats them as one unusable token and doesn't say which.

If this contract changes, run:

~~~sh
make -C server openapi-build
make -C server openapi-agreement
cd webapp
npm run api:generate
npm run api:check
~~~

Then review the generated `PasswordResetCompletionRequest` and
`completePasswordReset` operation types in
[schema.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/api/generated/schema.ts).

## 5. Read the feature API action

Read
[ResetPasswordApi.ts](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/features/reset-password/ResetPasswordApi.ts).

The action uses the shared typed client and sends only `{token, password}`.
It treats exactly HTTP 204 as complete. It then maps public errors into five
outcomes that are safe to present:

| Result | Meaning |
| --- | --- |
| `complete` | The declared success with no content happened |
| `invalid` | The credential or the request can't be used safely |
| `password_rejected` | The new password broke the server's policy |
| `rate_limited` | The next try should wait |
| `unavailable` | Any unknown, malformed or unexpected failure, or a transport failure |

The presentation never gets an HTTP status or a Problem Details object. The
action never uses an arbitrary `title` or `detail` as interface text.

Run its focused test:

~~~sh
cd webapp
npx vitest run src/features/reset-password/ResetPasswordApi.test.ts
~~~

The test covers the exact success, every mapped public code, an unknown
code, an unexpected 2xx response and a rejected request.

## 6. Follow the feature's states

Read
[ResetPasswordContent.tsx](https://github.com/sudosylabs/Proctor/blob/main/webapp/src/components/PasswordRecovery/ResetPasswordContent.tsx).

The visible state is deliberately small:

~~~ts
type ResetState = "ready" | "complete" | "invalid";
~~~

Pending and recoverable errors are properties of the ready form. They don't
pose as new states for the whole route. The credential lives in a single
`useRef`, so it never reaches the rendered output. If there is no credential
at the start, the page shows `invalid` without moving focus.

On submit, the content checks and acts in this order:

1. Ignore a repeated activation, or a missing credential.
2. Require the password, and focus it when it's empty.
3. Require the confirmation, and focus it when it's empty.
4. Compare the two values in the browser, and focus the confirmation if they
   don't match.
5. Mark the form as pending and clear errors that no longer apply.
6. Call the feature action.
7. On a `complete` or `invalid` result, clear the credential and the fields.
8. Replace the form, announce the heading and focus it, since the user caused
   the change.
9. If the password was rejected by policy, send the user back to the password
   field.
10. Otherwise, keep a rate-limit or unavailable failure in the persistent form
    feedback.

An edit clears only the errors it makes out of date. A transport failure the
user can recover from doesn't throw away the token or the values they
entered.

## 7. Look at the shared components

The ready state is built from existing components that know nothing about
the domain:

- `AccessTaskIntro` for the purpose, the `h1` and supporting context
- `PasswordField` for the label, required semantics, guidance next to the
  field, the link to its error and a named control to show the password
- `Notice` for stable evidence that Sessions will be revoked
- `Button` for an explicit submit and its pending behavior
- `FormFeedback` for the failure that stays next to the action

The final states use `TaskStateAnnouncement`, `TaskState`, `Notice` and
`TaskStateActions`. Their shared contracts define the hierarchy, the
announcement and how the actions respond to screen size. The feature still
decides which state is complete or invalid, and which text and navigation go
with it.

The feature's CSS Module owns its `40rem` task width, the local gaps, the
action row and stacking the actions on narrow screens. It uses the generated
semantic and scale tokens and adds no palette of its own.

## 8. Follow where the text comes from

Visible messages live in
[server/i18n/en.json](https://github.com/sudosylabs/Proctor/blob/main/server/i18n/en.json)
under `webapp.reset_password.*`, along with shared form message IDs. The
generator writes a typed catalog that the code reads through `message()`.

Run:

~~~sh
cd webapp
npm run i18n:generate
npm run i18n:check
~~~

The content picks whole message IDs. It never builds a sentence out of
pieces, or mixes a string from the server with local text. The pending label
uses the ellipsis character, and still makes sense when reduced motion
removes the animation.

## 9. Prove the behavior in the browser

The hosted-access Playwright suite intercepts the completion request and
checks that:

- the fragment credential leaves the URL before any interaction
- the request body has the token and the password but not the confirmation
- the declared HTTP 204 leads to the completion state
- the new heading gets focus and the live region announces it
- the token and password values are gone from the rendered page
- an invalid credential reported by the server leads to the unusable-link
  final state
- a missing credential is handled safely and doesn't take focus at the start
- the route stays in a single column in dark mode at `390×844`
- 200% zoom causes no horizontal overflow
- the same scenarios run in Chromium, Firefox and WebKit

Run the focused browser file across all configured projects:

~~~sh
cd webapp
npx playwright test tests/browser/hosted-access.spec.ts
~~~

Filter by title or line only while you iterate. Before you hand off, run the
whole browser suite. A change to a shared field, task, shell, theme or notice
can affect every hosted route.

## Use the pattern without copying it

Another feature may need no fragment credential, form, final replacement or
initial request. Keep only the parts its real states need.

- A read-only status page may use a route loader and no form controls.
- A form that takes no credential needs no fragment bootstrap and no
  credential lifetime.
- A validation result from the server may stay a general form failure when
  it can't safely point to one field.
- A recoverable unavailable state may use `TaskState` with a retry, instead
  of form feedback.
- A future signed-in product page may need a different shell, proven by its
  own real consumers.

What stays the same: the server is the source of truth for public and stored
state, generated adapters carry the reviewed contracts into the browser, and
the feature owns one small, well-defined set of interaction states.
