# States, forms and accessible recovery

An interface is finished when every state a real request can reach has a
clear meaning, a stable next action and the right focus behavior. A polished
screenshot of the ready state tells you nothing about pending, invalid,
denied, expired, offline or final behavior.

## Name the states first

Use only states the feature can really reach. Keep states apart when they
need different text, actions, focus or privacy handling.

| State | What you have to decide |
| --- | --- |
| Initial loading | What stays stable, what is announced, and whether a retry is possible |
| Ready | Which task and primary action are available |
| Empty | Why there are no items, and which action or guidance comes next |
| Field invalid | Which control is invalid, what guidance sits next to it, and where focus goes |
| Submission failure | Whether the values stay, where the persistent feedback appears, and how a retry works |
| Denied or signed out | Whether the resource's existence must stay hidden, and which safe navigation is left |
| Expired or unusable | Why the task can't go on, without exposing sensitive state |
| Unavailable | Whether a retry is safe, what stays visible, and what you don't claim |
| Pending | Which action is running, and how a second activation is blocked |
| Complete | What changed, what was cleared on purpose, and what the next safe action is |
| Fatal | Why the feature can't recover by itself, and what limited recovery the root still offers |

Don't merge a transport failure the user can recover from with an expired
credential. Don't call a result empty when the viewer isn't authorized to
see it. Don't show success just because a request got a 2xx response that
the contract didn't declare.

## Put feedback next to its cause

- Field validation goes beside the field.
- A general submission failure goes beside the action that caused it.
- Stable context the person needs before acting goes in the normal document
  flow.
- A final replacement becomes the main task.

Don't use a floating toast for a failure the person must read before they
retry. Don't move the main form just to fit in ordinary failure text. Don't
let a tinted panel, an icon or a color be the only thing that names a state.

`FormFeedback` stays mounted with space kept for it, so an ordinary failure
can appear without moving the fields or the submit button. Longer localized
text can make the page grow naturally. The space isn't a clipped box of
fixed height.

## Validate forms in a fixed order

On submit:

1. Prevent the browser's own navigation.
2. Ignore a repeated activation while the same submission is pending.
3. Check required fields, and relationships only the browser checks, in
   document order.
4. Show guidance next to each field that needs it.
5. Focus the first invalid control.
6. Clear old general feedback, but only when an edit or a retry makes it out
   of date.
7. Call the feature action with the smallest input it needs.
8. Turn its result into a presentation state the user can recover from, or a
   final one.

Use native form semantics even when the feature does its own validation. A
required single-line control keeps `required`, a visible label, a stable
`name`, the right `type`, `inputMode` and `autocomplete`, and descriptions
and errors linked in code. Never block pasting into passwords, codes or any
other field.

Password confirmation is input that stays in the browser. Don't send it to
the server. Showing the password stays an explicit, named button with
`aria-pressed`, a matching title and a decorative icon from the design
system. Showing or hiding the password must not change the value, the
request body or the URL.

## Tell field failures from form failures

The server may reject a password because of the password policy, and point
to the password field. Focus that field once the result arrives, and keep
what the person typed so they can correct it.

A rate limit or a temporary transport failure is a general form failure.
Leave focus where the person was working. Announce the persistent feedback
politely, without focusing it.

Never repeat the same message as a field error, a form status, a toast and a
focused heading. One event gets one announcement.

## Pending is a real state

While an action is pending, the page must:

- block a second activation
- set `aria-busy` on the form or task that owns the action
- keep a stable, localized progress label, such as “Setting password…”
- keep the values until a final outcome means clearing them
- avoid moving the layout
- keep its full meaning when reduced motion removes the animation

A spinner or a skeleton can't be the only sign. Don't disable the whole page
when only one action is pending. Don't hide the navigation someone needs to
cancel safely.

## Move focus only to help people find their place

Moving focus in code tells the user something. Don't do it for decoration.

- The first render and background loading don't take focus.
- A failed check in the browser focuses the first invalid field.
- A rejection from the server about one field may send focus back to that
  field.
- A general submission failure stays in a polite live region and doesn't
  move focus.
- When the user's action replaces the form they used, the new task heading
  gets focus.
- A final state that is already there when the page loads doesn't focus its
  heading.
- Closing a temporary panel sends focus back to the control that opened it,
  if it's still there, or to the nearest safe task landmark.

Headings that can take focus use `tabindex="-1"`, so they don't join the
normal Tab order. The first keyboard stop in the document is still the skip
link.

## Keep cookie, CSRF and origin behavior

The hosted client uses same-origin credentials. When the server's cookie is
there, unsafe requests get the CSRF header. The browser never treats a CSRF
cookie as application data or passes it to the presentation.

Authentication and authorization stay decisions for the server. Hiding an
action is useful presentation, but it's never an authorization check. A
feature must still handle 401, 403, a 404 that hides a resource, expired
credentials and an unavailable server exactly as its public contract says.

Discovery of the installation's own origin rejects a server response whose
declared origin doesn't match the page's origin. Don't add a cross-origin
fallback, a lenient redirect or a choice of issuer kept in local storage.

## Design for narrow screens and longer translations

Build mobile-first with CSS Grid or Flexbox and logical properties. Change
the layout where the content stops working, not at the sizes of particular
branded devices.

At the very least, check `390×844`, `768×1024` and `1440×1024`.

- At 200% zoom, the main task must still be available without the page
  scrolling sideways.
- Long labels, identifiers and translated text wrap, without being clipped
  or covering controls.
- Below the narrow breakpoint for actions, actions stack in document order
  and primary controls fill the available width.

Don't shrink body text below the token scale, cut off required guidance, or
measure in rendering code a layout that CSS can express.

## Check themes and user preferences

Every state you change must work in light mode, dark mode and the system
preference. Use semantic color tokens rather than checking a theme ID. State
colors are only for real state, and always come with text, structure or
another cue that isn't color.

Reduced motion removes repetition that isn't essential and collapses
generated durations. Components must still show the final state straight
away. Forced colors mode may remove decorative paint and shadows. Focus,
boundaries, state names and actions must survive it.

The current access pages, used before sign-in, follow the system theme.
Don't add a theme chooser, or a way to save the choice, inside a feature. A
saved appearance needs a separate, signed-in User Settings feature and one
reviewed owner that applies it before the first paint.

## Accessibility checks

For each real state, check:

- native landmarks, headings, forms, labels, buttons and links
- a logical keyboard order and a visible three-pixel focus style
- accessible names for controls that show only an icon
- descriptions and errors that sit next to their field and are linked to it
- one suitable live announcement for each asynchronous change
- pointer and touch targets at least the design system's default size
- browser zoom, larger text, reduced motion and forced colors
- both product themes and the system preference
- no required information that only appears on hover
- no secrets, private identifiers or arbitrary text from the server in the
  DOM
