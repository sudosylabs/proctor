# Test the hosted webapp

Webapp tests prove each decision in the part of the code that owns it. A
unit test can show that a feature action accepts only HTTP 204. A browser
test can show that when the form is replaced, sensitive values disappear,
completion is announced and the new heading gets focus. Neither one can
stand in for the other.

## Choose the narrowest test

| Change | Test it first with |
| --- | --- |
| Pure parsing, CSRF, fragment or result mapping | A focused Vitest unit test |
| A component's semantic markup and ARIA links | A component unit test |
| A generated route, API, i18n, token or brand adapter | The check of the generator that owns it |
| A page's state changes, focus, history or navigation | A Playwright scenario |
| Responsive layout, theme, zoom, reduced motion or geometry | Playwright on the real page |
| Packaging of production assets and routes | The Vite production build |

Write the smallest test that can prove the decision. Then add the widest
test that matters for the assembled behavior.

## Unit-test feature actions as closed mappings

A feature action test uses the same typed client, but replaces the request
method with a result held in memory. Cover:

- the exact declared success response
- an unexpected 2xx response
- each allowlisted Problem Details code that changes how the feature behaves
- an unknown problem code
- a malformed or missing problem body
- a rejected request

Assert on the small union of results, not on calls inside the code that
don't change behavior. Don't snapshot a whole generated schema, or copy
OpenAPI fixtures into every feature test.

## Unit-test components against their contract

Component tests check the choice of native element and the relationships
that must stay stable:

- a visible label points at the right control
- the required, invalid, described-by, live-region and busy semantics are
  there
- a show-password control that has only an icon has a localized accessible
  name and title
- a task replacement keeps one `h1` and a grouped region of actions
- the shared diagnostic attributes that browser tests use are still there

Don't assert every CSS class or every character of the serialized markup.
Those tests make harmless refactoring expensive and prove nothing about
interaction.

## Use Playwright for what users see

The pinned suite runs the same scenarios in Chromium, Firefox and WebKit.
Its Vite server runs on `127.0.0.1:5173`, which matches the installation
address in the made-up discovery fixtures.

Browser tests intercept only the requests the scenario needs. Use small,
made-up data, explicit statuses and complete response shapes. A test must
never depend on a developer's running server, account, browser profile,
clock or Institution data.

A complete route scenario proves whichever of these apply:

- the exact starting URL, and that history is cleaned
- the document title, one page heading and the route's purpose
- the request method, and a body of limited size
- the ready, failure, retry and final states
- which values are kept and which are cleared
- focus and live announcements
- safe, fixed navigation
- that credentials and sensitive form values are absent from the DOM and the
  URL
- responsive and theme behavior

## Prefer selectors that survive refactoring

Select the interface the way a user or an accessibility API would, in this
order of preference:

1. Role plus accessible name.
2. Visible label.
3. A stable form control ID, when the ID is itself part of the contract.
4. A narrow diagnostic `data-proctor-*` hook that a component contract owns.
5. CSS structure, only for a real geometry or ordering assertion.

Don't select by generated class names or DOM depth. Don't select by pieces of
English text when an accessible role exists. Don't add arbitrary
`data-testid` values that just repeat the code's structure.

A diagnostic hook may find the persistent form feedback area or the tone of a
notice. Product code never branches on that hook.

## Assert geometry only when it means something

Geometry assertions are worth having when they prove stability or
containment, for example:

- the submit button doesn't move when ordinary failure text appears
- a show-password button stays vertically aligned with its field
- a responsive pair of columns becomes a single column on narrow screens
- the page has no unexpected horizontal overflow when zoomed
- a container doesn't clip a focus outline

When the claim is about structure, measure document coordinates, not
screenshot pixels. Treat screenshots as extra evidence for review, never as
the only test of behavior.

## Cover the browser matrix

These are the minimum viewports for acceptance:

| Name | Size | What it checks |
| --- | --- | --- |
| Compact | `390×844` | A narrow, single-column task and touch target behavior |
| Tablet | `768×1024` | Wrapping and layout changes in between |
| Desktop | `1440×1024` | The full frame, reading width and deliberate whitespace |

For a visible feature, cover:

- Chromium, Firefox and WebKit
- light, dark and system theme modes
- moving through with the keyboard, and visible focus
- 200% browser zoom
- reduced motion
- short and long localized text
- the pending, success, recoverable failure and final failure states the
  feature can reach
- forced colors or high contrast where automated support exists, followed by
  manual review where it doesn't

WebKit automation doesn't mean complete Safari coverage. A feature that is
specific to a platform still needs evidence on that real, supported platform.

## Keep fixtures safe and repeatable

Made-up fixture values should be obvious, minimal and of limited size. Use
fixed example names and loopback addresses. Make credentials easy to
recognize as private test placeholders, and assert that they disappear from
the URL and the DOM.

Don't reuse production exports, realistic answer content, personal email,
random strings of unlimited length or real-time deadlines when a fixed value
will do. Failure output must stay safe even when the whole fixture is
printed.

## Run focused checks

While you build:

~~~sh
cd webapp
npm run typecheck
npm run lint
npm test
npm run test:browser
~~~

Run the generators for the sources you changed:

~~~sh
npm run routes:generate
npm run api:generate
npm run i18n:generate
npm run design-system:generate
~~~

Before you hand off:

~~~sh
npm run check
~~~

The full check verifies brand assets and design tokens, and rejects API,
localization and route adapters that are out of date. It also type-checks,
lints, runs the unit and browser tests and builds the production bundle.

For failures that only happen in the browser, use the browser's developer
tools and Playwright traces. [Tooling and debugging](../tooling-and-debugging.mdx)
covers the VS Code browser launch configurations kept in the repository and
the repository's Go debug entry points. When you debug a flow that depends on
the origin, keep the API server's public address the same as Vite's.

Continue with the [visual review guide](./visual-review.mdx).
