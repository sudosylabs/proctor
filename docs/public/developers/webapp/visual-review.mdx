# Review the product interface

Visual review asks whether the interface shows the right task and the right
state under real conditions. It isn't a last coat of polish once the
behavior is done. Layout, focus, where errors appear, order on small
screens, theme contrast and room for longer text are all part of behavior.

The current access pages should feel calm and precise, and make the next
safe action clear.

- Purple marks the main path that Proctor controls.
- Teal, amber and coral appear only when there really is success, something
  that needs attention, or a failure.
- Neutral surfaces carry ordinary structure.

## Start from a real, built state

The password reset form makes a good reference. It has:

- one task column
- two related password fields
- stable evidence shown before the action
- one primary action
- safe navigation
- space kept for form feedback

The screenshot shows the current implementation. It isn't a page template to
reuse. Another feature may need loading context, a split layout, an empty
state or no form at all.

## Review hierarchy before detail

Ask these questions in order:

1. Can a reader tell the page's purpose and current state without hovering?
2. Is there one action or decision that stands out visually?
3. Does supporting context come before the action that depends on it?
4. Can you tell ordinary evidence, a warning, a failure and completion apart
   at a glance, without a different card style for each state?
5. Does the page still read correctly if color, motion and shadow disappear?

Don't start by adjusting radii or colors while the hierarchy of states is
unclear. Don't wrap every section in a card to make the page look designed.
Borders, spacing, typography and one semantic rule are usually enough
structure.

## Good and bad places for failures

<GovernedFigure asset="developer-webapp-feedback-placement" />

A field failure done well sits next to its field and is linked to it in
code, and the action doesn't move. A general failure appears in the space
kept for feedback next to the action. It is announced politely and doesn't
take focus.

Reject a change when:

- the only sign of failure is a toast that disappears
- the error is far from the field or action that caused it
- adding feedback moves the primary action unexpectedly
- only a red border or an icon shows the failure
- arbitrary server detail becomes visible text
- several live regions compete to announce the same message

## Check tokens and components

Accept:

- semantic variables, such as background, foreground, action, focus and state
- the usual 8-pixel structural spacing, with 4-pixel optical corrections
- 6-pixel controls, 12-pixel cards and 16-pixel large panels, where those
  shapes are really needed
- shadows only for real elevation
- the shared product icon adapter
- local CSS Modules for laying out a feature

Reject:

- literal colors, or a palette that belongs to one feature
- gradients or colored cards added only for variety
- different radii on similar objects side by side
- shadows on every container
- emoji, text glyphs, one-off SVG controls or icons imported straight from a
  library
- `transition: all`, removed focus outlines or arbitrary high z-index values
- a new shared component without two real consumers and a narrow contract

## Review every interactive state

For each button, link, field, toggle, selection or temporary panel, look at
whichever of these states apply: rest, hover, active, focus-visible,
disabled, pending, invalid, selected and final.

- Hover may add confirmation, but must never reveal required information.
- Pending actions keep an explicit text label.
- Disabled content is never the only place an explanation lives.
- Destructive actions look different, and either ask for confirmation or can
  really be undone.

Keyboard review starts at the skip link and follows document order. Focus
indicators stay visible against every surface next to them. Overflow, sticky
content and rounded containers must not clip them.

## Treat responsive layout as rearranging

At `390×844`, don't just shrink the desktop page. Check that:

- every region goes back to a single column of document flow where needed
- primary actions stay reachable and use the available width
- the order of actions still makes sense
- labels and guidance wrap without covering controls
- the page itself scrolls vertically, with no task area that scrolls on its
  own inside it
- 200% zoom causes no horizontal overflow of the page

At `768×1024`, look for awkward wrapping in between, rather than assuming the
mobile and desktop sizes cover it. At `1440×1024`, keep forms and text at
their limited widths. Empty space is no reason to stretch controls or prose.

## Review themes without designing two products

Look at light, dark and system preference for every state you changed.
Components use the same semantic roles in both themes. Dark mode isn't an
inverted screenshot, and it doesn't give states new meanings.

Check:

- contrast of the canvas, surfaces, text, borders, links, focus, actions and
  states
- the correct Proctor lockup from the design system for the color scheme in
  effect
- the color scheme of native controls and scrollbars
- that transparent notices stay transparent
- that state surfaces appear only when their named state is true

Don't change feature behavior by theme, and don't pick a brand asset
directly in a feature component.

## Review longer text and both directions

Test long headings, field labels, validation guidance, action names and
paragraphs. Text may make the page taller. It must not clip, overlap, cut off
required meaning or make the page scroll sideways.

Use whole messages rather than joined-up pieces. Check logical padding,
margins, borders, alignment and directional icons with right-to-left text.
Protocol values and the Proctor brand may stay untranslated where their
contracts say so.

## Record evidence, not taste

A useful review note names:

- the state and route you looked at
- the browser, viewport, theme, zoom, motion setting and locale
- what you saw with the keyboard and focus
- the results for overflow and longer text
- any evidence from forced colors or a screen reader
- for a change you ask for, the token, component, feature or route contract
  that owns it

“This feels off” can start an investigation. But the conclusion you act on
should name the hierarchy, containment, contrast, meaning of a state,
interaction or ownership problem.
