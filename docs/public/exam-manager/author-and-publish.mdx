# Write and publish an Exam

An <Term id="exam">Exam</Term> holds the Exam's lasting identity and who owns
it. Each Exam has exactly one <Term id="exam-draft">Draft</Term> that you can
edit, and a history of <Term id="exam-revision">Revisions</Term> that never
change. A Sitting uses a chosen Revision. It never follows the Draft as you
keep editing.

## Create the Exam in the right Academic Unit

When you create an Exam, you name the Academic Unit that owns it, and give it
a first title and instructions. You are recorded as its creator for good, and
you become its current owner and first Manager.

The Exam itself doesn't store a title, policy, Resources, Class or schedule
that can change. Those live in the Draft, a Revision or a Sitting.

## Every edit checks the Draft revision

Each change to the Draft includes `expected_revision`. When the change
succeeds, use the revision it returns for your next change.

If there is a conflict, someone else has changed the Draft. Fetch the full
current authoring view, compare every area that changed, and then make your
edit again on purpose. Don't just add one to an out-of-date revision number,
and don't write one field over another Manager's work.

When you publish, these parts of the Draft are fixed:

- the title, which is required, and the instructions, which are optional
  Markdown that Proctor cleans up when it displays them;
- the typed Exam Policy Set, including the Focus Loss rule;
- the Browser Policy, which is separate;
- the Exam Resources, in order, with their exact File Revisions;
- the Starter Workspace's folders and files, with their content versions;
- the current Exam Capacity Policy values that set content limits.

There is no general-purpose policy JSON. Use the typed fields in the current
contract:

- Connection Loss is always `flag_and_suspend`.
- Focus Loss has an on or off switch, a minimum duration, a number of
  incidents that triggers it, a time window, and one outcome from a fixed list.
- Browser Policy has a version, a start rule, and a limited set of rules that
  allow HTTPS addresses and paths. Navigation that is blocked is recorded. The
  rules are never quietly widened to let it through.

Each Desktop security family has a mode: disabled, observe or enforce:

- An observed family only records.
- An enforced family stops the candidate starting while its check isn't met,
  and raises a Flag when the check stops being met during the Exam. Choose its
  outcome: a Flag, or a Flag and a suspension.

Turning on the applications family always blocks the apps the Desktop release
never allows, such as remote-control and screen-sharing tools. Its allowed list
may name only apps the release marks as allowable. When the list names any, no
other catalog app may run.

If the candidate's Desktop release can't check a family, the Exam is refused
at Start rather than the family being skipped. Each Desktop release says on
which platforms each check is reliable enough to enforce. An enforced family
refuses Start on a platform where it isn't, while an observed family runs
everywhere. Nothing can be enforced on Linux yet.

When the Exam records the screen, a candidate can start only once their
Desktop is allowed to record and has at least 3 GiB free, which is enough for a
long session and the clips cut from it. Linux can't record yet, so an Exam that
records can't start there.

## Check before you publish

Check:

- the title, and the instructions as they will appear after clean-up;
- the policy values;
- the Browser Policy start rule;
- the order and details of each Resource;
- the Starter Workspace's list of files;
- the content-capacity totals;
- the current Draft revision.

When you publish, Proctor checks the whole Draft in one step. If nothing has
changed since the last Revision, it doesn't create another one. An
out-of-date Draft, an invalid path, a Resource over the capacity limit or an
incomplete typed policy stops publication, and nothing is partly published.

## What publishing creates

Publishing creates the next numbered Revision and makes it the default from
now on. The Draft is then based on the new Revision. Proctor records who
published and when. It saves the audit record and the stored result of the
request before any short-lived side effects run. Editing the Draft later never changes existing
Revisions.

When Managers look up Revisions, they see the Revision's identity, its number
in the order, who published it and when, digests and overall counts. They
don't see the instructions, the exact policy bytes, Resource details, Starter
Workspace paths, opaque content identifiers or source bytes.

If something urgent needs fixing during an Exam, a live correction creates
another Revision that never changes, for one open or paused Sitting. A
correction can change only the instructions, Resources and Browser Policy. It
can't change the Exam Policy, the Starter Workspace, who is eligible or the
schedule. The full correction process is covered in the Phase 6 Sitting
guidance.
