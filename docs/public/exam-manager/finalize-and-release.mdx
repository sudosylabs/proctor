# Finalize the Review and release the result

Finalizing and releasing are two separate steps, on purpose. Finalizing fixes
your complete Review and its list of evidence. Releasing then makes one short
result visible to the candidate.

## Check before you finalize

Work from a freshly loaded copy of the Review, and check that:

- integrity collection has finished, as either `settled` or `gapped`;
- every current Flag has one current decision;
- private notes contain no secrets, credentials or student data that isn't
  needed;
- the remarks for the student contain only text approved for the candidate;
- you have worked in any changes other managers made to the Review revision at
  the same time.

Finalizing locks the sealed Submission. It also fixes the identities of the
Flags, decisions, evidence and discrepancies, as they stand, in a digest
calculated in a standard way. The operation has limits. It covers Browser
groups, stored copies, counts of records beyond the limits, and the list of
native conditions. Proctor never gets around a limit on that list by quietly
leaving records out.

Earlier finalized snapshots never change. If new qualifying Browser evidence
or native conditions arrive during the upload window, the current approval is
withdrawn and any released result is held back. Look at what changed in the
list, update the affected Browser Flag decisions, then finalize and release
again. A delivery that is an exact repeat doesn't start this process.

## Releasing is a separate decision

When you release, Proctor checks again that the Submission is still current,
and that you are releasing the exact finalized Review revision. Until the
release succeeds, the candidate's result is answered as "not found". Proctor
doesn't return it as an empty or “pending” private Review.

The released result contains only:

- the identifiers of the Review, the Submission and the Attempt;
- the approved Markdown remarks for the student, cleaned up for display;
- the release time.

It never contains Flags, evidence, discrepancies, decisions, private
rationale, manager notes, sealed Workspace content, a grade, a score, a
rubric, pass or fail, or any academic outcome. Proctor doesn't currently
model any of those academic results.

## If you aren't sure a request went through

Finalizing and releasing both need an idempotency key. If you lose the
response, set up the transport proof again, then retry exactly the same
operation with the same body and idempotency key.

A revision conflict means the Review has changed, and you need to read it
again. A state conflict means something it depends on isn't finished yet. It
doesn't let you skip the missing decision or an unfinished collection state.
