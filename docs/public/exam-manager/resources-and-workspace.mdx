# Add Resources and a Starter Workspace

Exam Resources and the Starter Workspace are both protected material that you
write. They do different jobs, though, and Proctor tracks them in different
ways.

| Material | How candidates use it | How it is identified and changed |
| --- | --- | --- |
| Exam Resource | read-only supporting material, kept outside the code Workspace | a fixed File Entry, with File Revisions that never change and a set order |
| Starter Workspace | the files and empty folders copied into each Attempt Workspace at the start | one tree of folders and files, with opaque content versions |

## Exam Resources

Each Resource has:

- a display name, which is required;
- an optional short Markdown description;
- a set position, counting from zero;
- an exact content revision that is available.

Replacing a Resource's content creates another File Revision, so Revisions
you have already published keep the bytes they chose. Removing a Resource
closes the gap in the Draft's order, but doesn't erase published history.

By default, the authoring policy allows ten Resources of up to 10 MiB each.
The server's fixed upper limits are 100 Resources and 100 MiB each.

At first, Proctor accepts only checked PDF, PNG, JPEG, WebP, UTF-8 text,
Markdown, CSV and JSON files. It doesn't accept executables, archives, files
with macros or disk images. Your Institution's current policy may be stricter,
and Proctor checks it again each time you change a Resource and when you
publish.

## Build the Starter Workspace as a tree

Paths are case-sensitive, relative POSIX paths in standard form. Proctor
rejects:

- empty or absolute paths;
- paths that use dots to climb out of the Workspace;
- repeated or trailing separators;
- backslashes;
- control characters;
- the reserved `.proctor` folder at the top level.

Folders are only records, not stored content. Proctor rejects removing a
folder that still has things in it, rather than deleting everything inside.

By default, a Starter Workspace can have 500 entries, 10 MiB per file and
50 MiB in total. The fixed upper limits are 5,000 entries, 100 MiB per file
and 1 GiB in total.

Each change to a file is checked against its current Workspace Content
Version, which is an opaque value. It exists only to stop two changes from
overwriting each other. It doesn't identify a file or a revision.

## How content is protected

While a file uploads, Proctor streams it into a new storage object in the VFS
whose name can't be guessed, and checks its type, size and checksum.
PostgreSQL makes the content visible only once its details, and its link to
the Exam material, have been saved. If that save fails, an invisible object
may be left behind, and a limited clean-up job removes it later. Visible
details never point to a half-finished upload.

Every protected read is authorized on its own. Proctor returns the content
inline, with a checksum ETag and `nosniff`, and never reveals the storage key
or a public URL.

When candidates take the Exam, there is no way to download, export, print,
drag out, open in another app or save the material to a local folder. To
display material, Proctor has to send a limited number of bytes to an
authorized app. What Proctor can guarantee is that the material can't be
exported, not that the bytes never reach the device.

If your Institution lowers its capacity limits, Proctor doesn't rewrite the
material already in your Draft. You can still remove Resources, reorder them
and fix their details. Any replacement content, and publishing, must meet the
new limits. Publishing fixes all the capacity values for future Attempts.
