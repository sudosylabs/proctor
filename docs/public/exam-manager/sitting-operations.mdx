# Run an Exam Sitting

An <Term id="exam-sitting">Exam Sitting</Term> delivers one Revision, which
never changes, to one exact Class during a time window. The window includes
its start time but not its end time. The schedule, the Class and the chosen
Revision belong to the Sitting, not to the Exam, which you can reuse.

<GovernedFigure asset="sitting-lifecycle-controls" />

## Schedule against the exact academic setup

When you schedule a Sitting, Proctor checks that:

- the Class's Programme belongs to the Exam's Academic Unit;
- the chosen Revision belongs to the same Exam;
- the whole time window fits inside the Class's exact Academic Period;
- any new or changed start time is strictly later than the current time in
  PostgreSQL.

You can reschedule or cancel a Sitting only while it is Scheduled. When the
Sitting opens, Proctor checks the academic setup again. So if the lineage or
the Period changes after you schedule it, a Sitting that is no longer eligible
still won't open.

Jobs for the start and the deadline are hints, and duplicates are dropped. The
state in PostgreSQL, and the recovery scan, are what decide.

## What each action does

| Action | When you can use it | What it changes for good |
| --- | --- | --- |
| reschedule | Scheduled | changes the Revision, Class or time window, checked against the Sitting revision |
| cancel | Scheduled | stops the Sitting from ever opening; creates no Attempts or Submissions |
| pause | Open | keeps the Exam on screen and integrity monitoring running, but blocks new Attempts, changes and submission |
| resume | Paused | lets eligible candidates carry on; it doesn't add the paused time to the deadline |
| extend | Open or Paused | moves only the scheduled end later; it can't shorten the Sitting or change the start |
| close early | Open or Paused | moves to Closing and seals every unfinished Attempt that was created |
| scheduled deadline | Open or Paused | moves to Closing by the server's clock, and records the deadline as the reason the Sitting ended |

At or after `scheduled_end_at`, the deadline wins over any manager command
that arrives at the same moment. In version 1, time spent paused doesn't
extend the Sitting. Closing is work you can watch happen. It doesn't mean the
same as Closed.

## Closing and no-shows

As soon as a Sitting is Closing, Proctor turns away new participation and
Workspace changes. A Job that can't be canceled then seals unfinished
Attempts, a limited batch at a time, from the last Workspace state the server
confirmed. It skips Attempts that already have a Submission. The Sitting
closes only when every created Attempt has finished.

Closing doesn't depend on any one worker, so losing a node can't stop it.
Retries rely on the rule that each Attempt has at most one Submission, and
recovery recreates any work that is missing or failed for good. A Sitting with
no Attempts closes through the same completion check.

Proctor never creates an Attempt or Submission for a student who didn't
enter. The no-show view lists the members who were active at the recorded
`opened_at` time, leaving out everyone who has an Attempt.

## Read candidate status at one server time

The status board is a limited view that is never cached. It is worked out at
one server time, which the board shows. It never shows a Session, credential,
Connection, evidence or private reason.

| Status | What it means while you run the Sitting |
| --- | --- |
| not started | an eligible member of the roster has no Attempt |
| ready | the Attempt exists but has no active Participation |
| connected | the current Participation lease is active and the candidate is connected |
| reconnecting | the candidate can still recover their connection before the lease expires |
| lease expired | the secure connection can no longer be renewed, and Proctor is applying the rules |
| suspended | the Attempt is blocked until someone authorized reviews it or lets the candidate back in |
| submitted | one final Submission exists |

Realtime events tell the board to fetch fresh data. They don't change the
board themselves, and they don't replace the state you get over HTTP.
