# Build the academic structure

Proctor models one Institution. Its Academic Units can stand for faculties,
schools, departments or any other hierarchy your Institution uses. What you
call them is only presentation. The names don't change how permissions work.

<GovernedFigure asset="academic-structure-ownership-map" />

## Create things in ownership order

1. Create the top-level <Term id="academic-unit">Academic Units</Term>, then
   their children. A Unit has at most one parent, and a Unit can't end up as
   its own ancestor.
2. Create each <Term id="programme">Programme</Term> under exactly one
   Academic Unit.
3. Create <Term id="programme-level">Programme Levels</Term> under the
   Programme they belong to.
4. Create <Term id="academic-period">Academic Periods</Term> at the
   Institution or at an Academic Unit.
5. Create each <Term id="class">Class</Term> under one Programme Level, and
   name exactly one Academic Period that applies to it.

A Period owned by the Institution applies everywhere. A Period owned by an
Academic Unit applies to that Unit and everything below it. Neither overrides
another Period, and their dates may overlap.

Proctor never guesses a "current year". Every Class, progression and transfer
names the exact Period it uses.

## Choose names that won't need to change

`name` is the stable name that software uses. It must be unique within the
owner. `display_name` is what people read. Use the description to explain what
something is for, not to encode its place in the hierarchy or any permission.
IDs are opaque. They say nothing about order or scope.

Before you create a Class, check that the Period you picked applies to the
Programme's Academic Unit. If it doesn't, the structure has a mistake to fix.
Don't work around it by creating a duplicate Period somewhere else.

## Move a Unit with care

Moving an Academic Unit to a new parent changes the chain Proctor follows to
work out Programmes, Classes, which Periods apply, and scoped permissions. The
server checks both the old and the new position in one step. It rejects a move
that would create a loop, cross into another Institution, or rely on
out-of-date dependencies.

Before you move a Unit:

- list its child Units, Programmes, Periods it owns, active memberships and
  Role Bindings;
- work out which inherited permissions will reach further or less far;
- make the change once;
- check the resulting hierarchy and the audit event before you carry on.

## Archive, don't delete

Archiving keeps the IDs, the place in the hierarchy, the timestamps and the
audit history. It does not cascade to active children or relationships, so you
resolve those first.

| Resource | What usually has to be resolved first |
| --- | --- |
| Academic Unit | Active child Units, Programmes, memberships, or permissions that depend on it |
| Programme | Active Programme Levels, or Classes under those levels |
| Programme Level | Active Classes |
| Academic Period | Classes or memberships that still use this exact Period |
| Class | Active memberships or exam dependencies |

Resolve each blocker through its own lifecycle. Never remove a parent just to
avoid ending a membership or a Role Binding. Old Classes and Periods stay
useful context for audit after you archive them.

## Check every structural change

After you create, update, move or archive something:

1. read the resource itself through its own endpoint;
2. list its direct owner or children, rather than rebuilding a tree from names;
3. confirm it is still visible at the scope you expect;
4. check the audit event for the action, resource, scope and outcome.

For request bodies, how retries work and how to recover from conflicts, follow
the <Link to="/api/recipes/academic-structure">Academic Structure API recipe</Link>.
