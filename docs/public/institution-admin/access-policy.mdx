# Govern account access

The <Term id="access-policy">Access Policy</Term> is Institution data that
Proctor stores and keeps a history of. It chooses among features the operator
has already set up:

- local sign-in;
- public local registration;
- adding a local password to an account;
- admission by Invitation;
- admission through an external provider;
- Desktop Authorization.

It never holds provider secrets, TLS files, SMTP credentials or any other
deployment configuration.

## What the deployment supports and what the policy allows are separate

Public discovery, which anyone can read before signing in, lists the sign-in
methods available right now. It also gives two facts from the deployment that
hosted pages show: the optional support mailbox and the minimum password
length.

The policy view, which needs you to be signed in, shows the policy's opaque
ID, its revision, its settings and a limited history of changes.

The policy can select a provider the operator has configured. Writing a
provider's ID into the policy does not make it available if the deployment
doesn't have that provider, or has it set up incorrectly.

Each provider mode treats people differently:

| Mode | Someone already linked to this provider | Someone not yet linked |
| --- | --- | --- |
| disabled | Cannot sign in | Cannot get in |
| linked only | May sign in | Refused, without revealing whether another account exists |
| Invitation required | May sign in | Must come in through the provider journey tied to their specific Invitation |
| auto provision | May sign in | May get a new User with no relationships, but only after the configured eligibility checks pass |

Auto-provisioning creates no Affiliation, membership or Role Binding. The email
address and username from a provider are suggestions for the profile. Proctor
never uses them to merge accounts.

## Preflight any change that removes a way in

Call <Link to="/api/reference/preflight-access-policy">Preflight access policy</Link>
with the settings you intend and the revision you expect. Resolve every blocker
it reports before you replace the policy.

Preflight is only advice. When the change is committed, the server checks
again in one step against the current policy in PostgreSQL, the active
administrators, their sign-in methods, which providers are available, and
whether mail is working.

A shared lockout guard stops two changes made at the same time from each
removing a way in that the other assumed would stay. The same guard also
covers disabling a User, ending the last `system_admin` binding, removing a
password and unlinking a provider.

Before you turn off local sign-in:

1. verify the first administrator's mailbox;
2. configure and test mail;
3. enable and test the external provider you plan to use;
4. link an active system administrator to a provider identity on purpose
   (the provider identity can't change once linked);
5. ideally, set up a second administrator who has a separate working way to
   sign in.

## Decide whether to end existing Sessions

Turning off a sign-in method affects new sign-ins only. Existing Sessions keep
working unless the same change sets `revoke_existing_sessions`.

When it is set, Proctor replaces the policy and ends the Sessions that signed in
through the newly disabled methods, all in one step. Sessions that used methods
you kept are left alone. `revoke_existing_sessions` applies to that one change
only. It is not a setting that stays in the policy.

## Require two-step verification for Role holders

The policy setting `role_holder_mfa_required` requires a second factor from
every Role holder. A Role holder is any User with a current Role Binding at any
scope, and that includes system administrators.

- If a Role holder without a second factor signs in on the web, they get a
  Session marked `mfa_enrollment_required`. That Session can only reach the MFA
  status, setup, activation and challenge operations, reauthentication and
  sign-out. This lasts until they activate a second factor or pass a challenge,
  which makes the Session multi-factor.
- For such a User, a CLI or Desktop sign-in, a Desktop code exchange, or a
  refresh of a single-factor Session fails with
  `authentication.mfa.enrollment_required`. A web refresh restricts the Session
  instead. So if someone becomes a Role holder partway through a Session, the
  rule takes effect at their next refresh.
- While the rule applies, a Role holder can't turn off MFA. The request fails
  with `mfa.required_by_policy`.

If you turn the rule on in the same change as `revoke_existing_sessions`, Proctor
also ends Role holders' Sessions that haven't proved a second factor.

Preflight refuses the rule, with the `mfa_unavailable` blocker, while the
operator has MFA turned off in the deployment configuration. If the operator
turns MFA off after the rule is on, the rule pauses instead of locking people
out. Nothing is restricted or refused, the node logs one warning, and the
policy view reports `role_holder_mfa_enforced: false`.

## Shorten Session lengths

The idle and absolute Session lifetimes the operator configures are the default
lengths, and also the maximum. The policy can shorten either one with
`session_idle_minutes` and `session_absolute_minutes`. A value of `null` keeps
the default. The policy view shows each default and the longest length the
policy may set.

The lengths have these limits:

- An idle length must be at least a minute longer than both the configured
  access-credential lifetime and the activity-update interval. It can never be
  longer than the absolute length in effect.
- An absolute length must be longer than the configured recent-authentication
  window and the minimum idle length.

The shorter lengths apply to new Sessions, activity, web and Desktop refresh,
and the Desktop code exchange. The access, refresh and activity-interval
lifetimes stay in the deployment configuration.

Shortening a length brings forward the deadlines of live Sessions and their
credentials, as part of the same policy change. Making a length longer never
extends a Session that is already running.

## Control who can use Desktop

The Access Policy turns the Desktop Authorization feature on or off.

A separate Desktop Compatibility Policy narrows the list of verified builds. It
can set a minimum release, a limited list of revoked build IDs, an availability
state, an optional time to try again, and a short message from the
administrator. It cannot make an unknown build valid.

When you are helping one person with their client, use the `system/ping`
result for their request. When you are reviewing what the Institution intends,
use the policy view, which needs you to be signed in. Don't publish update URLs,
and don't tell people to fake the values that select a build.

## Commit the change and check it

Replace the policy with the revision you expect and an `Idempotency-Key`. A
revision conflict means someone changed the policy after you read it. Fetch it
again, think through the whole state you want, and use a new idempotency key.
Don't simply overwrite another administrator's change.

After the change succeeds:

- read the new revision;
- check signed-out discovery from the public address;
- check the safe audit and history fields for the exact setting names that
  changed;
- check separately that the Sessions you meant to end were ended;
- test every administrator sign-in method you kept before you end the
  maintenance window.
