# Inspect audit history

Audit history is the permanent record, kept in PostgreSQL, of security-sensitive
attempts, changes and permission decisions. Operational logs describe what the
server process did. They are not a replacement for audit.

## Know what you can see

`audit.view` granted Institution-wide can reach the Institution's full set of
audit events. `academic_audit.view` is narrower. It
covers only academic changes, Invitations, batches and decisions whose scope
falls inside an Academic Unit or Class you are allowed to see, and everything
below it. It leaves out identity, provider and security events that aren't
related.

An Affiliation on its own doesn't make a User visible to you through a Unit.
You need a current relationship that makes them visible, as well as the
matching audit permission.

If your bindings change, what you can see in audit changes from then on. A
page you loaded earlier is not proof that you are allowed to see it now.

## Read events as decisions, not as copies of data

Each event gives you the action, the type of resource, the academic scope it
resolved to, the outcome, the actor or principal, request details and the
server time. Any before-and-after snapshots are safe and limited in size.
Events must never contain credentials, provider claims, Invitation claims, Exam
answers, file contents, private Review reasoning or unlimited user input.

When you investigate a change:

1. start with a narrow time range and resource filter;
2. page through results with the returned cursor, and keep the same filters;
3. when you need to, match the safe `request_id` against operational logs;
4. tell apart the outcomes `attempt`, `success`, `fail`, `allow` and `deny`;
5. note the audit event ID in your investigation, not a copy of private data.

When a permission decision must be audited and Proctor can't write the audit
record, the action is refused (it fails closed). For a critical change, the
data may commit and then the final audit step fail. That leaves an unresolved
attempt record. Operators resolve this case. They don't invent a
successful outcome from what the logs say.
