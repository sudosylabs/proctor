# Run imports and student progression

For up to 200 typed items, send a JSON batch. For larger work that comes from a
file, use a CSV import. Neither one runs arbitrary commands. Linking identities,
setting passwords, removing MFA, permanently deleting data and merging Users in
bulk all stay outside these workflows.

<GovernedFigure asset="onboarding-import-timeline" />

## Choose the scope in the request, not in the file

Student Class imports and teacher Academic Unit imports name their exact target
in the request, not in a row someone can edit. Institution-wide onboarding may
use the target names that its schema defines. Administration of existing Users
picks one Institution, Unit or Class scope outside the file, and no row can go
beyond it.

A CSV file must meet these limits:

- at most 10 MiB and 50,000 data rows;
- UTF-8, with an optional BOM;
- quoting compatible with RFC 4180;
- unique headers, and headers and fields within their size limits;
- no NUL characters and no invalid Unicode.

Proctor ignores unknown columns only where the import documents it. It lists
their names once in the preview, so you can spot a misspelled header.

## Review the preview before anything changes

Uploading a file starts a validation Job. It does not change any account,
membership or Role, and it sends nothing. When validation finishes, Proctor:

- turns names into exact IDs and revisions;
- normalizes the rows;
- deletes the original CSV bytes;
- freezes a preview that can't change, identified by a digest of its content.

In the preview, review:

- the scope, mode, digest, total rows, unknown headers and validation counts;
- every invalid or duplicate row;
- the resolved Users, relationships, targets and Role revisions;
- the dates each grant is valid for, and the rows that will change nothing.

Then choose how to commit. `require_all_valid` refuses to commit if any row in
the preview is invalid. `valid_rows_only` skips the invalid rows. Things can
still change after the preview, so Proctor checks permissions and validity
again for each row as it runs.

## Expect partial completion

Each row commits on its own, as one complete unit, and rows don't depend on
each other. If a later row hits a conflict, the import ends as
`completed_with_errors`. Rows that already succeeded are not rolled back.

Cancelling stops new rows from starting and lets a row that is already
committing finish. It never rolls back finished work.

To recover, you undo effects yourself:

1. read the report that Proctor keeps;
2. decide which successful effects to reverse;
3. reverse each one through its normal end, revoke or replace operation, which
   checks your permissions again.

Don't run the whole file again under new row keys just to hide partial
results.

For the limited time it keeps them, each report has the source row number, a
safe reference, the normalized operation, the status, the IDs created and the
public error code. Downloading a report checks your permissions again and
escapes spreadsheet formulas.

General Job views, logs, metrics and audit hold only safe IDs, counts, timing
and codes from a fixed list. They never hold full rows or lists of recipients.

## Transfer or progress students

Progression always names the exact source and destination Periods and Classes,
and the moment it takes effect. Do a dry run to see every student conflict
before you commit.

- A transfer within the same Period ends the active Class membership and
  replaces it, in one step.
- Progressing into another Period adds new history. The old membership is not
  rewritten.
- Each student commits on their own. Failures stay in the report.
- A student can have at most one active Class membership in an Academic
  Period.
