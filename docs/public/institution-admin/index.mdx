# Set up an Institution

Every Proctor installation holds one <Term id="institution">Institution</Term>.
Its academic structure, its rules for who can sign in, and the permissions you
grant at each level together decide how exams are created and delivered.

<Maturity state="preview">
  The administration features exist on the server, but the full set of
  administration screens does not yet. Use this guide to understand how the
  pieces fit together, and use the API guide for integration work today.
</Maturity>

## Set things up in this order

1. **Bootstrap the installation and the Institution.** This first protected
   setup step creates the installation's identity and the first
   administrator's authority.
2. **Create <Term id="academic-unit">Academic Units</Term>.** Use them for
   faculties, schools, departments or any other units in your hierarchy.
3. **Define <Term id="programme">Programmes</Term> and <Term id="programme-level">Programme Levels</Term>.**
   Each Programme belongs to its place in the academic structure. Its levels
   describe how students progress through it.
4. **Open <Term id="academic-period">Academic Periods</Term> and <Term id="class">Classes</Term>.**
   A Class is the actual list of students for one Programme Level in an
   Academic Period that applies to it.
5. **Configure sign-in and onboarding.** Before you bring people in, choose
   which sign-in methods are allowed, who may join, and how Invitations
   behave.
6. **Grant Roles through scoped bindings.** Affiliations and memberships
   record relationships. On their own they never grant broad permissions.

## Keep three ideas apart

| Idea | What it records | What it does not give |
| --- | --- | --- |
| <Term id="affiliation">Affiliation</Term> | A person's relationship with the Institution | Permission to administer every resource |
| Membership | A place in an Academic Unit or Class | Any broad Role |
| <Term id="role-binding">Role Binding</Term> | Permissions at Institution, Academic Unit or Class level | Control outside that level |

## Words to use

Say **Class**, not Group, for a list of students. Say <Term id="exam-manager">Exam
Manager</Term> for the person who created an Exam, or another teacher with the
same right to manage it. "Proctor" is the product's name. It never quietly
gives anyone a special role.

## First administrator checklist

Bootstrap creates all of the following in one transaction: the Institution,
the first User, their password, the protected `system_admin` Role and its
binding, Access Policy revision 1, and an audit record of the success. It does
not create a Session, and it does not prove that the administrator controls
the email address.

After bootstrap, the first administrator should:

1. sign in through the normal hosted sign-in page;
2. verify the email address used during bootstrap;
3. test transactional mail;
4. configure and enable any external sign-in provider, then link to it on
   purpose;
5. set up a second administrator who has their own working way to sign in;
6. only then consider turning off local sign-in.

Recovering access on the host is an offline procedure for the operator. There
is no administrator endpoint for it. Do not loosen the Access Policy as a
stand-in for a recovery process you have tested.
