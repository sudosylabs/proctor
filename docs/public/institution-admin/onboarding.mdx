# Invite people into the Institution

An <Term id="invitation">Invitation</Term> is a stored package that exists
before the person has a User account. Each one has a single purpose that never
changes. It is not an email, and it is never an empty placeholder account.

When you create an Invitation, Proctor records the package and the intent to
send its mail together, in one step. When someone accepts it, Proctor creates
or finds their User and applies every effect fixed in the package. Either all
the effects apply or none do.

## Pick the purpose that matches what you want to happen

| Purpose | What happens when it is accepted |
| --- | --- |
| Student Class | A student Affiliation if the person doesn't have one, and membership in one specific Class |
| Teacher Academic Unit | A teacher Affiliation if needed, membership in the Unit, and one chosen Role Binding at that scope |
| Academic Unit Role | One approved Role Binding at that exact Unit, for an existing User |
| Institution Role | One approved Institution Role Binding, for an existing User |

When you send an Invitation, you need the authority for every effect it
carries. An administrator scoped to one Unit cannot package a broader Role, or
pass on an action they don't hold themselves.

When the person accepts, Proctor checks again, as part of the same step that
applies the effects. It checks that the inviter still has the authority, that
the target and the Role are still valid, and that the Access Policy, the
account state and the academic rules all still allow it.

## Resend, replace, revoke and expire

These do different things.

- **Resend** keeps the same package but issues a new secret and a new
  deadline. Every link sent before stops working.
- **Replace** is how you change the recipient, purpose, target, Role or the
  dates the access is valid. Proctor creates a new Invitation and marks the old
  one as superseded.
- **Revoke** cancels one Invitation straight away, and cancels any mail still
  waiting to be sent where it can. If the SMTP server already accepted the
  mail, the link in it is harmless, because the hosted page always reads the
  Invitation's real current state.
- **Expire** happens by the server's clock, not by anything in an email
  client. If an Invitation expires while the person is away signing in with a
  provider, they cannot accept it.

Never change the contents of a package after a link to it has been sent. Never
paste an Invitation claim into logs, a ticket, analytics or a provider's
settings.

## What the person sees when they accept

The `/join` page removes the credential from the URL fragment before it shows
anything. It then exchanges that credential, once, for a short-lived handle
and a host-only HttpOnly proof cookie. The page shows, read-only, the address
the Invitation was sent to. For a student Class Invitation it also shows the
Class's display name. It never names an Academic Unit or a Role.

Depending on the policy and the package, the person may:

- create a local password;
- prove who they are with an enabled sign-in provider;
- accept, using their current Session, a package meant for an existing User.

An email address from a provider can prove that the person controls that
mailbox. Proctor never picks or merges an account because two email addresses
match. A provider mailbox that differs from the invited address is accepted
only if it is verified and doesn't belong to another User.

Role packages for existing Users still need the claim. They create no
password, Session, membership or welcome message.

## Check an Invitation without exposing the claim

Read the safe view of the Invitation. It shows the purpose, the recipient, a
summary of the target, the Role name, who sent it, when each lifecycle step
happened, the User who accepted it if anyone has, and a limited delivery
status. "Pending" does not mean delivered. An SMTP server accepting the mail
does not prove it reached the inbox.

If an acceptance fails, the claim stays unused, unless the Invitation itself
reached the end of its life. The recipient sees a short, limited message. You
use the specific Invitation and its audit record to find the cause, which may
be an invalid target, a changed Role, an inviter who lost their authority, the
policy, or a mail delivery problem.
