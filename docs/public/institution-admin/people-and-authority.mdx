# Manage people and permissions

Proctor keeps four things apart on purpose: who a person is, how they sign in,
where they belong, and what they may do. That way an enrollment import or a
claim from a sign-in provider can't accidentally make someone an
administrator.

## Each layer means one thing

| Layer | What it records | What it does not imply |
| --- | --- | --- |
| <Term id="user">User</Term> | The account itself, its profile and its lifecycle state | A password, a membership or any permission |
| Sign-in method | A password, or an external provider's subject (which never changes), linked to the User | An Affiliation or a Role |
| <Term id="affiliation">Affiliation</Term> | A relationship with the Institution | A place in an Academic Unit, or any authority |
| Academic Unit Member | A relationship with one Unit, for a set time | A Role Binding |
| Class Member | One student's place on the list for one Class in a Period | Permission to administer the Class |
| Role | A reusable, Institution-wide set of fixed actions | Any scope, on its own |
| <Term id="role-binding">Role Binding</Term> | One Role granted to one User at Institution, Academic Unit or Class scope | Control outside that scope |

A student may have several Affiliations at once, but at most one active Class
membership in an Academic Period. A teacher may have different Role Bindings in
several Academic Units.

## Use the current-User context for navigation, not for permissions

The current-User context is a small view of the signed-in User's identity and
the product areas that matter to them. It is never cached (`no-store`). Use it
to drive navigation, and fetch it again after relationships change. It is not a
snapshot of permissions. Every task still checks, at the time, whether this
User may perform this action on this resource.

Profile updates change the fields used to present the person. Uploading or
removing a profile picture uses a narrower action.

Academic Unit administrators can see a User only through a current
relationship inside the part of the hierarchy they are allowed to manage. The
view leaves out relationships outside it. An Institution Affiliation alone
does not make a User visible there.

To look at your own safe profile and your navigation context, call each one
separately:

```sh
curl --fail-with-body \
  --request GET \
  --url 'https://proctor.example.edu/api/v1/users/me' \
  --header 'Authorization: Bearer <access-token>'

curl --fail-with-body \
  --request GET \
  --url 'https://proctor.example.edu/api/v1/users/me/context' \
  --header 'Authorization: Bearer <session-access-token>'
```

The first response is your safe User profile. The second is a navigation view
for an interactive Session. It contains no credentials and is marked
`no-store`.

A Personal Access Token can read the profile if its scope allows it. It can't
stand in for the interactive Session that the context route needs. Fetch the
context again after relationship or account changes, and never cache it as a
permission decision.

## Update a visible User's profile

You need two things: the target User must be visible to you right now, and you
must hold the profile-management action at a scope that reaches them.

First read `GET /api/v1/users/<user-id>`, so you don't mistake a hidden or
out-of-date User for an account you can edit. Then send only the presentation
fields you mean to change:

```sh
curl --fail-with-body \
  --request PATCH \
  --url 'https://proctor.example.edu/api/v1/users/<user-id>' \
  --header 'Authorization: Bearer <access-token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "display_name": "Amina Diallo",
    "first_name": "Amina",
    "last_name": "Diallo",
    "locale": "en",
    "timezone": "Europe/Paris"
  }'
```

If it succeeds, you get the updated safe profile back. Check the identity and
fields it returns, then look in the audit history you can see for the change.

Fields you leave out, and fields you set to `null`, stay as they are. You can't
use `null` to clear a field.

- A `404` may be deliberate. It can hide a User who is outside your current
  scope.
- On `409 user.conflict`, fetch the profile again before you pick another
  username or retry the other fields.
- If authorization or audit is unavailable, treat the update as not made.

Email, account state, credentials, memberships, Affiliations and Role Bindings
are not profile fields. Each has its own operation.

## Replace or remove a profile picture safely

Proctor turns PNG, JPEG and WebP images into private WebP copies at 128, 256 and
512 pixels. They are protected content, not public URLs.

The first custom upload leaves out `If-Match`. A replacement sends the current
strong ETag, so one administrator can't overwrite a newer picture by mistake:

```sh
curl --fail-with-body \
  --request PUT \
  --url 'https://proctor.example.edu/api/v1/users/<user-id>/profile-picture' \
  --header 'Authorization: Bearer <access-token>' \
  --header 'Content-Type: image/png' \
  --header 'If-Match: "<current-sha256>"' \
  --data-binary '@profile.png'
```

Check the saved picture, and keep the ETag it returns for your next change:

```sh
curl --fail-with-body \
  --request GET \
  --url 'https://proctor.example.edu/api/v1/users/<user-id>/profile-picture?size=256' \
  --header 'Authorization: Bearer <access-token>' \
  --header 'Accept: image/webp' \
  --dump-header profile-picture.headers \
  --output profile-picture.webp
```

Removing a picture always needs the current custom picture's ETag. Removal
brings back the default picture, which Proctor keeps permanently:

```sh
curl --fail-with-body \
  --request DELETE \
  --url 'https://proctor.example.edu/api/v1/users/<user-id>/profile-picture' \
  --header 'Authorization: Bearer <access-token>' \
  --header 'If-Match: "<current-sha256>"'
```

A `409 user.conflict` means someone changed the picture after you read it.
Fetch the current picture and ask whether the newer one really should be
replaced or removed. Don't drop the `If-Match` header and retry without
looking.

If the image is invalid, or the service that converts images is unavailable,
nothing is replaced. Keep source images and downloaded copies out of logs,
tickets and ordinary audit fields.

## Build Roles from fixed actions

`system_admin` is the only built-in Role, and it is protected. Create your own
Roles, such as Teacher, Roster Manager or Reviewer, from the fixed list of
actions. Don't name a Role after an HTTP verb, and don't assume its display
name does anything.

Bindings only ever add access, and anything not granted is denied. Each scope
reaches as follows:

- Institution scope reaches the Institution.
- Academic Unit scope reaches the Units below it only where that action's
  inheritance rule allows.
- Class scope reaches that one Class.

Permissions for Programmes, Programme Levels, Academic Periods and Exams are
worked out through the Institution, Academic Unit or Class that owns them.
They are not extra kinds of binding.

## Delegate no more than you hold

You can't create a binding broader than your own, or pass on an action you
don't have. You also can't delegate protected system, Role-management,
Access-Policy or delegation authority unless you hold the separate parent or
Institution authority it needs. The server checks the exact target scope again
when it commits.

End a Role Binding in a way that keeps its history of when it applied.
Deleting a custom Role works like archiving it, and it is blocked while active
bindings depend on it. Ending a membership doesn't quietly end the person's
Role Bindings. When someone leaves a Unit, review both.

## Disable accounts only at Institution scope

Disabling a User acts on the whole Institution. It shares the lockout guard
that protects the last working way for an administrator to sign in. An
Academic Unit administrator ends relationships within their scope instead.
They don't disable the User for everyone, change the person's identity or step
in on their credentials.

Disabling changes the account state and ends active Sessions in one step. It
keeps past relationships, Attempts, Submissions and audit records. Enabling the
account later does not bring back Sessions, credentials, ended memberships or
Role Bindings.

After either change, check the safe profile that comes back and reload the
administration views it affects. If the guard returns
`409 user.last_system_admin`, set up another administrator with a working way
to sign in, check it works, and then try again. Never get around the lockout
protection.

For the exact operations and retry rules, see
<Link to="/api/recipes/roles-and-scopes">Roles and Scoped Bindings</Link>.
