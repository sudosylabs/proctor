# Back up, restore, upgrade and roll back

Proctor has no built-in backup command. To be able to recover an installation,
you back up four things together and restore them together:

| What | What it holds | How to back it up |
| --- | --- | --- |
| PostgreSQL | Every durable fact: Users, Exams, Attempts, Submissions, audit, Jobs, mail state, file metadata and leases | A PostgreSQL logical or physical backup |
| VFS | Managed file bytes under `VFS.Local.Root`, or in the `VFS.S3` bucket and prefix | A filesystem snapshot or an object-store copy |
| Configuration | The active JSON file and every `PROCTOR_` environment override | Your secret and configuration management |
| Key material | The MFA and mail sealing key rings, the bootstrap secret and the TLS files | Your secret store, kept with the backups that need them |

Redis and Memberlist hold only disposable state, so you don't back them up.

<Maturity state="preview">
  These procedures follow from how the current build stores and checks its
  state. They are not a certified disaster-recovery runbook. Proctor doesn't
  state a recovery point or recovery time objective, and you must try every
  procedure in your own topology before you rely on it.
</Maturity>

## How PostgreSQL and file bytes stay consistent

PostgreSQL is the source of truth. Managed bytes live in VFS under keys that
can't be guessed, never change, and belong to one revision. Only metadata in
PostgreSQL points to them. Proctor writes an object first and commits its
metadata afterwards. It deletes bytes only after the database has committed
their removal. As a result:

- an object with no database row is invisible to Proctor and does no harm;
- a database row whose object is missing makes that content unreadable.

A backup is consistent when every object the database snapshot refers to is
in the VFS copy. There are two ways to get there:

- **Cold backup, consistent every time.** Stop every application node, and
  confirm with `proctor cluster status` that no serving lease is live. Back up
  PostgreSQL, copy VFS, and start the nodes again.
- **Online backup, best effort.** Back up PostgreSQL first, then copy VFS as
  soon as you can. Objects created in between are harmless extras. Content
  that is removed and physically purged in between is missing from the copy,
  so keep that window short. With S3, turn on bucket versioning and keep
  noncurrent versions for longer than the backup window. A restore can then
  recover an object that was deleted during the copy.

Never back up VFS before PostgreSQL. Content uploaded between the two copies
would be referred to by the database but missing from VFS.

## Back up PostgreSQL

Proctor needs PostgreSQL 14 or later and the `pg_trgm` extension, which the
baseline migration installs. Either backup method works. Choose by what you
need to recover.

- **Logical backup** (`pg_dump --format=custom`) captures one consistent
  snapshot of the Proctor database. Restore it with `pg_restore` into an empty
  database on the same or a later PostgreSQL major version. It can't replay
  changes made after the dump.
- **Physical backup** (`pg_basebackup` with continuous WAL archiving) captures
  the whole cluster and supports point-in-time recovery. It restores only to
  the same PostgreSQL major version.

Include the Morph bookkeeping tables `db_migrations` and `db_lock`. They record
which schema version a restored database is at. Backups contain student data,
Exam content, answers and sealed secrets. Encrypt them, and limit who can reach
them as you would for the live database.

## Back up configuration and key material

Back up the active configuration file, and the environment overrides that your
service manager or container runtime supplies. `proctor config show` prints the
effective configuration with every secret redacted. It records how a deployment
is set up, but never the secrets themselves, so capture secrets from where you
keep them.

Keep these with the backups that need them:

- **The `Authentication.MFA` key ring.** TOTP secrets are sealed with it. After
  an MFA key rotation, a backup taken before the rekey finished still needs the
  old key. A node refuses to start if the configured ring lacks a key that
  seals a stored credential, or lacks the primary fenced by the last rekey. It
  names the missing key.
- **The `Mail.SecretSealing` key ring.** Pending mail payloads are sealed with
  it. A node also refuses to start without the required mail primary key, or
  without a key that still seals an active payload.
- **`Authentication.Bootstrap.Secret`**, which an uninitialized installation
  that can be reached over the network needs.
- **TLS** certificate and key files, and the Let's Encrypt `CacheDirectory` if
  you use that mode.
- **Memberlist** gossip keys. These protect no stored data, so after a restore
  any new key ring shared by every node works.

Retire an old MFA or mail key from your key archive only when no backup you
might still restore needs it.

## Restore in order

1. Stop every application node. Restore into a new or emptied database, not
   one a node is using.
2. Install the configuration and key rings from the time of the backup,
   including every key retired after the backup was taken. Run
   `proctor config validate`.
3. Restore PostgreSQL.
4. Restore VFS to the configured root, or bucket and prefix. Extra objects do
   no harm. Missing ones make their content unreadable.
5. If the cluster uses a Redis cache, flush it. Its entries are disposable, and
   nothing ever needs stale entries from before the restore.
6. Run `proctor migrate status`. The database schema version must equal the
   server schema version of the binary you will start, with no pending
   migrations. A binary refuses to serve a schema newer than its own, so use
   the binary that matches the backup.
7. Run `proctor cluster status`. Restored serving leases keep their old expiry
   and show as `expired`. No lease may be `live` before you start.
8. Start one node, wait for readiness, then start the rest.

## Check a restore

- `proctor migrate status` reports matching versions and no pending
  migrations, and every node becomes ready without a key-ring error.
- An administrator signs in, and a User enrolled in MFA completes a TOTP
  sign-in. This proves the MFA key ring can open the restored secrets.
- Open a sample of files, Exam Resources and recent Submissions. This proves
  the VFS copy holds the objects the database refers to.
- `proctor jobs list --state failed` shows no new failures, and queued mail is
  delivered rather than failing to open its payload.
- Record what the drill restored and how long it took. Proctor itself sets no
  objective.

## Upgrade

Every pre-release build ships a single squashed baseline migration, recorded
as schema version 1. The baseline's contents change between pre-release builds
while its version stays at 1. So `proctor migrate status` can't tell you that a
database came from an earlier baseline. Read the changelog for the build you
install:

- If an entry says the pre-release SQL baseline changed and databases must be
  reset, there is **no upgrade path**. Recreate the database and VFS content
  and set the installation up again. Never edit old rows to fit the new
  baseline.
- If an entry says nodes must be upgraded together, you can't mix builds, even
  briefly. One example is the change to the advisory lock key scheme, after
  which an older node no longer keeps a newer one out.

Until a supported release says otherwise, upgrade **all nodes together**:

1. Take a backup as described above, and keep the matching old binary.
2. Stop every node, and confirm with `proctor cluster status` that no lease is
   live.
3. Install the new binary and any configuration it needs, and run
   `proctor config validate`.
4. Run `proctor migrate up`, or let the first node migrate at startup under the
   migration lock.
5. Start one node, wait for readiness, then start the rest.

A rolling restart, one node at a time behind the load balancer, is for changes
within the same build. That means configuration, settings that need a restart,
and the staged key rotations in
[maintenance and recovery](./maintenance-and-recovery.mdx). The first
supported release freezes the baseline. After that, schema changes are designed
as append-only migrations that work with rolling startup, and that release's
notes will say when rolling upgrades are supported.

## Roll back

A node refuses a schema newer than its build, so rolling back the binary means
rolling back the database too.

- **Restore the pre-upgrade backup.** Stop every node. Restore PostgreSQL, VFS,
  configuration and key rings from the backup taken before the upgrade, in the
  order above, and start the old binary. You lose any changes made after the
  upgrade.
- **`proctor migrate down`** reverts a number of the newest migrations that you
  give it, while every node is stopped. With the single pre-release baseline,
  reverting it leaves an **empty schema** and drops every table and all data.
  It is a reset, not a rollback that keeps your data. See the
  [CLI reference](../reference/command-line.mdx).

Rollback never happens automatically. A node never reverts migrations at
startup.
