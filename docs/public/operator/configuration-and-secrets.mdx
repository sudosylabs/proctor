# Configuration and secrets

Proctor never creates your active configuration file, and never replaces it
behind your back. It looks for the file in this order:

1. the path given with `--config`;
2. the path in `PROCTOR_CONFIG`;
3. `config/config.json`, relative to the process's working directory.

## Create and check the active file

```sh
install -o root -g proctor -m 0640 \
  /opt/proctor/config/config.example.json \
  /etc/proctor/config.json

/opt/proctor/proctor config validate \
  --config /etc/proctor/config.json
```

Edit the PostgreSQL, VFS, cache, mail, public URL, TLS, authentication,
logging and cluster settings to suit your topology. `config validate` rejects
unknown fields, unsafe listener combinations, malformed keyrings and
addresses, and settings that conflict with each other. It does this without
starting any workers or listeners.

For every setting, read the [configuration reference](../reference/configuration.mdx)
and the generated [list of environment variables](../reference/environment-variables.mdx).

## Override values without losing track of them

An environment variable overrides the file for that process only. Proctor
never writes it back to the JSON file. Keep sensitive overrides in a protected
environment file, such as `/etc/proctor/proctor.env` with mode `0600`, or use
the secret mechanism your platform provides. An empty variable still counts as
a value, and Proctor checks it. It doesn't always mean “unset”.

Record where each effective value comes from. Don't split one structured
provider entry across shell fragments nobody has written down. Keep external
provider objects as structured JSON that has been reviewed.

## Keep each secret for one purpose

- The bootstrap secret protects only the first setup of an empty installation.
- MFA and mail each have their own envelope keyring of 32-byte keys, written
  in canonical base64.
- Memberlist has its own gossip keyring of 16, 24 or 32-byte keys.
- The public and metrics TLS private keys identify their listeners.
- The metrics bearer token protects remote scraping.
- PostgreSQL, Redis, S3, SMTP and provider credentials belong only to the
  component that connects to that service.

Never use the same key for two purposes. Keep old decryption keys only while
old data or nodes still need them. Proctor redacts these fields when it shows
configuration and in its logs. Controlling who can read the files and the
secret manager is still up to you.

## What reloads without a restart

Logging and the external provider registry can change while Proctor runs,
once a complete replacement passes its checks. Listener, timeout, cluster and
keyring settings, and most infrastructure settings, need a restart. Check the
new configuration first, change one consistent set of files, and confirm the
node is ready after the restart.
