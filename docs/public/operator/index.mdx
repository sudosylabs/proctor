# Run a Proctor server

This guide is for the people who install and run a Proctor server. One Proctor
installation serves one Institution. Whether you run a single application node
or several active nodes, the product behaves the same way. Adding nodes gives
you more redundant infrastructure. It doesn't change who can do what or which
features are available.

<Maturity state="preview">
  Packaging, configuration checks, hardened systemd and container examples,
  TLS modes, node lifecycle, serving leases, health, metrics, logs, Memberlist
  and the pre-release recovery limits all work today. Treat this guide as
  pre-production guidance, not a certified list of supported production
  setups.
</Maturity>

## How to use this guide

The pages follow the order you set a server up in. Work through them in turn
the first time, then come back to individual pages as you need them.

1. [Verify a package or image](./package-and-install.mdx), and check that the
   server binary and the hosted web application come from the same build.
2. [Create your configuration and secrets](./configuration-and-secrets.mdx),
   and check them before any listener starts.
3. Run Proctor with the [systemd unit or container](./systemd-and-container.mdx)
   from the repository, without weakening its non-root and read-only limits.
4. Choose [one node or several active nodes](./topology-and-dependencies.mdx),
   and decide who runs PostgreSQL, Redis, VFS, SMTP and the load balancer.
5. Set up [TLS and your reverse proxy](./tls-and-proxy.mdx), including the
   separate metrics and cluster connections.
6. Send traffic to a node based on [readiness and what you can observe](./health-and-observability.mdx),
   not on whether its process is running.
7. Connect a production relay and
   [check that transactional mail is delivered](./mail-delivery.mdx).
8. Use the [maintenance and recovery procedures](./maintenance-and-recovery.mdx)
   that exist today, within their stated limits.
9. [Back up, restore, upgrade and roll back](./backup-restore-and-upgrade.mdx)
   PostgreSQL, file bytes, configuration and key rings as one set.
10. Respect the [pre-production limits](./pre-production-readiness.mdx).
    Don't make up sizing, recovery objectives or support promises that
    Proctor doesn't make.

## What each dependency is responsible for

| Dependency | What it keeps |
| --- | --- |
| PostgreSQL | Application state, authorization facts, audit, leases, Jobs, mail state and Workspace metadata |
| VFS/S3 | Opaque managed bytes, chosen through metadata in PostgreSQL |
| Redis | A disposable shared cache, and installation-wide counters in cluster mode |
| Memberlist | Best-effort peer discovery and passing changes between nodes. It never holds durable state |
| SMTP | Accepting mail for delivery. It is not the record of what the application did |

Proctor commits to PostgreSQL before it clears caches, notifies other nodes,
publishes WebSocket events or sends mail over SMTP. If one of those later steps
fails, Proctor recovers from durable state and by fetching again. It never
treats the later step as the source of truth.
