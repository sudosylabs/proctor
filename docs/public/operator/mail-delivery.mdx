# Deliver transactional mail

Proctor writes each message and stores it durably along with the change that
caused it. A background Job then submits it to your SMTP relay. Proctor doesn't
sign mail, and it doesn't know whether a message reached an inbox. The relay
and the sender domain are yours to run.

## Set up a production relay

The [mail configuration reference](../reference/configuration/mail-and-files.mdx)
describes every setting. Each one also has a `PROCTOR_MAIL_` environment
override. For a production installation:

- set `Mail.Enabled` and use the `smtp` backend;
- set `Mail.SMTP.Security` to `starttls` or `tls`, and use SMTP authentication
  only over TLS;
- set a stable sender address and `Mail.SMTP.MessageIDDomain`;
- supply a separate `Mail.SecretSealing.EncryptionKey`, written in standard
  base64 and exactly 32 bytes long.

Cleartext SMTP without authentication is only for a capture server on loopback
during development. Don't use it with a production relay.

When mail is on, Proctor tests the SMTP connection at startup and logs the
result. If the relay is down at that moment, the node still becomes ready.
Queued mail is retried when the relay comes back.

## Make sure mail from your domain is delivered

Whoever runs the sender domain must authorize your relay in SPF, set up DKIM
signing at the relay, and publish an aligned DMARC policy. Proctor builds the
MIME message and submits it over SMTP. It doesn't sign with DKIM, and it
doesn't treat the relay accepting a message as delivery to an inbox.

Once mail is configured:

1. Send the test message with `POST /api/v1/mail/test`, with no request body.
   It goes only to the verified address of the operator who calls it.
2. Check its stable `Message-ID` and the `accepted` state in
   `GET /api/v1/mail/deliveries` or
   `GET /api/v1/mail/deliveries/{mail_delivery_id}`. `accepted` means only
   that the relay accepted the message data.
3. At an external mailbox, check that the message arrived and look at its SPF,
   DKIM and DMARC results.

Reading deliveries and `GET /api/v1/mail/metrics` needs the `mail.view`
action. These views show only a limited set of data: template, state, public
outcome, attempts, latency, queue and mail health.

You can cancel queued delivery work, or retry a delivery that failed but hasn't
expired and is still relevant. Use the nested `/cancel` and `/retry`
operations. Both need `mail.manage` and a recent interactive Session. A
Personal Access Token can't run them.

Watch the mail metrics alongside the relay's own delivery diagnostics.
Proctor's logs deliberately leave out recipients, message bodies, ciphertext
and the SMTP conversation.

## Get through a relay outage

If the relay is down for a while, keep mail turned on. Retries, with their
limits, and the mail health view then follow the normal recovery path. Setting
`Mail.Enabled` to `false` suppresses mail on purpose, and it can't be undone.
Outstanding work ends up suppressed, and it doesn't come back when you turn
mail on again.

## Rotate the mail payload keys

Proctor encrypts the stored mail payloads it needs to read again with the
`Mail.SecretSealing` key ring. While it re-encrypts stored payloads, up to
eight previous keys can stay in `Mail.SecretSealing.DecryptionKeys`.

The ring can be missing only while mail is off. Turning mail on needs a primary
key, and Proctor refuses to start with a ring that is incomplete or set up
unsafely. MFA, Memberlist and mail keys can never be swapped for each other.

Rotation happens in stages, and each configuration change needs a restart:

1. Add the new key to `DecryptionKeys` on every node, so that every node can
   read it.
2. Restart every node with the new key promoted to `EncryptionKey`, and the
   old primary kept in `DecryptionKeys`.
3. From a strong Session where you signed in recently, call
   `POST /api/v1/mail/rekey` with the old key's ID as `retiring_key_id`. It
   returns a durable Job.
4. Follow it with `GET /api/v1/mail/rekey/{job_id}`. The Job must succeed, and
   its recorded proof must show zero retiring and zero non-primary references.
5. Only then remove the old key from the configuration and restart the nodes.

A node won't start if it has the wrong promoted primary, or if it's missing a
key that stored payloads still use. The operation and its diagnostics show
only key IDs and counts, never key material. Never remove a fallback key
before the zero-reference proof succeeds.

During a rolling deployment, a node that still has the old primary hands the
rekey Job back, waits a limited time before trying again, and can't claim it
again under the same node identity. This doesn't use up the Job's failure
budget, and a node with the new primary finishes the work.

For the next rotation, the last successful zero-reference proof lets a node
restart with the next primary while keeping the currently fenced key as a
fallback. Until the next rekey request moves the fence, that node can deliver
existing mail but can't store new encrypted payloads. Nodes still using the
fenced primary can. Without a successful proof, this staged promotion isn't
allowed.

Back up the key ring together with the database it protects, as described in
[Back up, restore, upgrade and roll back](./backup-restore-and-upgrade.mdx).
