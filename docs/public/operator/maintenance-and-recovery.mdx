# Maintenance and recovery

The procedures on this page cover the lifecycle of application nodes and a few
specific security controls. For backup, restore, upgrade and rollback, see
[Back up, restore, upgrade and roll back](./backup-restore-and-upgrade.mdx).

## Drain or restart one node

1. Make sure the other ready application nodes, and the dependencies they
   need, can carry the traffic in the topology you have tested.
2. Remove the node from the load-balancer pool, or wait for it to drop out
   when readiness goes.
3. Send SIGTERM through systemd or the container runtime.
4. Let the configured HTTP drain and the external stop window finish.
5. Confirm that the process withdrew its serving and discovery leases. If the
   process is lost, the leases expire, which also limits how long recovery
   takes.
6. Start the matched set of files, wait for readiness, then return the node to
   service.

A normal shutdown marks the node unready before the HTTP drain. It then closes
Jobs, WebSocket, the transport, the serving lease, metrics, tracing and the
platform, in the reverse of the order they were started. All of this fits
within one `Server.ShutdownTimeout` budget.

## Rotate Memberlist keys

Key changes need a restart and a three-stage overlap:

1. Add the new key as a fallback on every node.
2. Promote it to primary everywhere, keeping the old primary as a fallback.
3. Remove the old fallback only after every node has caught up.

If you skip the overlap, nodes that can't decrypt each other's messages split
into separate groups. The fallback ring holds at most eight distinct keys.
This procedure rotates gossip encryption only. It doesn't rotate TLS, MFA,
mail or dependency credentials. MFA secret keys rotate as described below, and
mail payload keys as described in
[Deliver transactional mail](./mail-delivery.mdx#rotate-the-mail-payload-keys).

## Rotate MFA secret keys

Proctor seals TOTP secrets with the MFA key ring
(`Authentication.MFA.EncryptionKey` plus `DecryptionKeys`). A rotation
replaces the primary key, and a durable rekey Job re-seals every live secret
with it. The old key is removed only after the Job proves that no live secret
needs it. The operations need the `mfa.rekey` action and a strong
(multi-factor), recent interactive Session. A Personal Access Token can't run
them.

1. Generate a new 32-byte key. On every node, make the new key the primary by
   setting it as `EncryptionKey`, and keep the current primary by moving it
   into `DecryptionKeys`. Restart each node, since key changes don't reload
   while Proctor runs.
2. Check that every node has caught up with `GET /api/v1/mfa/keys` on each
   one. `primary_key_id` must be the new key everywhere, and every key listed
   under `active` must report `configured: true`.
3. Start the rekey from any node with `POST /api/v1/mfa/rekey` and the body
   `{"retiring_key_id": "<old key ID>"}`.
   The request fences the key ring on that node's primary. From then on every
   node must seal new secrets with it. On a node still configured with another
   primary, MFA setup fails as temporarily unavailable, and its rekey attempts
   hand the Job to a node that has the fenced primary. Start the rekey soon
   after step 2, because until the rekey moves the fence, any node whose
   primary differs from the current fence has the same restriction.
4. Follow the Job with `GET /api/v1/mfa/rekey/{job_id}`. It re-seals one
   credential at a time, and only if the secret is still sealed with the key
   it read. It saves a checkpoint after each one, so after a crash, restart or
   lost lease it carries on where it stopped without repeating work. Users can
   keep signing in the whole time.
5. When the status is `succeeded`, its `proof` must show
   `retiring_references: 0` and `retirement_safe: true`, and
   `GET /api/v1/mfa/keys` must list only the new key under `active`. Only then
   remove the old key from `DecryptionKeys` on every node and restart.

Proctor refuses a second rekey while one is queued or running. The fence moves
to a different primary only after the previous rekey has succeeded with that
proof, so if a rekey fails, run it again with the same primary first.

A node refuses to serve if its configured ring lacks the fenced primary or any
key that still seals a live secret, and it names that key. Removing a key too
early therefore stops the node, instead of locking Users out. Archived
credentials aren't re-sealed. Once their key is removed they can't be opened
again, which is intended.

## Recover administrator sign-in offline

Stop every application node. Check the exact Institution and active
system-administrator User identifiers. Then use the host-only commands
described in the [CLI reference](../reference/command-line.mdx):

- `administrator recover` can turn local login back on, read a replacement
  password from private standard input, or both.
- `administrator reset-mfa` retires lost MFA material and revokes the
  administrator's existing access. The administrator then has to sign in
  again with their primary method and enroll again. MFA must be on, and a
  permitted primary method must already exist. Accounts that only sign in
  externally keep using their linked provider.

These commands start no workers, listeners or transports.

Restart normally afterwards, so that Proctor writes the durable recovery
record into audit. Don't use this as a routine password reset, and don't run
it while another node is serving.

## Pre-release database limits

The current schema is a single squashed pre-release baseline. Older
development databases with incompatible migration histories can't be
upgraded. Recreate the dedicated development database and run the current
baseline again. Don't invent Session, Participation, Attempt Configuration,
Submission or terminal provenance records to make old rows fit.

`proctor migrate status` shows the state of the current migration set, and
`proctor migrate up` applies it. Neither proves that a backup is complete or
that a restore works. Running `proctor migrate down` to revert the baseline
leaves an empty schema. It resets the database rather than rolling it back.
The [upgrade and rollback guidance](./backup-restore-and-upgrade.mdx#upgrade)
explains how to tell when a build needs a reset.
