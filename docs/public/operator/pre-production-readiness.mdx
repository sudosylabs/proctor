# Check pre-production readiness

Use this checklist to evaluate the current preview runtime. Passing it proves
only the environment and scenarios you actually tried. It doesn't certify
Proctor for production.

## Package and build identity

- You recorded the archive checksum or the image digest.
- The binary's `version --json`, `BUILD_METADATA` and the hosted build identity
  match.
- You copied the configuration example, rather than using it as a source that
  holds secrets.
- The service runs as a non-root user, from application files it can't change.

## Configuration and secrets

- `config validate` passes for the effective inputs of every node.
- Configuration, environment and secret files have ownership and modes that
  let as few accounts as possible read them.
- The bootstrap, MFA, mail, Memberlist, TLS, metrics and dependency secrets are
  all independent, and you have recorded who rotates each one.
- Your deployment procedure lists every change that needs a restart.

## Traffic and topology

- You have tested the HTTPS `PublicURL`, proxy, WebSocket, uploads, redirects
  and the DPoP target from end to end.
- The application, metrics and cluster listeners are reachable only from the
  networks that should reach them.
- The load balancer uses readiness and respects the drain.
- When you use Memberlist, you have checked the shared PostgreSQL, Redis and
  VFS, and that every node has a unique stable Node ID.
- Nobody presents the single-container Compose example from the repository as
  highly available.

## Lifecycle and failure drills

- Cold startup, repeated startup failure, the SIGTERM drain and restart all
  work.
- A serving-lease or metrics failure removes readiness and stops serving.
- You can remove one application node and bring it back in the topology you
  tested.
- A delayed or lost peer notification recovers by fetching again and from
  durable state.
- You understand how queued Jobs and mail are retried and canceled.
- You rehearse administrator recovery only on an isolated copy that isn't
  production.

## Data and diagnostics

- You treat PostgreSQL and VFS as the set to recover, and Redis as disposable.
- You have reviewed logs, metrics, traces, screenshots and tickets for leaks of
  credentials, student, Exam, Workspace and mail data, and private Review
  details.
- Metrics are reachable only on loopback, or protected by both TLS and a bearer
  token.
- Operational screenshots and reports use synthetic data.

## Claims Proctor doesn't make yet

Don't publish or rely on any of these as if Proctor supports them:

- a supported production matrix;
- a sizing table;
- a backup and restore guarantee;
- an RPO or RTO;
- a stable policy for upgrades, mixed versions or rollback;
- alert thresholds;
- a support bundle;
- a release support window;
- a security-update SLA.

Each of these needs explicit decisions, and evidence from a declared
environment.

The systemd and container definitions in the repository are hardened examples
of how to run the implementation. They don't certify any particular operating
system, orchestrator, cloud, database service, object store, mail relay or
identity provider.
