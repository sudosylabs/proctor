# TLS and reverse proxies

Start by setting `Server.PublicURL` to the exact HTTPS address that people and
Proctor Desktop use, such as `https://proctor.example.edu`. Proctor builds
redirects, cookies, sign-in, DPoP checks and Desktop discovery from this value.
It never works out its own address from the `Host` header of a request.

Then decide who handles HTTPS. There are three options.

## Choose who handles HTTPS

| `Server.TLS.Mode` | Who holds the certificate | Several nodes |
| --- | --- | --- |
| `disabled` | Your load balancer or reverse proxy | Yes |
| `static` | Proctor, using files you provide | Yes |
| `lets_encrypt` | Proctor, renewed automatically | No, one node only |

### Behind a load balancer or reverse proxy

Use `disabled` only when a proxy you trust handles HTTPS. Keep Proctor's own
listener reachable from the proxy's network and nowhere else. The proxy should
pass HTTP and WebSocket traffic through without changing the address, method,
path, query or upgrade.

List the address of every proxy or load balancer that connects to Proctor in
`Server.TrustedProxies`. Only those addresses may tell Proctor the client's
address, in `X-Forwarded-For`, and a request ID, in `X-Request-ID`. Proctor
takes the rightmost address in `X-Forwarded-For` that isn't one of your
proxies. It ignores the `Forwarded` header.

Set up each proxy to:

- append the address it received the connection from to `X-Forwarded-For`;
- overwrite or remove any `X-Request-ID` the client sent. Proctor accepts a
  trusted proxy's request ID as it is, and most proxies pass the client's
  value through, which would let a client choose the ID that appears in your
  logs and audit records.

Without `Server.TrustedProxies`, every request looks as if it came from the
proxy. Audit records lose the real client, and everyone shares one sign-in
rate limit.

With several nodes, put HTTPS and the HTTP-to-HTTPS redirect on the load
balancer, and route traffic by each node's readiness. You can still use
`static` mode to encrypt the hop from the load balancer to each node.

### With your own certificate

Use `static` with a certificate and its private key. Only the account Proctor
runs as should be able to read them. Proctor accepts TLS 1.2 and newer.

To redirect plain HTTP as well, turn on `ForwardHTTPToHTTPS`. Proctor then
listens on a second address and answers every HTTP request, apart from
certificate challenges, with `308 Permanent Redirect` to the same path and
query on your public address. In the `Server` section:

```json title="config.json"
{
  "ListenAddress": ":443",
  "PublicURL": "https://proctor.example.edu",
  "TLS": {
    "Mode": "static",
    "CertificateFile": "/etc/proctor/tls/certificate.pem",
    "PrivateKeyFile": "/etc/proctor/tls/private-key.pem",
    "LetsEncrypt": {
      "Email": "",
      "CacheDirectory": "/var/lib/proctor/acme",
      "AcceptTermsOfService": false
    },
    "ForwardHTTPToHTTPS": true,
    "HTTPListenAddress": ":80"
  }
}
```

You can replace the certificate without a restart. Each node checks for new
files at most every 30 seconds while handling connections, and reloads them
straight away on `SIGHUP` (`systemctl reload proctor`). If the new certificate
and key don't load as a matching pair, Proctor logs the error and keeps
serving the old ones. So replace both files together, either by writing them
and then sending the signal, or by swapping them in one step.

Afterwards, check the hostname, certificate chain, expiry date and file
permissions, and that clients trust the certificate, by connecting through
the same path real traffic takes.

### With Let's Encrypt

`lets_encrypt` is a convenience for a single node. It needs:

- an HTTPS `PublicURL` with one fully qualified DNS name;
- a private cache directory that survives restarts and that Proctor can write;
- `ForwardHTTPToHTTPS` turned on;
- public DNS, and Let's Encrypt able to reach the node on ports 80 and 443.

Set `LetsEncrypt.AcceptTermsOfService` to `true` to record that you have read
and accept the current Let's Encrypt Subscriber Agreement. Proctor refuses to
start in this mode until you do.

```json title="The TLS block for Let's Encrypt"
{
  "Mode": "lets_encrypt",
  "CertificateFile": "",
  "PrivateKeyFile": "",
  "LetsEncrypt": {
    "Email": "operator@example.edu",
    "CacheDirectory": "/var/lib/proctor/acme",
    "AcceptTermsOfService": true
  },
  "ForwardHTTPToHTTPS": true,
  "HTTPListenAddress": ":80"
}
```

Proctor renews certificates only while it is serving HTTP. It keeps the
account and certificates in `LetsEncrypt.CacheDirectory` on the node, and
creates that directory with mode `0700`. If the directory already exists,
Proctor refuses to start when it can't write to it or when other users or
groups can read it. Listening on ports 80 and 443 may need an operating-system
capability, or a supervisor such as systemd that grants it.

Let's Encrypt mode isn't allowed with Memberlist, because each node would
issue and renew its own certificate without coordinating with the others. With
several nodes, put the certificate, ACME and the HTTP redirect on the load
balancer instead.

### HTTP Strict Transport Security

In `static` and `lets_encrypt` modes, every response includes
`Strict-Transport-Security`. Its max-age comes from
`Server.TLS.StrictTransportSecurityMaxAge`: 365 days by default, and `0` turns
the header off. Browsers that see it refuse plain HTTP to your host for that
long, so lower it before you first turn on TLS if the host might ever go back
to HTTP. In `disabled` mode Proctor doesn't send the header; set it on your
proxy instead.

## Other connections use their own TLS

The public certificate covers browser and Desktop traffic only.

- A metrics listener on anything other than loopback needs its own certificate
  and a bearer token. Its certificate reloads the same way as `static` mode:
  checked at most every 30 seconds, reloaded on `SIGHUP`, and the last good pair
  kept if a replacement fails.
- PostgreSQL, Redis, S3, SMTP and identity providers each have their own trust
  settings.
- Memberlist encrypts traffic between nodes with its gossip key, not with TLS.
- A TLS private key never stands in for MFA, mail, DPoP or cluster keys.

## Check the proxy

Before sending real traffic through a proxy, check that it:

- keeps WebSocket upgrades and long-lived connections open;
- never caches signed-in pages, responses marked `no-store`, or anything sent to
  a candidate;
- keeps Proctor's own request size and time limits, rather than buffering
  without a limit;
- passes a request ID without treating any client header as proof of who the
  client is. Proctor uses `X-Request-ID` only from a trusted proxy, which must
  overwrite the client's value;
- stops sending traffic to a node once it reports it isn't ready, and allows
  the configured shutdown time;
- exposes the application and cluster listeners only to the networks that need
  them.

Finally, test discovery, sign-in cookies, the DPoP target address, redirects,
uploads, WebSocket and large responses through the whole path.
