# Choose a topology and who runs each dependency

Proctor behaves the same on one node as on several active nodes. A cluster
keeps the application available only when every shared dependency it needs,
and the traffic path to it, is redundant enough as well.

## One application node

Set `Cluster.Backend: local` and give the node a stable node ID. Use
PostgreSQL and VFS that are fit for production, and the mail and provider
services you chose. The application may use a size-limited cache inside its
own process. Memberlist has no peers, so broadcasts do nothing.

A single node is simpler to run. Its application process, its host, and any
VFS or certificate cache stored on the node are each a single point of
failure. Built-in Let's Encrypt works only in this `local` cluster mode.

## Several active application nodes

Put identical, compatible application nodes behind a redundant external load
balancer, and send traffic only to nodes that are ready. Configure:

- one shared PostgreSQL installation that holds the durable state;
- shared S3-compatible VFS instead of content stored on each node;
- a Redis application cache for the disposable security counters shared
  across the installation;
- `Cluster.Backend: memberlist`, a unique stable Node ID on each node, and one
  gossip keyring that every node agrees on;
- private TCP and UDP bind and advertise addresses that the nodes can reach;
- the same checked application and policy configuration on every node;
- shared SMTP and identity-provider services, if you use them.

Memberlist carries best-effort cache invalidation and realtime updates. Redis
doesn't carry Memberlist messages. Neither of them takes the place of
PostgreSQL as the record of durable state.

## What happens when a dependency is lost

| Lost dependency | What to expect |
| --- | --- |
| PostgreSQL unavailable | Readiness, startup or the current operation stops safely. Durable work can't continue |
| Redis unavailable in Memberlist mode | The shared security and cache service the node needs is missing. Don't quietly fall back to local memory |
| VFS unavailable | Metadata may still be readable, but protected content operations fail. Don't use object listings instead |
| SMTP unavailable | Delivery stays queued and is retried according to its descriptor. Application state isn't rolled back |
| A peer message is lost | Affected clients and nodes recover by fetching again, through TTLs and renewals, and from durable state |
| Load balancer unhealthy | Application nodes may be ready but unreachable from outside. This is your infrastructure to fix |

## The Compose example is not high availability

The Compose file in the repository shows one immutable application container
with its mounts and ports. It deliberately doesn't package PostgreSQL, Redis or
object storage on a single host as a highly available production installation.
Before you claim any availability, run redundant dependencies and load
balancing that are operated independently.
