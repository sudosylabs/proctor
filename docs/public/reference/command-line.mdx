# Command-line reference

The CLI calls into the server and nothing more. It doesn't have its own,
separate set of rules. For translated usage and the current flags, run
`proctor help`, or `--help` on a command, from the exact release binary you
run.

Every command accepts `--config` (short form `-c`). A path you pass takes
priority over `PROCTOR_CONFIG` and the default `config/config.json`. The flag
applies to every command, so you can also put it before the command name.
`proctor completion --help` explains how to generate shell completion.

Help and messages are translated. The CLI chooses its locale from
`PROCTOR_LOCALE`, then from the standard `LC_ALL`, `LC_MESSAGES` and `LANG`
environment variables. Command names, flags and machine-readable values are
the same in every locale.

## Commands

| Command | What it does | Starts the server? |
| --- | --- | --- |
| `proctor serve` | Runs migrations and startup checks, connects to the services Proctor needs, and runs Jobs, WebSocket, HTTP and readiness, with a time limit on shutdown | Yes |
| `proctor config validate` | Loads the configuration in force, strictly, and checks it | No |
| `proctor config show` | Prints the configuration in force, with every secret hidden | No |
| `proctor migrate status` | Compares the database and server schema versions, and lists migrations not yet applied | No |
| `proctor migrate up` | Applies every pending migration, when you choose to | No |
| `proctor migrate down` | Reverts the number of newest migrations you name, while every node is stopped | No |
| `proctor cluster status` | Lists serving node leases, cluster discovery rows and the schema version | No |
| `proctor jobs list` | Lists the newest stored Jobs with their state, attempts, last error code and when they are next available | No |
| `proctor jobs show` | Shows one Job and its most recent attempts | No |
| `proctor administrator recover` | Recovers an administrator's local sign-in from the host, while all nodes are stopped | No |
| `proctor administrator reset-mfa` | Resets an existing administrator's MFA and makes them enroll again, while all nodes are stopped | No |
| `proctor version` | Prints the build version, commit, build time and Go version | No |

## Run and check

```sh
proctor config validate --config /etc/proctor/config.json
proctor serve --config /etc/proctor/config.json
```

When `NOTIFY_SOCKET` is set, `serve` talks to systemd. It reports readiness,
shutdown and reloads, and it feeds the watchdog when `WATCHDOG_USEC` names
this process.

The first SIGTERM or SIGINT starts a graceful drain. A second one makes the
drain finish at once, and `serve` exits with status 1. A third exits
immediately. SIGHUP reloads the configuration and static TLS certificates.

The CLI warns you when it runs as root. Run Proctor under its own service
account that isn't root.

## Show the configuration in force

```sh
proctor config show --config /etc/proctor/config.json
proctor config show --json --config /etc/proctor/config.json
```

`config show` loads and checks the configuration exactly as `config validate`
does: the built-in defaults, then the file, then any `PROCTOR_` environment
overrides. It prints one `Path = value` line for each setting, with the value
written as it would be in JSON. Above a line, a comment names any environment
variables that replaced the value from the file. With `--json`, it prints the
whole document in the same shape as the configuration file instead.

Both forms replace every secret with `[redacted]`. That covers the database
data source, the Redis password, the metrics bearer token, the Memberlist,
mail encryption and MFA keys, the SMTP password, S3 credentials, the bootstrap
secret, and OIDC client secrets. An empty secret stays empty, so you can see
whether a secret is set without seeing its value. The command doesn't connect
to any other service and never writes the file.

## Database migrations

```sh
proctor migrate status --config /etc/proctor/config.json
proctor migrate up --config /etc/proctor/config.json
```

The current pre-release baseline can't upgrade older development schemas that
don't match it. `migrate status` doesn't confirm that your backups, rollback
or a production upgrade are safe.

### Revert migrations

```sh
proctor migrate down --steps 1 --config /etc/proctor/config.json
proctor migrate down --steps 1 --confirm --config /etc/proctor/config.json
```

`migrate down` reverts the newest `--steps` applied migrations. You must give
the count, and it can't be more than the number of applied migrations.

The command first prints the current schema version, each migration it would
revert, and the version you would end up on. Without `--confirm` it stops
there, reverts nothing, and exits with status 1.

It refuses to run while any serving node holds a live lease, and names those
nodes. Stop every node first. If a node crashed, wait for its lease to expire.
While it reverts, the command holds the migration lock and the serving node
lease fence, so no node can start serving or run migrations in the meantime.

Proctor ships one pre-release baseline migration today, so `--steps 1` takes
you back to version 0, which is an **empty schema**. Every Proctor table and
all of its data is dropped. Only Morph's own `db_migrations` and `db_lock`
bookkeeping tables remain, and only a database backup brings the data back.
The command tells you this before it acts. A node you start afterwards applies
the baseline again and starts as an empty installation. Proctor never rolls
back migrations at startup.

## Read-only inspection

`migrate status`, `cluster status`, `jobs list` and `jobs show` only read.
They open the database with every session set to
`default_transaction_read_only`, so PostgreSQL itself rejects any write. They
never migrate, never take the migration lock or any other advisory lock, and
never create a table. You can run them safely next to serving nodes, and the
schema doesn't have to match the binary.

```sh
proctor cluster status --config /etc/proctor/config.json
proctor cluster status --json --config /etc/proctor/config.json
```

`cluster status` prints the database and server schema versions, how many
migrations are pending, the PostgreSQL time, and two tables:

- **Serving nodes** lists every serving node lease with its node ID, state,
  renewal time, expiry and lease ID. A node may serve only while its lease is
  `live` by the PostgreSQL clock. An `expired` row belongs to a node that
  stopped without giving up its lease.
- **Cluster discovery** lists the Memberlist bootstrap rows with their
  advertise address, server version and protocol range. These rows are
  disposable. Only the `memberlist` cluster backend writes them, never
  `local`.

Expired rows are shown, not hidden. Each list stops at 500 rows and says so. A
database with no schema reports no nodes.

```sh
proctor jobs list --config /etc/proctor/config.json
proctor jobs list --state failed --type mail.deliver,mail.cleanup --limit 20
proctor jobs show <job-id>
proctor jobs show <job-id> --json
```

`jobs list` prints the newest Jobs first, up to `--limit` of them (default 50,
at most 200). For each Job it shows the ID, type, state, attempts used out of
the maximum, the last public error code, when a worker can next pick it up,
and when it last changed.

You can repeat `--type` and `--state`, or separate values with commas. They
accept only known values, and the error for an unknown value lists the ones
you can use. The states are `queued`, `running`, `cancel_requested`,
`succeeded`, `failed` and `canceled`. Unlike the administrator API, listing
from the host includes internal Job types. When more Jobs match than it
shows, the output says so. Narrow the filters instead of paging.

`jobs show` adds the creation, start, completion and progress times, and the
20 most recent attempts with their node, heartbeat, lease expiry and error
code.

Neither command prints a Job's command, checkpoint, result or deduplication
key, or an attempt's claim token, because those can contain user identifiers
or content. Both refuse to run on a database without a schema. `--json` writes
the same fields for scripts. To cancel or retry a Job, use the administrator
Jobs API, which checks permission and records the change in the audit log.
The CLI never changes Jobs.

## Recover an administrator from the host

Stop every application node first. Confirm the exact Institution and the
active system administrator User. Then choose at least one recovery action:

```sh
proctor administrator recover \
  --config /etc/proctor/config.json \
  --institution-id <institution-id> \
  --user-id <user-id> \
  --enable-local-login \
  --rotate-password
```

`--rotate-password` reads the new password from standard input, which must be
redirected and not a terminal. You never pass a password as an argument or a
flag. Capture it without echo using your shell's private input, for example
`read -rs` followed by redirecting standard input, and never put the value in
the command itself.

The command doesn't create a Session, and it leaves MFA and existing Sessions
as they are. It writes a lasting recovery record while transports and workers
are still stopped. Restart normally, so that Proctor can complete its audit
record. The other flags are `--institution-id`, `--user-id` and
`--enable-local-login`.

If an administrator has lost their authenticator, use the separate MFA reset
command:

```sh
proctor administrator reset-mfa \
  --config /etc/proctor/config.json \
  --institution-id <institution-id> \
  --user-id <user-id>
```

MFA must be turned on and set up. The target must be an active system
administrator who already has a primary sign-in method they are allowed to
use. The command accepts no password, recovery code or proof of a factor.

It retires the old MFA material and revokes the target's Sessions, PATs and
unfinished access grants. It records that the administrator must enroll again,
along with lasting evidence of the host recovery. It keeps the primary
credentials and the Access Policy as they are.

Restart normally so Proctor can complete the audit record. The administrator
then signs in again with their password or provider and enrolls a new
authenticator. An administrator who signs in only through an external provider
must use a provider that is already linked and allowed. If that provider is
down, restore it first. Turning MFA off doesn't lift the requirement to enroll
again.

Proctor rejects a second host recovery command until it has completed the
record of the first. If a node crashed, wait for its serving lease to expire
before you retry either command.

Neither command migrates the database. Each refuses to run unless the database
schema matches the build exactly, and tells you to run `proctor migrate status`
and `proctor migrate up` first. Running an offline command never creates a
serving lease.

## Build identity

```sh
proctor version
proctor version --json
```

Use `--json` in scripts. Before you deploy, compare the binary's identity with
the release manifest and the packaged hosted application.
