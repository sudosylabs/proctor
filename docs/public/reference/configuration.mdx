# Configuration reference

Proctor reads one versioned JSON file when the process starts. This section
covers every supported field, its default, the values it accepts, and the
rules that tie fields together.

The defaults are a **local development baseline**. They are not a
recommendation for production size or security. The example uses loopback
listeners, development credentials, local storage, an in-process cache, and
mail turned off.

## Start from the complete example

Copy the example in the repository, restrict who can read the copy, and
check it before you start the server:

```sh
cp config/config.example.json config/config.json
chmod 600 config/config.json
proctor config validate --config config/config.json
```

The reference example is
[`server/config/config.example.json`](https://github.com/sudosylabs/Proctor/blob/main/server/config/config.example.json).
It contains every field, and its values match the defaults built into the
server exactly.

Proctor looks for the active file in this order:

1. The path you pass to `--config`.
2. The path in `PROCTOR_CONFIG`.
3. `config/config.json`, relative to the process working directory.

The server never creates the active configuration file for you.

## How loading works

Proctor starts from its built-in defaults and then reads your JSON file over
them. A field you leave out keeps its default. This means you can keep a
shorter file for your installation, but the complete example is still the
clearest place for operators and reviewers to start.

The file must hold exactly one JSON object. Proctor rejects unknown field
names, extra JSON values after the object, values of the wrong type, and
durations it can't parse. Field names are case-sensitive. Proctor then checks
each value's limits and the rules between fields, before it sets up anything
else.

Durations use Go duration syntax, such as `250ms`, `15s`, `5m` or `24h`.
Byte limits are whole numbers of bytes. Network addresses use `host:port`,
unless a field says it needs an HTTP or HTTPS URL.

## Environment overrides

Supported `PROCTOR_` variables override the values from the JSON file for the
current process. Proctor checks overrides together with the file, but never
writes them back to it. The generated
[environment variable list](./environment-variables.mdx) shows every accepted
variable and how to write its value.

Keep credentials and keys in a protected secret store. Never commit an example
with real values in it. Only the Proctor service account, or its protected
group, should be able to read the active JSON file and any environment file.

## What reloads and what needs a restart

Proctor applies only two areas after a successful reload: logging and the list
of external sign-in providers. Every other change needs a process restart.
This keeps listeners, connections to other services, and security settings
consistent for as long as the process runs.

Check the configuration you intend to run before you reload or restart.
Checking confirms the shape of the values and how they fit together. It
doesn't confirm that PostgreSQL, Redis, SMTP, object storage or your identity
providers are reachable.

## Keep secrets separate

Bootstrap credentials, MFA encryption keys, mail encryption keys, Memberlist
keys, TLS private keys, metrics bearer tokens, database credentials and
object storage credentials each protect something different. Don't reuse one
for another.

MFA, mail and Memberlist keys rotate the same way. Each has one primary key
for encryption and a short list of older keys that are still accepted for
decryption. Roll the new primary out to every node that needs it. Keep the old
key only while old encrypted data or cluster traffic can still use it, and
remove it once every node has the new one. Proctor rejects a key that is
reused across the MFA, mail and Memberlist purposes.

:::note[Production sizing status]

The repository doesn't yet define tested production sizes for connection
pools, cache memory, request limits, file content concurrency or log queues.
Stay within the ranges in this reference, then choose production values from
your installation's workload, the capacity of the services it depends on, and
how much failure you can tolerate.
