# Credentials, assurance, authorization and audit

Proctor makes three separate decisions about a request: whether the
credential is valid, how strong it is (its assurance), and whether the caller
has permission for this resource. A strong, recent Session can still lack permission. A Role
can't make a Personal Access Token good enough for a route that needs an
interactive Session.

## Credentials and how each is proved

| Credential | How the request proves it | What it is for | The most it allows |
| --- | --- | --- | --- |
| Browser Session cookie | HttpOnly cookie, with CSRF and allowed-Origin checks on unsafe requests | Hosted, interactive account and administration flows | The current Session's assurance and what the route declares |
| Bearer Session access credential | `Authorization: Bearer` | Session clients that don't use cookies, where the route allows it | Can't meet a requirement for a registered-key Desktop |
| DPoP-bound Desktop Session | `Authorization: DPoP` plus a fresh signed `DPoP` proof and nonce | Desktop discovery, realtime, and protected exam delivery to candidates | Proves the request came from a registered client, not that it may access the Exam |
| Personal Access Token | Bearer token, limited to certain actions and part of the academic hierarchy | Deliberate API automation | Refused by interactive-only routes and candidate delivery routes |
| Refresh credential | Its own rotation endpoint | Rotating the credentials of an existing Session | Not a general principal for the application |
| Bootstrap secret | Proof for bootstrapping an installation that has never been set up | Creating the one Institution and the first administrator | Useless forever once bootstrap commits |
| Invitation or recovery claim | A browser exchange for one purpose, usable once | Accepting an Invitation, verifying an email address, resetting a password, undoing an email change | Never a reusable Session or a general bearer token |
| Attempt continuity credential | A sensitive header plus the current Connection selector, under a DPoP Session | Operations on the exact Participation generation | Checked against the Attempt, Session, Participation, generation and Connection |

Credential sources are mutually exclusive where a route declares them so.
The server never picks a preferred identity from a mix of cookie, bearer
and DPoP inputs.

## Local password policy

Local passwords follow NIST SP 800-63B. There are no composition rules and no
forced rotation.

Every flow that sets a password applies the same checks. Those flows are
bootstrap, registration, Invitation acceptance, enrollment, self-service
change and reset. Each one:

- applies the configured length limits;
- refuses simple patterns;
- refuses entries on a bundled, offline list of common passwords;
- refuses values that contain the account's username, the local part of its
  email address, or its name.

Each refusal has its own public error code.

Reset, change and enrollment also refuse the account's
`Authentication.Password.HistoryCount` most recent passwords. Proctor runs that
comparison with the Argon2 verifier inside the credential transaction. It keeps
a limited number of old hashes per User and deletes them with the User. No
password or hash is ever sent to an external breach-checking API.

When a sign-in rehashes a password, Proctor checks only the length limits
again. So tightening the policy never locks out a password that already
exists.

## Undoing an email change

When an email change is applied, Proctor issues a hashed, single-use User Token
for the previous address. It sends the token in a credential mail, and the
token is valid for `Authentication.AccountRecovery.EmailChangeUndoTTL`.

Redeeming the token at the public undo route does all of the following in one
transaction:

- restores the previous address as verified;
- archives any outstanding verification and reset credentials, and their
  pending mail;
- uses up every outstanding undo token for the account;
- ends all of the account's Sessions;
- writes an `authentication.email_change.undo` audit event.

The change notice and the redemption share the account-recovery rate limits.
The notice is limited per target account, and redemption per token and per
source.

## Assurance sets a minimum for each route

Each route declares what proof it needs. The options are public,
principal required, interactive Session, strong, recent, strong and recent,
refresh, or a combination.

- Strong assurance comes from the sign-in method and the MFA state.
- Recent assurance comes from how long ago the primary proof happened, within a
  limit. The primary proof is the first sign-in or a later reauthentication.
  An MFA challenge never counts as fresh primary proof.

Proctor checks both before the application logic runs. Neither one grants
permission.

Proctor Desktop never shows a password form. When it needs recent
authentication, it opens a hosted "Confirm it's you" page in the system
browser. That page accepts only the method the Desktop Session itself used,
for that Session's own account. It never reuses a sign-in from the browser.
The page returns a one-use loopback code. The code refreshes the existing
Desktop Session only when that same Session, with its registered key, redeems
it.

A checked agreement between the routes and OpenAPI keeps three things in line:
the credential declarations at runtime, the OpenAPI `security` field, and
`x-proctor-auth`. The
<Link to="/api/guides/authentication">API authentication guide</Link> covers
the same ground for API consumers.

## Authorization uses current facts about the resource

To decide on permission, the application logic combines:

- the principal, which never changes;
- the fixed action;
- the resource itself;
- the current account state;
- the Role Bindings that apply;
- the academic scope;
- any ownership or management relationship built into the resource;
- the resource's lifecycle state;
- the token's limits.

It reads the current facts from PostgreSQL immediately before the protected
work or change.

Role Bindings only add access, and anything not granted is denied. Scope is
inherited only through the defined structure of Institution, Academic Unit and
Class. Whether a candidate may take part depends on their current relationship
and state, not on a general Role.

## Hiding whether a protected resource exists

For some resources, even knowing that they exist is sensitive. This covers
another User's private data, and any Exam, Sitting, Attempt, Submission, file
or unreleased result the caller isn't allowed to see.

Where the contract requires hiding, the application logic gives the same
not-found response whether the selector was denied, missing, mismatched,
inactive or out of scope. The internal reason never appears in the response.

## Durable audit for required decisions

Audit is security evidence stored in PostgreSQL. It is not an operational log.
A safe event holds a limited set of fields: the actor, the action, the
resource, the scope, the outcome, request and node correlation, the time, and
approved snapshots. It never holds credentials, Exam answers, content, provider
payloads, private reasoning or unlimited input.

Where audit is required and Proctor can't write it, the action fails closed.
A critical change either commits its state, its audit record and its stored
idempotent outcome together, or it follows a durable protocol that goes from
attempt to final outcome. If that protocol doesn't finish, the incomplete state
stays visible to operators.
