# Data classification, privacy and diagnostics

Proctor keeps data to a minimum by design, in the code's structure, not only
as a promise in the docs. Every transport and every view shows a smaller,
reviewed shape than the full record behind it.

## Classes of data and how they are handled

| Class | Examples | How it is handled |
| --- | --- | --- |
| Secret credential material | Passwords, Session, PAT and Attempt credentials, the DPoP private key, recovery and Invitation claims, provider tokens, MFA, mail and cluster keys | Never logged, audited, captured in screenshots, put in a URL, or returned after it has been shown once |
| Private academic content | Exam instructions before authorized delivery, Resources, Workspace and Submission files, answers, private manager reasoning | Authorization for each specific purpose, `private`/`no-store` transport, no general analytics |
| Private identity and structure | User profiles, memberships, Role Bindings, Class lists, provider subjects | Views limited by scope, limited audit, existence hidden across resource boundaries |
| Integrity and Review | Focus Loss and Connection Loss, Browser Activity, Flags, evidence, discrepancies, decisions, notes | Limited access for managers only. The candidate sees only remarks that were approved and released |
| Operational secrets and configuration | Database DSN, Redis, S3 and SMTP credentials, TLS keys, bearer tokens | Protected files or a secrets integration, redacted when displayed, a service account that can read as little as possible |
| Safe operational metadata | The fixed route template, result class, component, request and node correlation, limited IDs where approved | Logs and metrics with few distinct values, and no payloads or free-form error strings |

## Logs and metrics

Application services return errors. They don't log request data along the way.
The outermost layer logs an unexpected failure once, using only approved,
limited, single-value fields. The log configuration caps field size, queueing,
flushing, and how each log target behaves.

Metrics use labels from a fixed, small set of values. They never contain raw
URLs or VFS paths, cache keys, host, node, User, Session or Exam IDs, mail
recipients, content, credentials or error text. Prometheus scrapes each node
separately.

## Realtime updates and the cluster

Realtime events are small hints, in the past tense, that tell a client to fetch
again. Candidates and managers get separate events, and Proctor checks a
subscriber's current permission again before sending. Events leave out Exam
content, Workspace paths and bytes, evidence payloads, private reasons,
remarks and credentials.

Memberlist messages are limited in size and authenticated and encrypted with
the operator's keyring. Receiving one twice has the same effect as receiving it
once. They are never a source of truth.

## Browser Activity privacy

<GovernedFigure asset="browser-activity-privacy-boundary" />

Only a minimal set of facts about top-level navigation enters Browser Activity.
Proctor leaves out the query string, fragment, credentials in the URL, page
title and content, referrer, headers, cookies, DOM, downloaded files and local
paths.

The first version of integrity evidence also leaves out screenshots, webcam,
clipboard, source code and arbitrary payloads. When data is missing, Proctor
records an explicit gap. It never fills the gap with a guess.

## Documentation and diagnostics

Examples, screenshots, mail previews, bug reports and support files use made-up
data. Before you share anything, remove URL fragments, authorization headers,
cookies, DPoP proofs and nonces, file content, student identifiers and local
paths. A request ID lets someone match up server-side diagnostics without
revealing the private record behind them.
