# Errors, limits and compatibility

Public errors help an authorized client recover without revealing internal or
protected state. Limits stop untrusted input and stored evidence from turning
into unlimited work. Compatibility checks keep unsupported clients out of
security-sensitive exam delivery.

## Problem Details and hiding protected resources

Expected failures use stable, dotted application codes and a fixed list of safe,
typed fields. Over HTTP they become RFC 9457 Problem Details. WebSocket uses its
own versioned error envelope. The localized title and detail are only for
display. SQL errors, provider payloads, stack traces, private IDs and state,
and free-form strings stay inside the server.

A failure that is unknown, or that no code declares, becomes a single internal
error with a correlation ID. The outermost layer logs it once.

When even the existence of a protected resource is sensitive, Proctor may
return not found whether the request was denied, the resource is missing, the
selectors don't match, or the result isn't released yet. The response must be
the same in every one of those cases.

## Limits on input and work

The runtime applies header and body limits, plus stricter limits for each
operation, before it decodes or streams anything. JSON is parsed strictly where
an operation declares it. Collections come back in limited pages with opaque
cursors.

All of these have fixed limits: WebSocket frames, replay, queues, fan-out,
Browser Activity batches, sources and gaps, evidence, Reviews, uploads,
Workspace paths, mail, Jobs, logs and configuration values.

Rejecting a value that is too large or malformed is safer than cutting it down
into a command that means something different. If an inventory limit is hit
while integrity evidence is being finalized, that is an error to investigate.
It is not permission to leave evidence out.

## Idempotency and unknown outcomes

Each security-sensitive change declares whether it needs an idempotency key.
Replaying the exact same request returns the stored outcome, after checking
current permissions. Replaying it with a changed body is a conflict.

The transport credentials and the fresh DPoP proof are not part of what Proctor
compares between requests. When the outcome of a storage write is unknown,
Proctor keeps the staged bytes or the in-progress state. They stay until a
replay, or a limited reconciliation step, settles what is true.

## Desktop and node compatibility

`system/ping` compares the Desktop release, build ID, platform, architecture
and realtime protocol against the build catalog compiled into the server and
the current policy. Proctor refuses a client before admission if it is
unsupported, revoked, too old, too new, in maintenance, or speaks an
incompatible protocol. A client can't declare itself compatible.

Memberlist peers advertise protocol metadata compiled into their build. Proctor
rejects malformed, duplicate or incompatible peers when they join, and again at
later admission. Lost peer messages don't affect whether stored data is
correct.

## API and release compatibility

The API lives under `/api/v1`, but the product hasn't yet made the
compatibility commitment that comes with a first supported release. Until
then, the server, the OpenAPI description, the agreement tests and compatible
clients change together.

Development databases created from earlier, incompatible baseline histories
must be recreated. The server doesn't invent lifecycle facts to migrate them.
