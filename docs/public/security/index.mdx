# Review Proctor security

This section separates the controls Proctor enforces itself from the ones an
installation's operator has to provide. It describes what is built today, and
it says clearly where product or production policy has not been decided yet.

<Maturity state="preview">
  The server controls on these pages exist and have been checked against the
  current code and configuration. Some policy is still undecided: retention
  and purge schedules, legal hold, support windows, stable deprecation, and a
  production policy for encryption at rest that goes beyond the existing
  operator and secret-sealing boundaries.
</Maturity>

## Read the pages in this order

1. [Threat model and trust boundaries](./threat-model.mdx) sets out what is
   protected, who the actors are, what is assumed, and who owns each control.
2. [Credentials and authorization](./credentials-authorization.mdx) covers how
   a credential is proved and how strong it is, separately from permission to
   act on a resource, hiding protected resources, and durable audit.
3. [Data and privacy](./data-privacy.mdx) classifies credentials, student and
   Exam data, diagnostics and integrity evidence, and explains redaction.
4. [Keys, certificates and network](./keys-network.mdx) says who is
   responsible for Desktop, MFA, mail, Memberlist and TLS keys, for listeners,
   and for outbound connections.
5. [Content and Workspace](./content-workspace.mdx) covers stored files
   (VFS), the Workspace, Submission and Browser Activity.
6. [Errors, limits and compatibility](./errors-limits-compatibility.mdx)
   explains public errors that fail closed, input limits,
   compatibility, and safe recovery.

## Core security properties

- Authentication establishes a principal that never changes. It never carries
  a reusable snapshot of permissions.
- Every application action checks current permissions against the resource
  itself, and writes any required audit record durably.
- PostgreSQL is the source of truth for stored state. Anything in caches, the
  cluster or realtime updates can be rebuilt from it.
- Credentials, secrets, Exam answers, student content, private Review fields
  and unlimited input are kept out of ordinary logs and unsafe audit fields.
- Exam delivery to a candidate needs a Desktop Session with a registered
  key, and must also pass the continuity check for the exact current
  Attempt.
- Integrity signals are limited evidence that states its own uncertainty. They
  are not a verdict or an academic outcome.
