# Threat model and trust boundaries

One Proctor installation serves one Institution. Several application nodes
that share the same stored state are still one installation, not separate
tenants. So the threat model protects the academic and identity boundaries
across the whole Institution. It does not pretend that a tenant column or
state held on one node keeps anything isolated.

## What is protected

The most sensitive assets are:

- authentication credentials and keys;
- password and recovery material;
- provider tokens;
- Invitation claims;
- Session and Attempt continuity credentials;
- Exam instructions and Resources;
- candidates' Workspace and Submission content;
- integrity evidence and private Review text;
- student identity and membership;
- audit evidence;
- operator secrets.

Some assets matter mainly because they must stay available: Sitting schedules
and closing, active Participation leases, Jobs and mail occurrences, being able
to reach the VFS, and the serving-node lease.

## Actors and what they can do

| Actor | What it is expected to do | What it is not trusted to decide |
| --- | --- | --- |
| Unauthenticated network client | Public discovery, bootstrap while the installation is still new, and the entry points for sign-in and recovery | Identity, Role, whether a resource exists, or the result of a rate limit |
| Authenticated User | Actions allowed by its current account, credential, Role, binding, relationships and resource state | Its own scope, its assurance, what audit shows, or permissions that are out of date |
| Registered Desktop | Prove one P-256 key, and run the supported delivery protocols | Whether it is currently eligible for an Exam, a policy outcome, server time, guilt or severity |
| Exam Manager | Manage one Exam it is authorized for, and inspect sealed Submissions | The live candidate Workspace, wider student data, grading, or operator state it can't see |
| System administrator | Explicit, audited installation actions and override actions | Bypassing the lifecycle built into a resource, a publication that can't change, or the rules that hide protected resources |
| Application node | Run the same validated build with the current configuration | Treating its own cache or messages from peers as the source of truth |
| Infrastructure operator | Provide a trusted runtime, network, database, storage, mail, TLS and secrets | Quietly weakening the product's guarantees without a changed configuration that passes validation |

## How the boundaries fit together

<GovernedFigure asset="installation-authority-topology" />

The public listener and the metrics listener are separate. HTTP and WebSocket
input is untrusted until strict transport checks and authentication finish.
The application logic then checks permission for the current action on the
current resource. Named Store operations commit the stored state and any
required audit. Only after that can cache, Memberlist, WebSocket or mail
effects go ahead.

Proctor trusts PostgreSQL for stored application facts and for database time.
It trusts the VFS to keep the bytes that PostgreSQL metadata points to, but
not to decide identity or permission. Redis and Memberlist only speed up
coordination, and their data can be thrown away. An SMTP server accepting mail
doesn't prove the mail was finally delivered.

## Main threats and controls

| Threat | Main controls |
| --- | --- |
| Credential theft or replay | Credentials stored as hashes, rotation and revocation, DPoP binding, a fresh nonce and a unique proof each time, HttpOnly cookies, CSRF and Origin checks |
| Access across users, or with out-of-date permissions | Looking up the resource itself, authorization against current data in the Store, intersecting scopes, hiding protected resources, audit |
| Nodes disagreeing with each other | PostgreSQL as the source of truth, security counters shared in Redis in cluster mode, committing before any side effect, fetching again after gaps in events |
| Malicious or malformed input | Limited bodies and batches, strict decoding, fixed lists of allowed values, normalized paths, streaming limits for the VFS |
| Claims from a Desktop that can't be trusted | A registered build and key, the compatibility policy, identity and time worked out by the server, generation and sequence checks |
| Content leaking | Reads allowed only for a specific purpose, `private`/`no-store` caching, no storage URLs, redacted logs and views |
| Collecting too much evidence | Typed policies, minimizing data for privacy before it is stored, explicit gaps, limited inventories, a separate private Review |
| Operational secrets leaking | Protected configuration and environment files, a separate keyring for each purpose, redacted display, a service that doesn't run as root, as few writable paths as possible |

## Out of scope, and policy not yet decided

The code does not make a compromised PostgreSQL, VFS, operating system or
operator account safe. Deployments must isolate and monitor those systems.
Proctor's current server controls are also not a certified production
environment or an academic appeals process.
